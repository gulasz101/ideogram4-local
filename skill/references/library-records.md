# Library records

One record per rendered image, in the Obsidian vault. The format is the one `studio/library_backfill.py` `render_record()` writes, so back-filled and studio records sit in the same library and the same index.

## Where records live

```
~/wojtek.second.brain.obsidian.vault/3-resources/image-library/<YYYY-MM>/<YYYY-MM-DD>-<stem>--<job_id>.md
```

- `<YYYY-MM>` and `<YYYY-MM-DD>` come from the job's `created_at`. **A brief's record path is a hint, not the authority: the date prefix is computed from the renderer's own `created_at`, so read it fresh and check it against the brief's path.** On 2026-10-26 the `csrf-scissors-cap-r2` brief named `2026-10-26-csrf-scissors-cap-r2-aca3850f--zl7GqP1m5UM.md` while the job's `created_at` was `2026-10-25T22:18:56` — the brief's date was the round's date, not the render's. Writing the brief's path would have left the backfill's `record_relative_path()` pointing at a file that does not exist, so the next backfill would have written a second `verdict: unreviewed` record for the same job id. Across the library, 590 of 591 records carry the job's `created_at` date as their filename prefix, so the rule is settled; the one exception was a hand-named record. **A round brief's bookkeeping block writes `2026-10/<YYYY-MM-DD>-<fetched PNG stem>--<job id>`, and that `<YYYY-MM-DD>` reads like the day the close runs — copy it and a whole pass of records fails `filename starts with the job's created_at date` and `heading is the stem` together, one pair per file, while every other field is right.** Build the prefix inside the same script that writes the records, from each job's `imagegen status` `created_at`, and repair a set written that way with `mv`, not a rewrite.
- `<stem>` is the **fetched PNG stem**, i.e. the `label` slug plus the wrapper's 8-hex token: `<slug>-<token>`. `imagegen fetch` prints that path, so use its basename. **A render that was never fetched — an attempt held back at the self-check — has no `fetch` line to copy: take the stem from `imagegen status <job>` `.output_path`, whose basename is the same `<slug>-<token>.png`.** Build it from the slot label alone and the token is gone, so two attempts of one slot land on one record filename and the backfill writes a third.

**The studio's prompt and staging directories are shared by every post, so a slot-generic name collides.** A prompt file named after the slot alone (`header-r2.json`) is often already on disk from another post's round, so the write is refused and the natural next move — a slightly different filename beside it — leaves two prompts for two different pictures whose names differ by a character. Prefix the prompt file with the post number (`<nnn>-<item id>.json`) and keep the render name at the card's item id, so the file is findable from the brief while the render still joins the slot. **The same collision reaches staging:** two posts rendering a `header-r2` leave `<slug>-<token>.png` files whose slugs agree and whose tokens differ, so take the absolute path `imagegen fetch` printed and never glob the staging folder for the slot name — a glob silently picks the other post's render, and every check, record and card after it then documents a picture nobody reviewed. `library_backfill.py`'s `record_relative_path()` builds the same filename and skips a job only if that exact path exists; using the label alone would make the next backfill write a duplicate `verdict: unreviewed` record. **A slot's second attempt keeps the slot's id and only the attempt suffix changes** (`<item id>-r2b-<token>`), so the stem names the attempt that shipped, and the earlier attempt's record keeps its own stem. **The date prefix follows the job, not the brief**: a render that finishes after midnight in the worker's local time carries the next day's date, and the brief's folder is the round's date rather than the render's.
- `<job_id>` is the job id `imagegen submit` printed.

**Verify the finished filename against the job's own `created_at`, not by reading back the path you just wrote.** A writer that hands its own path to its own check tests nothing: the read returns whatever name it chose, so a missing or wrong date prefix passes every assertion and then fails only in the backfill, which writes a second `verdict: unreviewed` record for the same job. Build the expected name from the job's `created_at` date, the fetched stem and the job id, then compare it with a directory listing of `3-resources/image-library/<YYYY-MM>/`. A record whose name is shorter than that pattern is missing its prefix — rename it with `mv` (the heading stays as it is) and re-run the listing before closing the card.

**A brief that names a held-back attempt by its 8-hex token is naming the fetched filename, not the job id.** One brief's "held-back after this round's own check" list carried ids like `d661d423`, which is the token inside `permission-gate-proof-r2-flux-d661d423.png`; the job behind it was `HD53XC-4Ba0`, and a record built from the token would fail `job_id matches --job` and the filename suffix in one pass. Resolve every attempt the brief lists by the file it names — `ssh m1max "sqlite3 -json git/ideogram4-local/jobs.db \"select id,created_at,finished_at,output_path from jobs where output_path like '%<token>%'\""` — and take the id that comes back, because a missing row for the token reads like a pruned job when it is really a wrong key.

**A job id copied from a card or a brief can carry the wrong case, and the renderer's ids are case-sensitive.** One card listed the header job as `GhCoUj0MG-e` while the renderer's row for the same file reads `GhCoUj0MG-E`: `imagegen status` on the lowercase form answers `Job not found`, which reads like a pruned job rather than a typo, and a record built from the card's spelling fails the filename suffix against the job it documents. Resolve every id from the renderer's own row before writing anything — `select id,created_at,finished_at,seed,output_path from jobs where output_path like '%<fetched token>%'` over SSH — and use the spelling it returns in the record, the vault note and the closing comment, with one line saying the card's form was corrected.

**A held-back render's defect is a claim like any other, so re-crop it at the close before writing it into the record.** A held attempt never reaches the card, which makes its record the only account of why it was dropped, and the collect run's read is one run's reading. One header flux was held on "both hands fused lumps with no countable fingers"; a 6x re-crop during the close showed a thumb and a moulded finger mass with no lines between the fingers — still not countable, so the hold stood, but the note over-stated it. The record states the lower severity and says which crop settled it, because a record that repeats the collect-time phrasing keeps a defect in the library that the pixels do not show. **When the crop contradicts the collect read outright, the record keeps the contradiction instead of choosing the tidier story:** a held header flux read at collect time as a round shaft against a square socket came back from the close's 2x crop as a flat-sided shaft beside a round keyhole. The attempt never reached Wojtek, so no verdict can break the tie and neither read is corroborated — say what each read reported, which crop produced it, and that the attempt was replaced regardless. A record that picks one version puts an unverified defect claim into the library as a measurement, which is the one thing a held-back record exists to prevent.

Approved images live in the vault at `tech_blog/assets/<YYYY-MM-DD>/<slug>.png`, with the readable label slug (no token).

**The vault asset's filename follows the card's item id, not the render's name.** When a slot ships a later attempt, the two differ — the item id is the brief's id and the render carries an attempt suffix — and the asset keeps the item id's name while carrying the shipped attempt's bytes. So a slot whose item id is `node-parking-selector-r2` and whose shipped render is the `r2b` attempt stores those bytes at `tech_blog/assets/<date>/node-parking-selector-r2.png`, and the post's embed path names the same file. The brief's bookkeeping block names that path, so following it keeps the embed line and the asset in step; renaming the asset to the render's name instead breaks the embed the brief specifies and leaves a stray file in the vault. The **record** is the opposite case: its filename follows the shipped render's fetched stem and job id, because the record documents one render.

**The record's `asset:` value is vault-relative and the post's embed is not, so copying one into the other silently breaks the picture.** A record carries `tech_blog/assets/<YYYY-MM-DD>/<file>.png`; the post's own markdown sits inside `tech_blog/`, so its image line reads `assets/<YYYY-MM-DD>/<file>.png`. Writing the record's value into the post produces `tech_blog/tech_blog/assets/...` and the image never renders — while the record still verifies, because its own path is the right one, so the only tell is the draft. Build the embed path from the item id and the day folder in the same table as the record path, and assert after the write: each new path appears exactly once in the post, no `tech_blog/tech_blog/` string exists, and none of the displaced paths is left behind.

**Assert the rewritten alt text from a fresh read of the file, because an alt that a script prints as written is not a landed alt.** Every path count above passes on a post whose alt still names the old picture or still reads `header`: a close script that reports `alt <path>` once per slot and writes once leaves nothing in its own output to tell a landed line from a lost one. Read the post back from disk after the edit and assert the whole `![<alt>](<path>)` line per slot; `verify-slot.py` is what catches the leftover, and it names the old alt rather than the missing edit — `alt text describes the picture, not a placeholder word [header]` on a frame that has a description. A mismatch there is a re-apply, never a checker bug.

**A comparison copy's item id already carries the engine suffix, so its vault filename is the item id verbatim.** A close script that appends `-flux` to a `<slot>-r1-flux` item writes `<slot>-r1-flux-flux.png`, and the doubled name stays invisible until a reader follows the record's `asset:` to a file the card never named. Derive both engines' asset names from the item id alone (`<item id>.png`) and let the id carry the engine — then hash each vault copy against its staging file, which is the check that would have caught a misnamed target in the same pass. **That holds while the card's item ids carry the slot's own stem; when they do not, name the copy off the ship target instead.** A card generated by a review tool prefixes every id with the same short stem (`tsk-header`, `tsk-header-flux`) while the ship table and the draft embed keep the slot's name (`header.png`), so the item-id rule writes `tsk-header-flux.png` beside `header.png` and splits the pair across two naming schemes. Name the copy `<ship stem>-<engine>.png` — `header-flux.png` beside `header.png` — point the record's `asset:` at that file, hash it against staging, and state the departure in the closing comment, because the brief's item id says otherwise. What the doubled-name rule protects is the engine suffix appearing once, never twice; it does not require the item id's prefix.

## Format

Use exactly the frontmatter keys and the three sections of `render_record()`: `## Why`, `## Prompt`, `## Verdicts`. The `# heading` is the record's `<stem>` — the filename **minus** both the `<YYYY-MM-DD>-` date prefix and the `--<job_id>` suffix, so `2026-10-21-gitops-forklift-a-7f3a9c21--K3n8Qw7tY2c.md` carries `# gitops-forklift-a-7f3a9c21` and nothing more. **The heading is not the filename and never carries the date.** A script that fills the filename and the heading from one variable writes a prefix-less file — which looks correct, verifies against itself, and leaves the backfill's `record_relative_path()` pointing at a name that does not exist. **The other direction of the same bug is `Path(name).stem`**, which drops only `.md` and keeps the date prefix, so a builder that writes the heading from `Path(name).stem.split("--")[0]` puts `# <YYYY-MM-DD>-<stem>` at the top of every record in the round: the file renders, the frontmatter is right, and `verify-slot.py` then fails `heading is the stem` on all of them while printing the correct stem in that same line. Slice the date prefix **and** the `--<job>` suffix off the filename, assert the filename really carries both, and only then build the heading. Studio records differ from back-filled ones only in these values:

| field | studio value |
| --- | --- |
| `source` | `"studio"` |
| `verdict` | the latest verdict (`approved` / `rejected` / `deferred`) |
| `asset` | the vault-relative PNG path once approved; `null` when rejected |
| `asset_location` | `"vault"` when approved; `"max-only"` when rejected |
| `asset_present` | `true` when approved; `false` when rejected |
| `posts` | the post(s) the request came from, vault-relative |

**A record written at a card's approval is a studio record, so its `source` is `"studio"` — the same value the other card-approved re-renders use.** A handful of older records in the library carry `source: "backlog-review"`; they are outliers, not a second convention, and a record that copies one of them breaks the index the value is read by. Keep `source: "backfill"` on the records that came out of the backfill, and `"studio"` on every record a render produced, including the ones written when a verdict card's approval lands.

**A nanobanana re-review uses the same studio shape with these swaps**: `engine: "nanobanana"`, `prompt_type: "text"`, `width: 1376`, `height: 768`, `generation: {"model": "gemini-image", "seed": null}`. The `## Prompt` block carries the plain prompt text (no JSON). `created_at` and `finished_at` come from the nanobanana job's metadata when it is still available; when the job is pruned, the staged file's mtime is the only surviving timestamp (use it for both, +25s for finished_at), and the `## Why` notes that the dates came from the staged file. The vault copy, the embed and the `superseded_by` chain follow the same re-review rules as an ideogram slot (`.superseded-<old job id>.png`, old record's verdict stays `unreviewed`).

The remaining keys keep the back-fill meanings:

- `type: "image-record"`, `engine: "ideogram4"`, `prompt_type: "json"`.
- `width`, `height` as integers.
- `generation` is the prompt's wrapper-only `generation` block, or `null` — **except on a `prompt_type: "text"` (flux2-klein) record, which is never `null`.** A text prompt carries no wrapper block, so that field records what actually rendered: `{"model": "black-forest-labs/FLUX.2-klein-4B", "steps": 4, "seed": <seed>}`, read from the job's own row. Nothing in `verify-slot.py` asserts this field, so a twin written from the ideogram template passes a full close with the model, the step count and the seed gone (section **FLUX.2-klein record**).
- `created_at` and `finished_at` come from `imagegen status` — and from **that job's own** status line, read fresh. They are the renderer's timestamps, not yours to compose: a record whose `created_at` and `finished_at` are copied from a neighbouring job, taken from a prompt file's mtime, or inferred from a clock is wrong in a way nothing else in the record contradicts, so it survives review. When a record's dates and the renderer's `status` line disagree, the renderer wins and the record is patched. Compare the two before writing the record and again before closing the card. **Copy the string as `status` returns it, fractional seconds included** — the back-filled records carry values like `2026-10-09T01:08:34.546446`, and truncating to whole seconds is composing the timestamp by another route: the date and the minute still agree, so no later check flags the drift.
- **When the renderer no longer holds the job at all, the record says so rather than borrowing a neighbour's dates.** `imagegen status <job>` answers `Job not found` for a pruned row — usual for a held-back attempt whose record is written days after the render — so `created_at` and `finished_at` are `null` and the `## Why` names the staged file's mtime as the only surviving timestamp. Composing them from the slot's shipped job puts two renders of one slot on one set of dates, and nothing else in the record contradicts it.
- **`superseded_by` is `null` unless a later job replaced this image; a rejected render whose slot was later approved points at the approved job id (see **Multi-round slots**).** Write the bare YAML `null`, never through a format string: a builder that fills every field with `'superseded_by: "%s"' % ('null' if …)` stores the quoted string `"null"`, which reads correctly in the file and fails `approved record's superseded_by is null` on every approved record of the round. The quoted word is the frontmatter mistake that survives every other check, so quote only the fields that hold a string and build the two-valued ones as literal `null` and `"<job>"`. A builder's data table carries Python `None` for an absent asset: the string `"null"` writes `asset: "null"` and an `![[null]]` embed.
- The **approved** record's `superseded_by` stays `null` — nothing replaced it — while **every** earlier record of the slot points at that one approved job id, the back-filled one included. Write the chain in one pass over all of the slot's records, not one record at a time, or the history ends in a dead end.
- `post_status` is the post's frontmatter `status` (for example `draft` or `published`), or `null`.
- `asset_location` values match the back-fill: `vault` or `max-only`.

**The `## Why` section names the post's section with the post's own heading text and nothing else.** The provenance line reads `From [[<post>]], section "<heading>":` and the heading string is copied verbatim from the draft, including the empty string for a header image that sits above the first section. **A header with no heading above it has two honest shapes, and the label has to match the passage you picked:** either the empty label with a passage from the post's opening lines, or a label naming a real heading — in which case the quote must be a passage under that heading, so a header image can quote the first section below it and label it by that section's name. A label of your own invention (`the opening`, `header`) fails `section label is the nearest heading above the quote` with `heading=''` even when the passage is real and the label reads accurately, because the check compares against the draft's headings rather than against your description of the frame. Do not append a parenthetical gloss after it: no record in the library carries one, and a gloss is not part of the heading, so anything matching that label against the draft's headings cannot find it. Put the explanation of an empty label in the prose above the line, where it belongs. **Do not open `## Why` with a `> <item id>` label line.** Every blockquote in `## Why` is read as a quoted passage and each one goes through the line-position check, which asks for the nearest heading above it; a label the post never contains fails `section label is the nearest heading above the quote` with `heading=''` even when the real quote below it matches perfectly, and the failure names the label rather than the stray blockquote, so it reads like a wrong section label. Prose first, then the provenance line, then exactly one blockquote. The older records that carry `> header` are the empty-label case, where the label and the heading are both nothing.

**The provenance of a `## Why` is verifiable, and the check is mechanical.** A record's section label and the passage it quotes must come from the same place in the post, and that can be settled without a read: find the quoted passage in the post file, take the **nearest heading above it**, and compare that heading with the record's label. Equal means the provenance is right; different means the record quotes a different section than the one it names, which is the provenance defect the review-card scope calls out. **Take the heading above the quote by line position, not by searching for the heading text** — a post often repeats a phrase, and the first match is not the one the quote sits under. The defect is worth stating precisely because the two halves look fine separately: the label names a real section of the post and the quote is a real passage of the post, so a check that only asks "does this label exist in the post" or "is this quote in the post" passes on a mismatched pair. **And do not inherit the quote from the slot's earlier record.** A record for a later attempt is usually drafted from the record beside it, and that record's quote is often the very one a card flagged as off-by-one — copying it forwards the defect into a record nothing will re-check, because the new record's label now agrees with a passage that sits under a different heading. Take the heading and the passage from the post by line position every time, even when a sibling record looks ready to copy. **A passage sitting under a Jekyll admonition marker is quoted from its own line, never glued to the marker.** `{: .prompt-danger }` (and `.prompt-warning`, `.prompt-info`) sits on a line of its own in the draft, so a quote built by joining the marker to the sentence below it appears in no line of the post and the line-position check cannot place it — and a record that inherited that glued quote from an older record carries the defect forward. Copy the whole paragraph line: filter the post's lines for the ones starting with the passage's first words, assert exactly one match, and leave the marker out of the blockquote.

**A failing assertion is a claim about the check until it is a claim about the artifact.** When a verification script reports a failure, establish which of the two is wrong before touching anything: a check that searches for a phrase the file never had will fail on a perfectly healthy record, and "fixing" the record to satisfy it corrupts a good artifact. Read the file the assertion names, work out what the check actually compared, and only then decide whether the artifact or the check is at fault. **The same rule covers output that looks mangled: a run of `***` where a record's own value should be is the shell masking a string that resembles a secret, not damage to the file.** A frontmatter sweep printed two records correctly and masked the third, which reads exactly like a half-written edit; `read_file` on that record showed an intact line. Confirm the bytes before repairing a record, and never rewrite a healthy record to satisfy a display artifact. **A record that was deliberately left alone is verified by asserting it is unchanged** — its verdict, its `superseded_by`, its source and its `## Why` prose all stay as they were, and the check that a neighbouring slot's record was not touched is part of the closeout, not a nicety.

**A record's prose is a durable claim, so it states what the check reported rather than a tidier version of it.** A record is read later by someone who cannot re-run the check and does not have the render in front of them, so a sentence that overstates a measurement becomes a fact nobody can contradict later. **A check that fired is reported as firing**, with the reading that settled it: a flat-band detector that fires on every cel-shaded frame is a detector, not a verdict (engine-pitfall #66), so the record says the detector fired and that the named rows read as ordinary painted content on disk crops — not "no flat colour band anywhere". The same applies to a count, a spelling, a gaze and a colour: the record carries the number the measurement gave and what it was compared against, and when a check was inconclusive it says so rather than rounding up to a clean result. **Write the record's prose from the check output, not from the impression the picture gave** — the impression is what the check is there to test. **That includes every number the brief handed you.** A brief's check note is one run's reading, so a count in it can be wrong in either direction, and a record that repeats it puts a secondhand claim in the library as a measurement: re-count the props on crops, and when the frame disagrees with the brief, the record's Why carries the measured numbers plus one clause saying the brief's figure was corrected, and the closing comment repeats it — otherwise the wrong number outlives the only run that could see the pixels.

**The `## Prompt` block is the prompt that was submitted, byte for byte.** Copy the file that was submitted into the block; do not retype it and do not re-serialise it. A retyped JSON block silently loses the things that decide the render — the `bbox` order above all, since a transposed box is what the model obeys over the prose and a record with the axes swapped sends the next run after the same defect (engine-pitfall #61). **Verify the block against the file rather than against your memory of it**: read the file, read the block, and compare them. A `diff` of the two is cheap and it is the only check that catches a reordering, a dropped element or a reformatted number. **A raw-text diff that reports a difference is not a defect on its own: `imagegen status` serves `prompt_value` as the wrapper's own compacted re-serialisation of the prompt, so the served string and the file differ in whitespace while holding the same prompt.** Compare them parsed (`json.loads(served) == json.loads(filed)`) and keep the file as the authority for the block — "normalising" the block to the served compact form throws away the format a future run reads. **A parsed compare that comes back FALSE is a different finding: the file now holds another picture's prompt, and the job's own served `prompt_value` is the only surviving record of what was submitted.** The slot-generic prompt filename collides across posts, so a later post's run overwrites `header-r2.json` and every earlier attempt that used it loses its file; a record written from that file would carry a living-room prompt under a workshop render, and nothing inside the record contradicts it. Write the served `prompt_value` as the block and say in the `## Why` that the file was overwritten by another post's slot of the same name, so a reader knows why this block is the compact form rather than the pretty one.

**Assemble a new record from files instead of writing it in one pass.** Two parts of a record are copies of another file — the `## Prompt` block and the earlier round's Verdicts row — and both are corrupted silently by retyping: a hand-copied block loses a `bbox` axis, a hand-copied reason loses a letter, and nothing in the record then contradicts either. So write the frontmatter, the `## Why` prose and the opening `json` fence to a scratch file, `cat` the submitted prompt file into it, append the closing fence and the Verdicts header, and pull the earlier round's row into the same assembly with `grep '^| <round> |' <the record that owns it>` so the reason never passes through your hands. Then extract the block back out and compare the bytes:

```bash
awk 'BEGIN{f=0} /^```json$/{f=1;next} f&&/^```$/{exit} f{print}' <record> > /tmp/block.json
cmp /tmp/block.json <the submitted prompt file>    # silence is the proof
python3 -c 'import json;json.load(open("/tmp/block.json"));print("ok")'
```

A silent `cmp` is the only pass that proves the block is the file; the `json.load` on the extracted copy proves the fence did not swallow the JSON. **When the close is scripted, extract the block in Python instead of shelling that `awk` program:** the one-liner carries its own quotes, so a script that hands it to `subprocess` as a single argument writes an empty block, and the empty block then fails `json.loads` and reads like a malformed record rather than a broken extractor. Slice the record's lines between the fence after `## Prompt` and the next bare fence, then compare parsed. The `cmp` is worth running even when you assembled by `cat`, because a head file that already ends inside a fence, or a prompt file without a trailing newline, shifts the boundary without changing a character of the JSON you can see. **Get the newline count right instead of adding one "to be safe":** assemble as `cat head.md prompt.json tail.md` with **no separator inserted anywhere**, after checking what the prompt file actually ends with (`tail -c 1 prompt.json | xxd`). A prompt file that already ends in `0a` needs nothing added — insert a newline anyway and the record carries a blank line inside the fence, so the extracted block is one byte longer than the file and the `cmp` fails on a record whose JSON is perfect. **A script that assembles the record reproduces this exactly by starting its tail with a newline:** building `head + prompt_text + "\n```\n\n## Verdicts…"` puts a blank line inside the fence for the same one-byte reason, and the tell is identical — `cmp` reports `EOF on <the prompt file>`. Build the tail as `"```\n\n## Verdicts…"` with no leading newline, since the prompt file's own trailing `0a` already ends the line the fence sits on. **A `cmp` reporting `EOF on <the prompt file>` is exactly that defect and nothing worse**: it means the block holds trailing whitespace the file does not, so fix the assembly and re-extract — never "fix" it by trimming the prompt file, because the file is the thing the render was made from.

**The opposite newline — a prompt file with no trailing newline — glues the closing fence onto its last line, and the tell is a record with ONE fence.** `head + prompt_text + tail`, where the tail starts with the bare closing fence, writes the last JSON `}` and the backticks on one line, so `grep -n '^```' <record>` prints one fence line instead of two and `verify-slot.py` answers `record carries a prompt block in a fence` — the same FAIL as an unclosed block, on a record whose prompt is intact. A JSON prompt produced by `json.dump` without a trailing newline, and every FLUX text file that ends on its last word, both land here. So normalise the boundary in the builder instead of assuming it: `if not prompt_text.endswith("\n"): prompt_text += "\n"` before the tail is appended, then assert exactly two fence lines per record in the same pass. Neither direction is repaired on the prompt file itself.

**A script that reuses one fence variable writes the closing fence with the opening fence's language tag, and the record then swallows its own tail.** Keep the opener (` ```json `) and the closer (a bare ` ``` `) in separate variables: a tail built from the opener's value emits ` ```json ` twice, the extractor that stops at a plain fence reads straight past the record's `## Verdicts` heading into the tail, and the run spends a pass chasing a `cmp` difference it cannot see in the file. The tell is one command — `grep -n '^```' <record>` must print exactly two fence lines for a record holding one prompt block, and the second must be bare. Once a script has written a whole round's records, re-check every file it wrote, not only the one that failed first.

**A script's tail has to open with the bare closing fence.** Building `head + prompt_text + "\n## Verdicts…"` leaves the prompt block unterminated, so the whole tail — heading, table and all — reads as part of the prompt, and `verify-slot.py` reports `record carries a prompt block in a fence` FAIL: a message about the block being absent when the block is present and merely unclosed. The tell is `grep -n '^```' <record>` printing a different count than two per prompt block, with the last fence missing rather than malformed. Build the tail as `"```\n\n## Verdicts…"`, and treat that particular FAIL as a fence problem before looking at the prompt file. **A text prompt's opening fence is bare too — no `text` language tag after the backticks.** The flux record shape is `prompt_type: "text"` with the prompt inside a plain fence, and `verify-slot.py`'s `prompt_block()` searches only for a json-tagged opener and a bare opener, so a builder that keys the fence language off `prompt_type` writes a `text`-tagged fence and the close fails `record carries a prompt block in a fence` on a healthy record. The tell is the first of the record's two fence lines carrying a word after the backticks.

**The opening fence is a line of its own, and a head that ends on it glues the prompt into the fence.** Assembling as `head + prompt_text` where the head's final line is the bare backticks writes the fence and the prompt's first words on one line, and `verify-slot.py` answers the same `record carries a prompt block in a fence` FAIL as an unclosed block — a message about absence on a record whose prompt is right there. The head ends with the fence line plus a newline (join with `"\n"`, or build the block as `"```%s\n%s\n```" % (lang, prompt.rstrip("\n"))`), and the tell is `grep -n '^```' <record>` printing one long line where two fences belong. **Repair a whole round of records in one pass rather than rewriting them one by one:** take the bytes between `## Prompt` and `## Verdicts` from the submitted prompt file, rebuild that span as `## Prompt`, a blank line, the fence with its language tag, the file, the bare closing fence, a blank line, `## Verdicts`, then assert each record's extracted block equals its file with only the trailing newline normalised. A builder writes every record of the round through the same defective path, so one script over all of the round's files is the fix, and checking only the first file leaves the rest broken.

**Build each Verdicts row from whole cells, never as a `verdict|reason|` fragment dropped into a template.** A row assembled as `| {round} | {date} | {cells} | [issue](…) |`, where `cells` already carries its own pipes, writes `approved|Approved on review.|` — the table still parses and reads close enough to right, and `verify-slot.py` then fails `reason cell is padded on both sides` at the very end of a long close. Compose the finished row as one string and print it before the record is written, so a missing pad shows up in the output instead of in the checker.

**A row taken out of another record is rebuilt with `"|".join(row.split("|"))` and nothing else.** A well-formed row splits into seven cells whose first and last are empty strings, so the plain re-join reproduces the line byte for byte; prepending another `|` because the line "should start with a pipe" produces eight cells, and the close then fails `row splits into 7 cells` on a row that renders perfectly in the file. Edit cell 4 and re-join — never re-wrap the assembled string.

**Strip an existing prefix only when it matches the stem of the record the row came from.** A generic `^[\w.-]+: ` on a copied reason eats the first word of his text whenever he opens with a word and a colon (`Style: early 1990s …`, `Ruling: …`, `Note: …`), which turns a verbatim quote into a corrupted one that no check afterwards can catch — the row still parses, still pads, still reads plausibly. So pass the owner's stem, strip only `<owner stem>: ` (or the bare stem), and assert the reason that remains equals the owner's cell with its prefix removed before the row goes into the record.

## The mechanical closeout check (`verify-slot.py`)

`scripts/verify-slot.py` runs the whole mechanical half of an approval close in one command: the filename against the job's `created_at`, the heading against the stem, the `## Prompt` block against the submitted file, the duplicate-record guard, the `superseded_by` chain of every earlier record, the vault asset byte for byte, the post embed and its alt text, the Verdicts table shape, and the `## Why` quote against the post by line position. Run it before the issue is marked done and quote its counts in the closing comment instead of re-deriving any of them:

```bash
python3 ~/.hermes/profiles/matejko/skills/image-studio/scripts/verify-slot.py \
  --record <new record.md> --job <job id> \
  --earlier <every earlier record of the slot> \
  --post <post.md> --prompt <the submitted prompt.json> \
  --asset-source <staging png> --source studio
```

**Run the checker from the vault root and pass vault-relative paths.** `--record`, `--earlier` and `--post` are resolved against the current directory, and `--vault` does not resolve them — a run started from the skill's own `scripts/` directory with `3-resources/...` arguments reports `FAIL record exists` with the path printed right there, which reads like a record that was never written. `cd /Users/paperclip/vault` first and keep every path relative to it (absolute paths work too, but mixing the two is how half the `--earlier` set goes unresolved).

**Pass every earlier record of the slot, the held-back attempts included.** The duplicate-record guard compares the library's records that mention the job id against exactly `{this record} ∪ {the --earlier set}`, so an attempt whose own prose already names the replacement's job id is in that set whether or not you name it on the command line — leave it out and the guard reports a mismatch on a perfectly healthy close.

**A job id that begins with a dash breaks the filename and heading assertions until the checker strips it.** The record filename drops the job's own leading dash (`--GfBL3Y7iWY.md`, not `---GfBL3Y7iWY.md`) while the frontmatter keeps `job_id: "-GfBL3Y7iWY"` verbatim, and the checker built its expected suffix from the raw id — so a healthy close failed `filename ends with --<job>.md` and `heading is the stem` together, which reads like a misnamed record. `verify-slot.py` now strips one leading dash when it builds the name and still compares the full string for `job_id matches --job`. Pass such an id as `--job=-GfBL3Y7iWY`, because argparse reads the bare form as a flag and exits on `expected one argument`.

**The same dash stops `imagegen status` from reading that job at all, so take its timestamps from the worker's own `jobs.db`.** `imagegen status -_ySI23odgo` and `imagegen status -- -_ySI23odgo` both answer `error: the following arguments are required: job_id`, and the record still needs the renderer's `created_at`/`finished_at` rather than a composed one. Read the row over the wrapper's own SSH host: `ssh m1max "sqlite3 -json git/ideogram4-local/jobs.db \"select id,status,engine,seed,created_at,finished_at,output_path from jobs where id='-_ySI23odgo'\""`. It answers the same fields the CLI would, the strings keep their fractional seconds, and the `.output_path` basename is the fetched stem the record name is built from.

**A sibling engine's rejected record belongs in `--earlier` too, because its `superseded_by` names the approved job.** When one card pairs an ideogram with a flux companion and he approves the ideogram and rejects the companion, the companion's record points at the approved job id — so the duplicate guard finds that id in two files and the approved record fails `job id appears in exactly this record plus its earlier records` unless the companion path is passed with `--earlier`. It then passes its own two assertions (it points at the job, and its verdict is not this approval), so passing it is the whole fix.

**The comparison copy's own run takes no `--earlier`, and two of its failures read as defects when they are not.** Verify a flux companion with the slot's back-filled record passed as `--earlier` and it reports `job id appears in exactly this record plus its earlier records` and `earlier points at the approved job: <back-filled>` — both false, because that record's `superseded_by` names the ideogram that shipped, not this companion, and the companion's job id appears nowhere else in the library. The `--earlier` set belongs to the record the chain points at. Run the copy with `--record`, `--job`, `--post`, `--prompt` and `--asset-source` only. Its failures then depend on one field, and only one of the two shapes is by design: a copy whose `superseded_by` is `null` fails `post embeds the asset exactly once` alone, while a copy chained to the job that shipped — the correct value when the companion is the same slot's comparison — fails that check **and** `approved record's superseded_by is null`, two rather than one, because the chain is what the shipped record's own `--earlier` assertion reads. Quote the pair as `35 checks, 2 failed: the embed check, which is why the copy is not in the post, and the approval-shaped superseded_by assertion that a chained copy cannot pass`.

**`verify-slot.py` is approval-shaped, so a rejected record fails exactly five checks by design.** On a rejected render it reports `verdict is approved`, `asset_location is vault`, `asset_present is true`, `approved record's superseded_by is null` and `asset names a file` as failures — those are the approval assertions, not defects. Quote it as `23 of 28 checks, the five approval-shaped assertions not applicable to a rejected render` and do not edit the record to satisfy them; a rejected record with `asset_location: vault` or `superseded_by: null` is the defect the checks are pointing away from. **A held-back record whose `asset` is `null` fails a sixth, the embed check**, because there is no asset name to match against the post — quote that one as `33 checks, six failed: the five approval-shaped assertions plus the embed check, none applicable to a record with no asset`, so the extra line reads as the same class instead of as an unaccounted defect.

**A verdict that lands the next morning does not re-date the record.** The filename prefix is the job's `created_at` date even when the card is answered hours later, and a brief that says "use the record date" means that date, not the day the close runs. Re-dating the record to the approval day reads fine in a directory listing and fails the checker's first filename assertion.

**An approved record whose image is deliberately not embedded fails the embed check, and that is correct — do not call the verification failed.** A library-only copy has no post embed; a copy chained to the shipped job fails the `superseded_by` assertion beside it, by design (see the comparison-copy bullet above). Quote that as `34 of 35 checks, the embed check not applicable to a copy that is deliberately not in a post` and do not "fix" it by embedding both images: two embeds on one beat is a defect the post does not have. The same shape applies to any record whose asset ships somewhere other than the post it names — the close reads the count, not the exit code alone.

**A cross-reference to the sibling render names it by stem or item id, never by job id.** The duplicate-record guard asserts a job id appears in exactly one record plus that record's `--earlier` set, and it counts every file in the library — so a Verdicts row in the *shipping* record that quotes the companion's job id makes the companion's own verification fail on `job id appears in exactly this record plus its earlier records`, with the failure naming the companion file and reading like a duplicate record. Write the cross-reference as `<stem>` (`ip-hops-r2-flux-6c781d33`) or the plain item id; a job id belongs only in the record that documents that render. **The guard reads the whole file, not only the Verdicts table, so the `## Why` prose obeys the same rule:** a held-back attempt whose Why says "replaced by job `<sibling job id>`" writes that id into a second record, and the sibling's own verification then fails `job id appears in exactly this record plus its earlier records` on an otherwise healthy close — name the replacement by its stem or item id there too. The one job id a record other than its own may carry is the one in its `superseded_by`, because the approved record that owns the chain lists that record under `--earlier`.

**A script that writes the `## Prompt` block must put the closing fence on its own line.** `verify-slot.py` reads the block as the text between "```json\n" and "\n```", so a template that interpolates the submitted JSON and appends the fence straight onto it only works when the prompt file happens to end in a newline: a file that ends at `}` closes the fence as `}``` `, the search for "\n```" runs past the end of the block, and the close reports `record carries a prompt block in a fence` FAIL on a record that visibly contains one — followed by `prompt block is the submitted file byte for byte` also failing, because the block is `None`. Interpolate the file verbatim with the fence on the next line and both checks pass at the same byte count.

**The section label is copied with the post's own characters, quotes included.** A heading that itself carries double quotes (`The GitOps wrinkle: "Helm upgrade succeeded" ≠ live`) goes inside the provenance line's quotes unescaped; writing `\"` in the markdown stores a literal backslash, and the check then fails with `label='… \\"Helm…'` against an unescaped heading. Repair the record, never the check — the post's heading text is the authority.

## Before copying a PNG into the vault, check the target path is free

The asset filename is the item id plus the day's folder (`assets/<YYYY-MM-DD>/<item id>.png`), so two posts reviewed on the same day with the same item id collide — `header-r2` is the item id on nearly every post. A copy to an occupied path silently replaces another post's **approved** image, and no check fails, because the bytes are right and only the neighbour's draft breaks. So `ls` the target folder and `grep` the drafts for the path before the copy; when it is taken, the post reviewed now ships under a post-specific name (`dns-header-r2.png`, `post033-header-r2.png`) and only that post's embed changes. The item id on the card, the prompt file and the render name do not move — the vault filename is the only thing that bends. Say the new name in an issue comment at card time, because the next run reads the brief's bookkeeping block, and the brief was written before anyone looked.

**A backlog re-review replaces the draft's own picture in place, and that copy is expected — the file it overwrites still has to be kept.** Here the target is this post's current asset: the ship table names it, the draft already embeds it, and it is not another post's file, so the free-path refusal above does not apply and declining the copy leaves an approved render unshipable. Copy the new bytes over it, and first preserve the file being replaced as `<slug>.superseded-<old job id>.png` beside it.

**When the image file is shared by more than one post, a re-render approved for one post must not overwrite the shared file or supersede the shared record globally.** The brief's note ("replace the embed only in this post") is the signal. Ship the new bytes under a new filename (`<slot>-r<N>.png`), repoint only this post's embed, append a Verdicts row to the shared record documenting this card's verdict, and write a *new* record for the new file with `posts: [this post]` and `verdict: approved`. Leave the shared record's `asset`, `asset_location` and `superseded_by` untouched — the other post still embeds that file and its card judged it separately. Do not set `superseded_by` on the shared record, and do not rename its file.

**A pre-flight `ls` and a `grep` of the drafts are a check against a snapshot, and the day folder is shared with every run closing a post at once.** Another run can create `assets/<today>/` and write its own `<item id>.png` in the minutes between your `ls` and your copy, so a folder that listed `free` or did not exist at all is occupied by the time you write. That is not a hypothetical race: it is the normal shape when several cards are in flight, and the losing write replaces an approved image with no error. So make the copy itself the check, in the same script that copies — `if os.path.exists(dst): raise SystemExit(...)` immediately before `shutil.copy2`, then hash the copy and compare it with the staging file. **That guard belongs to the new-name branch only, because the in-place re-review needs the opposite order.** A copy function that ends with a blanket exists-check before `shutil.copy2` aborts the re-review's own path *after* it has preserved the old bytes: the close dies with the preserved file on disk, the draft still embedding the old picture, the new bytes never written — and the retry hits the same line and reports `preserved already`. Write it as two branches: preserve the target then overwrite it for this post's own asset, refuse an occupied target only where there is no preserved file to justify the write. A copy that refuses is the only proof the path was free at the moment that mattered; a retry under the same name defeats the guard, so the refusal means pick the post-specific name.

## Write the approval pass so it can be re-run

An approval close is five writes over six files (vault copies, post embeds, records, the `superseded_by` chain, the card), and a run can die in the middle of it — a missing `section` key in the slot table killed one pass after every copy and all three embeds had already landed. The second attempt must therefore **converge on the finished state instead of refusing it**: a vault copy whose bytes already match is a copy, an embed whose new line is already present is rewritten, a record that exists and carries the job id is written, and a chain that already points at the approved job is set. Each step checks the state before it writes and prints what it found, so the re-run's output is the audit trail of the finished close. The only hard refusal is a target that exists with *different* bytes or a different job: that is another post's write, and it needs a post-specific asset name rather than a retry. A pass that raises on every existing target cannot be finished once it has been interrupted, and the interrupted state — copies in the vault, embeds already repointed, no records — is exactly the state nothing else will repair.

**The chain step takes each earlier record's path whole from the enumeration, never `<library>/<this close's month>/<filename>`.** A slot routinely chains a record written in an earlier month — a back-filled image has its own `image-library/<YYYY-MM>/` folder, which is the month in its own filename prefix and not the month this close writes its new records into — so joining the close's month constant to that filename builds a path that does not exist. The failure lands at the last step of the pass, after the vault copies, the embeds and the new records have already been written, which is the most expensive place to discover a typo. Resolve every earlier record through `grep -rl '<post path>' 3-resources/image-library/` and keep the absolute path it prints, then assert each of those paths exists **before** the pass writes anything: a wrong member of the chain is then caught while the run is still cheap to abort, and the re-run converges as the section above requires.

## The Verdicts table

Always keep the header exactly:

```markdown
| round | date | verdict | reason | issue |
| --- | --- | --- | --- | --- |
```

Append one row per round that resolves for this record:

```markdown
| 1 | 2026-10-21 | approved | Warm light and the forklift read as the migration story. | [GUL-42](/GUL/issues/GUL-42) |
```

Never rewrite an earlier row. The table is the verdict history; a later rejection does not erase an earlier approval.

**Every row's reason cell is non-empty, the approval included.** `verify-slot.py` asserts it on each row, so a blank cell fails a close whose other checks all pass — the failure lands at the very end of a long pass and reads like something else. An approval he gave with no reason still needs a cell, and the library carries two shapes for it: `Approved on review.`, or one line naming what the picture carries written as the record's own note. Write one of those two. Do not leave it blank, and do not write him a reason he did not give — an invented sentence in that cell becomes his words the moment a later record copies the row forward.

**The owning record's row is itself a copy, so verify it against the card before copying it forward, and check the earlier records' post paths in the same pass.** A back-filled row carries the reason as the review run typed it, and one 260-character reason came back with the word "any" missing ("generally does not make sense" for his "generally does not make any sense") - invisible in the rendered table and reproduced as a "verbatim" quote by every record that copies it forward. At a close, `GET /api/issues/<the card that owns the row>/interactions`, take `result.items[].reason` for the slot, and assert the whitespace-collapsed string appears in the owning record; repair the owner's cell when it does not and say in the closing comment which word was restored. **The same pass reads each earlier record's `posts:` field and its `From [[...]]` wikilink and checks the file resolves under `tech_blog/`** - two attempt records of one post named `teaching-my-server-agent-...md` where the real file is `teaching-my-media-server-...md`, so the record pointed at nothing. Repair both places.

**An earlier round's row is copied from the record that owns it, never retyped.** When a new approved record reproduces the rounds before it, each row's reason is a durable quote — his words for a round he judged, the attempt's own note for a render held back at the self-check — and a hand-retyped copy silently corrupts it. A reason retyped into a freshly written record came out with one letter tripled inside a nonsense word, which converts a verbatim quote into a fabricated one that nothing else in the record contradicts, so it survives review. Copy the row out of the earlier record with a text tool or a script, then compare it with that record's row character for character before the record is written. The rows are the only place a reader can check the slot's history against the report that was actually given. **Prefixing is an edit to the reason cell alone: the cell keeps its `: ` after the prefix and its own spaces at both ends.** Splitting the row on `|` and rebuilding the reason cell with a stripped remainder yields `<stem>:the reason`, one malformed token, where the convention is `<stem>: the reason` as in the example rows above. **The mirror-image bug is on the other end of the cell**: a `.rstrip()` on the copied cell eats the space before the following pipe and the row comes out `…not fitting the picture| [GUL-…](…)`, which still parses as a table, renders correctly enough that no eye catches it, and is no longer the row that was copied. So build the cell as `" " + prefix` followed by the cell **exactly as it came out of the split**, and assert both ends before writing: the prefix and his first word separated by exactly `: `, and the reason still ending ` |`. Print the finished table and read it before the record is written.

**A row records who decided it, and a render you held back is not a verdict Wojtek made.** The table is read later as the library's account of the slot's history, so a row whose reason is his words must be a row he decided. A render that never reached him because your own self-check held it back still gets a record and a `rejected` row — that is the render's status and it keeps the chain whole — but its reason has to say so (`held back at the self-check, never shown to Wojtek`). Never write a rejection reason in his voice for a render he never saw; a misattributed reason reads back later as a rule about his taste, and the misattribution is invisible in the note itself.

**Enumerate the slot's earlier records from the library, not from the brief's count.** A brief's bookkeeping block can miscount them — post 036's said "three earlier records" and listed two, while the third name it warned about belonged to a different post whose header shares the item id — so `grep -rl '<post path>' 3-resources/image-library/` is the list, and each hit's `posts:` field confirms which post it belongs to before it joins the `superseded_by` chain. A record that names the same item id but a different post stays untouched, and the closing comment states the corrected count so the next reader does not go looking for the missing one. **Never follow a record's own `superseded_by` outward to build the chain.** A same-slug record from another post can point at yet another post's approved job, so a chain assembled by walking the pointers gathers files from three posts and then reads as one slot's history. The chain is exactly the records whose own `posts:` field names this post, and every member of it gets the one approved job id this close accepted; the pointers those records already carry are history, not instructions.

**An earlier round of the slot can have no record at all, and the brief will still name one to chain.** A rejected attempt that never got a record leaves a gap nothing in the brief can see: the enumeration above returns only the surviving records, the job id in the brief's `superseded_by` instruction matches no file, and there is nothing to set. The close is not the place to reconstruct that record — its render and its prompt may not exist any more, so anything written now is invented history for a picture nobody can look at. Chain the records that do exist, take that round's reason from the card that answered it (`GET /api/issues/<card>/interactions`, `result.items[].reason`, the same authority used for verifying any copied row) instead of from a record that is not there, and say in the closing comment that the round has no record — so the next reader neither hunts for the file nor reads the shorter chain as a broken slot.

**Write the held-back record in the run that holds the render back, not in a later approval pass.** The run that fetched the render and read the crops is the only one that knows what the defect was; a later run rebuilds it from a comment, and the row is what the slot's history reads long after. Write it at the moment of the hold-back: `asset: null`, no embed, `superseded_by: null`, the row prefixed `<stem>--<job id>` and numbered for the round the attempt was made in even when that round's card does not exist yet, and its issue column the card that was open when you decided it. The `## Why` names the attempt, says which clause of the owner's reason it did clear, names the defect that held it back with the crops that showed it, and names the job submitted to replace it — a replacement still in flight is named as submitted, never as shipped.

**A held-back render that never got a record is reconstructed later from the renderer, and it keeps the two-value `asset_location` enum.** When a round's attempts went unrecorded, the whole slot's history reads as if three renders never happened — so write them after the fact, in one pass over every attempt, rather than leaving the gap: a reader of the approved record's chain otherwise cannot tell a clean single-render slot from one that spent five. `asset: null`, `asset_location: "max-only"`, `asset_present: false`, no `![[…]]` embed, `superseded_by` set to the job that actually shipped, and a row whose reason is `held back at the self-check, never shown to Wojtek`. **Do not invent a third enum value for a render that is still sitting in staging** — `asset_location` describes the vault (`vault`) or the absence of a vault copy (`max-only`), so `staging` plus `asset_present: true` claims a vault file that does not exist and breaks any reader that switches on those two values. The staging path and the byte size belong in the `## Why` prose, where they are prose rather than schema. **Check it with one grep over the month folder — `grep -l 'asset_location: "staging"' 3-resources/image-library/<YYYY-MM>/*.md` must print nothing** — because the value looks like schema, passes every reader that does not switch on it, and a batch of records written from one script carries it into every attempt of the round. The same pass asserts `asset_present: false` on each reconstructed held-back record, since `true` beside `asset: null` is the other half of the same false claim.

**The inverse shape is the one that slips through: a held-back record whose frontmatter was copied from the approved sibling.** Building an attempt's record from the record beside it inherits `asset:` naming the slot's shipping PNG, `asset_location: "vault"` and `asset_present: true` — a claim that a vault copy of this render exists, when the file at that path is a different picture, so a reader who opens the record to see the attempt is shown the approved frame instead. The `staging` grep above does not catch it, because nothing in the file looks like the invented enum. Audit by verdict instead: every record whose frontmatter reads `verdict: "rejected"` and whose body carries no `![[…]]` line must also read `asset: null`, `asset_location: "max-only"`, `asset_present: false`; a rejected record naming a vault asset is the defect whatever the render was held back for, and it is invisible to `verify-slot.py`, which checks the chain and the embed and nothing about this pair.

**A review-card run that holds an item back writes that record at the hold-back, and it reads this section before it does — the two-value enum is not negotiable at that moment either.** Those runs reach for the record format without opening this file, and the shape they invent (`asset_location: "staging"`, `asset_present: true`, the staging path in `asset:`) passes `verify-slot.py` cleanly, because no assertion switches on those two values; the staging path and the byte count belong in the `## Why` prose and the grep above is the only thing that catches the invention. **That run also cancels the brief's vault-copy instruction for the held-back item.** The bookkeeping block is written before any verdict, against the items the brief expects to show; a render that never reached a card cannot become a vault asset, so the close says in one line that the copy did not happen, and why, instead of leaving a silent gap between the brief's instruction and the vault's contents.

**Run that grep over the month folder on every close, and repair the hits it finds in other posts' records in the same pass rather than only reporting them.** The repair is the two frontmatter values — `asset_location: "max-only"` and `asset_present: false` beside a null `asset:`, which a hit can carry as an empty string (`asset: ""`) instead of `null` and needs setting in the same edit — never that record's verdict, Verdicts rows or `superseded_by`, which belong to a slot this run did not touch. Re-run the grep to an empty result, because a value that looks like schema keeps passing every reader that does not switch on it, and name the repaired files in the closing comment: nothing on that post's own issue will ever show the edit. Leave their `## Why` and chain alone — a record whose prose still describes the staging file is honest; a record whose frontmatter claims a vault copy that does not exist is not.

**Except when the post that owns the hit is still mid-round — then that round's own close repairs it, and a second writer racing it is worse than a wrong enum for a few hours.** Read the queue first: a post whose state is `rendering` or `card` with an open issue is a round some run is writing into right now, and its records' enum belongs to that close. Name those files and the post in your closing comment, leave the edit to the owning round, and re-run the grep at your next close. The repair rule stands for every hit whose post is closed.

**Reconstruct from `imagegen status <job>`, and compare the prompt block parsed.** The prompt file may have been overwritten by another post's slot of the same name meanwhile, and the job's own served `prompt_value` is then the only surviving authority for what was submitted — read that job's `created_at`/`finished_at` in the same call. Compare a json prompt as `json.loads(block) == json.loads(prompt_value)` and a text prompt as string equality, and print each comparison; five records written in one pass from a shared script share one defect, so assert every file rather than the first.

**In a combined table the attempt's row carries the `<stem>--<job id>` prefix, and the held-back record itself may or may not — so strip before you prefix.** The prefix exists to tell the slot's renders apart in an approved record's history; a record whose table holds one row has nothing to tell apart and reads better unprefixed, but the library's own held-back records exist in both shapes and the prefixed one is common. The failure mode is a script that copies a row out of an attempt record and prepends the prefix to a reason cell that already starts with it: the finished row reads `…--NjxmCF6oZgE: …--NjxmCF6oZgE: held back at the self-check`, which no reader questions and which doubles a durable quote. So the copy step is `reason = strip_prefix(reason)` then `prefix + reason`, and the finished table gets printed and read before the record is trusted. **Take the data rows by position, not by character class:** the table is the `|` lines in the `## Verdicts` tail, whose first two are the header and the separator, so slice `rows[2:]` and assert the count you expect — a filter that keeps only lines made of pipes and dashes also drops a legitimately short row, and a filter built the other way round keeps the header and then loses the data to the slice. **Audit every held-back record for the table itself at the closeout, not only for its contents:** a record written fast for a render that never reached a card can end at the `## Why` with no `## Verdicts` section at all, which leaves the attempt with no verdict anywhere. `grep -c '^## Verdicts' <record>` returning `0` means append the header, the separator and that one row — round number of the attempt, issue column the card that was open at the hold-back.

**A slot that approved one engine and then replaced it with another engine's render is a chain verify-slot.py had to be taught.** Post 040's slots shipped an ideogram render on the round-2 card and then shipped a flux render on the round-3 card, so the approved record's `--earlier` set holds a record whose own verdict is `approved` and whose `superseded_by` names the new job. `verify-slot.py`'s `earlier keeps its own verdict` check read that as a failure because it assumed every earlier record was rejected or unreviewed; it now accepts an `approved` earlier record when that record points at the job under verification, which keeps the invariant (one accepted image per slot) without demanding a false verdict. Pass every earlier record of the slot — the September back-fill, the earlier engine's approval, the rejected comparison render and any held-back attempt — because the duplicate-record guard counts the job id across all of their files. **Copy the Verdicts rows from the record that owns each round, and only from there:** the ideogram record already carries both round-2 rows (its own approval and the rejected flux comparison), so also copying the rejected flux record's row duplicates the round and breaks `round numbers ascend`, which is exactly how the first attempt failed on a healthy close.

**A record's `## Why` may not claim a render ships after the render was held back.** The prose above the `From [[…]]` line is written when the attempt is submitted, and it is easy to copy the approved record's wording into the attempt's own record — which then says "This is the render that ships" about a picture that never reached a card. Check every held-back record's Why against its own Verdicts row: the row will say `held back at the self-check`, so the prose has to agree, name the attempt's number, and name the job id that actually shipped. A reader of the attempt's record otherwise reads the dead render as the accepted one.

**Every prop the Why names is checked against the PNG, because the prose is written from the prompt's intent and the render is what ships.** A Why drafted while the prompt is in hand tends to describe what the prompt asked for, and the model changes small physical facts often enough that the two drift: a prompt that asked for two wide cloth strips across the eyes renders as one band, a prompt that put the mirror in the man's hands renders with him standing beside it and one hand raised. Each of those turns the record into a description of a picture that does not exist. So before the record is written, walk the props it names and confirm each on the render — a full-frame read plus one crop of anything the Why makes specific — and write the sentence the picture supports. **The same pass covers the post's alt text on an approved re-render**, because the alt text is the reader's description of the same file and a stale one is a post-prose defect a review card may not fix. **A brief's own supplied alt text is not exempt, and it can contradict the brief's check note for the same image** — one brief handed over an alt reading "an upturned bucket on the step at the bottom right" for a frame whose corner holds an upright metal milk can with a bail handle and a lid, while its own check note for the render said milk can. The brief was written before anyone looked at the shipped frame, so crop-settle the two or three props an alt text makes specific and publish the picture's version; swapping the one noun in the brief's sentence is the whole correction, and it belongs in the same edit as the embed path. **The card's own item description is a third prediction of the same picture, and his approval does not make it true.** Whoever built the card wrote it from the brief and one run's check note, so it can assert a prop state the render does not have — a tower described with its side panel taken off, whose crop shows a closed side sheet with drive bays and no internals. The close settles it on a crop exactly as it settles the alt text, writes the record from the picture, and names the contradiction in the closing comment: the approved file ships either way, and the record plus the comment are the only two places a later reader can tell what the frame actually holds. **When the beat itself is a count, leave the number out of the alt text.** A slot whose meaning is "the beam now rests on three posts" can render four, and the crops may not settle it before the card closes; an alt text that repeats the brief's number bakes the disputed count into the draft that will ship, while one that names the props ("fresh pale posts beside one old dark one") stays true whichever count the frame carries. Put the measured count in the record's `## Why`, with the clause that the brief's figure was corrected, and repeat the disagreement in the closing comment — never in the post's alt text, which no review card may edit again.

## Approving or rejecting a back-filled record

A back-filled record (`source: "backfill"`, `verdict: "unreviewed"`) is an image that has been in the vault since before anyone reviewed it, so its verdict round changes the record and nothing else. Three edits, no more:

- `verdict:` becomes `"approved"` (or `"rejected"`; a defer is a rejection too, see below).
- Append one Verdicts row. Without a reason on the card use `Approved on review.` for an approval and `keep-as-is: <reason>` for a defer that keeps the image; never invent a reason he did not give.
- Delete the line `Back-filled from jobs.db; not reviewed yet.`

**The row replaces the blank line the back-fill left under the header.** A back-filled table ends with the header, a separator, an empty line, then the marker; put the new row where that empty line was, so the marker is gone and the table has exactly one data row. Appending below the marker leaves the record still reading as unreviewed. After editing, grep the record for `Back-filled` (expect no match) and print the whole Verdicts table, not just the frontmatter, to confirm the shape.

**Use `scripts/approve_record.py` for every verdict on a back-filled record, approval and rejection alike, and append the row yourself on a studio record.** The script's job is the three back-fill edits, and it refuses any record without the `Back-filled from jobs.db` marker — `error: <record> has no marker line; is it a back-filled record?` — so a held-back attempt's record, which was written as a studio record, cannot go through it. There the verdict is already in the frontmatter and the work is one row: assert the table header is present, assert no data row already exists for that round, reject a reason containing a pipe or a newline, and append `| <round> | <date> | rejected | <stem>--<job>: <reason> | [<card>](...) |`, then print the table and read it. `approve_record.py <record.md> --approved --issue GUL-x` and `approve_record.py <record.md> --rejected --issue GUL-x --reason "..."` do the three edits in one pass and verify the result, so a half-applied edit (row added, marker left behind) cannot pass unnoticed. The script also sanitizes the reason for a table cell — a pipe inside a cell splits the row into two columns and a newline ends it, and Wojtek's reasons are free text that can contain either, so hand-copying a reason can silently break the table. Hand-editing the same three spots across 153 posts is where a half-applied edit creeps in, so prefer the script. Verify anyway by grepping the record for the marker and reading the whole Verdicts table, not just the frontmatter.

**Pass `--round <k>` for the round the verdict belongs to.** The script defaults to round 1, which is right only for a slot's first verdict. On a second or third card the row has to carry that round's number, because the table is the slot's history: two rows both numbered 1 read as two verdicts for the same round and lose the round the second one belongs to. A round-2 verdict is `approve_record.py <record> --approved --issue GUL-x --round 2`, and the same `--round` goes on a rejection.

**The row's `date` is the host's local date, not UTC, so a verdict handled after local midnight carries tomorrow's date.** The script stamps `date.today()`, while the card's `resolvedAt` and every Paperclip timestamp stay on UTC — a verdict given at 21:28 UTC and applied at 00:03 CEST lands as the next day's row. Read that as correct: it is the day the edit was made, not a drifted clock and not a defect, so do not "repair" a row that reads one day ahead of the card, and do not spend a check on the discrepancy.

**Every timestamp you type into a comment, a monitor `notes` or a `backlog.py note` is read off `date -u` in that same command, never off the hour the shell or the calendar shows you.** The board, the queue and the monitors all stamp UTC while the host runs on the local zone, so a note written from the local hour lands ahead of every other timestamp about the same event, and nothing compares them afterwards — a queue note announcing a card "up at 22:40Z" sat beside an activity feed that dated it 21:34Z, and only a reader holding both would see it. Run `date -u "+%Y-%m-%dT%H:%M:%SZ"` and paste that string. When a stamp has already gone out wrong, append a one-line correction naming both values instead of leaving the thread with two clocks: `backlog.py note` appends and cannot be edited, and a comment can be deleted only by the run that holds the issue, so naming the correction is the repair a later reader can follow.

Leave `source: "backfill"`, `asset`, `asset_location`, `asset_present` and `superseded_by: null` exactly as they are: the file is already where the post points, so nothing was copied and nothing replaced it.

**A back-filled draft that your own self-check held back and that never reached a card carries no verdict of his, so the approval close sets its `superseded_by` and edits nothing else.** It keeps `verdict: "unreviewed"` and the `Back-filled from jobs.db; not reviewed yet.` marker: the frontmatter is the library's statement that this image was never judged, and writing `rejected` there puts a decision in his name that he did not make. The slot's account of that hold-back lives in the approved record's stem-prefixed row instead, which is where a reader looks for the slot's history. **The post brief and the runner's own "Records" instruction both say to set `verdict:` to `"rejected"` on the brief's record, and that instruction is written for an image he judged — it does not override this case.** When your own self-check held the draft image back, that record was never in front of him, so the close touches its `superseded_by` and nothing else: setting `rejected` there, and replacing the `Back-filled from jobs.db; not reviewed yet.` marker with a rejected row, writes a verdict in his name and deletes the library's only statement that the image was never judged. Read the brief's records table as applying to verdicts he gave. When in doubt, ask which of the two the record is: a draft that reached a card gets the brief's three edits, a draft your check stopped does not. This is verified rather than inferred: `verify-slot.py` treats `unreviewed` as passing `earlier keeps a verdict that is not this approval`, so an approved record whose earlier set holds such a record still closes with zero failures. State it in the closing comment, because the next reader sees an `unreviewed` record pointing at an approved job and cannot tell it from an edit someone forgot. **The tell that you are about to break this rule is the record itself: an `unreviewed` record whose `superseded_by` is already set reads like a half-finished edit, and the tidy-up — `approve_record.py --rejected` with the defect that sank the draft picture in the reason — is exactly the edit this rule forbids.** Those two fields together are not a gap; they are the library saying the image was displaced without ever being judged, so leave the record alone and say in the closing comment that it is deliberately unreviewed. The hold-back's account lives in the approved record's stem-prefixed row. **Do not edit the post and do not write a second record for the same job id** — `library_backfill.py` skips a job only on the exact `<stem>--<job_id>` filename, and a duplicate record splits the slot's history.

**Flip `superseded_by` one line at a time, never as a multi-line block.** Every back-filled record in a slot shares the same frontmatter tail — `superseded_by: null`, `posts: ["…"]`, `post_status: null`, `verdict: …`, `source: "backfill"` — so a find-and-replace whose `old_string` spans from `superseded_by:` through `verdict:` matches that whole run and replaces it with the one line you meant to change, silently deleting `posts`, `post_status` and `verdict` from the file. Nothing errors: the record still parses as YAML and a reader sees a record with no post and no verdict. Match the single line (`superseded_by: null` → `superseded_by: "<approved job id>"`) and re-read the frontmatter afterwards, asserting `posts`, `post_status`, `verdict`, `source` and `superseded_by` are all still present with the values you expect. When several earlier records need the flip, do them one file at a time and read each one back; a batch edit through one shared block is the shape that produces three damaged records and one correct one.

**A back-filled record that a close set to `rejected` by mistake is restored, not explained.** If the record's image never reached a card because your own self-check held it back, `rejected` in its frontmatter puts a decision in his name and deletes the library's only statement that nobody judged it. The repair is three edits in the reverse direction — `verdict: "unreviewed"`, the `Back-filled from jobs.db; not reviewed yet.` line back under the empty Verdicts table, and its row removed — while `superseded_by` stays pointing at the approved job. Do it in the same pass that finds it, and name the repaired files in the closing comment, because the post's own issue will never show the edit. The tell when auditing a close: a back-filled record with `verdict: "rejected"` whose reason row says anything about a self-check rather than quoting a decision he gave.

**`superseded_by` is set at approval time, not at rejection time.** A rejected back-filled record keeps `superseded_by: null` while the re-render is still in flight, because the field names the job that *replaced* this image and no replacement has been accepted yet. When the re-render is approved, set `superseded_by` to the approved job id in every earlier record of the slot, the back-filled one included. Pointing it at a render that was never approved makes the slot's history read as if the work were finished.

**A rejection does not set `superseded_by` — and neither does a render that is still in flight.** The temptation is to point a rejected record at the render that is now queued to replace it, so the history looks tidier. Do not: the field names an image that was *accepted*, and a render sitting in the queue has not been accepted by anyone. Leave it `null` until Wojtek approves, then set it in the same pass that writes the approved record.

## Rejected renders

Write the record for a rejected render too, with `asset: null`, `asset_location: "max-only"`, `asset_present: false`, and the rejection reason in the table. The render may be deleted from staging; the record is what preserves why that prompt did not work.

**A close that finds no records for a slot's held-back attempts reconstructs them in the same pass, and takes their issue column from the campaign issue that decided the hold-back.** The render rounds for a backlog post often run on a campaign issue rather than on the post's own card, so a slot can reach its approval with three or four attempts and not one record — the slot's history then reads as a single clean render. Resolve each attempt from the renderer (`jobs.db`, by the stem's 8-hex token when a note only names a file), and find the round that justified the hold-back by grepping the campaign issue's comments for the post number: those comments carry the crop and the defect in the words of the run that saw the pixels, which is what the attempt's `## Why` is written from. Its row's issue column names that campaign issue, never the approving card, because the approving card never saw the attempt. The commands to fetch a comment set and filter it by post number are in `references/paperclip-api.md`.

**A studio record for a render that never reached the vault carries no image embed.** A record with `asset: null` has nothing in the vault to point at, so it gets no `![[…]]` line under its heading — and in particular it must not carry the embed of the *older* image the render was meant to replace, because that embeds a different picture inside a record that documents this one: whoever opens the record to see the render finds the rejected original and reads it as the attempt. A back-filled record is the opposite case and keeps its embed, because its PNG is still in the vault and the post still points at it. The library's own convention is the check: `grep -l '^asset: null' 3-resources/image-library/<YYYY-MM>/*.md` and look under each heading — none of them carries an embed.

**A candidate record written at card time is `verdict: "unreviewed"` with an empty Verdicts table, and promoting it at approval adds the embed as well as the frontmatter.** Writing the record for a render when it goes on a card — rather than waiting for the verdict — is what stops `library_backfill.py` writing a second `verdict: unreviewed` record for the same job id, since it skips a job only on the exact `<stem>--<job_id>` filename. Write it then with `asset: null`, `asset_location: "max-only"`, `asset_present: false`, `superseded_by: null`, no embed and the table left as header and separator. **At approval three things change, not two:** the verdict and asset fields, the Verdicts rows, and a new `![[<vault asset>]]` line under the heading — a record promoted from candidate to approved that keeps its empty embed looks unreviewed to anyone opening it, and the asset exists so there is nothing left to explain the absence. The same pass rewrites its `## Why` from attempt-language into the render that ships. **`verify-slot.py` does not assert that `![[…]]` line, so a promotion can report every check green while the record still has no picture in it — check it by hand in the same pass.** Its checks cover the filename, the heading, the prompt block, the chain, the asset path, the post embed and the Why provenance; the record's own embed is not one of them. The cheap proof is the frontmatter's own `asset:` value appearing twice in the file: `grep -c '<asset path>' <record>` answering `1` means only the frontmatter carries it and the embed line is missing. Do not read a green `verify-slot` run as the whole closeout — it verifies what it checks and says nothing about the rest. **A candidate's `## Why` also fails the checker twice until its provenance is written in, because the record was drafted before any post quote existed**: it needs `From [[<post stem>]], section "<the heading above the embed>":` and exactly one `>` blockquote copied from that section by line position. Add both; never relax the check. **A quote taken out of the post by line position arrives without its `>` marker**, because the post line it came from never carries one, so a builder that splices the line in raw writes prose where the blockquote belongs and the run ends on `Why quotes at least one passage`. Prepend `> ` in the builder and assert the marker on every record it writes before moving on, rather than re-running the checker per file.

## Multi-round slots

A slot normally takes more than one round, and every render that reached a card gets its own record — rejected ones included. Write the records so the slot's history reads correctly from either of them. **Run `verify-slot.py` (the mechanical closeout check above) with the new record as `--record`, the shipped job as `--job`, and every earlier record of the slot in `--earlier`, and quote its counts, before the card issue is marked done — a green run is the gate, not a nicety. In this round that gate caught four defects on a record written in one pass (a date prefix taken from the brief instead of the renderer's `created_at`, a prompt block re-serialised instead of copied so it failed byte-for-byte, a `## Why` quote inherited from the round-1 record that sat under a different heading, and a prefix that named the slot rather than the render): all four were fixable, and all four would have shipped as defects without the check.**

- **The approved record carries the history of the slot.** Its Verdicts table has one row per round: the round-1 `rejected` row, with the reason prefixed by the rejected render's stem so the row names the image it is about, then the round-2 `approved` row.
  - **A round can hold two verdicts, and the attempt's row carries the same round number as the approval that followed it.** A silent re-render that was held back at the self-check is an attempt inside a round, not a card round of its own, so the approved record's table carries a row for it next to that round's approved row — both numbered for the same round, and told apart by the stem prefix in the reason column. The attempt's own record exists separately and keeps its own single `rejected` row; the approved record's table is the slot's history, so it names every render of the slot. **A slot with two held-back attempts has two attempt rows**, one per attempt, each with its own stem prefix and its own issue — a slot that spent three renders says so in three rows, not two.
  - **Two attempts of one slot can BOTH reach the card, he can approve both, and one still does not ship — that is not a hold-back and must not be recorded as one.** Two renders of the same beat go on one card when the composition is in question so he can pick; the brief states which one ships if both are approved (the one that meets the rule the rejection was about — a figure count, say), and his approving the other does not move it. So the non-shipping attempt is a render he **saw and approved**, and its row must not say `held back at the self-check` (false — it was shown to him) and must not state a rejection in his voice (false — he approved it). Write what happened instead: `approved on the card as well, but the other render ships because <the rule>, so this is the attempt that did not`. Its record still carries `verdict: "rejected"` with `asset: null` and no embed, because the frontmatter records the image's **state** — it ships nothing — while the row records **his verdict**; the two are different fields and the sentence is what stops them contradicting. The approved record's table names it too, same round number, stem-prefixed, directly above the approved row, and it joins the same `superseded_by` chain.
  - **A second ENGINE approved for the same slot is not that case: it keeps `verdict: "approved"`, its vault asset, and no post embed.** When one card pairs an ideogram and a flux render of a slot and he approves both, the ideogram ships in the post and the other engine's render stays in the vault as the comparison copy — `asset: "tech_blog/assets/<date>/<item id>.png"`, `asset_location: "vault"`, `asset_present: true`, `verdict: "approved"`, `superseded_by: null`, and a row whose reason is the record's own note, e.g. `Approved on review as the flux comparison copy; the ideogram ships in the post.` Marking that render `rejected` because it embeds nothing writes a verdict he did not give: the `verdict: "rejected"` shape above governs two renders of the SAME beat where he picked one, not an engine pairing he approved side by side. The record still carries its own `![[<vault asset>]]` line under the heading, since the asset exists and a record with an empty embed reads as unreviewed.

**A brief's "no vault copy until he says what it replaces" is about the post's embed, not about the vault, and reading it as a ban on the copy leaves an approved picture owned by no file.** The comparison copy is the library's only surviving record of a render he accepted, so it goes into `tech_blog/assets/<date>/<item id>.png` under the item id with `asset_location: "vault"`, `asset_present: true` and its own `![[…]]` line; what waits for his sentence is the *post's* embed, which stays on the other engine's asset. A companion recorded `asset: null, asset_location: "max-only"` also fails the approval-shaped assertions in `verify-slot.py` (`asset_location is vault`, `asset_present is true`, `asset names a file`), so a close that wrote it that way reports three failures on a render that was approved, and the repair is the vault copy plus the three frontmatter values — not a note explaining the absence.
  - **A brief's bookkeeping block can contradict that shape, and the library rule wins — say so in the closing comment.** A brief is written before any verdict exists, so it sometimes instructs that a render shown but not shipped is recorded `rejected` and "never approved". When the card comes back with that render approved side by side, follow the second-engine shape above and state the departure in one line: name the convention you followed and why (a rejected row writes a verdict he did not give). The brief is a prediction of the verdicts; the interaction result is the verdict.
  - **An attempt's issue column names the card where the hold-back happened, which is not always the card the approval lands on.** An attempt rendered and held back while the previous round's card was still open belongs to that earlier card, and its row keeps that earlier card's identifier — the attempt was never shown to Wojtek, so the round it was made in and the round it was judged in can be different cards. Read the attempt's own card's comments to find where the hold-back was decided, and put that identifier in the attempt's row and in the attempt's own record; putting the approving card's identifier there claims the attempt was judged on a card that never saw it.
  - **Prefix the row with something that names exactly one render, and the stem alone is enough when it carries the token.** A back-filled record's stem carries no 8-hex token, because the PNG in the vault is the label alone, so on a slot whose later attempts share the same label prefix the stem alone is ambiguous between the slot's own attempts — there, prefix with the full `<stem>--<job id>`: `header-session-normalizer--cpgtPVyzWTw: the reason as he gave it`. **When the stem already ends in the fetched 8-hex token (`h2-11-dryrun-bug-r1-flux-ec0598ae`), prefix with the stem and leave the job id out.** The token names one file, and the job id adds a second record that mentions the attempt's job: the approved record is not one of the attempt's own `--earlier` records, so the attempt's `verify-slot.py` run then fails `job id appears in exactly this record plus its earlier records` on a healthy close. The same rule as the cross-reference one above — a job id belongs only in the record that documents that render.
- **Every earlier record of the slot points at the same approved job id.** When a slot takes three rounds, that is three earlier records — the back-filled one, the rejected render, and the silent attempt that never reached a card — and all of them get `superseded_by` set to the one job Wojtek approved. The chain is a pointer to the accepted image, not a link to the next render in line: a rejected render's `superseded_by` names the render that **replaced** it, and when that replacement is itself later replaced, the pointer moves again. So a render that was superseded by a *rejected* render still ends up pointing at the approved job, not at the render that briefly followed it. Write it in one pass over every record of the slot, or the slot's history points at a dead end.
  - **The chain's job id is the one the shipped render was submitted under, and a hold-back can change it from the id the brief names.** A brief's bookkeeping block names a job id for the `superseded_by` chain, written when that render was the one expected to ship. If the self-check holds that render back, the named id becomes a held-back attempt and the chain has to point at the replacement's job id instead — and the held-back render needs its own record in the chain like any other earlier record. Take the id from the render that actually shipped, not from the brief, and check every earlier record of the slot against that one id in the same pass.
- **The rejected record keeps its own single `rejected` row**, with `asset: null`, `asset_location: "max-only"`, `asset_present: false`, and `superseded_by` set to the job id of the render that replaced it. This applies to studio renders that never reached the vault; a back-filled rejected record keeps its `asset`, `asset_location` and `asset_present` as they are while its PNG is still in the vault.
- **The approved record keeps `superseded_by: null`** — nothing replaced it.
