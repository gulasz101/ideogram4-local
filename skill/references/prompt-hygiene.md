# Ideogram 4 prompt hygiene

Session: 2026-07-02 safety-filter investigation.

## Finding

The Ideogram 4 local GGUF grey box ("Image blocked by safety filter") is primarily a prompt-vocabulary and JSON-structure filter baked into the model weights, not a pixel-level classifier. Community experiments on r/StableDiffusion showed that plain text or non-canonical JSON drifts off-distribution, and naming flagged garments/anatomy/situations flips the safety attractor even for harmless scenes.

## Fix hierarchy

1. **Prompt hygiene first.** Rewrite the prompt to use sparse canonical JSON and describe situation/location/mood rather than naming items. Keep only `high_level_description`, `style_description`, `background`, and 1-3 `elements`. Drop `canvas` and `layout` fields; dense structured prompts can drift off-distribution.
2. **Encoder swap second.** Set `IDEOGRAM4_LLM_MODEL=aggressive` (HauhauCS) or `generation.llm_model: "aggressive"`. In our 2026-07-06 A/B tests, only the aggressive encoder rendered a clean image, and only with a sparse prompt.
3. **Sampler workarounds third.** If a clean prompt + aggressive encoder still greys out, enable `two_pass` (neutral-prompt first pass + img2img second pass) or the cheaper `single_pass` CFG schedule.

## Canonical JSON shape (schema-compliant)

```json
{
  "high_level_description": "one-line situation / persona",
  "style_description": {
    "aesthetics": "...",
    "lighting": "...",
    "medium": "...",
    "art_style": "...",
    "color_palette": ["#..."]
  },
  "compositional_deconstruction": {
    "background": "...",
    "elements": [
      {"type": "obj", "bbox": [y1, x1, y2, x2], "desc": "situation-based description, no clothing/anatomy nouns"}
    ]
  }
}
```

The exact schema is documented in `references/ideogram4-oss-schema.md`. The key rules from the official `ideogram-oss/ideogram4` code:

- Only three top-level keys in order: `high_level_description`, `style_description`, `compositional_deconstruction`.
- `style_description` must contain exactly one of `photo` (for photos) or `art_style` (for illustrations/renders/design), plus optional `aesthetics`, `lighting`, `medium`, `color_palette`.
- `compositional_deconstruction` must contain exactly `background` and `elements`.
- `canvas` and `layout` are **not** in the schema and should be removed.
- Use bboxes for important, individually placeable elements; omit them for dense unplaceable groups like crowds or starry skies.

The older dense shape with `canvas`/`layout`/many elements was a community experiment, but the official verifier rejects those keys.

## A flux comparison must carry the ideogram's linework, not just its composition

When a card pairs an ideogram4 render with a flux2-klein render of the same composition, Wojtek judges the pair as one picture in two finishes, and the composition can be identical and still be wrong. Two verdicts in a row settle it: a clean digital flux beside a grainy ideogram was rejected with no defect named in any of the three frames, and the round that answered that with a grain-heavy prompt came back *too flat and too polished* — the ideogram **linework** was the style he wanted, not the grain.

The mechanism is that an instruction to be uniform is an instruction to be smooth. "An even layer of fine film grain over the whole picture, the walls, the floor and the empty air alike" tells the model that every part of the frame is the same material, and a frame with no material difference renders as a clean digital image wearing noise. So the opener is the **drawn line**, and the grain is a light finish carried on top of it:

> Drawn as a hand-inked comic cel: tapered inked contours with a slight hand wobble, shadows built from visible hatching and cross-hatching instead of airbrush, individual strokes through the hair and the cloth, flat cel colour laid slightly off-register so paper shows at each colour edge, halftone dots in the half-shadows, no glow, no blur, no vector finish.

`references/hold-back-or-ship.md` carries the same clause and the case behind it. It costs about fifty words, which puts a 300-word flux prompt at 320–360; the encoder holds it, but the negative tail is the first thing at risk, so trim scene description rather than the tail and read the first render for a pasted panel before trusting it. **Approved flux prompts have run to 374 words, and about 400 is where the tail starts coming back cut** — a rewrite that overshoots is not a reason to wait or to delete the clause: there is no cancel, so send the trimmed version as a second job behind it, check both against the same bar, and keep whichever passes. **Check the twin's length with `wc -w` before the submit, and write it as its own compact prose — never by pasting the element descriptions in sequence.** A twin assembled from the JSON's `desc` strings inherits every clause twice (the room once in the background and again as an element) and comes out at 600-plus words, where the negative tail is the first thing the encoder drops; the version that fits is hand-written at 400–430, keeping the ink clause, the palette line, the room in one sentence, the beat, the figure, and the tail. Trim the scene description to make the number, not the clause. The long one is the one that loses its tail, so the trimmed prompt is usually the frame that ships, and the two jobs cost one fetch each rather than a lost round.

**And the hand still beats the clause.** A prop held up above shoulder height in flux came back as a closed fist with the little finger merged away on five successive attempts, and that slot shipped ideogram-only rather than with a broken comparison beside it. Carry the same pose rules in flux as in ideogram (`references/figure-and-prop-prompts.md`) and settle the hands on a crop either way.

## An audit's suggested replacement can carry the defect it is meant to fix

A pixel audit's `replacement` column names the scene a fixed prompt should ask for, and it is written by a reader looking at the picture, not at the prompt rules — so it can hand back the same defect family in a new costume. One post's column asked for two monitors showing a stopwatch and a lightning bolt (screens holding pictures of other things: the flat-UI family), a box holding up a blank red warning triangle (a literal mark), and a dial with its needle in the red zone (a face that invites invented numerals — the rejected render had a name stamped across it).

Translate the prop, keep the beat: a screen becomes the thing it was reporting on (a ringing alarm bell beside a healthy boiler), a literal mark becomes the state it stands for (a snapped belt against a running one), and a dial becomes the mechanism at its limit (a coil spring crushed flat between two plates). Say in the issue comment which suggestions you replaced and why, because the audit's author reads the render against their own table.

## The linter reads your prohibitions, so a negative clause cannot name the banned thing

`lint` scans for the term, not for the intent wrapped around it. A prohibition that names a flagged noun is still the term appearing in the prompt, and it counts: `no other human figure` trips the `human_shape` flag, while the same prohibition phrased around the count — `one person only in the picture, no second person, no crowd` — does not. The picture can be entirely safe and the prompt still be rejected over a word used to forbid something, and a shape the model never drew has already cost you a lint cycle.

So: **phrase a ban in terms of what the picture should contain, not in terms of the thing to keep out.** "one person only in the picture, no second person, no crowd" forbids the duplicate without naming a body part; "no other human figure" spends the same meaning and buys a risk score. The standard overlay clause in this file already has this shape, which is why it never trips anything — it names *shapes* (poster, banner, placard, chart) and never a body part. Re-lint after every reword: the score is the check, not the intent.

**The flag fires on plain description too, not only on bans.** `with his whole body facing it` trips `human_shape` in an element `desc` that forbids nothing at all, while `facing the wall` scores 0. The linter cannot tell a description from a prohibition, so the same rule covers prose about the figure: describe his stance by what he faces and what he does — `he stands in front of the wall, one hand raised toward it` — and keep the mass words (`whole body`, `full body`, `limbs`, `anatomy`) out of the prompt entirely. **`full body` fires as readily as `whole body`, and a sentence written to prove the figure is ALONE still scores**: `he is the only figure in the picture and the only full body anywhere in the frame` trips `human_shape`, while `he is the only figure in the picture; the rest of the floor is bare flags with nobody on it` says the same thing for nothing. So the rule covers prose about isolation and not only prose about anatomy. The rewrite is the cheap fix, because the flagged word is the term appearing whatever the sentence meant by it. **But do not read that as "no body words at all": the flag is per word, not per family, and the geometry words a coherent figure needs score 0.** A prompt that states head-to-body ratio, a narrowing waist, level hip points, square shoulders, a pelvis on the seat, level knees and vertical shins lints at risk 0, so the body can be specified in its own vocabulary. The word that does fire is `thigh`: `both thighs run forward at knee height` scores +2 per occurrence (4 for the plural and the singular in one prompt), and `both legs run forward below the pelvis at knee height` scores 0 with the same geometry. Same for the arm: `his left hand lies on his left thigh` becomes `on his left leg just above the knee`. So when a pose has to be pinned down, lint the draft once, read the flagged term off the output, and swap that one word for its plain synonym rather than deleting the sentence the render depends on.

**The flagged noun need not belong to the body family.** A ban clause written for overlays still trips whatever flag an ordinary word in it happens to match: `no paper sheet` scores on the garment flag for *sheet*, while the same ban as `no paper page`, or dropped, costs nothing. **A verb phrase fires it too:** `the key wrapped in a folded cloth` scores on the garment flag for *wrapped in*, while `the key held inside a folded cloth` scores 0 — so when a legitimate prop is enclosed in fabric, describe what holds it rather than the wrapping action, and re-lint rather than assuming the flag came from a noun. Any ban list is prose and passes through the same scanner, so after a non-zero score read the flagged term and not only the score — the word to replace is usually a plain noun sitting in the harmless half of the clause.

**A plain scene word can trip the violence flag on a machine.** `the machine is dead and quiet, no light on it anywhere` scored +2 on `violence` for *dead*, inside an element `desc` that describes nothing violent at all, and `the machine sits quiet and dark, no light on it anywhere` scores 0. The state is what the picture needs and the word is what the scanner reads, so describe the state — dark, unlit, silent, still — and keep the diagnosis out of the prompt. **The flag does not care whether the word is a diagnosis or a measurement:** `both cut pipe ends are dead flat at the break` costs the same +2 for *dead* on a joint that is not alive in any sense, while `sawn flush` scores 0 — a word that reads as emphasis to a person still reads as the term to the scanner, so lint the draft and swap the one word rather than dropping the measurement the render depends on. Read the flagged term off the lint output every time: the score says a word is wrong, only the term says which one. **And a blade in a still life is that flag on an object:** a plain cook's knife lying beside a cut onion — no violence in the picture at all — scored on `violence` for *knife*, and the fix is to replace the prop rather than soften the word, because the object was never carrying the beat. A shallow bowl of the peel curls beside the cut onion says the same thing at risk 0. Lint the prompt before deciding which props the scene needs; a prop that trips a flag and earns nothing in the frame is deleted, not reworded.

## The negative clause for things the prompt did not ask for

The model fills a gap it is given, including gaps the prompt did not intend. A bare region of the frame — a flat wall, an unoccupied third, an empty band along an edge — is an invitation to paste something there: a logo, a poster, a promo card, a pseudo-chart. The defence is twofold and both halves are needed.

**Fill the gap with described content.** Give the region a prop the prompt can describe concretely and the model can draw: a shelf of closed plain ledgers, a low bench with loose coins, a crate stack, a hanging tool board. A region with described content has no room for an invention.

**The most dangerous gap is the one behind a figure.** A paste in an empty corner is read as an overlay; the same paste where it touches the character's back or shoulder is read as something growing out of his body, which fails the character rather than the background and gets a harsher verdict. So describe the space behind and beside the figure in its own words — `the bare concrete floor behind him, nothing standing on it` — move any prop that was sitting there clear of him and say so in the prose, and drop the `color_palette` array, because the shape's saturated hue usually came from that array rather than from the scene. A repair that redraws the region but keeps the palette gets the shape back in a new outline.

**Name the shapes you do not want.** Put one clause in `high_level_description` listing the specific overlay shapes that have bitten you, so the model has a target for the negative:

```
no poster, no banner, no placard, no overlay card, no advertisement,
no charts, no graphs, no logos, no badges, no emblems
and no readable lettering anywhere in the image
```

Naming the shape is what works; "no text" alone does not stop a chart-shaped grid of tiles, and the shape is what a reader sees. Keep the clause in `high_level_description` rather than in an element `desc`, because a negative inside one element reads as describing that element.

**A ban list must not name the shapes your own props are made of.** The clause is read as a rule about the whole frame, so "no circles, no squares" takes the round padlock and the round brass lamp out of a picture that asked for them. The model obeys the ban and drops a prop the scene needs, which is a worse defect than the one the ban was written for. **Read the ban list back against the elements: every shape named in the ban must be a shape the picture should not contain anywhere, including on a prop you described.** When the two collide, reword the ban around the artifact rather than the geometry — ban the pasted overlay, the graphic, the logo, the flat shape, not the primitive it happens to be made of. A ban list of overlay nouns (poster, banner, placard, card, advertisement, chart, graph, logo, badge, emblem) is safe against any prop, because a prop that is not an overlay is not one of those words. **And a long ban list is its own risk**: the more shapes it names, the more of them the model has to avoid, and a shape it cannot avoid it will draw anyway in a variant you did not ban — so a list of four shapes invites a fifth, and a list of geometry can empty the scene. Two or three overlay nouns beat ten primitives.

**But a negative clause does not fix lettering the model invented on its own.** The clause stops a shape the prompt put a gap for; it does not undo an invention the composition invited. A prop standing alone on empty ground is a product in an advert, and the model gives an advert a name — the word appears in the render even though the prompt asked for no lettering anywhere, and adding "no readable lettering" to a prompt that already said it changes nothing. The fix is to change the **composition**: give the prop neighbours and a setting so it reads as part of a scene rather than as an item on a backdrop. Say the negative too, but treat it as the belt to the composition's braces — the braces are what carried the fix. `references/engine-pitfalls.md` #42 carries the case.

**And do not ask for a prop the model cannot spell or chart.** A `desc` that requests numerals, a data visualisation or a labelled panel gets faked: garbled digits, aligned tiles with no axes, an empty band under the grid. Replace the prop with a physical object instead of rewording the request for the same one — a glass porthole showing gears, a plain wooden panel with three carved discs, a row of closed ledgers. `references/engine-pitfalls.md` #36 and #37 carry the mechanism.

**Grep the rejected prompt for the words that order writing outright.** `labelled`, `marked`, `sign`, `plaque`, `log`, `readable` and `with text` are instructions to print words, and a negative clause does not undo one. A prompt asking for `small labelled collection trays` produced invented lettering on three shelf labels in the same render whose ban list already said no readable lettering anywhere, and the fix that worked was deleting the word and every surface it described. **A ban argues with the prop; deleting the word removes it.** Run the list over the prompt before the submit, and when a rejection names invented text, treat a hit as the cause rather than a wording to soften. **And a container is a surface with a label face whatever adjective precedes it**: `plain unlabelled jars and tins` still comes back with one jar wearing a sticker of dash-lines, because the noun is the instruction and the adjective is not something the model can act on. Replace the container with a shape that has no label face — closed wooden boxes, a coiled cable, a stack of ledgers — rather than adding a ban. `references/engine-pitfalls.md` #77 carries the case, and the check that catches it is a 4x crop of the shelf: three dashes on a small sticker read as `no lettering` in a full-frame pass.

**A repeated container is a whole row of label faces, so plainness has to be stated across the set rather than the prop.** When the containers are the subject — a hoard of drums, a belt of canisters, a shelf of identical tins — the replace-the-container fix above is not available, and the row is what invites the mark: a render of a belt of yellow drums came back with five of them wearing small embossed loops filled with illegible squiggles, invisible in a full-frame pass and unmistakable in a 2x crop of the row. Write the plainness as a positive inventory in the same sentence that counts them — `every drum is completely plain and bare: no labels, no stamps, no embossed marks, no scuffs shaped like letters, nothing printed on any drum anywhere` — and settle it on a crop of the row rather than of one member, because the marks land on some of them only and read as dents or shading at frame scale.

**An inherited prompt is an old prompt, so run the audits on it before you reuse it.** A record back-filled from an earlier job, a round-1 prompt a brief quotes, or a re-render named in a handoff was written before these rules existed: it will carry a `color_palette` array and props described as `labelled`, and both triggers come back exactly as they did the first time. Copying such a prompt forward and editing the one thing the rejection named reproduces the other defects it was already carrying. So before a re-render from an inherited prompt: delete `color_palette` and rebuild the look from `aesthetics`, `lighting` and `medium`; strip every word from the grep list above and the surface it described; then fill every edge and corner with a described prop. The one part to keep is the composition the owner praised — the action, the position of the figure and the prop he acts on.

**A prompt recovered from the renderer's job database is the strongest case of the rule above, and "it lints clean" is not a clean bill.** When a job failed and its row still holds the prompt, that prompt was written months before these rules and can carry all of them at once: a `color_palette` array, literal marks (*green checkmarks arranged around the rack*, *badges with a small lock symbol*), logos and a monitor screen, and `arms crossed`. `ideogram4_local.py lint` reads **schema shape and safety vocabulary** — risk score, flagged terms, density — so it answers 0 on exactly such a prompt and says nothing about the acceptance bar. Run the three audits (palette, literal marks, text surfaces) over a recovered prompt like any other inherited one, and keep the recovered composition, the character and the engine while replacing the mark-family props with the state they stood for: four bays each carrying one small round green lamp replaces a column of tick badges, and a grin with two simple fists replaces arms crossed.

**An author's paste-ready prompt is an inherited prompt too.** When the post's writer hands you a JSON block to submit, it was written to a description of the picture, not to these rules, so it arrives carrying the same triggers: run the three audits before it reaches the renderer — `check-bboxes.py` for axis order (a writer who thinks in `[x1, y1, x2, y2]` transposes the cabinet door and the crate into full-width bands across the frame), the `color_palette` deletion, and a rewrite of any ban clause that names a shape. Then say in the issue comment which edits you made and why: he will read the render against the prompt he wrote, and a silently changed prompt turns a defect of his block into a defect of yours.

**A post's images written in one sitting share their prompt traits, so they share the defect family and differ only in where it lands.** A draft whose images were generated in one batch from one template carries the same array, the same `fills the entire frame edge to edge with no empty space` phrasing and the same absence of props in the corners — and the model answers all of them the same way: a pasted graphic in a corner on one image, a band along the bottom edge on the next, a labelled card strip on a third. So the audit runs over every prompt of the post, not only the one whose rejection you are answering: when a review card shows one image with the artifact, open every sibling prompt before writing the notes, because the same two causes will be in all of them and the card's per-item reasons are where he will point. On the re-render side the same fact cuts the other way — a sibling's **style block and character description** are what makes a new image belong to the set, never its element list, because that list is the thing carrying the defect.

**But the array is a trigger, not a certainty, so measure the strip instead of inferring it.** Renders carrying the same six-entry `color_palette` can come back with no strip at all, so the presence of the array never decides a verdict on its own: run `check-palette-strip.py` and read the block for *each* edge, because its headline names only the edge that fired first and the same blocks can be lying along the other one at 99% of the width. A note that calls the array itself the defect puts a false defect on a frozen card, and a sibling render carrying the same array may be the clean one he approves.

**When the picture does want text, the prompt gives the exact characters.** The standing rule from this owner: text is asked for as human-readable language and spelled out, never as a `label`, `title`, `caption` or `text` field the model fills itself — a request for lettering without the lettering in the prompt is a request for invented words. If the section needs no writing at all, ask for none and remove the surfaces that invite it.

**A speech balloon, sign or callout is the one prop whose whole job is a sentence, so it gets exact words or it does not go in the scene.** A blank balloon reads as an unfinished placeholder however well it is drawn, and a balloon tinted with a `color_palette` accent reads as a graphic pasted onto the wall — plain white with a clean ink outline is what reads as drawn. Letter it by putting the exact phrase inside that element's own `desc` and stating in `high_level_description` that this phrase is the only writing in the picture; when the section needs no words, drop the balloon and carry the beat on a prop that does not need lettering. `no random letters, no pseudo-text` cannot rescue a blank one, because it leaves the hole where the sentence should be. **And check the lettering on a crop**: a balloon's words are small relative to the frame, so a full-frame read reports `no lettering` and a single wrong character is invisible at that scale — read the balloon at 2x or more, character by character, before the render goes on a card.

**`check-bboxes.py` reads spatial words, so a correct box can be flagged by the sentence beside it.** Its rules fire on `the left`, `top edge`, `at the bottom`, `in the lower`, `full width` and similar, and a full-width shelf plank or a prop described as "hanging head down" will trip them while the box is exactly right. The fix is the wording, never the box: describe the position without the trigger phrase ("at the end of the plank that the picture cuts off" instead of "at the far left end", "hangs from its own nail with bare wall above it" instead of "head down at the bottom"). Rewriting the sentence keeps the layout the author gave you; moving the box to satisfy a keyword deletes it.

**And on a re-render of a slot that was already rejected for pseudo-text, the answer to "would you like a bubble?" is none.** The owner offering a bubble is permission, not a request: a bubble adds a spelling risk to a slot that has already cost him one rejection, while the beat usually reads without words once the props are physical. Draw it wordless, and say plainly in the issue comment that you took the wordless version and that the bubble is available if he wants a line in it — a picture with no lettering cannot fail the lettering gate.

## Editing a prompt: the prose and the element list must name the same props

A re-render edits one field at a time, usually the `elements` list. The `high_level_description` and the `background` are prose about the *old* composition, and the model reads all three fields as one instruction: a prop deleted from the elements but still named in the prose comes back — wherever the model decides to put it — and a prop moved out of its own element into the background prose can be drawn twice, once as furniture and once as loose goods. **So read the prompt top to bottom after every edit and make the three fields describe one scene** — same props, same count, same places. Check `high_level_description`, `background` and every `desc` against each other before the submit, not after.

**And there is no cancel.** `imagegen submit` prints a job id and nothing undoes it, so an inconsistency you notice after the submit costs the render or a re-render on a picture he has to judge. The read-back before the submit is the only cheap moment.

**When `lint` answers `density risk: yes` with a non-zero score, the fix is fewer elements, not a reword.** Fold the props that share a region into the `background` or into the room element, and keep the elements whose *position* decides the picture: the figure, the prop he acts on, and the thing that fills a region that would otherwise be bare. Folding four dressing props into the background commonly takes a seven-element prompt from risk 2 to risk 0 without losing a single described object, and it leaves the element list as the short list of things whose placement matters.

**Some `check-bboxes.py` flags are ordinary adjectives, not geometry — reword the `desc`, never narrow the box.** The audit exists to catch a transposed box and a slab where the `desc` names a region, and it does not know that a long object is legitimately long: `thin dark outlines` reads as NARROW, and `from the left edge … to the machine on the right` reads as LEFT and RIGHT on a conveyor whose box spans the frame by design. Clear it by taking the misleading word out (`crisp outlines`; `its near end at the frame edge and its far end running into the machine`) and keep the box — a track or a connector whose box stops short of its target is the defect the wide box was drawn to avoid. Only a box that contradicts a *position* the picture really has gets its coordinates changed. **The NARROW flag only fires on a box over about 400 px on both sides**, which is why the same adjective passes on one element and returns on the next: take the word out first and re-run the audit before you suspect the numbers.

**A fraction is a region word too, so `left two thirds` on a box that genuinely is 640 px wide is flagged as a full-width band.** The scanner reads the direction and measures the box; it cannot tell a fraction of the room from a region of the frame, and the message (`desc says LEFT but the box is 640px wide`) reads like a coordinate error when it is a wording one. Write the extent instead — `spanning most of the width of the room` — and keep the box, because a bench narrowed to a third no longer stands under the objects laid along it.

**The same flag fires on direction words that qualify the members of a set inside one element, not only on the element itself.** One wide element holding three heaps of card described `a tight bundle of cards on the left, a loose drift in the middle, and a stack standing in a tin on the right` answered LEFT *and* RIGHT against an 840 px box, and a trough spanning the frame answered RIGHT for `the near right end of the trough bare and dry`. Ordinal language costs nothing and reads the same to a person — `a tight bundle of cards tied with plain twine, a loose wide drift beside it, and a small stack standing in an open tin at the other end` — and `one end of the trough bare and dry` clears the same claim. The compass word is never the thing the picture needs; the ordering of the set is.

**The other common contradiction is a region word written from the scene in your head rather than from the box you typed.** A `desc` opening `in the lower right of the picture` over a box at `y 110-420, x 830-1000` is in the upper right, and `cropped by the bottom edge` over a box that ends at `y=620` describes a crop that is not there; the audit answers `desc says BOTTOM but the box starts at y=110`, which reads like a coordinate error and is a wording one. Read the region word off the box's own numbers before the submit — `y` first, so a small `y` is the top of the frame — and when the word is what is wrong, change the word. Move the coordinates only when the picture genuinely needs the prop at the other end.

**A prop described by its own extent is read as a region of the frame, so a flag's `bottom edge` trips the same rule.** A `desc` that fixed a hanging flag with `its top edge at his shoulder height and its bottom edge at his hip` over a box spanning `y 300-520` was flagged `desc says BOTTOM but the box starts at y=300` — the audit cannot tell a measurement of the prop from a claim about where in the picture the prop sits, and both words in that sentence are frame words to the scanner. Write the extent in the prop's own vocabulary (`its upper edge … its lower edge level with the top of the workbench below it`), or express the anchors as heights the scene already has, and keep the box. The tell is a flag on an element that is plainly in the right place: a hanging prop, a plank, a banner — anything whose described span starts at one edge and ends at another.

**A prop he holds belongs in the figure's own element, because a prop in its own element gets a second figure invented to stand beside him and hold it.** A prompt that describes the man's raised hand holding a phone, and then lists that phone as its own `element` with its own `bbox`, hands the model a prop whose described holder sits in a different element; the model resolves that by drawing another person. The render comes back with two identical copies of the character side by side, one holding each device — which reads as a mistake, and is one, but the cause is the element list and not the prose. **The fix is the fold: delete the prop's element and put its description into the sentence about the hand that holds it.** Then re-count: one figure plus the prop he acts on is two elements besides the background, and anything beyond that should be a thing standing on the ground rather than a thing in his hands. State `one person only` inside the element that describes him as well as in `high_level_description`, because the count is read where the body is drawn. More prohibitions do not clear it — the extra body comes from the structure, not from a missing ban. **This is also the one duplicate-figure case that earns a silent re-render rather than a card note**: the defect is a structural artifact with a mechanical fix you can state in one line, whereas an extra figure the model added for its own reasons is a note for the card. **The same structure resolves the other way just as often: the prop floats.** A `desc` that said the prop was "held between his thumb and forefinger", in an element with a box of its own, came back as a twig hanging in mid-air beside an empty hand — no second figure, just a prop with nothing holding it, which is the same lost beat in a quieter costume and not something a card can explain away. Write the grip into the figure's own sentence and make the two one shape — "his hand CLOSED AROUND the middle of it, arm and prop one connected shape" — and give the prop a described place to be (directly above the open bin it is about to go into) so a drift has a position to land on. **A third cause is the box itself: a lone figure's `bbox` spanning nearly half the frame width is room for two people, and the engine puts two in, whatever the count sentence says.** Narrow his box to one column the width of one person and say what occupies the rest of the floor; `references/hold-back-or-ship.md` carries the case. **And narrowing his column moves him into other boxes, which the audit will not tell you about.** `check-bboxes.py` compares a `desc` with its own box; it never compares elements with each other, so a figure re-boxed into a 220 px left column can end up sitting on top of a prop's box and the audit still answers *no bbox contradicts its own desc*. After any box moves, walk the rest of the grid by hand — read the figure's `y`/`x` span against every other element on the same rows — and move the prop rather than widening the figure, because the narrow column is the thing keeping the duplicate out. **A narrow box does not stop a twin that stands where a person could stand.** With the man written at one end of a workbench, the engine mirrored him at the other end — two identical men, each with his own shadow, and the singleton clause said twice. The repair is the one that fills a bare region: put a described non-figure object in the counterpart position (a low stool against the brick, a stack of crates, a sack leaning on the wall) and say that position is the only thing there, because a position shaped for a person is filled with one however the count is worded.

**A fold must carry the prop's description with it.** Moving a prop into the `background` prose and leaving its old element in place is the double-draw above; deleting the element and not describing the prop in the background leaves a vacancy, which is exactly the gap the overlay clause exists for. Move the words, then delete the element.

## Tooling

### Prompt files in the shared backlog directory carry the post number

`~/image-studio/backlog/prompts/` and `~/image-studio/staging/<date>/` are shared by every post in the backlog, and item ids repeat across them — `header`, `header-r2`, `mobile-test-r2` all exist for several posts. So:

- Name the prompt file `<post number>-<item id>.json` (`032-header-r2.json`) while the render name stays the bare item id (`--name header-r2`), so the card's item row, the fetched PNG stem and the record stem still resolve to the same string.
- A write refused because the file *exists but this task has not read it* is a collision with another post's prompt, not your own earlier draft from a run that died: list the directory before writing instead of reading a prompt file you do not own.
- **The identical refusal in a run-scratch directory is your own earlier throwaway, and the fix is a new name rather than a read.** Helper scripts in the profile's scratch directory are reused verbatim from run to run, so a generic name (`runner-comment.py`, `create-card.py`) is already occupied by a previous run's script written for a different post. The error text is the same as the shared-directory one and the two need opposite responses: in `backlog/prompts/` the existing file is another post's work, so you read it before writing; in scratch it is yours and disposable, so reading it back to satisfy the guard costs a call and leaves two near-identical helpers. Suffix the name with what this run serves (`runner-comment-<post number>.py`) and write again.
- The same collision bites on the render side, because `staging/<date>/` can already hold a `<slug>-<8 hex>.png` from a different post. Always carry the exact path `imagegen fetch` prints; never glob for the slug.
- **Batching renders: the last job sets the wait.** A queued job's `eta_minutes` already counts the jobs ahead of it, so schedule the monitor from the LAST job's ETA plus five and re-read the clock then — a deeper queue puts a late submit hours out even when its own render is 21 minutes, and arming on the first job's ETA wakes you to nothing collected. **On a deep queue the ETA is a floor, not a promise**: other runs submit behind you and the queue grows, so a submit quoted at fourteen jobs ahead can finish well over an hour later than the number said. Expect the first wake to be a reschedule rather than a collect, treat that as the monitor working instead of a fault, and on that wake re-read both jobs before touching anything — when neither is `done` there is nothing to fetch, so PATCH the monitor again from the fresh ETA plus five, keep the issue `in_progress`, and end the run. **When the fresh number is many hours out, arm a shorter checkpoint instead of trusting it** — a couple of hours, then reassess — because an early wake costs one run, while a render that finishes with no monitor waits for ever, and a card held on a quote that long is a card that could have shipped. A wake that reschedules an already-scheduled monitor is one line of work; a wake that fetches a half-written PNG or submits a duplicate render is a wasted round. **The monitor's `notes` field is a hard 500-character limit, and a longer note 400s the whole PATCH — including the comment riding in the same request.** Keep the note to one or two imperative sentences (what to fetch, which crop to take, what to do with a failure) and put the reasoning in the comment body, which has room for it. When a PATCH answers `Validation error … path: ["executionPolicy","monitor","notes"]`, nothing was written: re-send with a shorter note and re-read `monitorNextCheckAt` afterwards, because a failed request leaves the old schedule silently in place.

### The linter and the rewriter

**Where a new prompt rule goes.** `references/backlog-review.md`, `SKILL.md` and `references/engine-pitfalls.md` have all reached the 100,000-character file cap, so `skill_manage` refuses a patch to any of them and rolls the whole batch back — a one-bullet append to `SKILL.md` is already enough to answer `content is 100,488 characters (limit: 100,000)`. Do not spend a run trying to squeeze a rule into them. Until they are split, new prompt-shape and file-naming rules land here; anything about verdicts, hand-offs and rebuilt rounds goes to `references/re-render-defect-persistence.md`; batch-scale work — auditing a whole backlog's prompts, repairing slots, engine pairs, sizing a render batch against the shared queue — goes to `references/prompt-repair-audit.md`; and the series' standing look — the style block, the one named palette, the cast, real national flags, the props that invite lettering, how the hands are described, and the companion-FLUX request — lives in `references/series-style.md`, which every post prompt is built from. **Measuring what is still broken across the backlog** — walking the drafts rather than the asset folder, resolving embeds, telling a card's in-flight replacement from a defect, and handling a dead embed — is in `references/backlog-measurement.md`.

The repo ships `ideogram4_prompt_tools.py` and `ideogram4_local.py lint`/`rewrite` commands:

```bash
python3 ideogram4_local.py lint prompts/my-scene.json
python3 ideogram4_local.py rewrite prompts/my-scene.json -o prompts/my-scene-safe.json
```

The linter returns a risk score and flags explicit garment/anatomy/situation/violence terms plus **density risk** (`canvas`/`layout` or many elements). The rewriter applies whole-phrase reframes, masks remaining flagged words, and now drops `canvas`/`layout` fields. It preserves canonical JSON structure when present.

## The pre-submit lettering gate (Wojtek's standing instruction, 2026-10-27)

**Text in a picture must ALWAYS be readable for a human. A prompt that would have the model print something that is not a human word is rejected and rebuilt, not sent.** His words, post 031 round 1: *"text MUST be ALWAYS readable for humans, do not let those prompts with not human readable text to go through… you can also validate, if prompt already contains text which is not human word to be printed, just reject it! and autonomusly recreate it, always followup with Florian on context"*.

The gate is a read of the prompt file, run before `imagegen submit`, not a feeling about the picture:

1. List every element whose `desc` names lettering, print, a label, a badge, a sign, a caption, a wordmark, a chip, a panel readout or a number display.
2. For each one, either the **exact characters are quoted in the prompt**, or the prop is **removed** and its face described as a physical object.
3. If a prop survives with characters nobody wrote down, the prompt is refused — do not send it.

Remedies in order of preference: quote the characters when the post itself supplies them (a version number, a command, a status string), otherwise take the prop away. Two consequences that are easy to miss:

- **A removal leaves a hole, and a bare region is exactly where the model pastes a badge or a banner.** Fill every vacated region with a described diegetic prop — a pegboard of hand tools where a dashboard was, a rail of cable tails where a tariff chart was.
- **The negative clause names the shape you are banning, and a concrete instruction is what the model draws** (#62, #63). Phrase it around what the picture contains rather than around the object being forbidden, and re-lint after every reword.

Cost: one file edit before the submit, against 21 minutes and one round of his attention after it. The library agrees — `unreadable-text` is 8 rejected / 0 approved and `pasted-overlay` 9 rejected / 0 approved (run `scripts/verdict-class-rate.py` bare for the live counts).

**One card's approval does not lift the gate.** On the card that carried this instruction he approved a picture that still had two garbled caption pills on it, because its scene made sense. The gate stays for the next prompt: his rule is the rule, and an approval is evidence about one picture.

**The gate governs the prompts you write; it is not a forecast of his verdict on a picture that is already in a draft.** On one review card he approved two images carrying exactly the surfaces the gate forbids — a flat dark UI card pasted over the corner of the room, and a plain white caption across the bottom misspelling the section's own subject — both of them named on the card face as hard defects with the class rate quoted. He kept them because the scene still read. **That reading is retired: the owner has since said he does not want to review pictures that are already broken, so a draft image failing the gate is repaired and re-rendered instead of shown (the one exception is a slot that cannot be re-rendered at all, which goes up with its defect and class rate named on the card face), and the gate is now a filter on what reaches a card — `references/prompt-repair-audit.md` carries the gate and the method.** What survives from that card is the other half: the gate is never proof he will reject a picture, and the size and dominance of a defect in the frame is what decides a rejection from an approval. The gate is a filter on what you submit, and the class rate is a prior that decides whether a defect is worth *naming* — the size and dominance of the defect in the frame is what decided his two rejections from his two approvals on that same card.

## The pose rule: a held object above the shoulder buys an extra arm

**A closed fist holding an object above shoulder height is the single most reliable way to get a third arm, and no hand-count sentence in the prompt prevents it.** Post 034's header asked for "a man holding a large golden padlock up in one hand", stated nothing about the other arm, and came back with three: one raised with the padlock and two hanging at his sides. Wojtek named it one clause above the lettering and the red line — *"main character has like 3 hands, it is bullshit"* — so an anatomy duplication outranks every other defect on the frame.

What fixes it is the composition, not the count:

- **Drop the raised object.** Put the act at bench or chest height and give both hands a job on the same prop ("both flat palms pressed on the cage door's solid iron edge band, fingers spread, thumbs hooked round the edge"). A two-handed grip on one prop has no spare limb to invent.
- **Same prop is not enough: both hands go to the SAME HEIGHT, side by side.** A re-render that put the right palm on the door's top corner and the left palm "on the same band lower down" still came back with both arms leaving one shoulder, folded over each other, reading as three — the count sentence was in the prompt twice and lost to the pose. Two hands at two heights on one vertical band force one arm to cross in front of the other, and the model resolves the crossing by growing a second arm out of the chest. Send both hands to one horizontal line about a hand's width apart, turn his chest square to the prop so both shoulders are visible one on each side, say in the figure's own `desc` that the right arm begins at his right shoulder and the left at his left and neither crosses the other, and keep both hands away from the prop's top edge — a hand drawn at the top pulls one arm up and the overlap returns.
- **Keep the object, remove the gesture.** The padlock survived as scenery snapped shut through the hasp, never in his hand. A prop that must be seen does not have to be carried.
- **Put both hands at the same height on the prop.** Two hands sent to two *different* heights on one vertical surface is the second reliable way to buy an extra arm: the arms have to fold over each other to reach two levels, and the model resolves the overlap by growing a second arm out of one shoulder. On post 034 the r2 render asked for the right palm "at the top corner of the cage door" and the left "on the same band lower down", and both arms came back leaving his right side, one hand on the curved top bars and one on the side bars. The r2b render asked for both palms "on the vertical edge band at exactly the same height, side by side about a hand's width apart" and the count came back clean. Spreading two hands along one line reads as two arms; stacking them does not.
- **Then state the count anyway**, in the `high_level_description` and in the figure's own `desc`: "both of his arms are fully visible and clearly drawn as whole limbs from shoulder to hand ... exactly two arms and two hands, nothing in either hand, no third arm and no extra hand anywhere in the frame, and nothing raised above his shoulder." Also name the shoulders: "each arm begins at its own shoulder, one on each side of his chest, and neither arm crosses or passes in front of the other" — a count with no attachment point is a sentence the pose can still overrule.

**Count limbs on a crop before a figure goes on a card.** A whole-frame read reported one raised hand and missed the pair hanging at the sides; the defect was settled on a 3x `crop-probe.py` crop of the figure, where three arms are unmistakable. An extra arm costs a round and it is the cheapest thing on the frame to check. **And when the full-frame read and the crop read disagree about the number, the render is already failed** — one calling it three arms while the other calls it two arms leaving the same shoulder, distorted and overlapping, is not a close call to settle in the render's favour. A picture whose arm count cannot be settled in one look is the defect he names first, whatever the true number turns out to be, so hold it back rather than putting a disputed count on a frozen card.

**Count and contact settle opposite ways, and which one a disagreement is about decides the render.** A disputed *number* fails the picture, as above. A disputed *grip* does not: a full-frame pass reported a raised hand "hovering just behind or underneath the knob without the fingers securely grasping it" while a 3x crop written to disk showed the fingers closed round the shaft directly below it, so that render shipped on the crop's reading. The reason is scale — a hand is small enough in the frame that a whole-frame read answers from the pose it expects rather than from the pixels — so ask the crop the narrow question (are the fingers closed on the prop, or open beside it) and let the crop decide. Getting this backwards in either direction is expensive: failing a good render over a contact claim spends 21 minutes, and accepting a hover as a grip puts a picture on a card whose action does not read.

**A pinch is the same failure squeezed into the hand, and the fix is a closed fist.** A `desc` that has the figure pinch a small prop between thumb and forefinger comes back with a fused multi-thumbed mass — two thumbs, extra knuckles, a shape that cannot be read as a hand — because the model has to invent where five digits wrap a cylinder whose far side it cannot see. State the grip rather than the fingertips: *a closed fist, the thumb laid over the folded fingers, no separated fingers sticking out*. Then give the prop **plain flat ends** so it has nothing to resolve into: a short brass cylinder came back as a cartridge until *no flange, no ring, no cap, no bullet shape* was added, and a flanged peg is a second object for the hand to mangle around. Check the hand on a 3x crop before the render reaches a card — a whole-frame read called one of these "a hand pinching the peg" and the crop showed a fist with two thumbs.

**An enumerated set gets its count stated, and the shape that can stand in for a member is banned by name.** A board asked for four device-shaped tags on five hooks came back with three tags and **two** bare hooks: the fourth hook's own mounting plate carried a round cutout, which the model treated as that hook's tag, and its prongs were left empty. The prompt listed the set ("a phone, a tablet, a pair of earbuds and a small speaker") but never the arithmetic, and the count was the whole joke of the frame. State it as a count in `high_level_description` — *exactly five hooks, exactly four tags, the first hook is the only bare one* — and ban the substitute explicitly (*no hook carries a round hole or a circular cutout*), because a backplate with a hole reads as a tag at a glance. `wrong-count` is 2 rejected / 0 approved in the library, so a set that arrives short is a re-render, not a card note.

## A handover between two figures cannot be drawn in transit

**An object described as travelling across a gap comes back held at one end, and the end it picks is the wrong one.** A prompt that asks for a new pair of spectacles "passing from his open palm toward the robot's face", with its own element boxed across the whole gap, renders the man with both hands open and empty and the object already in the other figure's grip — so the picture shows the fault without the repair, which was the section's entire point. The model draws states, not motion: a mid-air object has no state to draw, so it resolves to the nearest one it can.

So the spanning `bbox` is necessary and not sufficient. Describe the **contact state at one end**, by the actor who should be doing the work — his thumb and forefinger on each temple of the new pair, pressing it onto the robot's face, the old broken pair lying on the floor beside them — and keep the box spanning from his fingers to the face. The transfer is then a fact about the picture rather than a hope about the motion.

The tell in the self-check is the **empty hand**: a figure whose `desc` said offering, passing or reaching, drawn with an open hand and nothing in it, is this defect. It is a re-render, not a card note, because the beat the picture exists for has gone.

## When a re-render still letters something, change the prop rather than the prompt

**Lettering is prop-driven, not wording-driven, so a third round of rewording is the wrong spend.** On post 034 both rejects were pictures asked to *explain a mechanism*, and the engine renders "explain" as lettered surfaces and colour-coded tiles: a round badge on a canister came back as a mangled "ri", an app block with a shape on its face came back as an icon with invented words, and a row of blocks plus a set of coloured lines came back as five flat panels reading nonsense. The remedy that works is removing the surface, not describing it more carefully — the blocks went entirely and a fan of real cables took their beat.

So the order after a lettering rejection is: list every surface in the prompt that is *built to carry a mark* (a badge, a face of a block, a screen, a card, a caption strip, a chart, a checklist, a book spine), then take away or replace each one with a prop whose face has no flat blank plane. If round 2 still letters anything, the next move is another prop change — not a reworded ban.

## The pre-prompt forbidden-memory gate (Wojtek's standing instruction, 2026-10-27)

**Before writing any new prompt, query Hindsight for what is forbidden. "Good" is defined by his verdicts, not by your judgement.** His words, on the GUL-244 round-1 card: *"colorful artifacts here and there, that is clear no! remember to not allow any colorful artifacts, always before generating new prompt look up memories on what is actually forbidden to understand what is definition of good"*.

So the order of work on a re-render is: `hindsight_recall` on the defect class the rejection named ("colourful artifacts", "swatch strip", "invented text", "pasted overlay") and read the remedies the bank already holds, then write the prompt, then lint, then the lettering gate, then submit. The recall is cheap and it is the difference between re-deriving a known fix and buying a render to discover it again: on this card it returned the palette-array trigger, the undescribed-corner mechanism (#75) and the corner-overlay-without-a-ban rule (#60) in one call.

**Colourful artifacts are never allowed, whatever the rest of the picture does.** The class has 0 approvals in the whole library and it does not shrink into an acceptable quirk: a small pasted block is the same defect as a full-width band. Two mechanical causes carry most of it, and both are fixed in the prompt file before the submit:

1. **A `color_palette` array** — its entries come back as an edge strip, a mid-frame band, or a cluster of flat blocks in the one corner the prompt left undescribed. Delete the array and rebuild the look from `aesthetics`, `lighting` and `art_style`, naming two or three hues in prose ("warm amber lamp light, cream paper, medium brown wood").
2. **A bare region** — every corner and both long edges get a described prop cropped by the frame edge (a ceiling beam with a hanging lamp along the top, floorboards along the bottom, a bench or desk in a near corner, a shelf in a far one). A rule that forbids the shape is not the lever; content in the region is.

## A shape analogy in the prompt is a concrete instruction, not a simile

Naming a thing to describe the *shape* of another thing makes the model draw the named thing. On post 031's `header` re-render the shell was written as "a thin brushed aluminium shell shaped like a flat computer screen frame, open on its back" — the intent was a thin rectangle, and the render came back as a two-part hinged housing with a lid carrying a filled dark panel: a laptop with a blank screen, the exact object the composition's own reject list forbade.

The rule is the same one that governs negative clauses (#62): **the model reads nouns and draws them.** A shape reference is a noun. Replace it with geometry the model can build and nothing else:

- not "shaped like a screen frame" -> "four bare metal strips joined into one open rectangle"
- not "like a control panel" -> "a flat steel face with two rows of rivets"
- not "like a dashboard" -> "a rail with five cable tails clipped along it"

And the second half, which is the easy one to miss: **the corrective re-description must not list the things you are banning.** Writing "no lid, no cover, no glass, no panel" to fix the laptop keeps all four nouns in front of the model. Describe only what is there, in the positive, and let the absence be an absence.

**A conditional or counterfactual prop draws the prop** — "an empty rectangular recess where a handle would bolt on" came back with a handle bolted to the door beside the recess, which inverted the section: a door with a handle is a door you can open. This is the absence rule stated above applied to a clause rather than to an adjective, and the repair is the same one: describe the surface the eye should find (a shallow blind mortise, its interior bare shadow, four bolt holes round its rim) and, if the missing thing has to be felt, carry it on what a figure does instead of on the missing part's name.

**When two attempts of one slot fail on different invented artefacts, the scene is too busy — reduce it instead of rewording a third time.** A header slot came back first as a laptop (the shape analogy above), then as a flat black panel carrying invented characters pasted over the upper picture; the third attempt passed once the composition itself shrank: a tighter crop onto the bench, the pegboard cut to three spanners, and the jars, parts box, rag and oil can deleted. Two failures that name *different* objects are evidence about the scene's density and the number of surfaces it offers, not about the phrase that failed — so keep the concept, the room, the light and the figure, and take the prop count down until the action the picture needs is the only thing left in frame. A slot that fails twice on the *same* object is the opposite case: keep the scene and change that one prop (`references/re-render-defect-persistence.md` carries the escalation ladder).

**A word borrowed from another medium drags that medium's marks into the picture.** The same post's header needed a thin rectangular object and the prompt called it a "frame" six times; the render came back with a flat black panel over the picture carrying clean white characters (`23 -0`), a glyph and a grey L-shaped **crop-mark** — the furniture of a film or photo frame, drawn literally. Avoid the vocabulary of printing, photography, film, screens and dashboards when you mean a shape: say `four thin aluminium bars joined at their corners into one open rectangle`, not `frame`; `a bare metal rim`, not `bezel`; `a shallow tray`, not `display housing`. The same rule bans `crop`, `letterbox`, `slate`, `watermark` and `caption` from a prompt unless the picture is genuinely about them.

Check this on the file before the submit by grepping the prompt for every noun that names a typable or UI object — `screen|display|monitor|panel|plate|label|badge|sign|dial|dashboard|browser|notification|card` — and for each hit ask whether it is a prop the picture needs or an analogy standing in for geometry. An analogy is a rewrite, not a reword.

**A product's name draws its logo, and the logo comes back wearing invented branding.** A homelab section's subject is usually a named service — a tunnel daemon, a photo server, an observability stack — so the prompt naturally writes the product in, and the model answers a product with a mark: a pasted icon over the scene carrying a made-up word under a cloud glyph (`cloamflareTunnel` was one), or a flat vendor-UI panel in the corner. Both pass `check-grey-bars` and `check-palette-strip`, so nothing upstream of a crop will catch them, and a card shipping one is a card he reads as broken. Translate the product to its physical form before the submit — the tunnel becomes a cable through a brick wall, the photo server a plain stack of drives with no face, the dashboard a rail of cable tails — and keep the product's *shape nouns* out as well (`cloud`, `tunnel`, `hub`, `portal`, `console`), because a cloud is drawn as a cloud and a cloud in the corner is a logo. Grep the prompt for the section's product names, not only for the UI nouns in the list above.

## A prop with several states is one element per state, and an absence is not a description

Three failures with one cause: an element that asks the model to draw more than one thing.

**Instances that differ by state cannot share one element.** A prompt that asks for "four brass spigots, three sealed over the mouth with welded steel caps, the fourth open and dry" inside a single element comes back as a row of identical open spigots — five of them. The count is drawn from the row's shape and the state words become modifiers on a prop the model has already resolved, so both halves of the idea are lost at once: the number is wrong and nothing in the picture is sealed. **Give each state its own element and its own box** — three stub pipes ending in flat welded steel discs, then the one open spigot standing apart at the end of the row — and state the count on the element that carries it ("exactly three of them"). The same rule covers any set whose meaning is the difference between its members: the sealed ones and the open one are two props, not one prop with a caveat, and so are the cut cable tails and the live one, the full crates and the empty.

**A flux twin has no boxes, so the same separation has to be carried by the sentences.** The rule above is stated for the JSON prompt, where each state gets its own element; the paired text prompt has no elements at all, and a row of three written as one flowing clause — "three sieves in a row, the first with chaff run through it, the middle clogged with flour, the right clean with an even layer" — comes back as **two** sieves, the two most contrasting members, because a prose row is read as a description of a row rather than as three separate objects. Give each member its own sentence, in the same order, each with its size, its own state and where its result lands: "the left one has a wide coarse mesh and chaff has run through it, piled on the boards beneath; the middle one has a mesh so fine the flour has clogged it solid; the right one stands clean with one even layer resting on its mesh, a drift fallen into a tin below". Restate the total once ("three sieves and three states") and, at the collect, count the members on a crop of the whole row rather than of one of them.

**A count spread over two elements is a count the model rounds up.** Post 038's allow-list attempt described a plate with four sockets where "the three right-hand sockets each hold a slug and the left-hand socket is empty", plus a separate element for one loose slug standing on the bench. It rendered four sockets, **all four filled**, and a fifth slug on the bench — a legal reading, because nothing in the prompt said how many slugs exist in the frame, so the loose one became an addition. When a spare copy of a prop shares the frame with the fitted ones, state the total in the `high_level_description` ("exactly four slugs in the whole picture: three seated in sockets and one standing on the bench") and keep the empty socket described by the surface the eye should find, per the absence rule below.

**A container described as empty, dry or bare is still a container the model fills.** "Bone dry" is a modifier, and the model answers a trough with the shape it has drawn a hundred times: full of water. Describe what is visible *in* it instead — the pale dry stone floor of the trough, the seams of its slabs, a ring of grey dust along the rim — because a described surface has no room in it, while an absence has all the room. Naming the missing thing is worse than saying nothing: a negative about water carries the noun `water`, and the noun is read as an instruction (#62). This is the rule for every absence — the empty recess, the bare shelf, the dry run, the plugged socket — describe the surface the eye should find, never the thing that should not be there.

**Two ends facing each other across empty space become one connected part.** A beat that says *this does not reach that* — a shaft that stops short of its socket, a pipe that ends before the flange, a plug that never goes in — cannot be drawn as an air gap however carefully the gap is said. Describe the stub and the matching socket inside one element, name what is visible through the space between them, restate the gap in `high_level_description`, and the engine still runs one continuous member from end to end: it reads two aligned ends as the instruction and the gap as the decoration. So the repair is not a third wording of the gap. Take the connecting member out of the linkage altogether and carry the break as a member **laid aside**, where its state is a fact the model can draw: two bare sprocket wheels with the drive chain coiled on the bench between them and both ends on the wood, a belt hanging on a hook beside two bare pulleys, a plug lying in its own coil beside an open socket. State that the laid-aside part touches neither end. A coil on a bench is drawn as a coil; a gap is drawn as a connection.

**A substance named as scenery draws the substance.** "A rust bloom at the joint" on a manifold came back as rust-red stains running down the wall beneath two of the taps, one heavy enough to read as a wound rather than as metal. Same mechanism as the shape analogy above — the model reads nouns and draws them. If a joint should look old, describe what is there (dull grey pitted iron) and not what has stained it.

**Describing one prop in a bare region does not fill the region — describe the whole band.** Post 035's permalink slot spent four renders and three of them invented an object in the same bare strip of floor: a tall black office chair (rejected by Wojtek as "a black object that i can not even name"), a second corkboard on the receding wall, and — after the fix that put a described pale pine stool on that floor — a small pale panel leaning on the skirting board beside the stool, which two 4x crops could only call "a portable appliance or a floor vent cover". Every one of those prompts described its own single prop and left the rest of the floor line to the model, and the model filled what was left of the strip. So when a reason names an invented object, the repair is not a better description of that object's replacement: state the band the whole way across (the floorboards run unbroken from the desk to the man's feet, the skirting board runs the length of the back wall) and give every free-standing thing in that band its own sentence. A region described for one stretch and left bare for the next gets a prop in the bare stretch — and two crops calling it unnameable is the test that it is still a hold-back, not a quirk.

## A before/after pair needs the reversed state on every part, not a cue

Two slots on one post that tell a before and an after — cords pulled out of the board / cords seated again, a snapped belt / a running belt, a dark lamp / a lit one — are two independent pictures to the model, and the after-frame only changes the parts its own words name. So an after-frame written around a single cue comes back with the before-state intact everywhere else and the cue sitting beside it: a switchboard asked for "every socket seated with a short cord" plus a capsule newly arrived in its brass cup rendered the capsule, its dust and a still bell correctly, and left the upper rows unplugged with several cords hanging loose and their connectors dangling. On a card the two images then show the same state twice and the pair stops arguing about anything.

- **Write both frames as a full inventory of the same mechanism, part by part, in the same order**, so the difference is only in what the words say about each part: all three rows filled and cabled, not one empty socket anywhere on the board, not one cord left hanging loose with a dangling connector, nothing lying loose on the floor. Counts and states carry the change; the cue does not.
- **Never describe the before-state's signature object in the after-frame.** "Three cords hanging out of the lower edge" is a fact of the frame it belongs to; repeated in the after-frame the words redraw it and the picture reverts.
- **The cue prop is what a reader notices and not what the engine reverses.** The capsule in the cup, the lit lamp, the moving belt is the second sentence; the mechanism's own state is the first.
- **Check the pair, not the frames.** At the collect, ask of the two images side by side whether a person could tell which is the after. If they read as the same picture twice, the after-frame is the one that gets the re-render, and the slot's other engine goes on the card meanwhile.

## Motion marks are the house style; an arrowhead is a symbol

The ink arcs a cartoon puts around a ringing bell, a struck hammer or a spinning wheel are part of the look and pass the bar. What the same stroke does at its end does not: an arc finishing in a pointed head is a **drawn arrow**, a graphic mark lying over the painting rather than movement in it. One header's arcs carried an arrowhead that no frame-level read named and a 5x crop of the bell's mouth did. Keep `no arrow` in the negative clause beside the overlay nouns — it costs nothing, because the ban names a shape the picture never needs — and when one still arrives, name it on the card rather than holding the frame: the bell, the rack and the figure are what the section needs, and a single arrowhead is a caveat the reviewer can see for himself, unlike a pasted panel. It becomes a hold only when the arrow points at something the picture does not contain, which is an invented relationship rather than a mark.

## An industrial panel invites engraved labels above its sockets

A switchboard, a patch panel, a row of brass terminals is a surface the engine labels for you: on one verification frame the panel filled correctly — 24 seated brass terminals, six cords plugged in — and then drew a small tally-like glyph above each plug, the I, II, III family, drawn as ink rather than pasted and invisible at full frame. Three crops (a wide board crop, a 3x bottom band, a 5x single column) all reported written characters, and the wide board read alone would have called it panel texture.

Two rules follow. In the prompt, say the panel face is **plain and unmarked**: "no plate, no number, no engraved mark and nothing written above the sockets" — the same ban the bell and the drums already carry, because a row of holes reads to the engine as a row of things to name. At the collect, crop the panel face itself at 3x–5x above the plugs, not the whole board: the marks survive a full-frame read and a wide crop, and they are one of the few lettering shapes that never resolve into a word you could mistake for English.

## A swept-dust mark draws as a white patch

"A clean pale rectangle where the dust has been swept away", "a bare patch in the dust", "the clean mark of something that stood there" — every one of those phrases comes back as a **stark white rectangle laid on the surface**, with straight edges and a different texture from the wood around it. It is the pasted-panel defect arriving through the back door: two engines drew it on two attempts of one header, the second attempt after the prompt had been rewritten to say "bare wood worn pale, not white, not paper, no rectangle", and both put the same bright rectangle on the middle board.

The fix is not another negative. **Show absence with marks the surface already owns**: four pale round foot-rings pressed into the dust where the crates stood, a worn band following the wood grain, boards with visible nail heads and a cobweb strung across the corner, a dry water-ring round the base of a jar. A ring, a band or a scratch is drawn faithfully; a rectangle is drawn as paper.

## A canister, tin or box with a flat face gets a small rectangular label

Any closed container drawn in a row — pewter tins, canisters, crates, jars, steel boxes — invites a small rectangular label stuck on its face. It comes back as a pale rectangle with a blurred line inside, which survives a full-frame read ("no readable text") and only shows up on a 2x crop of the chest. It is the lettering family even when nothing resolves into a word.

Say the container is **plain and seamless** and name the shapes to keep off it in the same clause: "a smooth seamless cylinder with a rounded shoulder and a flat lid, no band, no plate, no label, and nothing written or stamped on any face". Then crop the row at 2x at the collect and look at the faces, not the count. Naming it in the negative clause alone is weaker than describing the object as seamless, because the description is what the engine draws.

## A member that can reach the walls gets rested on them, and the count it stands for collapses

When the beat is a **count of supports** — one beam on three posts, one old and two newly cut — the engine anchors any long member it can to the room: a beam written as "running level from the left wall to the right" comes back as exactly that, with its own weight taken by the brick and only two posts under it. The picture then states the wrong number, which on a post titled *two new arms* is a header that contradicts its own title.

The fix is structural, not adjectival. **Make the member shorter than the room** so it has nothing to rest on: both ends stop in mid-air past the outer posts, overhanging by a hand's width, the whole frame standing free on its own flat stones and touching nothing but them. State that in the prose once and the count in the same sentence — three posts, one old, two newly cut — and the wall is no longer an option the model can take.

At the collect, two crops decide it and neither is a full-frame read: the beam line at 1.2x–1.6x to confirm it sits **on** all three heads rather than floating above them, and each free end at 4x for a visible gap to the brick. A member that spans a room and reaches neither wall reads to some viewers as impossible architecture, so name that as a caveat if it is the only one — the count it protects is worth more than the oddity it costs.

## A mechanism comes back complete, and in its resting state

Two failures from one batch, same cause. Asked for "a game trap that has already fired, its jaws snapped shut on empty air", one engine drew the trap **open and untriggered** — the neutral state — which reads *armed and waiting*, the opposite of the section. Asked for "a bell hanging with no clapper in it, the clapper lying in a dish", another engine drew a complete bell **with a clapper inside**, because a bell is drawn as a bell.

The engine completes mechanisms and rests them. So do not ask for a mechanism *with a part missing*, and do not rely on an adjective like "sprung" for the state:

- **Write the spent state as parts.** "The two toothed jaws are closed and lie flat against each other along their whole length, the teeth interlaced with empty air between them, the trigger plate flat down under the near jaw, the spring arm swung over and lying across the top of the closed jaws, the chain run out in a coil" — then add that no jaws stand apart anywhere in the picture.
- **Or take the object out of its mechanism.** A bell that must not ring is better *off its bracket and standing mouth-down on the bench* with a bare empty hook above it, than hanging with its clapper removed: the engine cannot put a clapper into a bell whose mouth is hidden, and the empty hook says who did it.

Crop the mechanism at 3x-4x at the collect and ask one question: is it in the state the section needs, or in its resting state?

**Measured limit.** On one post the spent-state-as-parts wording was tried on both engines, twice each, and three of the four attempts (one ideogram, both flux) still came back with the **jaws open**, including the attempt that spelled out "the teeth interlaced with empty air between them, the trigger plate flat down, the spring arm swung over, and no jaws stand apart anywhere". A spring-loaded trap is drawn unsprung the way a bell is drawn with its clapper. So for a mechanism beat, budget one attempt on the parts wording and then **change the object or empty the frame**: the trap became a still life of the shut trap with the chain coiled and nobody in the room, which is also the fix for the doubling figure that appeared in the same slot on the same batch. Two failures on a mechanism is not a wording problem.

**Then take the mechanism out and keep only its trace.** A fifth attempt on the same slot went further: a still life with the trap as the only subject and **nobody in the room** — which did fix the doubling figure — and the jaws still came back open, a clear 45° gap between the teeth at 2.2x. So the state of a spring mechanism is not drawable at all, in any pose, on either engine. What worked was replacing the object with the **mark it left**: two short rows of triangular dents sawn into the bench top, lifted splinters at their edges, a ridge of displaced dust along each row, the boards between them bare and empty, and no jaw or spring or chain anywhere in the picture. A trace on a surface has no state to get wrong. Same move for any "it fired / it closed / it emptied" beat: draw the scar, the dent, the ring pressed in the dust — not the device.

**But a mark on a surface gets tiled into a field.** The first trace attempt — "a matched pair of short rows of triangular dents sawn into the oak, a hand's width apart, closing toward each other at their inner ends" — came back as **many long parallel rows of small raised triangular blocks**, dozens of them, with sawdust round their bases: the count was lost and the mark was lifted off the surface it was supposed to be cut into. Two words carry the fix. Say the mark is **pressed or cut INTO** the surface rather than lying on it ("pressed deep into the oak, each dent with a lifted splinter at its outer edge"), and **bound the area**: the two rows occupy one hand-span of the bench top under the middle of the bench, and the rest of the boards are plain worn wood with nothing on them. State the number of marks in the same sentence as the area, and at the collect count them on a 2x–3x crop of the whole surface rather than one mark — a tiled field reads as decoration at frame scale and only shows its number up close. The same trap waits for scratches, nail holes, water rings and footprints: an unbounded mark is a pattern.

**Measured, second attempt, same slot:** the ideogram did cut the dents into the oak this time — a 2x crop shows splintered edges and the grain running continuously into each wedge — and it made **sixty to seventy of them** in two blocks of neat rows and columns, sawdust at their bases. Its flux twin cut nothing at all: a small cluster of pale **loose** triangles lying on the boards, reading as debris. So neither engine can be told a count on a repeated mark; one rounds it up into a texture and the other lifts it off the surface. The exit with anything left in it is to ask for **one** mark, sited where it cannot be repeated — a single deep V notch cut across the **front edge** of a board, one scar on a door stile, one ring pressed into dust in a corner — because a mark with no neighbours has nothing to tile with. Budget one trace attempt per slot; if the trace tiles or goes loose, the object changes rather than the wording.

**The rule that survives both objects: a pose plus a calm room, never an absence and never a mark.** The header slot that burned seven renders across two engines was finally handed to the post's author, and his diagnosis is the one to keep: the trap asked for a **state that reads as an absence** — a trap's identity in every training picture is "open and waiting", so closing it leaves the engine nothing iconic to draw and it draws the iconic version, five renders running, on both engines, even with nobody in the frame. The dents asked for **negative detail**, and models do not subtract — they added raised triangles in rows. What draws is an object in an unmistakable **pose** plus a room that is plainly undisturbed: his answer was a small brass bell mid-strike with three inked arcs, and a mug of coffee still steaming on the bench below it. Two props, one movement, the empty wall between them load-bearing. When a beat is "it fired and nothing happened", draw the firing and the nothing, side by side — do not draw the after.

**And when one post's records carry several defect families at once, choose the empty room for the whole batch up front instead of after the failures.** A post whose prompts ask for literal marks in one slot, a text surface in the next and a second figure in a third is cheaper to draw as still lifes from the start: an object in a state, nobody in the frame, the beat carried by the prop alone. The two families that have cost the most renders across this campaign — a duplicated figure and a mangled hand — cannot occur in a room with nobody in it, so those frames reach a card without a limb check, and the batch does not spend its six renders discovering that for the third time.

**A light-and-shadow beat is settled by measuring the bands, not by reading the frame.** A before/after pair built on "the light now falls on the thing it watches" gets its verdict from mean luminance: crop the band where the object sits and the band of wall beside it, and compare. One batch read it exactly backwards — a full-frame read of the lit frame said the light fell on the bare wall and the shelf was in shadow, while the numbers said the opposite (shelf 99 against wall 87, and 74 against 102 in the companion frame). A 1.5x crop of the lamp and its object confirmed the crates' faces and iron straps lit with the brick beside them dark. So a wide read can **miss** a lit object as easily as invent a defect: for any beat carried by light, measure the two bands, then crop to explain the number.

**The wall band must be the brick immediately beside the object, at the same height — and that is how this rule failed me once.** The pair above was passed on the numbers quoted in the previous paragraph, and the pass was wrong: the "wall" band had been measured on a patch that sat in shadow to one side of the crates, so the crates beat a dark surface and looked lit. Re-measured against the brick immediately beside them, the same two frames read crates **103** against brick **185** in the header, and crates **60** against brick **147** in its companion: the light was on the wall in both, the pair did not argue, and the header frame was showing the absent state. So pick the comparison band as the nearest same-height brick the object does not cover, measure both frames of the pair the same way, and treat a margin under about 15 points as no contrast at all. A pass on a light-contrast pair is only as good as the patch it was measured against. Run `scripts/check-light-contrast.py` rather than measuring inline in a heredoc — it takes `--object x0,y0,x1,y1 --wall x0,y0,x1,y1` (0..1 fractions work too), several frames in one call, and `--pair` for the verdict, and it prints the sign per frame so a session's numbers stay comparable with the ones already in the notes. A pair whose frames all come back with the same sign is the failed pair, whichever engine drew it. And when a pair exists to argue a contrast, both frames of the pair are checked against each other — two frames in the same state is a failed pair even when each is a clean picture, and the frame that fails is the one whose whole purpose was the contrast.

**A lamp drawn in the frame lights its own wall — take the light source out of the picture.** Both engines, three renders: told that a lamp "shade tipped toward the shelf, so the warm ochre light lands on the three crates", every frame came back with the bright pool on the brick around the lamp and the crates in spill, because a lantern in a frame is drawn with its halo on the wall behind it and no adjective moves that halo onto a shelf. Writing "the crate faces are the brightest surfaces in the picture" changed nothing while the lamp was visible. The fix is structural: state that **no lamp, lantern, bulb, flame, shade, bracket, glow or halo is anywhere in the picture**, and that the light arrives as a single shaft **from off the left edge, as from a doorway out of sight**, landing only on the object, with the wall around it the darkest surface in the frame. Then the only surface the engine can light is the one the beat needs. Same move for any "the light is on X" picture.

**But a shaft from off the edge still crosses the wall first, so taking the lamp out is not enough on its own.** The next attempt on that slot followed the advice above exactly — no lamp, flame, shade or halo anywhere, one shaft arriving from off the left edge — and came back with warm light on the crates at **113** against brick at **165**: the nearest crate strongly lit, the middle partly, the far one in half shade, and the brick the shaft crossed still the brighter surface. Light that enters a frame from its edge falls on the wall before it reaches anything standing on a shelf against that wall, so the pair argued the same state twice again and the pass had to be withdrawn.

A light beat needs an **aperture inside the frame**, not an edge: a narrow high window, a slot, a vent, a shuttered opening, with the pool landing where the beat needs it and the wall outside the pool staying dark — the opening is an object the engine can draw, and it bounds the light the way a lamp cannot. Budget one attempt per mechanism, measure the band immediately beside the object after each, and when both the lamp-in-frame and the off-edge-shaft versions put the light on the wall, the beat changes object rather than the light being re-worded a third time.

**Bare forearms at cel scale come back saturated.** "Sleeves rolled to the elbow" on a man leaning over a bench produced, on both engines' attempts, forearms and hands in vivid red-orange that reads as a colour artifact against an ochre and grey palette. Keep the sleeves **buttoned at the wrist** and mention no bare skin on the arms at all; a figure whose hands must be seen and whose palette must stay quiet is better with its cuffs down.

**A bell hidden mouth-down still gets its clapper at the lip.** The other fix tried on the same batch was to take the bell off its bracket and stand it mouth-down on the bench, "its flared mouth flat on the boards so the inside is hidden and nothing can be seen in it", with the loose clapper in a tin dish beside it and a bare empty hook above. Both engines put the clapper ball back at the rim, peeking out from under the flared edge — visible only at 2.2x and 4x, invisible at full frame — and neither drew a separate clapper in the dish. Hiding a part does not remove it; the clapper is drawn with the bell the way the jaws are drawn open. The version that passed first time had the bell **hanging with its mouth open and empty** and the clapper lying loose on the bench in plain sight, two objects the picture can count. So for "the part is out": show the empty socket and the part **separately, both visible**, rather than hiding the socket.

## An object that must not join its twin gets joined — change the kind, not the wording

Two pipes, two cables, two rails where the beat is *these never meet* is the hardest relationship in this style: the engine reads two members of one kind running near each other as a run, and joins them whatever the prompt says twice. One post's bypass pipe — "runs low across the floor, in from the left edge and out through the brick at the right, never rising to the vessel, touching neither the plinth nor any pipe feeding it" — came back on the first attempt with no bypass at all, and on the second with the low pipe curving up and feeding the vessel. A 1.6x crop of the floor line settled it: the phrase "never touches" was obeyed as decoration and the drawing followed the topology.

So when a picture needs two things of the same kind kept apart, do not describe the separation — **make them different kinds**, or put a physical barrier between them that no line can cross: the bypass becomes a shallow brick gutter in the floor with its own iron grate, the pair of pipes becomes a pipe and a chain lying slack, the parallel rail becomes a raised stone lip the eye follows. If it must stay two pipes, they leave the frame on different walls and never share a floor.

**The same mechanism runs the other way: a pair that plainly belongs to one object gets joined even when the beat wants them apart.** Two halves of one small brass message capsule, written as "lying a hand's width apart" in a shallow tray, came back **joined by a short ribbed collar** — the engine saw two matching halves and made one object of them. When the separation is cosmetic, accept the link and name it as a caveat (two hollows with dust in them still read as an opened capsule that carried nothing); when the gap itself is the beat, the two parts have to stop being members of one thing: give each its own kind, or put one somewhere else entirely — on the flags, in a second tray, beside the bench — because a matched pair drawn on one surface is drawn as a pair.

## Closure is geometry: raise the camera, do not re-word the loop

Post 087's provisioner slot asked, in prose, for "a narrow iron rail runs a closed circuit: it leaves the near left, crosses the bench to the right, turns away from the viewer at the far right and comes back along the far side, ending where it began, and the circuit is complete with no gap anywhere in it". The ideogram drew a straight double rail crossing the bench and passing behind the crank post **off the edge of the bench**, with one turn at the far corner. Every object in the frame was right; the return — which is the whole section — was not in the picture.

Two causes, both structural:

- **a straight-on camera cannot show a closed loop.** From eye level a ring reads as a line with a bend; the far side is hidden behind the near side. Say the camera is at a raised three-quarter angle looking down at the surface at about forty degrees, so the loop lies open in the frame like a map.
- **an object described by its route gets drawn as a route.** A rail "that goes out, across, turns and comes back" is a path, and a path has ends. Make the object a **closed shape first**: one small oval lying flat on the bench, two parallel sides and a semicircular curve at *each* end, both curves visible on the boards — then say that no part of it leaves the bench top and nothing runs off the edge behind the mechanism.

The same rule covers a beat of return ("the work comes back where it started", "the same thing happens every hour"): the return has to be **visible inside the frame**. A track that leaves the picture reads as a track, not a cycle, however the prose describes it.

Two smaller findings from the same frame: identical objects named once come back in three sizes — say **one size repeated three times**; and `check-bboxes.py` rejects the words *left*/*right* inside the description of a wide box, so a ring spanning the frame has to be described by its ends ("the curve at each end"), not by sides.

Third, found on post 089's header: the checker's NARROW rule matches **thin**, **narrow** and **slim** anywhere in a full-frame element's description and calls it a narrow-strip claim on a 1000x1000 box. Plain scenery language trips it — "thin ground mist" did, twice, even after the phrase left the `high_level_description`. Write "low ground mist", "fine haze" or "pale drift of dust" in any element whose box is the whole frame, and re-run the checker after every wording change that touches element 0.

## The flux engine flattens structure — give it the pose, not the cross-section

Measured on post 087's first round: three of three flux frames failed on the *structure inside the object*, not on the object, while the ideograms on the same prompts were drawn correctly.

- a cut onion: the ideogram drew eight separate nested contours, the flux came back with **one smooth pale surface and vertical striations** — the rings, which were the whole beat, were dropped;
- a shelf with one bracket snapped through and the board hanging steeply: the flux drew the shelf **level with both brackets intact** and four jars instead of five;
- a closed iron rail loop carrying three crates: the flux drew **two crates on parallel rails**, no loop.

So before spending a flux twin, ask what carries the beat. If it is **a structure inside an object** — a cross-section, a state contrast between two identical brackets, a closed loop with a count — the flux frame will draw the room and lose the meaning. Pair the ideogram with the flux on a beat that is an **object in a pose** (a bound hammer, a hatch with light under it, a bell with no clapper), which flux draws well. A held flux twin is cheaper than a wasted one, but the honest saving is to not submit it.

## A repair that adds a decoration buys a new defect

The provisioner r1b fixed the whole beat — camera raised, oval closed, both ends curving on the boards — and came back with an **oversized spanner** lying on the flags, several floor flags long, its handle carrying faint stamped pseudo-lettering on a 4× crop. The beat was right; the prop I added to fill the floor was not, and the slot cost a third ideogram to remove it.

Two rules follow, and they hold on every repair:

- **Change one thing per repair.** If a frame fails on one part, fix that part and leave the rest of the composition byte-identical. A repair that also restyles the surroundings cannot be read, because two changes arrived at once.
- **A repair that only needs to subtract should subtract.** When the defect is on a prop the section never asked for, remove the prop rather than re-describe it; a smaller object drawn where the lens is close will keep its flaws, and pseudo-lettering on metal survives any wording about "no marks". In r1c the spanner became a short iron chain coiled flat on the flags, and the frame passed.

## Lesson

For this user, always try prompt hygiene first. Only fall back to `two_pass`/`single_pass` for persistent false positives on otherwise safe prompts. Do not rely on sampler tricks to bypass the actual safety guardrail on genuinely policy-violating prompts.

## A brass fitting is drawn as an instrument with a numbered plate

Post 089's `cpu-fire` slot asked for a small brass measuring collar clamped on a pipe, with "no gauge face, no dial, no needle, no numerals" already in the negative clause. The engine drew a round brass fitting with a knurled rim, radial tick marks, a central hub, and a **small rectangular plate on its side carrying a numeral** — read as `6` at 4x and as `60` at 1.6x. Two reads disagreed about what the object was (handwheel against gauge) and agreed about the plate and the digit, which is all the verdict needs.

Two rules:

- **Name the metal for the job, not for the look.** "Brass" plus "round fitting on a pipe" is the instrument family; the same part in **dull flat iron, a band the width of a thumb, held by two square nuts** came back plain. Warm brass in the palette invites the same class anywhere a fitting has a circular face.
- **A fitting with a face gets a plate.** Ban the plate as well as the face: "no plate, no tag, no tab, no label brace bolted to any pipe, no numeral on any plate or fitting" — a gauge is refused, and the engine hangs its number somewhere else.

The same batch also flattened a **relation between two widths** that was written in prose: "three times the width of the collar" came back at about 1.5–2×, which reads as a collar slightly smaller than its pipe rather than as an allowance measured for a thin pipe. State the small part by a body measure ("no wider than two fingers") and the large one as a multiple of it ("at least four times that collar"), and check it on a crop of the two together, not on a full-frame read.

## A lighting clause can paint a bar across the frame

The restyle slot of post 089 asked for "deep indigo shadow at the near edge of the bench", and both the prose and the lighting block said it. The engine painted exactly that: the scene ends at row 724 and the remaining **108 px (13 % of the 832 px height)** is a featureless dark band, first a grey strip then a near-black one. Every edge script but one passed it, and `check-blank-margin` only fired on it because it was uniform.

Two rules:

- **Never ask for shadow "at the near edge of the bench" or "in the corners" as a location.** A shadow named by location becomes a bar along that edge. Say where the light falls and let the shadow gather **behind** the objects, and say outright that the boards run to the last row of pixels and the frame ends on them.
- **Fill the near corners with a described object.** The same repair added an iron paddle at the lower left; a void invites paint, an object does not.

When `check-blank-margin` flags a band, settle it with a per-row luminance and unique-colour count before cropping: 600–900 distinct colours per row means painted noise, not a flat bar — but at 41 luminance with no drawn edge it still reads as an empty strip to a viewer, which is the only verdict that matters.

## Comparing a text prompt file with the job's served prompt

A flux (`prompt_type: "text"`) prompt file ends with a newline while `imagegen status` serves the prompt without one, so a plain string equality test reports a mismatch on a healthy record and reads like the file was overwritten by another post's slot. Compare with both sides `.rstrip()`-ed, or accept `served == filed.rstrip("\n")`, and treat any remaining difference as the collision the rule is about. The json case keeps its parsed comparison, which is immune to this.
