# Re-render Defect Persistence

When a re-render of a round-1 rejected image carries the same defect that caused the round-1 rejection, the prompt revision must explicitly address every clause of the rejection reason. The model may re-invent the same artifact (e.g., pseudo-text, UI panels, other model-invented elements) if the prompt only softens the original prohibition rather than giving a concrete replacement or removal instruction.

**The 1990s anime film-still style is the standing style brief since 2026-10-28.** Its clauses in his own words, the style block to copy and the clause-to-prompt mapping live in `references/1990s-anime-style.md`. Read it before revising any prompt that came back with the film-grain / green-accent / unreadable-text / two-main-characters reason, because that reason rebuilds the whole style block rather than one prop.

## Key Cases

### 1. Text/UI Panels Defect

**Rejection Reason:** "as always, when you are asking model to put some text, you must be explicit what text is there, otherwise we have situation like here, nothing readable"

**Prompt Fix — the props first, the ban never:**
- **Remove every surface that could carry words.** A prop the prompt described as a label, a plaque, a panel, a scale, a sign, a dial face or a readout is a place the model will put invented characters, so delete it or replace it with a physical object that has nothing to write on. **This is the fix that works; a ban does not.**
- **Removing the named text-bearing surfaces does not stop the model from adding a new floating UI label or banner with garbled text, a speech or thought bubble with symbols, a framed poster, or a sign with pseudo-text, duplicating a figure, or clipping a torso into a prop. The self-check must scan the whole frame for invented elements, not only the surfaces the prompt named — a re-render that cleared every named surface can still fail on an invented one. See `references/text-in-images.md` for the full ban list (bubbles, captions, floating text, question marks, symbols, framed posters, signs, flat label faces).
- **When an invented element does appear, the silent re-render keeps the surface removal and may add a ban naming only that specific invented element, as a secondary defence — not a substitute for removing the surfaces, and never the generic "no text, no labels, no banners" clause, which names the shape and invites it (#62).** The ban is a hedge and must be verified by self-check, not trusted: if the banned element reappears or a new one appears, remove the ban and change the composition (crop, prop, camera) instead of rewording.
- **Removing a prop and then naming it in the closing ban is the same mistake as banning it in place, and it is the easier one to make.** The edit that deletes a corkboard, a notice or a label from the positive description leaves the word in your hand, and it lands in the negative clause a few lines later — so the prompt meant to remove the prop still carries its noun once, and the model draws it. **Check the finished file mechanically: sweep the whole JSON for each removed prop's noun (`corkboard`, `paper`, `notice`, `label`, `plaque`) and require zero hits anywhere in the prompt.** A hit is a failed removal no matter which clause it sits in. Replace the ban with a positive description of what now fills that region — the stain, the pans, the wall — so the region is described rather than prohibited.
- **Do not name the banned shape in the negative clause.** A clause like "No text anywhere in the image / No UI panels or pseudo-text anywhere / No floating text, no banners, no labels" is a concrete instruction, and a concrete instruction is what the model draws. On a slot whose picture was full of labelled surfaces, the round-2 prompt kept the composition and added exactly that clause, and the render came back **worse** — bigger blue overlays, pseudo-text on banners and buttons, a progress bar with a purple icon. The ban named the shape and the model drew it. `references/engine-pitfalls.md` #62 carries the case; #34 and #55 say the same for a palette strip and for any prop that invites writing.
- **Provide concrete replacements** for the props you keep: "a brass plaque with a green checkmark" instead of "a plaque with a checkmark", "a blank metal nameplate, its face empty except for a horizontal groove" instead of "a nameplate".
- **When the section's meaning is a comparison, carry it by shape instead of by a prop that must be read.** Four dead routes and one live one does not need a chart with rows — a chart is a prop built to be lettered, and the model letters it. The same meaning is physical: a rail of five cable tails, four cut with frayed copper, the fifth live and running into the one lit box, with the figure's magnifier over the live connector. Ask what the information *is* before keeping any surface that would carry it as words, and give the answer a shape, a count and a place in the frame.

**A dictated inscription needs its own element at frame scale, or it truncates.** Dictating the characters is only half of the working shape: the surface that carries them has to be a declared element with its own `bbox`, in the open, large enough to read. A table written into another prop's description — headers `session_id, title, model, started_at` inside a magnifying glass, a count on a wall display, lines of text on a sheet that the press outputs — comes back truncated or garbled even though every character was given, because the model is drawing a surface at one or two hundred pixels wide and has no separate instruction for it. So when the picture's meaning is a document, a log or a count, ask first whether it can be carried as a physical object instead (a bound codex held up, a shelf of volumes, blank sheets), and keep the dictated inscription only for a surface you can give a real box. That is why the zero-text default is the cheap one: it removes the surface rather than betting on a size the frame may not have.

**The number of text-bearing surfaces is the variable, not the wording of the ban.** A prompt that asks for several labelled surfaces at once — readable UI labels, plain name tags, a wall of plaques — gets every one of them garbled, because the model is improvising words on each surface it was given. Two prompt shapes clear it, and they are not the same shape:

- **Dictate the one inscription you need, character for character, and delete every other surface that could carry words.** Name the single prop that holds the text, say what it is physically (a small card held up in one hand, a tag on a rail), and give the exact words: `"a small white card held up in his right hand, with the two lines 'HTTP Header' and 'per-session' written on it in clear black hand-printed capitals"`. Everything else that was a label becomes a blank, unlettered surface: a blank nameplate, a blank placard, a card whose face carries only a scribble. This is the shape that renders the wanted words legibly, because the model has exactly one writing task and it was told the characters instead of being asked to invent them.
- **Ban the text and say what the surface is instead of what it says.** `"a blank metal nameplate, its face empty except for a horizontal groove"` keeps the prop's shape and its place in the scene while removing the invitation to write on it.

Asking the model for "readable UI text labels" or for "plain name tags" is the third option and it is the one that fails: it hands the model a writing task on every surface at once and leaves the characters to it, and what comes back is word-shaped noise. Wojtek's standing instruction is that text placed in a picture must be given explicitly, and this is the prompt-side form of it — but the reading of that instruction that survives contact with the model is the narrower one: *give the characters explicitly where the words matter, and take the surfaces away everywhere else.* A prompt that names no text at all is not a shortcut around the rule, it is the same rule applied to every surface that had lettering and did not need it.

**One slot failing the self-check on a defect class is a prompt for the whole card, so audit the sibling prompts before you submit any of them.** The prompts of one post are written from one template family and one reading of the post, so the habit that put a display, a note card and a labelled barrel into one slot is in the others too — and each one is a separate render at ~21 minutes behind a shared queue. When slot A comes back with invented lettering, hold it back, then sweep every other slot of that card for the same class (surface nouns, a count on a screen, cards with headings, labels on props) and fix them in the same pass; submitting the untouched siblings costs a whole render cycle each and returns the same defect hours later. The sweep is cheap, the re-render is not.

**His standing rule for a picture that does carry words: readable English, on the image's own palette, in a comic-book bubble with a white fill.** In his own words — text "is for humans and must be combined out fo readable words in english preferably", it "must keep general color palete of image", and if you do place some, "just put them on comicbook style boobles ... white background always fits". Three consequences for a prompt: the characters are dictated exactly (never left to the model to invent), the bubble is a described element with its own `bbox` and a white fill rather than something the model adds, and its lettering colour stays inside the colours the frame already uses. So a slot has exactly two safe shapes — **no text at all**, or **one declared bubble with dictated words** — and a prompt that asks for words without declaring a bubble sits between them and gets the defect back.

**A re-render that fixes an "unreadable text" rejection by adding more readable labels is the wrong fix.** The rejection says the surfaces are garbling words; adding labels adds surfaces and garbles more of them (round 3 of this slot asked for four readable labels on stone tablets and came back with a comma instead of a dot on two of them plus a wall of garbled secondary text). The fix is to remove the surfaces, or use one declared bubble with dictated words — per the two safe shapes above — never "more readable text".

**The cheap default is the zero-text one. A bubble buys one joke and costs a spelling risk on a slot that has already been rejected once, so offer it rather than assume it: state the choice with your recommendation on the card comment, and ship wordless unless he asks for the bubble. When you do offer it, use an `ask_user_questions` card (`resolverPolicy: human_only`, `continuationPolicy: wake_assignee`) rather than a comment — a comment can supersede the round-1 card and expire the interaction, while a question card survives and wakes you with the structured answer. If he picks readable English, follow it: the verdict is Wojtek's alone and overrides the standing zero-text rule, but keep the number of text surfaces to the minimum the composition needs and dictate the exact words character for character, and note the spelling risk on the card so the choice is visible in the record. Either way his rule is what the hand-off question to an author must carry, because an author writing a composition cannot see the model's failure mode and will propose a labelled surface unless the constraint is spelled out for him.

**A silent approval confirms the zero-text shape, so read a reason that demands readable lettering as a demand to end the writing task.** A slot whose only complaint was invented lettering — with the art praised in the same breath — came back approved on a re-render that carries no characters at all, and the approval gave no reason: one data point, not a rule about the series, but it settles which of the two prompt shapes that clause licenses. Deleting the surfaces is what clears it; asking the model for "readable" text is the shape that fails. The same card carried two deviations I had named on it and neither cost the image — a figure turned away from the prop its beat wanted him to study, and a countable prop off by one against the prompt — because a composition-level beat outranks a small count nobody can check off the picture. Those belong in the card's note, not in a re-render.

**An attempt held back at the self-check is a prompt-side A/B worth keeping.** When one prompt shape produced garbled pseudo-text and the next shape produced a legible inscription, and the second reached the card, the pair is the evidence for the fix — so keep both prompt files, and in the record's Why say which surface the model garbled and which one it rendered cleanly. The limit to carry with the observation: a comparison inside one slot on one post is one data point about the model, not a rule about his taste, and the memory that keeps it must say which of the two it is.

### 2. General Defect Persistence

**Prompt Fix:**
- **Compare each element of the new render against the round-1 rejection reason clause by clause**
- **Ensure every banned element is addressed by:**
  - A positive description (e.g., "a brass plaque with a green checkmark" instead of "a plaque with a checkmark")
  - An explicit removal (e.g., "no floating text, no banners, no labels")
  - A concrete replacement (e.g., "a glass jar with engraved measurement marks" instead of "a jar with measurement marks")

**Example:**
- If the round-1 rejection was about "inconsistent jar scale", ensure the re-render prompt explicitly describes the correct scale:
```json
"desc": "A tall glass jar with brass rim standing on the workbench, filled with golden liquid that stops at a low height mark, with many engraved measurement marks above the liquid line reaching to the jar top."
```

**A brief that says the render budget is spent is not a licence to show a hold-back class.** A handoff can carry a line like *no silent re-render budget left for this slot*, written by the run that rendered the attempt, and it reads as an instruction to card that attempt with the defect named. The show bar outranks it: a duplicated protagonist, a third arm, a green badge or a pasted panel is a class he rejects whole frames over, and naming it on the frozen card spends the round and leaves the slot with nothing. Spend the render instead — rewrite the prompt from the mechanism, submit, arm the monitor at the new job's ETA, and open the card from the collect wake — then say in the issue comment that the brief's budget line was overruled and why. The same arithmetic runs in the other direction: when the defect is small and the section's beat still reads, a brief that asks for yet another render is the line to overrule, and the attempt ships with the residual named.

## When Prompt Fixes Fail — Escalation After 3 Rounds

Some model behaviors persist despite explicit negative prompt instructions. The Ideogram model, for example, consistently adds colorful abstract overlays (geometric shapes, browser-logo-like patterns, multi-color blobs) to the top-left corner of frames, even when the prompt explicitly bans colorful overlays, browser logos, and abstract graphic shapes, and even when the background element's bbox spans the full frame (y=0 to y=1000) to eliminate bare regions.

**Signals that a defect is a persistent model behavior rather than a prompt phrasing issue:**
- The same defect appears in all three renders (original + 2 re-renders) despite different prompt wording
- The defect occupies the same region (e.g., top-left corner) in every render
- Adding explicit negative constraints to both `high_level_description` and the background element's `desc` does not reduce the defect
- The defect is a specific visual pattern (colorful geometric shapes, browser-logo-like patterns) rather than a general quality issue

**When to escalate:** After 3 rounds with the same defect persisting, do NOT render again. Instead:
1. Open a saved `ask_user_questions` interaction on the card: `resolverPolicy: "human_only"`, `continuationPolicy: "wake_assignee"`, one text question, and the card set to `in_review`. **A comment is not a waiting path.** The board re-parks an issue that sits `in_progress` with no monitor and no pending interaction, so the card loses the work and the escalation has to be redone. The interaction is what brings you back; the comment is only the evidence.
2. In the question, name all three attempts and their job IDs, describe what the prompt tried and what the model still produced, and offer the alternatives: change the composition to remove the artifact-prone region, try the other engine, or accept the overlay as a decorative element.
3. Retain the pattern to Hindsight with tags `taste`, `verdict`, `re-render-failure`.

**Two different escalations, and they are not interchangeable.** The ceiling case above is the 3-round limit running out with a slot still unapproved, and it is a question for Wojtek about what to change. The concept case below is a question for the post's author about what the picture should carry, and it is a child issue with a blocker. **Read the reason to tell them apart: a reason that names the concept, says the image must be completely new, or says to ask the post's author is the author's case, and it is handled on the round it arrives rather than after three rounds.** When the reason only says the image is wrong, take it to Wojtek. The author hand-off is the stronger shape, because the concept question belongs to the person who wrote the post, and a child issue with a blocker is a wake path while a question card on the card is one more thing to keep alive.

The 3-round limit exists precisely for this case: prompt engineering has diminishing returns against persistent model behaviors, and Wojtek's judgment on whether to accept the defect or change approach is the right next step.

**The stop signal is often rotation rather than persistence, and it arrives before the third round.** A slot can fail five renders without ever repeating a defect: each attempt clears the clause the last one broke and introduces one new small wrong thing — a head joined to a torso, then a head over the box with a headless body, then a head alone, then a duplicated pot, then a second cord the brief says must not exist. Every one of those is a new sentence in the record, so "the same defect" never fires and the run keeps feeling one fix from done. **Count attempts, not identical defects:** when two consecutive renders answer their predecessor and break something new, the composition has more joints than the engine can hold at that scale, and the next render is a coin flip rather than an iteration. Change what the picture contains (delete the prop, take the figure out, tighten the camera) instead of re-describing it, and if the picture is already a stripped-down composition, stop rendering.

**On a card whose only remaining slot has nothing shippable, no verdict card goes up.** A blank item or one you would hold back hands the judge a decision with no picture behind it, and a card he cannot rule on is worse than a question. The shape that works:

1. Upload the best held-back attempt **to the card issue** and link it with a comment carrying `attachmentIds` — verify a non-null `issueCommentId` on the read-back. It is evidence, not a card, and the thread now has the picture he is choosing about.
2. Post `ask_user_questions` (`resolverPolicy: human_only`, `continuationPolicy: wake_assignee`, one `single_select` question with `customAnswer` enabled) offering three concrete routes with a recommendation: **one more render with the specific fix named**, **ship this attempt with the flaws named on the record**, or **drop the picture from the section**. Vague "what should I change" wastes the ask; each route has to be a thing you will do the moment he picks it.
3. Set the issue `in_review`. The pending question is the waiting path, and no monitor goes with it.

**Say in the question what the attempts have in common and what they keep breaking** — the count, the class and the two routes in one or two sentences — because that is the information he cannot get from the picture itself, and it is what makes the answer cheap for him. Then do what he picks and put the outcome in the closing comment; a route he chose is not a plan to re-open. **And offer the render route as neither the cheapest nor the default: an owner who has watched a slot fail repeatedly may still take it, because he would rather see one more picture than ship or drop one. Reading that answer as licence for an open-ended render chain is the mistake; the stopping deal is what makes it one render.**

**When the stopping deal comes due, the closeout has its own shape and it is not a failure report.** No picture ships, and every durable artifact still has to be right:

- **The held-back attempt gets a record like any other**, `verdict: "rejected"`, the defect named in the row, `superseded_by: null`, `asset: null`, and the prompt block byte-identical to the file that rendered it. A slot with seven attempts has seven records; leaving the last one unrecorded makes the library end on the picture before the failure.
- **Nothing is copied into the vault and no embed changes.** The post keeps whatever it pointed at, even when that is the round-1 file the owner rejected — the state is honest and the decision is not yours.
- **Release the post in the queue** with `card-done <n>` (a post sitting in `rendering` with nothing in flight is the state this closes), confirm it reads `done`, and do not call `next` — a batch card never held the slot.
- **The closing comment is the whole set, in a table, in order**, one row per attempt (job id, what it drew, who held it back), then two short sections: what actually shipped on the post, and what the draft still carries. That last one names the open item plainly — the file the draft points at, the alt text in front of it, and the one-line edit you will make if he says so — because it is the only place a reader will find the slot's real state.
- **Post a row for the post on the runner** rather than trying to PUT its queue document: the card's run does not hold the runner's checkout, and the row is what the document is rebuilt from.
- **Count the attempts before you write the number down.** The comment says how many renders the slot cost, and it is the sentence a reader checks against the record list; a table of seven under a heading that says six reads as sloppy in the one place the audit lives.

**A one-more-render route is only worth asking for with the stopping deal attached, and the deal is stated before he picks.** Put it in the comment that submits the render: if this one comes back with the same class of defect, the slot ships nothing, the card closes with every attempt named, and the draft's next state is his decision — not a second question card. That sentence is what keeps a third ask off his desk, and it is also what makes the render a decision he has already approved rather than a hope you will report back on.

**Then aim that one render at the mechanism the defect comes from, not at the adjective that describes it.** A cable that arcs off the bench because the plug sits high on the case is fixed by moving the socket down to bench height and saying the cable runs level into it — the arc was geometry, and no amount of "lies flat, never rises" moved it. Read the last render's defect as a question about where a part is or how many of a thing the frame holds, and change that number or that position; only when the defect is genuinely wording does another sentence help.

**An inventory clause clears a duplicated prop but not a line running along a surface.** Stating the frame's count of long thin things and what the bench around them holds is the right fix for a prop that came back twice (a second plant, a second pot), and on that slot it did clear the plant. It did **not** clear the cable: the next prompt carried the count statement in both the high-level description and the cable's own element, and the render still returned a second thin cord behind the main one, plus the same arc. **A surface with a long thin thing on it is where the model invents a second line, and a number in the prose is not what stops it.** When a cable comes back doubled, change what the frame holds: put the plug and the socket at one end of a short visible run, or drop the cable run entirely and let the seated plug carry the beat — the receptacle and its plug read as the connection without a metre of cord to lay down. Two renders on the same slot failing on the same line is the point to take the line out, not to re-count it.

**The inverse is the commoner case, and it is not an escalation: praise plus one named defect is a targeted fix.** When the reason opens by approving the picture and then names a single defect class — the lettering is unreadable, the bar along the bottom does not fit — his verdict has already told you the composition is right, so the re-render keeps the scene and changes only that thing. An offer attached to such a reason ("ask the author if you need more context") is conditional: it licenses the hand-off, it does not order it, and blocking a slot he is waiting on to ask a question the reason did not pose costs him a whole round. Escalate when the reason questions the picture's idea; fix the prop when it questions the picture's craft.

**A reason that names the concept is the escalation instruction, and it does not wait for round 3.** The 3-round limit is a ceiling, not a schedule: a verdict that says the image must be completely new, that the picture has no sense, or that it must be checked with the post's author has already settled the question, and spending another render on it is spending 21 minutes on a concept the verdict overruled. So read the reason for the instruction it carries, not only for the defect it names: "ask Florian what this should show" and "introduce completely new image" are both escalation orders, and they are followed on the round they arrive. The author hand-off below is the shape they take.

**Before you park a slot on the author, check that the author can answer.** `GET /api/companies/{companyId}/agents` carries every agent's `status`, and an author whose adapter sits in `error` cannot pick the issue up — so the hand-off becomes a card blocked on a question nobody will read, with no render behind it. When that is the state, do not escalate into it: spend the next attempt yourself on the clause, changing what the picture *contains* rather than the wording around it, and say plainly in the issue comment that the hand-off was skipped and why, plus that the attempt after this one is the owner's decision rather than a second hand-off. Checking the recipient is one call; discovering it after the card is blocked costs a wake and a render.

**On an author-escalated slot, the count of renders spent before the answer lands is zero — including "just in case" attempts.** The temptation on a rejected slot is to submit one better attempt while the question is out, so something is moving. Do not: a render submitted before the author answers is a render of the concept the verdict already overruled, and it will be held back or, worse, shown to him as if it answered his reason. A slot that spent five renders across three rounds had two of them submitted in exactly that window, both held back, and the author's answer then shipped a working picture first time within the hour. The order is: ask, wait, render once from the answer. If the slot must show progress meanwhile, the progress is the hand-off issue, not a render.

**When the answer names another person, hand the question to the post's author as a blocker, not as a comment.** The direction that comes back is often "ask the blog writer what this picture should actually show", because a persistent model artifact is a sign the concept is underspecified, and the person who wrote the post is the one who knows what it should carry. That hand-off has its own shape, and getting it wrong leaves the card parked again:
- Create a child issue of the card assigned to the post's author, with a self-contained description: the post's path, the section, the rejection reason verbatim, what the current prompt describes, and exactly what is being asked for (the idea, the props, the one action, the text, the alt text). The author cannot read your card, so the description carries everything.
- Set the card's `blockedByIssueIds` to that issue and the card to `blocked` — **unless another slot on the same card still has a render in flight.** A blocker on a real issue is otherwise the cleanest waiting path: when the author finishes, the blocker resolves and the card wakes, where an `in_review` card with no pending interaction does not. **The exception is a card with renders still running, and it is not optional:** the server refuses a status write to `in_progress` while a `blockedByIssueIds` entry is unresolved (`422 Issue is blocked by unresolved blockers`), and `blocked` disables the render monitor, so no disposition is both blocked and monitored. In that case create the author's issue as a **child of the card** and leave the card `in_progress` with its render monitor — a child that reaches `done` fires `issue_children_completed` on the card's assignee, which is the same wake the blocker would have produced. Name the child issue in the handoff draft and in the queue note, because a round that closes on the monitor wake otherwise looks complete with a slot missing. `references/disposition-repair.md` carries the longer form.
- Then render from the answer and put the render on the next round's card, with the author credited in the card's long note.
- **Ask the author about prose defects in the same hand-off.** A review card may not edit a post, so a stale alt text can only be reported, never fixed — but the post's author owns the draft and can edit it. The alt text is part of the image question anyway: it has to describe the picture the render ships. **Then re-read the post before reporting those defects as still open:** an author who owns the draft often closes them in the same run — every alt text rewritten and an embed re-homed into the section the picture actually illustrates — and a defect he has already fixed needs no go-ahead and must not be "fixed" a second time from the card. **An author often closes the library side too, not only the draft** — a provenance defect reported on the card (a `## Why` quoting the section after the image) is his to patch in `3-resources/image-library/`, and he may do it in the same answer. So re-read each record's `## Why` before repeating that defect as still open in the round-2 brief or the closing comment, and say in the comment that the author closed it, so a later reader does not go looking for work that is done. Verify the replacement quote really is the right section; the record edit is not yours to make, but the check is.
- The author's answer is often a **composition**, not a prop patch: "head-on, no perspective, both doorways cropped by the top edge, a described prop in every corner". That is the shape that fixes a corner artifact, and it is worth asking for explicitly — the question should offer the composition as one of the things wanted, not only the idea.
- **The author's answer is a starting point for the prompt, not the finished prompt.** An author solves the picture; the engine still gets the last word, so apply the engine's own rules to what came back and say what you changed:
  - **Drop the `color_palette` array** unless the render is known to be safe with it. The array is the trigger for a rendered swatch strip (#34), and a composition with a wide horizontal band is where that strip lands (#34a). The series look survives through `aesthetics`, `lighting` and `art_style`.
  - **Give every bare region of the frame described diegetic content.** A wall the author's composition left empty is an invitation to paste something into it (#32, #59). Say so in the issue comment — the author can fill it, and the picture is his.
  - **Lint the prompt and audit the bboxes** as usual. An author's JSON can carry a transposed box, and `lint` cannot see one (#61). **A prop the brief places twice takes one element each** — two windows either side of a door cannot be one `desc` reading "two of them, one either side of the centre line" inside a box that covers one half, because the checker reports the contradiction and the model obeys the box rather than the words. **And keep a shape adjective on the element whose own box has that shape:** `narrow` in a desc whose box is 480x940 is flagged, and the repair is to drop the adjective, not to shrink the box to fit it.
  - **When the composition arrives as a table rather than as JSON, transcribe the boxes and then verify the transcription mechanically.** An author writes the element set as a markdown table of `[y1, x1, y2, x2]` numbers, and every one of them has to reach the prompt unchanged. A digit read wrong or a row skipped passes both `lint` and `check-bboxes.py`, because the file you wrote is internally consistent — and the render then places an element where nobody asked for it. Extract the arrays from the answer with a regex over the table rows, load the prompt JSON, and compare the two lists element by element; it is ten lines and it is the only check that proves the boxes in the file are the ones the author wrote.
  - **When the author delivers the finished prompts, extract them out of his document instead of retyping them.** An answer often arrives as an issue document whose fenced `json` blocks *are* the prompts, one per slot, with the intended file name in the heading above each block. Write the body to a file (`GET /issues/<id>/documents/<key>`, then `jq -j '.body'`), pull each block with a regex over the heading, the ` ```json ` fence and the closing fence, and write them straight to `backlog/prompts/<post number>-<slot>-r<k>.json` — **prefix the post number, because the prompts directory is shared by every post and a bare `header-r2.json` already belongs to some other post's round 2.** The write that would replace it is refused, and forcing it would leave that post's record `## Prompt` pointing at a different picture. The render's `--name` stays the card's item id; the prefix rides the file only. A retyped prompt is a prompt nobody wrote, and the difference is one box you will not notice. **Then run the checks yourself even when the author reports them as passing** — `lint` for risk and flagged terms, `check-bboxes.py` for a transposed box, and the lettering sweep over every noun that could carry type. His numbers describe his copies; the file you submit is yours, and the render answers to the file. `scripts/extract-author-prompts.py <doc.md> --out-dir ~/image-studio/backlog/prompts --prefix <post number> --round <k>` does the extraction and the box comparison in one command: it writes every fenced block under a `### `<slot>.json`` heading, names each file `<post>-<slot>-r<k>.json`, compares each element's `bbox` against that slot's markdown table row by row, and exits non-zero on invalid JSON, a missing table or any mismatch — so a skipped row fails there instead of on a card.
  - **His prompt can still carry the noun that invites the defect, so write a standby beside it rather than editing his text.** A composition that describes a prop as "the shape of a flat computer screen frame" has named a screen inside a positive description, which is exactly what the model draws (§4 above). Do not rewrite the prompt the author owns over a risk that may not materialise: submit it as written, and put the corrected variant in `<slot>-r<k>b.json` — that noun reworded to a physical shape ("a shallow rectangular frame") and the negative clauses that named it dropped, because a ban naming the shape is the same instruction (§2). File it, do not submit it; if the render comes back carrying that defect, the standby is the silent re-render and it costs no round.
  - **One figure, one prop, one action** still holds on someone else's concept (#47, #48), and a count clause in the description does not fix a duplicated figure — the layout does (#50). **Worse, a count clause written as a prohibition is what produces the duplicate.** `no second person, no twin, no duplicate of the same character, no copy of him anywhere in the frame` on a one-figure prompt came back with two identical men on two consecutive attempts, and the attempt carrying three such clauses was the worse of the two; the words naming the unwanted figure are read as an instruction to draw it, exactly as a ban naming a shape is (#62, #70). State the cast **positively and once** — `he is the whole subject of the shot and the pavement at his feet is bare` — and change the composition so a duplicate has nowhere to stand: a tight portrait from the knees up leaves no room for a second figure where a full-length figure on an empty walkway leaves plenty. **Two attempts of the same defect is the point to stop re-describing and change the shot**, and if the shot has changed and the duplicate survives that too, it is the concept's problem rather than the prompt's.
- **The author's answer is not a licence to skip the engine's rules on the props.** The author's composition is written in the language of the scene, not of the prompt, so it can name a prop that invites writing — a scale, a dial face, a plaque, a label — in the middle of a scene that is otherwise free of them. Translate the answer into a prompt the engine can draw: a measurement scale becomes a jar of liquid with a visible level, a labelled panel becomes a blank surface with a described mark, a readout becomes a physical object. The author's answer fixes the concept; the prompt still has to be one the model can render without inventing characters.
- **Ask the author for the constraint as well as the composition, and put it in the hand-off question.** The reason the previous render failed is usually a property of the *scene* the prompt described — too many surfaces that look like they want writing — and the author has to hear that to avoid proposing the same class of scene. Name the defect in the hand-off description in terms of the constraint it implies: "no screens, plaques, labels, dials, signs, tapes or numbers anywhere; one figure, one prop, one action", plus the specific prop-count and foreground-size problems the last render had. The author also has to know the series look the picture must match, because a composition that does not fit the series fails on a different axis. **Ask for his pass/fail list too, and say that you want it as questions you can answer on a crop.** An author who has thought about the engine writes the conditions he would judge his own composition by — does either key float, is the inserted key visibly in the hole, does the bottom-right corner read as hair and jaw rather than a slab — and those arrive as the most useful part of the answer: each one is checkable on a disk crop, so the self-check becomes condition-by-condition instead of an impression, the card's note can answer them in order, and his own fallback line ("if the corner reads as a slab, drop the shoulder and lower the camera") is the first thing to try on a silent re-render. It costs one sentence in the hand-off and it is the difference between a check you invent and a check the picture's designer already wrote.
- **The hand-off can be answered inside the same run — read the issue back before you end the run.** The author is an agent on the same board and a self-contained question can be answered within minutes, and the answer can arrive before your run ends. **Read the hand-off issue back after creating it**: if it is already `done`, its answer is waiting, and the card must not be left `blocked` on a resolved blocker, because the resolution wake has already fired and the card will never be woken by it. Take the answer, write the prompt from it, submit the render, and schedule the monitor in the same run. **A later pointer comment can name a comment id you did not read, and the ids on an issue are not stable across an edit** — fetch the id the pointer names and diff its body against the text you built the prompt from. When the only difference is cosmetic (a formatting marker in a notes line), the prompt stands and the issue comment says so with the boxes quoted; when a number differs, the composition changed and the prompt follows the newer text. Do not settle it by id equality, and do not rebuild the prompt on a suspicion. **And the deliverable may not be in the thread at all — read every comment, not just the status, and follow any path one of them names.** An author whose own write to the board was stopped by an approval guard says so in a comment and leaves the work on disk instead, so the answer arrives as a file path: a concept note and a prompt JSON that the card's run has to read, lint and audit itself. Read the comments **newest-first and then the older ones too**, because the short successful summary can sit above the longer comment that carries the paths and the reasoning. **A child-completion wake delivers only a truncated summary of the answer, so never build the prompt from the wake payload.** The `issue_children_completed` payload carries the child's closing message cut off mid-sentence, with the composition and the prop detail in the part that was dropped, and the full answer sits in the child's issue document (`GET /issues/<child id>/documents/<key>`, then `jq -j '.body'`). One read of the document replaces a prompt guessed from the visible fragment, and the fragment is convincing enough that guessing from it looks like reading.
- **That completion wake can also land after the run that already consumed the answer, and then it is a duplicate, not new work.** The child reaching `done` fires `issue_children_completed` on the card, and when the answer was taken inside the run that created the hand-off, the wake arrives afterwards with nothing left to do. It looks exactly like the call to start the round, so read live state before anything else: `imagegen status` on each job of the round, the card's `monitorNextCheckAt`, and the post's state in the queue. A monitor already armed and jobs `pending` or `running` mean the collection is scheduled; a post in `rendering` with the round's queue entry dropped means the release already happened. When that is the state, submit nothing — a re-submission is another hour of the worker for pictures already queued, and the slot then carries attempts nobody asked for. Spend the window on work that does not depend on a render existing (the draft half of the hand-off brief, the standby prompts, the pre-checks) and end the run.
- **When the answer lands on a `blocked` card, the resume write must clear the blocker and arm the monitor in one PATCH.** A `blocked` issue can never fire an issue monitor, and a `blockedByIssueIds` entry that still names the hand-off issue answers `422 Issue is blocked by unresolved blockers` on a status write — so the single write that restarts the round carries all three parts: `blockedByIssueIds: []`, `"status": "in_progress"`, and `executionPolicy.monitor.nextCheckAt` at the last job's ETA plus five. Read the response back and require all four: `blockedBy` empty, `status` `in_progress`, `monitorNextCheckAt` non-null, `assigneeUserId` null. A resolved blocker is not a cleared one — the child reaching `done` fires the wake, it does not edit the card's own array.
- **A multi-slot submission waits for its last job, and the last job is the slow one.** `eta_minutes` already includes `queue_ahead`, and on the shared worker other agents' jobs sit in front of yours, so the number reads in the hundreds rather than the ~21 minutes an empty queue gives. Monitor at the last job's ETA plus five when that is under about two hours out. A `nextCheckAt` several hours into the future is silently dropped by the board, and a dropped monitor collects nothing at all, so when the queue depth pushes the ETA hours away arm a **2 h hop** instead (`nextCheckAt` = now + 2 h), keep the issue `in_progress`, and re-arm at each wake; a hop that fetches nothing is cheap, while a dropped long monitor is a render nobody collects. Say the queue depth in the comment so a card whose monitor sits hours out reads as queued, not stalled.
- **The author's alt text is the one that goes into the draft.** When the author writes the caption for the picture, it is his line, not yours, and the re-render's bookkeeping carries it verbatim. If the asset has to be renamed, tell the author and let him move his own line rather than editing the same embed from two sides — two writers on one line is how the draft ends up with a caption that describes neither picture.
- **The conditions the author names become the card's check note, and they are proxies for the beat rather than pass/fail gates of their own.** An answer usually ends with two or three things that can be measured on a crop — "the collar sits flush, the slot is hidden behind it, the collar breaks the target's outline". Check the render against exactly those on a disk crop, and answer them condition by condition in the card's note. **A render that clears the defect the author was fixing and misses one condition narrowly is a ship with the residual named, not a hold** — a recessed port still visible around a plug that is visibly in the laptop reads as a plugged-in cable, which is what the conditions existed to guarantee. Hold only when the miss means the picture says the wrong thing — and a picture that has lost the composition's single action is exactly that case. A render that clears the rejection's own clause can still be a hold: one that carries no lettering at all, as the reason demanded, came back with the figure working the wrong prop — a pipe wrench on a threaded coupling where the prompt asked for a plug pressed flat onto the open mouth of the one dry spigot — plus five uniform open taps where the composition needed three sealed and one open, and a trough holding water where the beat needed it empty. Every prop was present and the picture said nothing the section says, so it is the silent re-render and not a ship with a caveat, however clean it is on the clause he named. **Clearing the reason is a necessary condition, never the acceptance test**: the fresh inventory has to find the one verb of the composition still happening, in the direction the prompt asked for. And do not round a failed condition up to clean: the card says which condition held, which did not, and what the file actually shows, because the note is frozen where Wojtek judges it.

#### A shared reason that names the look is a brief for the whole card, not an indictment of the prompting

A reason repeated on every item can be two different things, and the first line tells them apart. If it opens by liking the picture and then names **register, grain, palette, cast or lettering**, it is a style brief: the idea landed and the finish did not. If it says the picture makes no sense, that the prompts must be rebuilt, or that the author should be asked, it is the concept case below. **A style brief is the "praise plus one named defect" shape applied to every slot at once**, so no author hand-off is owed and no composition is rebuilt — the same scenes are re-described in the wanted finish.

- **Rewrite every slot of the post in one pass, and the sibling prompts of the same template family with them.** A look is a property of the template the prompts were written from, not of one slot, so a card that rejects three images for the same six clauses has three prompts carrying the same six traits.
- **The clause list is usually already mapped.** Check `references/1990s-anime-style.md` and `references/style-and-companions.md` before writing anything: a register-and-cast reason that has been given once is recorded there clause by clause, and re-deriving the mapping costs a run.
- **When the same reason also asks for a comparison engine, the round ships pairs**, and that is what sets the batch: three slots times two engines is the six-render cap, the companions go into the queue first because they clear in minutes, and the monitor sits on the last job's ETA plus five. The next card carries two items per slot, because one card item holds one attachment.
- **The wake's order is fixed:** apply every record's `rejected` row first, reason verbatim; then rewrite the prompts; then the gates (`lint` risk 0, `check-bboxes.py`, the lettering sweep, and a `wc -w` on each flux file so the negative tail survives the encoder); then submit; then write the **draft** half of the handoff brief with the clause mapping and the approval bookkeeping; then `card-done <n> --rendering` with the monitor, then Advance. The round's own card is created by the monitor wake from the ready queue, not here.
- **Do not answer it by re-showing the same files.** A style reason takes the draft's images out of the show bar, so the next card carries renders. A round-2 card that re-posts the rejected PNGs spends his attention on pictures the reason already ruled on.

#### A card whose every item carries one shared concept reason

A single reason covering **every** item on a card — "no sense, very poor prompting, recreate prompts from beginning, ask the author for more context" — is one verdict about the prompting as a class, and it changes the shape of the escalation in five ways:

- **One hand-off, not one per slot.** The reason is about the card, so one child issue of the card carries every slot as its own block; split it only when the slots genuinely need different people.
- **The records go first.** Every item still gets its own `rejected` row with the reason verbatim, before the hand-off issue exists. A record left at `unreviewed` while the card is in a conversation with the author is a library that disagrees with the card, and the record edits are seconds against a multi-slot wait.
- **Rebuild, do not patch.** A reason that indicts the prompting forbids starting from the rejected prompt's element list: the new prompt is written from the author's answer, and the old JSON survives only as the record's `## Prompt`, for provenance.
- **The hand-off answers the failures, so it carries a table of them.** Per slot: the section it sits under, what the old prompt asked for, and what actually came back. The author is answering against the pictures that failed; without that table he is guessing which part went wrong.
- **The post is not released, because nothing is in flight.** `card-done <n> --rendering` sets the post to `rendering` and frees the slot, and it is wrong here: the render count on every slot of that card is zero until the answer lands, so the post stays `card`, the card is `blocked` on the hand-off issue, and the release happens when the re-rendered slots are judged on their own card.

It also carries the prose defects the author owns and a review card may not fix — alt texts that describe nothing, an embed that sits a section early — because he is the one person who can close them without Wojtek's separate go-ahead.

**A mixed card takes the same shape, and the approval is booked before the hand-off exists.** Some items approved, the rest rejected with reasons that differ in wording but agree that the pictures make no sense: edit the approved item's record first, in the same pass as the rejections — it is seconds of work, and an approval left unapplied is one you have to re-verify later. Then one child issue covers **every** rejected slot as its own block. The reasons differ, and only some of them name the author, but they are one question about one post's pictures, and one blocker on the card is one wait where three is three. Name the approved slot in the hand-off as finished and untouchable, so the author does not spend his answer on it.

**Nothing is released while the hand-off is open, so the post stays `card`.** `card-done <n> --rendering` is for renders in flight; a card blocked on an author has none, and releasing it there is a post marked as re-rendering with nothing queued. The release happens in the run that actually submits the renders, once the answer is in and the prompts are validated.

#### Checking a rebuilt round: the author's kill list is necessary, not sufficient

The brief's kill list is the set of things the author knows will break his picture, so check it first — but it is not the whole of what gets judged. Run the library's own class rates over every rebuilt render as well, because a class with no approvals is a re-render whatever the brief did or did not name: a rebuilt roster frame cleared every rule in its brief (one figure, no lettering, both edges and all four corners filled, no pale band, no grey bars) and still carried three device tags where four were asked for and two bare hooks where one was meant, because the fourth hook's own backplate had a round cutout that stood in for its tag. That is `wrong-count`, 2 rejected / 0 approved, and it went back. The brief stated the constraint in prose — every device has a hook, one tag is off its hook — and never the arithmetic, so the count is the reviewer's job, not the author's.

**When the brief's composition cannot be drawn as written, move the target rather than the figure.** A composition that puts the figure in the left third and has him raise a tag toward a hook at the far right describes a reach nobody has. The idea survives moving the empty hook to the near end of the row, and that adaptation is the reviewer's to make and to say out loud on the card — an impossible gesture renders as a man holding a prop somewhere near some hooks, which is the "no sense" the rebuild existed to end.

### 3. Collage Artifact Defect (Colorful Abstract Overlays)

**Rejection Reason:** "top left corners are colorfur blobs which are not fitting general concept of image" or similar phrasing about colorful abstract shapes, pasted logos, or graphic overlays that don't belong in the scene.

**The ban is not the fix, and the composition is.** The negative clauses below are worth writing, but they are not what clears this defect: a prompt that named the shape in both places still came back with a green square, a blue square, a yellow circle and a red circle pasted over the corridor. The model puts a graphic in a region the composition leaves free, so the fix is to take the free region away and give it something — a crop that cuts the region out, a described prop in every corner, a head-on framing with no empty band. **Do the composition work in the same prompt as the ban, and if the defect is still there after the second attempt, stop and escalate** (the rule above) rather than writing a third ban.

**Prompt Fix:**
- **Add explicit negative constraints in TWO places:**
  - In `high_level_description`: "No colorful overlays, no browser logos, no abstract graphic shapes."
  - In the `background` element's `desc` (or the element covering the artifact region): "filling the entire canvas from the very top edge to the very bottom edge with no empty space, no colorful blobs, no browser logos, no abstract overlays, no graphic collage elements."

- **Fill the artifact region with diegetic content:** The model pastes overlays into bare frame edges. Ensure the background description and at least one element's bbox span the full frame (y=0 to y=1000) so no empty band exists for the model to fill with a collage artifact.

- **Remove `color_palette` if the artifact appears along an edge:** The palette array can render as a swatch strip (#33 in engine-pitfalls.md). If the collage artifact aligns with the top or bottom edge, drop `color_palette` and keep the series look through `aesthetics`, `lighting`, and `art_style` instead.

**Example:**
```json
"high_level_description": "A wide cinematic anime illustration... The frame is filled edge to edge with a pale wall corridor, wooden floor, and ceiling fixture. No colorful overlays, no browser logos, no abstract graphic shapes.",
"compositional_deconstruction": {
  "background": "An interior corridor with a pale wall filling the entire frame edge to edge with no empty space and no overlapping graphic elements.",
  "elements": [
    {
      "type": "obj",
      "bbox": [0, 0, 1000, 1000],
      "desc": "A corridor with a pale wall containing one wide open doorway and one narrow bolted door beside it, wooden floorboards below, filling the entire canvas from the very top edge to the very bottom edge with no empty space, no colorful blobs, no browser logos, no abstract overlays, no graphic collage elements."
    }
    ...
  ]
}
```

### 4. The prompt may be asking for the defect

Before rewriting the ban, search the prompt for the shape, the colour or the verb the rejection named. The cause of a "colourful artifacts with some letters on them" rejection can sit inside the positive description, and then every added prohibition is being applied to a picture the prompt still requested:

- One element read `two small red X marks drawn on the wood beside the hole`. A red X is a letter-shaped glyph, so the lettering he complained about was the element being obeyed. Delete the element; do not forbid lettering harder.
- The same prompt carried a `color_palette` array, and the colour artefacts were that array rendering as a band (#34). Dropping it is the remedy, and `aesthetics`, `lighting` and `art_style` carry the series look without it.

**A success symbol is a pasted sticker, so carry the win in the action and leave the mark out.** A prompt that asked for "a green checkmark above the switch" on a fixed-lever beat came back with a flat vector tick floating over the scene, sharing neither light nor outline with anything in it, while the figure's hands fused in the same render; the sibling prompt's "a diagram with a red X on the wrong path and a tick on the right one" came back as a flat chart laid behind the figure, whose chest emblem then read as a stray letter. A tick, a cross, an arrow, a badge or a diagram is a **graphic**, and the model lays a graphic on top of the picture instead of into it — so a mark can never be how a beat lands, however small it is. When the section's point is that something now works, draw the state instead of the verdict: the lever at the end of its throw with the machine's lamp lit, the door standing open, the queue moving, the figure's shoulders down — and say the panel's face is blank rather than letting a glyph do the talking. The same applies to a fix for a text-only rejection: the rejection asked for the writing out, not for something else to be drawn in its place, so the re-render answers it by removing surfaces and changing nothing about the action.

So the first pass over a rejected prompt is a **search, not a rewrite**: every described mark that is a glyph, every palette array, every prop whose face could carry words, and every negative clause that names one of them. A hit in the positive description is the defect itself; a hit in a ban is the cue to draw it. Both are deletions.

### 5. Draw the fault in the direction where it stays visible

When a picture has to show a mismatch between two things, which side is wrong decides whether the model can draw it at all. **A part too big for its hole covers the hole**, so a prompt asking for that shows a fit that is wrong with no evidence on screen — and the model, handed a beat it cannot draw, fills the empty surface with invented props: a second plank, a bracket, a mounting plate, a framed board, trestles. That inventory reads as slop and gets rejected as making no sense, and it is a symptom of an undrawable brief rather than a prop problem, so re-describing the props cannot clear it.

The same fault inverted is drawable: **a socket a size too wide for the block**, where the dark gap stays visible on both sides of the part. Ask of any mismatch you specify — after the model draws both parts, is the wrong still on screen? If one part hides it, invert which part is the wrong size instead of adding a prop that is supposed to reveal it.

### 6. A count asked as items inside a container does not survive the rebuild either

When a prompt has to say "four of these, out of ten", the count has to live in the prop's own structure, not in a heap of objects the model places. Post 038's round-1 header asked for "an open toolbox showing four plain tools" and came back with **five** — spanner, screwdriver, spirit level, hammer, pliers — because objects lying in a box have no boundary the model must respect, and the wrong count is `wrong-count`, a class with 2 rejected and 0 approved rows. The same post's allow-list asked for a book page whose grid held four clean tools among crossed-out ones; the crossed-out ones came back as invented glyphs, because a red X is a letter-shaped mark and a page grid is a writing surface (#55, #36 in `engine-pitfalls.md`).

**The rebuild that worked asked the count as holes:** a steel plate with exactly four holes in one row, three already holding a seated slug, the fourth in the figure's hand above the empty one. Holes are countable off the picture, the model cannot add a fifth without changing the prop's shape, and the plate's face invites nothing. **So give the four a container whose count is its own geometry — holes, pegs, notches, stalls — and leave the rejected rest out of the frame entirely rather than drawing them crossed out.** Verify the count on a crop before the card goes up: a full-frame read undercounts small repeated features and will happily report "four" or "five" from the same file.

### 7. A prop small enough to pinch is a grip the model cannot draw — take the hand out

A short round object held between thumb and forefinger is one of the model's least stable subjects. The failure is not the prop, it is the hand: renders come back with a fused palm carrying two thumbs and a bottom thumb that belongs to the other hand, a third arm growing out of the same wrist, or the prop duplicated and one copy floating in mid-air beside the fingers. That reads to him as "the arms are gone, it looks broken", which is a hard defect, not a quirk, so the attempt cannot go on a card.

**Re-describing the grip does not fix it.** Two attempts at the same beat — the first with a thumb-and-forefinger pinch, the second rewritten as a closed fist with the thumb laid over the folded fingers plus an explicit "exactly two arms and two hands, each drawn once, five fingers each" clause — both came back with broken hands, and the second was worse. A limb-count clause governs the figure's silhouette, not the geometry of a small grip, so it is not the remedy.

**The remedy is to remove the hand.** Stand the prop on its own base on the surface next to the thing it has to be compared against, keep the gap between them and the size mismatch that carries the joke, and drop the figure from the frame. An object-only composition cannot mangle a hand, and the beat survives because it was never about a person holding something — it was about two shapes that do not fit. Say it plainly in `high_level_description` ("no people at all, nobody in the picture and no hands anywhere") and put a described object in every corner so the vacated space is filled.

Two consequences to check before that frame goes on a card:

- **The prop's own proportion drifts once no hand sets its scale.** The thumb-sized cylinder in the object-only frame rendered as a tall standing post — measured at 67 px across and 476 px down a 1216x832 frame, a post rather than a peg — while the slot still read as too short for it. That is a deviation to name on the card, not a hold-back, because the mismatch the slot exists for is still legible; but measure the prop on a blob sweep (`crop-probe.py --find <r,g,b> --min-px <n>`) and put the two numbers in the note, or the card claims a peg that is a post.
- **A prop that needs to look machined gets its parts spelled.** The same render re-introduced the cartridge rim the first attempts had, because "short brass cylinder" leaves the ends to the model; "flat ends, no flange, no rim, no cap, no bullet shape" is the wording that keeps it a plain peg.

### 8. Two large props floating in the air have no action, so the model lays them out as a diagram

A prompt can name every object the section needs and still produce a flat vector mock-up — rows of icon chips, two numbered panels, two token key glyphs — with no person, no room and half the frame one flat fill. The cause is **contact**: nothing in the composition was touching anything. Two keys "drawn large in the air side by side" and a man "standing and looking up at them" is a comparison, and a comparison is a thing the model can only draw as a layout.

**Every large object in the prompt must be held, hanging from, screwed to, or standing on something else, and one of them must be acted on.** That is the rule a picture written from a section's information needs before it is a scene: the ring is gripped in a metal hand, the key is driven into a keyhole plate, the plate is screwed to a door, the door stands on a floor. Say the contact in the element descriptions rather than relying on the props being near each other in the bbox list, and state it once in the `high_level_description` as a property of the frame ("every large object in the frame is in physical contact with something else").

Two consequences for the review loop:

- **This is the author's question to answer, not a wording fix.** A slot that renders as a layout on two attempts is not a phrasing problem, so it escalates with the request for the **one action** spelled out: who does what to which prop. When the author's answer comes back with the diagnosis ("nothing was held, nothing touched anything, so there was no action to draw"), put that sentence in the handoff brief — it is the acceptance criterion for the render, because a picture that again shows isolated objects has failed whatever else it gets right.
- **A composition that arrives with contact also arrives with a camera,** and the two travel together: over-the-shoulder rather than head-on, because a head-on cabinet or crate is a rectangle and this model fills rectangles with panels and rows of small shapes.

### 9. A figure the prompt describes in 3D can render as a flat artwork on a surface

Flux (and Ideogram on a busy lane) sometimes draws a described 3D figure as a 2D picture lying on a desk or leaning against a wall — a watercolor painting of the robot, an artwork depicting the android — instead of a figure standing in the scene. It is the flat-panel class even though no panel was requested: the model collapsed the figure into a flat surface, and the render has no cast. Hold it back; the slot rides the other engine if that one passes. If both fail, silent re-render with the same prompt (the defect is usually engine-specific, not prompt-specific).

How to spot it on a read: the figure is described as "a painting of", "an artwork", "a drawing on the desk", "leaning against the wall" rather than "standing/walking in the scene". Confirm with a crop of the figure's region; a full-frame read that calls the whole frame "a photo of a printed illustration" is the medium-hallucination case in `references/vision-route-fallbacks.md` and is not by itself a defect.

## Validation

After revising the prompt, validate the new render against the original rejection reason:
1. **Check for the same defect:** Use `vision_analyze` to confirm the defect is resolved
2. **Compare each element:** Ensure every element mentioned in the rejection reason is addressed
3. **Verify the scene intent:** Confirm the overall composition and story beat are preserved
4. **Prove a colour-artefact rejection cleared with a sweep, not a read.** When the reason names a colour or a blob, the acceptance criterion is a measurement against the rejected render's own count: sweep the whole frame for that colour and put both numbers on the card. A render that cleared an amber blob measured **0 px** against **3958 px** on the rejected one, which is a claim a reader can check and a read is not. `scripts/crop-probe.py --find <r,g,b> --min-px <n>` does the sweep; the eye misses a small artefact and a read can invent one that is not there.
5. **A detail that was already in the rejected render is not what he rejected, so compare the old pixels before you hold the new one.** When the re-render carries a small quirk — dash marks where handwriting would go, a prop drawn slightly wrong — the first question is whether the same detail was in the picture he judged. Crop that region of the rejected PNG (the file is still in `tech_blog/assets/<date>/`) and compare: if it is there and his reason named something else, it is not his clause, and a render spent on it is a render on a defect he has already looked past. Ship it with the detail named in the item description and the next composition in one line, so a rejection costs him one click instead of a round. **The class rate decides a defect the render introduced; it does not overrule his own verdict on the same pixels** — a `0/8` class on a detail he saw and did not name is evidence about that detail, and the card note is where you both see it.

6. **Re-lint after any reword, and treat a flagged word as prose, not a scene problem.** `dead end` trips the violence filter on `dead`; the repair is the plain synonym (`leads nowhere`, `a blocked corridor`), not a change to the picture. Risk 0 has a mechanical cause — the linter scores a flagged term anywhere in the scanned fields — so swap the word and re-lint until it reads 0 before submitting.

## A prop held against the body fuses into it — separate the boxes, then re-close the contact

A figure holding a wide flat object against his chest comes back with the object and
the torso sharing **one continuous outline**: the prop's upper edge flows into his
shirt, the hands are ambiguous lumps on its face, and there is no boundary where the
object ends and he begins. At 1216x832 it reads as a man working at something; on a
1x crop of the figure and a 2x crop of the junction the fusion is unmistakable. He
rejects it as the figure not reading whole — the same complaint as "the main
character is cut in half" — so a fused prop is a hard defect, not a quirk: the action
the section needs is not legible.

**The cause is overlapping boxes, and the fix is to move the prop, not to reword the
grip.** When the prop's element and the figure's element claim the same region in
both axes, the model draws them as one mass. Seat the prop in its own box entirely
clear of the figure's, let one hand reach it at arm's length, put the other hand at
his hip, and say what is between them (`open air between his chest and it`). Same
scene, same action, same cast and palette — the staging changed.

**The audit before every submit:** for each prop a figure holds or leans on, compare
its `bbox` with the figure's `bbox`. Any overlap in both axes is this defect written
into the prompt.

**Separating the prop is half the fix, and the other half is re-closing the contact.**
The re-render that moved the prop into its own box and wrote "open air between his
chest and it" came back with the hand raised a hand's width from the module's face and
plain wall visible between the fingertips and it: the fusion was gone and so was the
action, and the frame read as a man gesturing at a machine rather than fitting one.
So when you separate, name the contact in the same sentence as the separation — which
hand, on which face of the prop, and that the metal and the hand meet (`the flat of
his left hand pressed on the front face, the gap between hand and metal at zero`) —
and keep the prop's box adjacent to the figure's rather than far from it. A prop with
open air on both sides of the hand has been moved out of the picture, not staged.

**One crop settles both questions.** The 2x junction crop answers "do they share one
continuous outline" and "does the hand reach the prop" in the same look, so run it
before the card goes up. A fusion is a hold-back and a silent re-render inside the
round; a short contact on a slot whose rejection clauses are all otherwise answered
is a ship with the residual named — state the render count and the next composition
in one line so a rejection costs him one click. The hold-back is for the frame that
has stopped showing the action at all; the ship is for the frame that shows it
weakly, because he is judging the picture, not your contact geometry.

## A defect that answers every wording change is geometry — read the boxes before the next rewrite

When several attempts in a row each fix the clause the last one broke and each comes
back with a new *placement* fault, stop editing prose and read the `bbox` values.
The model follows the boxes over the words, so a box written in the wrong axis order
is a silent layout instruction and no rewording can clear it (the full case is
engine-pitfalls #61). The tells that a placement fault is a box fault, not a
composition fault:

- **A figure drawn inside a surface** — the man inside the monitor's screen, framed by
  its bezel, when the words say "standing in front of the monitor". Overlapping boxes
  fuse the two elements into one mass.
- **A panel or checklist landing somewhere the words never put it** — the code boxes in
  a rectangle on the floor instead of inside the archway they belong to.
- **One scene in the words, several panels in the picture** — a white gutter across the
  middle, a hard vertical seam, a comic page.

Two minutes of arithmetic settles it before the submit: `scripts/check-bboxes.py`
prints every box as `y a-b (h), x c-d (w)` in the schema's `[y1, x1, y2, x2]` order,
so read each printed pair against the spatial words in that element's own `desc`.
A box authored from memory rather than copied from `templates/` is the usual cause of
the transpose — start from the template and overwrite the numbers, never the key order.
Then check the pair that matters most: **a figure's box must not share both axes with
the surface it stands in front of**, or the two will be drawn as one object.

## A companion animal in the frame leaks into the figure — take the animal out

A small animal element in the same prompt as the chibi figure produces crossover
features that survive rewording and both engines: the boy grows a tail, the fox grows
a third ear, the boy's feet detach, the animal's paws merge into his hand. Each render
breaks a different thing, so no rejection reason is ever "the same defect" and the
slot keeps feeling one fix from done (the rotation trap above). The overlap in feature
space — fur, tail, rounded paws, big eyes — is what the model blends, and a clause
like "no tail on the person" does not separate them.

**The fix is to drop the animal from that slot, not to describe it more carefully.**
One figure, one prop, one action still holds; a companion is a second character and
costs a joint the engine cannot hold at header scale. State the removal in the issue
comment and put the absence on the card as a caveat ("no fox in this frame — it kept
merging into him"), because a series character missing from one image is a deviation
he accepts, while a human with a fox tail is a frame he rejects.

## Two readers on one frame: the specific read wins

A full-frame `vision_analyze` read and a `scripts/vread.py` read of the same PNG can disagree on the whole style of the picture — one calling a cel scene a "photo of a printed illustration on a desk" with empty margins, the other calling it full-bleed with no defects. When they disagree, the read that names concrete evidence (a specific margin measurement, a specific prop, a specific count) wins over the read that redescribes the whole frame in a different style. A read that misidentifies the picture's medium (cel vs. photo-of-print) is unreliable on everything downstream of that, including its defect list. Settle the disagreement with a crop of the disputed element, or with the mechanical probes (`check-blank-margin.py`, `check-grey-bars.py`) for the margin claim, before holding a render back on the first read alone. Name in the check note which reader produced which claim and which one you trusted, so a later round can see the disagreement was settled and not inherited.

## A slot that dies twice is the engine, not the prompt

`sd-cli exited with code 1` with no stderr, twice on the same prompt, is a machine
failure and not a bad prompt. The tell is timing plus load: the job starts, samples
for a while (one attempt ran 18 minutes before dying), and another agent's `sd-cli`
or LM Studio is holding memory at the same moment. Check before the third attempt:

```bash
ssh m1max "memory_pressure | tail -2; ps aux | sort -k4 -rn | head -4"
```

Free memory under ~15% with large pageout counts means the next ideogram attempt will
die the same way, and a third submit only takes a queue slot from every other post.
Do not rewrite the prompt to fix an engine failure: the prompt was never read. Ship
the flux companion when it passes the bar, and write in the comment and the backlog
note that the ideogram route failed at engine level with the job ids, the run times
and the memory reading, so nobody mistakes it for a prompt defect later.

One shared serial queue serves every engine (`ideogram4`, `flux2-klein`,
`nanobanana`) on that machine, so `queue_ahead` is the whole backlog, not this
engine's: a flux job created after 34 pending ideogram jobs waits behind all of them.
Read the head of the queue in `jobs.db` before promising an ETA, and expect ~12h
behind a 40-deep queue even when single flux renders take two minutes.

## A surface named by its text-bearing kind draws the text even under a ban

A surface whose name is a text-bearing object ("stop sign", "label", "nameplate", "plaque", "screen", "clipboard", "board", "sign") invites the model to write on it even when the prompt says "no lettering" — the kind name is the invitation, and the ban only tells it what not to write, which it treats as a writing task. The result is readable "STOP" on a stop sign and garbled pseudo-text on "unmarked" boxes, both under an explicit no-lettering clause.

- **Do not name the surface by its text-bearing kind.** Describe the shape and the material instead: a "blank red octagon, solid flat red with no face detail, no border, no writing" rather than a "red octagonal stop sign, no lettering". The word "sign" is the trigger; remove it.
- **Describe every flat face that could host text as a non-writing surface.** A box described as "plain unmarked" still gets a label face; describe it as "a solid cube of one colour with painted wood grain, no flat label face, no face detail that could carry text". The flat face is the invitation; remove the face, not just the text.
- **A ban on the kind ("no stop sign text", "no labels") is still a kind name.** It fails the same way as the positive description. Replace both with the shape-and-material description above, and sweep the whole prompt for the kind noun (sign, label, plate, screen, board, clipboard) the same way the noun-sweep checks for removed props.
