# Bulk triage of the whole image library

Screening a library before a review round, and the show bar that decides what may be shown at all. A whole generation series can share one broken prompt template, so most of the list is derivable without looking at a single picture.

## The show bar

An image reaches a review card only if it passes all four clauses. This outranks the older round-1 habit of showing a draft's broken picture so a rejection costs him one click.

1. **The figure is correct** — two hands, two arms, one head, one person unless the prompt says otherwise. No three hands, no missing limb, no body that reads as broken. A count sentence in the prompt is not the count in the frame, so count heads on a read of the whole frame: a second copy of the same figure is drawn behind a large prop that could swallow a body (a crate, a bin, a pile of sheets) even when the prompt named one man, and it sits cropped by the prop or the frame edge, where it reads as scenery until it is counted. **A glossy surface beside the figure is the other way a second copy appears:** an open brushed-steel door, a mirror, a window over dark glass draws the man again inside it, and two readers will then agree the frame holds two figures while disagreeing about whether the second is a reflection or a second man. The count is the finding and the interpretation is not — two copies of the man is a hold-back whatever the second one is called, so the note says "two figures, the second inside the open door" instead of arguing about reflections.
2. **No colourful artifacts** — no flat panel, badge, tile, sticker, banner, notification card or swatch strip pasted over the painted scene; nothing drawn in a different idiom from the frame; no photograph with flat vector graphics laid over it.
3. **Text only if it is readable English** — `Racoiving`, `HelmRelest`, `H16`, `- 156` are defects, not quirks. A picture with no lettering at all is fine.
4. **The beat reads** — the prop the section names is present, the action points the right way, and the frame is one continuous scene.

A render that fails gets one silent re-render inside the same round, then the slot waits. It does not go on the card with the defect named.

**Settling clause 3 when `vision_analyze` is text-only.** A `vision_analyze` that answers "This API supports text input only" is not a reason to skip the show-bar text check: it is the route failing, not the picture. Run `scripts/vread.py IMAGE.png "One line: any misspelled or garbled text?" deepseek-v4.1-flash-1017-ds` on the full frame and `tesseract IMAGE.png stdout --psm 11` on the same file. Tesseract's output is the lettering evidence — a frame with no clean words passes, while one with `Racoiving`, `HelmRelest`, `locaI` or `noatation` fails clause 3. Settle the class with `scripts/verdict-class-rate.py`, and when it returns 0 rows for the class, grep the library's verdict rows for the relevant words (`grep -rhoiE "grey bar|empty margin|..." 3-resources/image-library`) before accepting the class as never-rejected — the keywords may have missed, not the history. The script's own 0-row message says the same; the grep is the faster first step.

**Settling clause 2 on literal marks: a mark is the pasted class a full-frame read most often calls scenery.** This is the frame that reports no flat panel at all — the read says "green checkmark symbols arranged on the rocky ground" or "red 429 badges scattered on the rocks" and passes them as painted detail, because a mark sits where a painted detail would sit. So the crop has to be triggered by the mark itself, not by a "flat panel" headline: crop the mark's own region (`crop-probe.py <png> --box <region> --scale 1.6 --out <scratch>/marks.png`) and ask the diegetic question on that crop, then confirm with a second reader on the same written crop (`scripts/vread.py`). A mark that casts no shadow, does not follow the surface's contours and shows no perspective is a flat paste whatever the first read called it, and the frame fails clause 2. One read is not the evidence; two independent readings calling it a pasted overlay is. The green-share number is the cross-check: a frame the whole-frame pass called clean that still counts a few percent green in one 2-3% blob is the banned hue concentrated in a pasted shape — an approved frame with no blob sits near 0.1-0.5% (`references/series-look.md`).

**The bar outranks a card description that says round 1 renders nothing.** A backlog-review card's own description carries the parent's older line — this is not an image request, do not render anything for round 1 except a missing image — and that line governs only a draft whose images already pass. Read every draft PNG against the four clauses before opening the card: when one fails, the slot is re-rendered as an ideogram + flux pair and the broken draft PNG never reaches the card, with the opening comment naming the slot, the defect and the job ids. Holding the check behind "round 1 renders nothing" is the habit he retired.

## A brief's table is a snapshot, so check the slot before you show it

A backlog brief is written when the post enters the queue, and it names the record and the job that existed then. By the time the card runs, another campaign can have replaced that post's image and had the replacement approved on its own card: the record the brief names then carries `superseded_by` pointing at the live job, and the file the draft embeds is the newer picture. Read every row against the library record and against the draft's own embed before the card goes up.

- **Put the file the draft actually embeds on the card, never the brief's.** Name the live record and its job id, and say in the comment that the brief's row is stale, so nobody reads the brief's job id as this round's work.
- **A replacement render that is already in staging is the card's picture, and the campaign that made it must not open a second card for the same post.** The nano banana campaign and a backlog card often reach one post in the same hour: the campaign submits a slot's new render, fetches it to `~/image-studio/staging/<date>/`, and has not carded it yet when the backlog card wakes. Read staging for the post's number before writing any prompt of your own — `ls ~/image-studio/staging/$(date -u +%F) | grep '^<nnn>-'` — and put those renders on the card, with the campaign's job ids, instead of re-rendering a slot that already has a picture. Then post one comment on the campaign issue saying which post's renders the card now carries and that the issue should not open its own card for that post, so he is not asked twice for one picture. A campaign prompt file with no PNG beside it is a spare, never submitted; it stays on disk and the card names it as such.
- **A slot he has already ruled on is not re-asked.** When the live file's record reads `verdict: "approved"` with his decision on another card, that row leaves the card: showing one file twice in a day asks him to click twice on one picture. Say on the issue which slot was skipped and where his verdict lives. When every row of the brief is in that state, no card is posted at all — the card issue closes with the finding, the record paths and the reason, and the queue note carries the same. **The brief's own count and the "one item per image, in brief order" line in Per post do not override this rule:** a brief that still lists the slot still lists it, and the card still drops it, so the card's item count will not match the brief's image count and that is correct. **A card that already went up with the skipped slot on it is withdrawn and rebuilt**, with the idempotency key suffixed `-corrected` (`verdicts:<issueId>:round-<k>-corrected`), and the issue comment names the skipped slot and where the verdict lives.
- **The rest of the brief still decides the card.** A skipped row does not relax the show bar for its neighbours: the remaining slots are read, and the failing ones re-rendered, exactly as if the brief had been fresh.

## Repair the prompt by removal, not by ban

- Drop the `color_palette` array — it renders as the swatch strip and nothing else depends on it.
- Delete literal marks (a red X, a green checkmark) and show the state instead: a bent part against a straight one, a dead lamp against a lit one.
- Take the text-inviting prop out of the hands — clipboard, label, plaque, screen, tablet, board, nameplate — and replace it with a plain object.
- **When the beat itself is the screen, the screen goes, not just its text.** "A monitor showing the list with two entries at the top" cannot be repaired by asking for a blank screen: a screen surface is what the model writes on, and it comes back full of pseudo-text whatever the prompt says. Carry the beat with a physical arrangement in the same order the list had — a vertical board or rail of identical plain objects with the newest two clipped at the very top and the rest dusted over — and say what the objects are made of and that their faces are blank. The prop carries the story; the monitor, if the room needs one, is turned side-on with its face away and dark.
- State the cast and the limbs, describe a prop in every corner, and end the description with the negative clause naming the shapes to keep out.
- **Name each limb and what it is doing, not just "two arms".** A stump or a third limb growing from the torso is drawn from an under-specified body, and it survives a ban on extra limbs: state the cast as a count plus a pose — "exactly two arms and two hands: his right arm is raised holding X, his left arm hangs down at his side with the hand on his knee, nothing else grows out of his body". The pose sentence is what removes the stump, because the model has no room left to invent an arm.
- **Describe every surface matte when a glossy prop stands beside the figure.** A steel cabinet door swung open, a window or a polished panel reflects him, and the render puts a second copy of the man inside it. The repair is not a ban on reflections — that hands the model a synonym to draw — but a scene where nothing can mirror: "every surface in the room is matte: bare plaster, painted steel, unwaxed wood", the doors "folded flat back against the cabinet's own sides as plain scuffed panels", and the cast stated as "he is the only person in the room and he appears once".
- **A shape mismatch has to be described hole by hole.** "The wrong part is in the slot" gives a tidy row of identical inserts and the beat is gone. Name the shapes in order and say where the empty space is: three round holes each holding a round disc flush, and one square hole holding a round disc, "so the four corners of the square hole stand open and empty around it". The empty corners ARE the picture; a part that fits hides the fault.
- **Write a consequence as a state already reached, not a motion in progress.** A second figure whose job is to be the *result* of the action — the machine knocked flat, the prop knocked over — comes back still standing with an expressive face when the prompt asks it to be *falling*: mid-motion is an instruction the model resolves by keeping the figure upright, and the beat then reads as two machines standing around a joint. Describe the end state with its contact points: "already down on the floor boards, its back and the side of its head on the boards, its legs kicked up, the wrench loose beside it", plus "it is a separate machine lying on the floor, not part of the standing one" so the two bodies are never merged into one. A pull gets the same treatment — "half of it already out of the socket" beats a hand on a plug that has not moved.
- **A prop in the hand is drawn a second time growing out of the body, so state the count of the prop.** A rod held in a mitt comes back with a second rod protruding from the chest plate, and the frame fails the figure clause without any extra limb being obvious at first read. Say it as "its right mitt holds one single iron rod … its whole front plate is plain, nothing protrudes from its chest, its back or its head", and settle the claim on a written crop of the torso before it decides anything.

## The pre-submit box check fails on one stray word

`scripts/check-bboxes.py` matches words, not meaning, so one adjective in a long `desc` can flag a box for an axis that box does not describe: "a faint wisp of dust lifting away from the vent", written inside a tall rack's description, trips the thin-axis check ("NARROW") on a 410x740 box that is correct. Reword the off-axis clause and keep the geometry. The same matcher flags the left/right words on a genuinely full-width prop — word that prop by its extent ("spanning the whole width of the wall across the middle band") and never "from the left of the frame to the right", which describes the box's own edges instead of the prop. It reads top/bottom/upper/lower as placement claims too: "each end's corner hangs past the bay's edge" passes where "its bottom corner hangs past" answers BOTTOM on a box that sits in the top half, so word a corner or an edge relative to the prop it belongs to and never to the frame. Move a box only when the prose it carries really places the prop somewhere else.

## The sweep

`scripts/audit-assets.py` walks every PNG under `tech_blog/assets/`, runs `check-grey-bars.py` and `check-palette-strip.py` on each, and writes a JSONL row per asset plus a per-post markdown table of the failures.

```bash
PY=/Users/paperclip/image-studio/.venv-imgcheck/bin/python
$PY ~/.hermes/profiles/matejko/skills/image-studio/scripts/audit-assets.py \
   --out ~/image-studio/backlog/audit/<run>-sweep.jsonl \
   --table ~/image-studio/backlog/audit/<run>-sweep-table.md
```

It prints a progress line every fifty frames and flushes each row, so a killed run still leaves a usable partial table. Keep both files: the table is what the next batch reads, the JSONL is what a later run re-derives it from without re-scanning.

## Joining an asset to its post

The library record is the join key, not the filename. Each record's frontmatter carries `asset:` — but it is spelled three ways across the library (`tech_blog/assets/2026-09-26/x.png`, `tech_blog/…`, `assets/…`) while a filesystem walk yields `2026-09-26/x.png`. **Strip every prefix (`tech_blog/assets/`, `tech_blog/`, `assets/`) before comparing, or the join silently matches nothing and the report says zero defects on a library full of them.** A record whose `superseded_by` is `null` is the live one for its slot; a superseded record points at an image the draft no longer carries, so count those separately rather than as work. **A superseded record is not closed by `superseded_by` alone.** Setting the pointer leaves the frontmatter at `verdict: "unreviewed"` with the back-fill line still under the Verdicts header, so the library reads as an image nobody judged while the draft has already moved past it — the tell is a pointer set beside an unreviewed verdict. Close it with the same three edits an approval makes (`scripts/approve_record.py <record> --rejected --issue <GUL-x> --reason "never shown: <the defect that kept it off a card>, replaced by <job id>"`): the verdict, one row, and the back-fill line deleted. Do it in the run that applied the approval, because the round that owned that record has usually closed by then and nobody else is coming for it.

## What the sweep can and cannot see

- **Can settle, no model needed:** grey bars (an empty band at the top or bottom) and a rendered `color_palette` strip along an edge. **A strip is only half-settled by the script, so crop the band it reports (its row range, full width, upscaled) and read it:** the model sometimes signs the strip, so one chip carries a word while its neighbours stay flat, and that strip fails clause 2 and clause 3 at once because it is a badge as much as a palette array. Quote the word verbatim in the check note beside the row range and the chip widths the script printed. **The rendered array does not always come back as colour chips.** A batch whose prompts carried a `color_palette` array plus a screen, label or calendar surface comes back with the array as a **dark caption bar across the bottom edge holding a whole pseudo-English sentence** — read by a full-frame pass as a letterbox border or a painted plinth — or as a floating UI panel with doodle arithmetic over the scene. Both are the same finding: `check-palette-strip.py` reports the band at flat-column percentages in the fifties with several hue groups, and the lettering is legible only on the upscaled crop of the reported rows, so crop and read it character by character before the note names the class. It fails clause 2 and clause 3 at once, and the repair is the array **and** the text-bearing prop, because deleting one of the two leaves the other to reproduce the bar. Depth is not a defence — a strip fifty rows deep on an 832-row frame is still the palette array rendered, and at that depth it looks like a border to a full-frame read. **The colour test does not clear a strip: a band whose hues also appear on props in the scene is still the array rendered.** SKILL.md step 6 lets a band whose colour matches a palette entry and is also painted on a described prop count as a prop, and that test fails on any scene with a strong house palette — a workshop with a blue machine, warm amber lamp light and a grey steel cabinet carries three of a six-entry array's hues in scenery, so every chip of the strip finds a prop to hide behind and the false clearance is easy to write down. Judge the shape instead: one row at the very edge, equal-width hard-edged blocks with no shading or perspective, and `check-palette-strip.py` reading 80%+ flat columns against a single-digit control band. A band with that shape is an artifact however many of its colours the scene happens to use, and the colour argument belongs in the note only as the weaker second piece of evidence.
- **Cannot settle:** three hands, a pasted panel with invented lettering, a photograph with vector graphics over it, a beat pointing the wrong way. Those need a read of the frame, or a crop on disk when one prop decides it.
- **Two readers on one disk crop settle a pasted-panel claim.** `vision_analyze` on a `crop-probe.py` crop, then `scripts/vread.py` on the same box with the same narrow question ("is there a flat UI card pasted over the scene; read its text verbatim"), returned the identical garbled strings twice on each of three images of one post — that agreement is the evidence, and one read is not. `check-defect-signature.py` corroborates it numerically: the two blue panels carried `blue_px` 154,465 and 129,861 against 12,092 on the same series' header, so a panel's own colour is where the count spikes.
- **When the two readers disagree about a count, the question was the defect, not the picture.** One reader called a 2x crop "three arms, a hand at the chest" on the same file where the other called it "2 hands, 2 arms, all traceable", and a question that offers the defect ("is there an extra arm?") gets the defect confirmed. Settle it in this order: re-ask **both** readers the same neutral wording on the **same written crop** ("how many hands, and can every arm be traced from a shoulder to its hand"); then crop the **seat** of the alleged extra limb at 6x and count there, because two hands side by side at 2x is one hand at 6x and what the model filled was the gap between a bent forearm and the prop's edge; then write the count both readers agree on into the note. A count you did not settle never goes on the card as a caveat.
- **A disagreement about WHAT a mark reads is not a disagreement about whether the defect exists.** Two readers gave the same flat decal as `C3` and as `83` on the same crop; the string is unsettleable and irrelevant, because clause 3 asks only whether the lettering is readable English and neither reading is. **The disagreement also comes from one reader at different scales**, which is the faster route on a small surface: a status readout on a prop screen, a plate on a machine, a sticker on a shelf, read at full frame and then on two crops at increasing zoom, answers with a different string each time — three strings from three zooms settles the surface as pseudo-text without resolving a glyph, so quote all three in the note and name the class. `tesseract <png> - --psm 11` on the native file corroborates, and one clean word beside the garbage (`Blog` out of a screen of invented characters) does not clear the surface: the test is whether the surface as a whole reads, not whether a word survives. Do not spend a third read chasing the exact glyphs and do not soften the finding to "unclear": quote both readings in the note and name the class. The same asymmetry runs the other way for a count — there the number IS the finding, so it must be settled before it goes on a card.
- **Attached to a wall is not the same as diegetic.** A flat shape with uniform fill, hard edges, no perspective and no cast shadow is a pasted sticker whether it floats in mid-air or sits flush on the painted wall, and a reader will call a wall-mounted one "a decal that belongs in the room". The idiom test decides, not the contact: if the frame's own drawing gives it no thickness, no light and no shadow, it is an overlay and the frame fails clause 2.
- **When a full-frame read reports "flat panels" or "UI cards", settle the diegetic-vs-pasted question before holding the frame.** A first read often names the shape as a flat panel, which sounds like a clause-2 failure, but the same read asked specifically "is this panel diegetic (part of the scene's architecture, with perspective, bevel, shading, ambient light) or pasted (drawn in a different idiom over the scene)?" can come back with the opposite answer. The idiom test is the deciding factor, not the first read's label, so ask the diegetic-vs-pasted question explicitly on a crop of the panel before the frame is held — a render with diegetic panels passes clause 2 even though a careless read of the same frame would flag it.
- **`check-flat-bands.py` is never part of the sweep's verdict.** It fires on virtually every cel-shaded frame — a full sweep returned a hit on all 566 assets — because flat colour blocks are the art style. It is a prompt to crop and look.
- **A keyword grep over the prompts is not a defect list either.** Counting `color_palette`, mark words and text-prop words across every record flags approved images at the same rate as broken ones, because a prompt that *bans* lettering contains the same nouns as one that asks for it. Use the prompt scan on a slot you are already looking at, and let the pixels decide.

## Reading the result

Group by post, worst first, and put every row into the repair queue with its slot id and record path. A frame that fails grey bars or a palette strip is a re-render, full stop — those two are the failures that never turn out to be intentional.

## Pace it

At most six renders per run (three slots × two engines), and one batch per run. Do not empty the board at once: withdrawing every open card means re-rendering everything behind them while the worker is already hours deep. Take the posts whose card sits closest to the review front, and say plainly in the issue comment which posts you did not touch and why — a decision he can overrule, stated where he reads it.

**When every slot of a draft fails, the slot is released at submit time, not held until the render lands.** A round-1 card whose whole image set fails the bar becomes a render round with no card, and the queue's single slot token is what every other post's card is waiting for: held for a deep-queue render it stops the entire backlog for as long as the queue takes, which on a shared worker has been most of a day. So `backlog.py note <n>` the failures and job ids, `backlog.py card-done <n> --rendering`, arm the monitor, and Advance; the renders' card is queued from `ready` at the collect wake and is still the post's round 1. The queue note is what the next run reads (queue.json), not the Paperclip comment — write both, but the note is the one that survives a fresh run. The exact order, the brief's wording for a card that shows nothing already in the draft, and the `ready` call are in `references/review-loop.md` §4 — follow that rather than inventing a slot-holding variant because no card was ever shown.

**Open the round-2 card yourself from the collect wake, and register it with `reopen-card` so the ready entry cannot become a second card.** Do not leave the brief sitting in `q["ready"]` for a later closeout to pop when the renders are already checked in hand: create the card issue directly (`POST /api/companies/<company>/issues`, `description` = the brief text, `parentId` = the runner issue — copy the parent and `projectId`/`projectWorkspaceId` off an earlier round-2 card — `assigneeAgentId` = you, `status` `todo`), then run `backlog.py ready <n> <k> <brief>` followed by `backlog.py reopen-card <n> <GUL-id> <k>`. `reopen-card` moves the entry from `ready` into `batch` and drops the ready entry in the same pass; skipping it leaves the round queued, and the moment the live slot frees `next` pops that entry into a second issue for the same round. Verify afterwards that `ready` no longer lists the post and `batch` names the new issue. Close the round-1 card issue `done` with a comment naming the new card; its own run uploads and shows the PNGs.

**A partial failure on a batch card ships the passing slots on a live round-1 card, and the post's queue state then stays `card`.** Because a batch card holds no slot, the ETA gate above decides only how long he waits, not whether another post's card waits. When the failed slots' ideograms are hours out (a shared queue read 842 minutes on post 153), post one card carrying the slots that pass, name every held slot in `detailsMarkdown` with its job ids, its defect class and its ETA, and leave the post's batch entry in place: its round-1 card *is* open, so `card` is the true state and `card-done <n> --rendering` would release a post whose card is still waiting on him. The renders need a wake path the card cannot give them, so arm the 2h hop monitor on the same issue with the four job ids in `notes` (500-character cap) and the collect action spelled out; the card's own verdict wake and the hop chain then both land on the same run, which applies the verdicts first and queues the held slots' round from `ready` with `backlog.py ready <n> <k> <brief>`. Mark the two held-back draft PNGs' records `rejected` in the same run with `"never shown: <the defect>; replaced by <job id>"` — a picture that will never reach a card must not sit at `verdict: "unreviewed"` while the renders are in flight, and the `superseded_by` pointer still lands only when the replacement is approved.

**When the round-1 verdict lands while the held slots' renders are still pending, apply the verdicts and retain first, then move the post to `rendering` and re-arm the monitor — but do not queue round 2 yet.** The verdict wake and the collect wake need not arrive together: Wojtek can answer the card hours before the ideograms finish. In that case the run (1) applies the verdicts to the passing slots' records and retains them to Hindsight, (2) `backlog.py card-done <n> --rendering` to drop the batch entry and set the post to `rendering`, (3) re-arms the 2h monitor hop for the still-pending renders, and (4) posts the comment. It does **not** write a round-2 brief or call `backlog.py ready` — there is nothing to queue yet, and the collect wake does that when the renders are done. The issue stays `in_review` across both waits; the monitor is the live path, and the card being answered does not close the issue while renders are in flight. When the verdict and the collects do land in the same run, apply verdicts first, then collect — the order matters because the records' `superseded_by` pointers for the held slots only resolve at approval time.

**On a batch card the all-fail round stops at `card-done <n> --rendering` — there is no slot and no Advance.** A batch card never holds the live slot and never calls `next`, so the "release the slot, then Advance" half of that order does not apply: `card-done <n> --rendering` drops the batch entry and sets the post to `rendering`, the monitor stays on the card issue, and the collect wake rebuilds the round through `backlog.py ready <n> <k> <brief>` then `batch-open-ready 1` + create + `batch-opened`. Keep a monitor armed on the issue across the whole wait; ending with the post in `rendering` and no live wake path is the stranded shape.

**A partial failure is the other case: hold the slot, but only while the last render is inside the hour.** When at least one slot of the draft passes the bar, the round still owes one card that carries every slot, so the passing image waits instead of going up alone — two cards for one post is what the one-card rule forbids, and a card with a third of the post on it is not the review the brief asked for. Gate the hold on the queue's own numbers: read `imagegen status <last job>` for the ETA, hold when it is under about an hour (two renders per failed slot, FLUX submitted first, usually lands inside it on a shallow queue), and release with `card-done <n> --rendering` plus the standard monitor hop when it is longer, because a slot held for a night stalls every other post's card. Either way the note and the opening comment name which slots failed the bar, why, and the job ids, so the round reads the same whether the card comes now or at the collect wake. **A hold that outlives its first hop is no longer a sub-hour hold:** when the collect wake fires and the last job is still running, re-arm once more, and on the wake after that release the slot with `card-done <n> --rendering` and queue the renders' card from `ready` — the estimate that justified holding has already been wrong once, and a second silent hour is the deep-queue stall the release rule exists to prevent.

## Render pairs and the queue

- Every regeneration goes twice: `--engine ideogram4` (main) and `--engine flux2-klein` (comparison), both items on the same card so he can compare per slot. FLUX also exposes a bad *concept* in three minutes, before 21 minutes go on the Ideogram render. The brief has an id only for the slot, so the ideogram keeps it and the companion takes `<slot>-flux` as its own item id and label, with its own attachment and its own description — one row per render on the card, the slot's record and asset chain following the ideogram whichever one he approves. **The two submits take different flags:** `imagegen submit --prompt-json <file>.json --engine ideogram4 --name <slot>-r1` for the main render, and `imagegen submit --prompt-file <file>.txt --engine flux2-klein --name <slot>-r1-flux` for the companion. Flux takes its natural-language text through `--prompt-file` (or `--prompt`); `--prompt-json` is the ideogram4 structured prompt and is not the flag for a `.txt`.
- Both engines share **one FIFO queue ordered by submit time, not by engine speed**. Submit the FLUX jobs first so they lead the batch, and compute the monitor from the *last* Ideogram's ETA plus five minutes. `queue_ahead` counts every pending job regardless of engine, so a 'fast' engine submitted behind fifteen Ideograms still waits hours.
- **`eta_minutes` is a static estimate, not a countdown.** The same number read twice means the job has not moved in the queue, not that it will land in that many minutes, and a running job can pass its estimate by ten minutes or more when the worker is slow. Set the monitor hop twenty to thirty minutes past the estimate so the wake does not fire on an unfinished job, and read a second job's estimate as the queue's position rather than its own speed.
- **A render cannot be waited out inside the wake.** A foreground wait is capped at a few minutes, so an Ideogram that needs twenty-one comes back as a failed sleep and an idle run, and two or three of those cost more than the collect would have. Do the half of the work that can be done early (the draft brief, the queue note, the reply to anything waiting on the thread), arm the monitor, and end the run; the collect belongs to that hop.
- **A sibling run's "do not spend a render" is only as fresh as its timestamp.** Another run of yours can write prompts for the same slot and post a hand-off asking you to hold, after your jobs are already submitted. Compare the comment's created time with the submit time before acting on it: when the renders are already in the queue, the message changes nothing about the spend. Answer on the issue thread both runs read — what is already submitted, which staged prompts are spares with nothing rendered from them, and a plain request that the other run not submit its own copy for that post. A staged prompt nobody rendered from is kept, never deleted, and named in the brief as the spare beside the renders that ship. **An outage claim in that hand-off is a point-in-time read too:** one `imagegen status` on your own job settles whether the worker is answering, and a run that reports a dead renderer while your jobs are running and fetching is reporting a moment that has passed.
- **The renderer's queue is shared with every sibling run, so the ETA you read is the queue's, not your job's.** When several card runs render in the same hour the queue can sit seventy-odd jobs deep and the last job's `eta_minutes` is a night away, not twenty-one minutes. Read it before promising anything: `imagegen status <last-job-id>` prints `queue_ahead` and `eta_minutes`, and those two numbers are the whole wait.
- **Size the queue from its own database, not from your job's number, when the answer changes the plan.** The jobs live on the generation host, and the local `~/image-studio/jobs.db` is not them:

  ```bash
  ssh m1max 'cd ~/git/ideogram4-local && python3 -c "
  import sqlite3; c=sqlite3.connect(\"jobs.db\"); cur=c.cursor()
  for r in cur.execute(\"SELECT status,engine,count(*) FROM jobs GROUP BY status,engine\"): print(r)"
  '
  ```

  The table is `jobs` and the state column is **`status`**, not `state` (`pending`, `running`, `done`, `failed`). It tells you whether your render is behind forty Ideograms or whether the queue is shallow and the worker stalled — two different problems with two different answers.
- **A long ETA is handled with short monitor hops, because one long `nextCheckAt` is silently dropped.** A monitor set many hours out does not come back at all; **two-hour hops persist**. So arm the issue monitor at now + 2h, and on every wake re-read `imagegen status` for each job and re-arm for another 2h until the jobs are `done`. Say in the issue comment that the watch is a hop chain and why, so the long wait does not read as a forgotten card.

**A collect wake that finds only some renders done fetches and checks those immediately, holds them, and re-arms for the rest.** Do not wait for all four before fetching the ones that are `done`: fetch each finished render to `~/image-studio/staging/<date>/` with `imagegen fetch <id> --dest <dir>`, run the show-bar checks (grey bars, palette strip, grain, vision read) on what you have, and note the result. The still-pending renders keep their monitor hop. When the last one lands, all checked renders go into the same round-2 brief and card — a partial collect that defers fetching until the end wastes a wake and risks losing the fetched file's path. The fetched renders that pass are candidates, not yet carded; the card opens only when the round is complete.
- **A pair is not all-or-nothing, so one held-back companion does not hold the card.** When the main render passes and the companion fails the show bar, post the card with the items that pass and name the missing companion in `detailsMarkdown` with its job id and the class that sank it. The slot's image is the deliverable and the companion is a comparison; parking five good renders for hours behind one cheap draft costs him a review day for nothing. Re-render the companion under the same slot with a `b` suffix (`<item id>-r1b-flux`) and keep it as the spare that rides the next round if he rejects the main render. Do not put the failed attempt on the card with its defect named. **This is the bar-failure case and it is not the deviation case:** a render that passes the bar and merely departs from the prompt in one prop ships with that departure named on the card, because his eye overrules your read. A render that fails a bar clause (a stump limb, invented lettering, a lost beat) never reaches a card at all, whatever it cost.
- **He can approve both rows of one pair, and the slot then owns two approved pictures.** The card asks him to approve one and reject the other, but approving both is allowed and he has done it, with no reason given. The ideogram still ships: vault copy under the slot's name, the one embed repointed, its record's `superseded_by` left `null`. The approved companion is neither promoted nor deleted — vault copy under `<item id>.png`, its own record chained to the shipped job, no second embed, because two pictures on one beat is a defect the post does not have. Say in the closing comment that the companion is an approved library copy and that a swap costs no render, so a later change of mind does not read as a new round. **Put what an approval of both rows means into the card's own legend before he clicks:** the approve/reject framing alone leaves the outcome to whoever closes the card, and a legend that names it costs one sentence.
**When the main render fails and the companion passes, the passing companion does not rescue the slot.** The ideogram is the engine that ships, so a companion that clears the bar still leaves the slot with no shippable image and the slot waits. **This holds even when the slot's previous image also failed the show bar:** a broken draft PNG being re-rendered does not make the companion the main render; the re-render's ideogram is still the one that has to pass. Re-render the **ideogram only**, once, under the same round with a `b` suffix (`<item id>-r1b`), and keep the already-fetched companion as the card's comparison item rather than spending a second flux render on a picture that already passed. If the companion also fails a bar clause, it is simply not on the card and needs no re-render now — note its job id and defect class so it can be re-rendered as a spare only if the ideogram is later rejected; the slot still waits for the ideogram. The card's item id stays the slot's round id (`<slot>-r1`) with the attempt suffix on the render name alone, so the slot remains one row and the held-back attempt is named in that row's note by its job id. Do not promote the companion to the slot's image: a comparison render that becomes the shipped asset inverts the engine convention that every record, alt text and later round is then read against. **A render round whose corrected ideogram is hours out therefore waits, and waiting costs the queue nothing** — a post released with `card-done --rendering` holds no slot, so the only clock running is his review, not another post's card. That is what separates this case from the deep-queue rule in `references/review-loop.md` §4: there a replacement is pushed to the next round because it is holding the live slot behind it, and here nothing is. Post the card when the `b` ideogram passes — but **when the correction is hours out rather than minutes, ship the slots that already have a main render and name the waiting slot on the card face** with its job ids, its class and its ETA, instead of filling the row with the companion. Hours is the test, not a day: a shared queue refills under you, so a five-hour estimate read at submit time has turned into a night by the next wake, and a round-1 post that has never shown a card is the strongest case of all — four checked renders in front of him beat a complete round much later. The held slot then rides its own card when its render passes, and the post stays in `rendering` until that card is answered; record the split with `backlog.py note <n>` and write the draft brief so the next run inherits the paths, the hashes and the check notes rather than re-deriving them. **A clause the ideogram fails twice is the author's, not a third prompt's.** When attempt `a` and the corrected `b` that states the clause positively both come back with the same defect — one figure asked for twice and drawn twice, in two different compositions — the engine has said what it will do, and a third attempt spends a render on a coin already flipped twice. If the companion passes the bar it then goes up **as the slot's candidate**: one row, and one clause on its face saying that approving it makes this flux frame the picture for that embed, so the verdict cannot be mistaken for a comparison pick. The engine convention bends only when the card says so in the open — what the rule forbids is the *silent* promotion, an approved flux asset that no reader was told about. When he rejects a disclosed companion, the slot goes to the post's author for a composition (`references/re-render-defect-persistence.md`), because the defect is the scene and the wording has already been tried. **Name the item for the round its card carries, not the round the render was made in:** a slot that first reaches a card on the post's round 2 takes `<slot>-r2-flux` as its item id and asset stem while its staging file is still `<slot>-r1-flux-<token>.png`; the brief carries the staging stem, the record follows the fetched stem, and the row carries the job id, so none of the three has to be inferred from another.
- **A campaign run can stage nano banana prompts for a slot your card already rendered, and its "do not spend renders" instruction can arrive after the spend.** One agent holds several live runs, so the sweep run and the card run work the same post without seeing each other's queue. Check the timestamp before obeying either side: renders submitted at 12:28Z are not duplicates of prompts written at 12:47Z, and stopping the batch the sweep asks for would strand a render already paid for. **The reconciliation goes on the thread the sweep commented on:** name which jobs were submitted when, which prompt files exist, and ask plainly that the sweep's prompts for that post not be submitted. Keep those prompt files — they are spares on disk, not work to delete — and say that they are different pictures rather than a swap, so a different concept is a later round and his call on the card. **Once the slot is approved and the post is closed, the staged prompt is a dead spare:** the picture is chosen and paid for, so the closing comment names it as never submitted and a later run must not render it, or it burns a queue slot on a decision already made.
- **Never clear, cancel or delete queued jobs to shorten the wait — they belong to sibling runs.** The queue depth is a fact to report and plan around, not a misconfiguration to fix. **A render whose slot got approved by another picture stays queued and uncollected, and that is the correct end state:** name it in the closing comment and the queue note as a spare attempt with its job id, so a later reader does not read an orphaned job as a lost render. Collect it only if he rejects the approved picture it belongs beside.
- **An ideogram render can fail at the worker level while its flux companion succeeds.** `sd-cli` exiting with code 1 and "Insufficient Memory" on Metal means the worker ran out of unified memory (LM Studio plus a heavy render plus other processes); it is not a prompt defect and re-submitting the same prompt immediately will fail the same way. Treat it as "main failed, companion passed": retry the ideogram with a new job id, keep the flux render staged and self-checked, and name both the failed and the retry job ids in the comment. Check `queue_ahead` before promising a turnaround — a retry submitted behind a 60-deep queue is ~15 hours out, so release the slot with `card-done <n> --rendering`, arm 2h monitor hops, and let the collect wake open the card. Do not retry while the worker is mid-job; the retry just queues behind it.
- **flux2-klein renders carry no film grain.** Ideogram 4 adds the grain layer; flux2-klein does not, so a flux render that passes every show-bar clause still reads as "no grain" on a close read. Grain is a taste preference, not a bar clause, so the render passes and goes on the card, but name "no grain" in its check note when the slot's approved history or the taste model calls for the layer, so the card says what the picture actually shows instead of implying it matches the ideogram.

## A job id that starts with `-` cannot be read through the wrapper

`imagegen` job ids are random strings, and roughly one in thirty begins with a hyphen. `imagegen status -MA22KAvZHU` answers `the following arguments are required: job_id` because argparse reads the id as a flag, and the `--` separator does not survive the SSH hop (`imagegen status -- -MA22KAvZHU` answers the same, from the remote CLI). It is not a lost job: the submit returned that id and the row exists.

Read those rows off the worker's own table, in the same one-liner shape the queue-count query above uses. Put the ids in a python tuple so the shell and argparse never see a leading dash:

```bash
ssh m1max 'cd ~/git/ideogram4-local && python3 -c "
import sqlite3
c = sqlite3.connect(\"jobs.db\")
for i in (\"-XXXXXXXXXX\", \"-YYYYYYYYYY\"):
    print(c.execute(\"SELECT id,status,engine,created_at,output_path FROM jobs WHERE id=?\", (i,)).fetchone())
"'
```

That one call answers existence, state and output path for every id in the round, the readable ones included, so a collect wake does not need one CLI call per job.

The `jobs` table's columns are `id, status, prompt_type, prompt_value, output_path, width, height, verbose, created_at, started_at, finished_at, pid, error, engine, seed` — there is no `name` and no `slug` column, so select by `id` and take `output_path` for the file's location on the Max. Fetch such a job by copying that `output_path` down with `scp` rather than through `imagegen fetch`, and check the same way everything else is checked: the fetched PNG still goes through the bar. Every other job id reads normally through `imagegen status`.

**Put every job id of the round in the monitor `notes`, not just the last one.** A hop wake re-reads the set from the ids, and the dash ids cannot be re-read from the CLI at all, so the note plus the worker's table is the whole recovery path for them. Ids and the next action fit; the long form of the wake belongs in the issue comment (`references/review-loop.md` §4).
