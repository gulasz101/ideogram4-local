# Closing an approved card

The verdict wake starts the close. `review-loop.md` §8–9 has the order (retain, copy, record, edit the post, close the queue and the issue); this file holds the decisions that order assumes, because each one has a second plausible answer that breaks something quiet.

The close produces six things and proves each: the vault copies (hash against staging), their records (`verify-slot.py`), **the earlier record of any file the close replaced — its `asset`, its `superseded_by` and its own `![[...]]` embed, all three**, the post's embed lines and alt texts (asserted from a fresh read), the queue's state, and one closing comment that names the paths and the checker counts. Patching only `asset` and `superseded_by` leaves the old record displaying the new picture from the shared name, which is the same defect from the other side: a record has to describe its own bytes in every place it shows them.

**Run the close as one re-runnable script, and make every step skippable.** The close moves a vault file, copies new bytes, patches an earlier record, writes a record and rewrites the post; a failure halfway (a wrong prompt path, a missing directory) leaves the vault holding the new picture while the old record still names the shared file. Guard each step with its own precondition — move only when the plain name exists and the preserved name does not, patch only while the shared name is still in the record, write the post's alt text through a regex that matches either sentence — so the second run finishes the close instead of double-moving, double-patching or crashing on its own earlier work.

## Write a vault file through the name you read it from

The vault answers to two absolute paths, a symlink and its target, and `write_file`'s stale-read guard tracks the path string rather than the inode: a record authored through one name and then overwritten through the other is refused as "exists but this task has not seen its full current content" on a file this same run wrote minutes earlier. Pick one absolute path for the whole run and stay on it, and prefer `patch` for the close's targeted edits — a candidate record's frontmatter and its pending row, an earlier record's three fields — so a full-copy write never replaces a record a concurrent run has already touched.

**A copy whose bytes had to change cannot be hash-matched, and the proof is pixels.** An engine that returns JPEG while the post's file is a `.png` forces a re-encode, which changes every byte by design; a close that demands a hash match there reports a correct ship as a failed upload. Prove that one by decoding both files and comparing arrays — `max(abs(a-b)) == 0` on `numpy` RGB — and say in the comment that the proof was pixel equality, so a later reader does not read the absent hash as an unverified copy.

**The extension alone does not force that re-encode.** nano banana returns JPEG bytes under the `.png` name it was asked for, for every render, so run `file` (or `PIL.Image.open(...).format`) on the staging file before concluding the container has to change. When nothing requires a true PNG — the post embeds it and browsers sniff the payload — copy the bytes verbatim and keep the hash proof; re-encoding for the sake of the extension trades the stronger proof for a cosmetic one, and the comment then has to explain a mismatch nobody asked for. Say in one line that the shipped bytes are JPEG under a `.png` name, so the next run does not "fix" it.

## The vault name comes from the ship table, not the card's item ids

A card built from a campaign brief often prefixes item ids with the post's stem or topic (`alerts-absent`, `sso-header`) while the brief's own ship table and the draft's embed use the slot's plain name (`absent.png`). Ship to the ship-table name and leave the embed path as it is: the item id names the render, the slot names the file. Renaming the asset to the item id splits one post's pictures across two conventions and leaves the replaced file beside a differently-named replacement.

## The engine suffix marks the companion, never the only approved render

When both engines of a slot are approved the pair ships as `<slot>.png` and `<slot>-<engine>.png`, and the companion is not embedded. When only the second engine's render is approved, that render **is** the slot's picture: ship it as `<slot>.png`. The engine lives in the record's `engine:` and in the caveats, not in the filename — a `<slot>-flux.png` that has no `<slot>.png` beside it tells a reader the slot was never filled.

## Preserve the replaced file, then repoint the earlier record at it

Move the file being replaced to `<slot>.superseded-<old job>.png` before copying the new bytes in. Then patch the slot's earlier record in three places: `superseded_by` names the new job, `asset` names the preserved file, and the record's own `![[...]]` embed also points at the preserved file. The chain rule elsewhere asks only for `superseded_by`, which leaves a record whose `asset` points at bytes it never documented — a record's asset is a claim about its own render, so it follows the moved file, and an embed left on the shared name renders the new picture inside the old record. Say the edits in the closing comment, because the earlier record now differs from the one a backfill would write.

**The preserved name belongs to the earlier record only.** The approved record's `asset` and its `![[...]]` are the shipped `<slot>.png`, the name the draft embeds; writing `<slot>.superseded-<old job>.png` there, because the two records are built in one loop from the same variable, fails two `verify-slot.py` checks together — `vault asset is byte-identical to the source file` (it compares the record's asset against `--asset-source`) and `post embeds the asset exactly once` (the post still embeds the plain name). Keep two names in the loop: `ship_asset` for the new record and the post, `kept_asset` for the earlier record's three edits.

**Three edits only: the earlier record's Verdicts table is history and is not rewritten.** An earlier record often carries an approval that never came from a card — a blanket instruction on the campaign issue, or a verdict given before the picture was known to be broken — and it still takes the chain unchanged: `superseded_by`, the preserved `asset` and the `![[...]]` embed move, while its `verdict:` and every row stay as they were. Rewriting the old row to mention the replacement falsifies who approved what and when, and `verify-slot.py` will not catch it: `earlier keeps a verdict that is not this approval` asks that the row exists and belongs to an earlier round, so an older `approved` row passes either way.

**A back-filled earlier record that the self-check held back keeps `verdict: "unreviewed"` and its marker, and still takes all three path edits.** Read `library-records.md`'s "edits nothing else" as governing the verdict and the table, not the paths: the image never reached a card, so writing `rejected` into its frontmatter puts a decision in his name, and the hold-back is recorded as a row in the approved record instead. `superseded_by`, `asset` and the embed still move to the preserved name, because leaving them on the shared name makes that record display the shipped picture while its frontmatter says nobody judged it — the byte claim and the verdict claim are separate and both have to be true. Check the result with a grep for the marker (expect one match) and a read of all four fields, not just `superseded_by`.

**A clean `verify-slot.py` run proves the approved record and the post, not the earlier ones.** The chain assertions read an earlier record's `superseded_by` and verdict and nothing else, so a close can pass every check with an earlier record whose `asset:` and `![[...]]` still name the shared file that now holds the shipped bytes. After the checker returns zero failures, read each earlier record's `asset:` and embed back and require the preserved `<slot>.superseded-<old job>.png` in both, then name the files checked in the closing comment — the checker's green is not their proof.

**Resolve the earlier-record paths under `3-resources/image-library/`, not by searching the vault.** A brief lists them as `<YYYY-MM>/<YYYY-MM-DD>-<stem>--<job>.md`, and that prefix is relative to `3-resources/image-library/`, so the file is one `ls` away. A `grep -rl` or `find` over the vault root, or over the whole `image-studio/` tree, runs past the tool timeout — the vault is large and the record sits in a single month folder — while the brief already hands you the address.

## A close does not wait for a re-read, and the record says what it has

When a fresh read is unavailable at the close, write the record's `## Why` from the check notes the render run and the card produced, and put one line in the closing comment naming which frames were read at close and which carry the card's note. Never fill the gap with an invented number, and never hold an approved close for a re-read: the verdict is what authorized the ship, a record with a named gap is honest, and a ship delayed for prose is not a better one. The corollary is that a number only the note supplies (`two crates where the ideogram draws three`) is written as the note's number, not as a measurement this run made.

**When both vision routes are down at the close, the alt texts come from the card's check note too.** The aux proxy answering 502 and the profile provider (through `vread.py`) answering 429 in the same window is common enough to plan for: write each alt as the objects and their states the note names, say in the closing comment that no frame was re-read in this run and that the alt texts and `## Why` carry the card's read, and stop. This does not break the rule further down that the card's wording never overrides the pixels — that ban is on a card phrase replacing what a read shows, and with no read there is nothing to contradict. What it forbids is inventing a prop the note never named. Keep the card's caveats out of the alt as well: an alt describes what a reader sees, so a key hanging on the same pier and a wire on the tap neck go in `## Why` and the closing comment, not in the caption.

## Round-3 approval of a re-render: the draft still points at the old asset

A round-3 approval is the case where the draft's embed still names the replaced image, so the close has to do four things a normal approval does not:

- **Copy the approved staging PNG to a name that keeps the round suffix** — `tech_blog/assets/<date>/<slot>-r3.png` (not the plain `<slot>.png`). Verify bytes with `shasum -a 256` against staging. The round suffix survives because the asset is a distinct file, not a rename of the slot.
- **Repoint the header embed in the post to that new path and rewrite its alt text.** The old alt text described the replaced image; carry over nothing from it. The new alt text describes the picture that ships (props and states), and it must not carry the card's caveats (a key on the same pier, a wire on the tap neck) — those go in `## Why` and the closing comment.
- **Write the approved record with `superseded_by: null`**, and set `superseded_by: <new job id>` in **every** earlier record of that slot — back-filled, round-1 rejected, round-2 rejected, and held-back attempts. The approved record keeps `superseded_by: null`. The held-back attempt records get the same `superseded_by` even though they were never shown.
- **Do not touch `ip-header`/approved images and their records.** Only the records of the slot being re-rendered move.

The `## Why` for the approved record is written from the card's check note when vision was unavailable at the close (see "A close does not wait for a re-read" above); name in the closing comment which frames were read at close and which carry the card's note.

`verify-slot.py` compares the fenced block against the `--prompt` file byte for byte, its final newline aside. The engine's stored `prompt_value` is the same prompt as compact JSON: parsing both and comparing the objects can answer equal while the byte lengths differ by a few hundred, so a block written from the job's string fails on formatting alone. Write the block from the prompt file's own text.

- **When the file and the job disagree as objects, the job is what was rendered and the file is what the checker measures.** Regenerate the prompt file from `imagegen status <job>` before writing the record, and say in the closing comment that the file was rebuilt from the stored prompt.
- **Read `created_at`, `finished_at`, `width`, `height` and `engine` from `imagegen status <job>` too.** The record filename's date prefix is that renderer `created_at`, not the day of the close, and the two timestamps are the only source of the ordering a later backfill would reproduce. The file's own pixel size (1376x768 on this engine) is what the record carries when it differs from the requested canvas the status reports.
- **A job id that begins with a dash cannot go through the client at all.** `imagegen status -GfBL3Y7iWY` is read as a flag and answers nothing; `imagegen status -- <job>` answers nothing either, so the JSON parse fails on an empty string and looks like a dead render. Read that row from the renderer's own database instead — `ssh <render-host> "cd ~/<remote-dir> && sqlite3 -json jobs.db \"select id,status,engine,prompt_type,created_at,finished_at,width,height,seed from jobs where id='<job>'\""` — and note that the record filename drops the leading dash while `job_id:` keeps it verbatim.
- **The prompt file is named without the render's 8-hex token.** A render `091-gpu-too-small-r2-31733b0f.png` was submitted from `prompts/091-gpu-too-small-r2.txt`, so a record builder that appends `<stem>.txt` misses the file it needs; derive the prompt path by stripping the trailing `-[0-9a-f]{8}` from the stem. **When no file exists to find — a round submitted without one — write the rebuilt prompt under the rendered stem with its token kept (`prompts/<full stem>.txt`)**, so a second attempt of the same slot cannot overwrite it, and say in the closing comment that the file was created from the stored `prompt_value`.

## A record filename is derived, so the checker's heading failure is usually the name

`verify-slot.py` derives the heading it expects by stripping the `created_at` date prefix and the `--<job>.md` suffix from the record's filename. A name written as the stem and job id only therefore fails `filename starts with the job's created_at date` and `heading is the stem (no date, no job id)` together, while the heading inside the file is correct: fix the filename and never the heading. Build the name from the record's own frontmatter date, which is the renderer's `created_at`, not the day the close runs.

## A record written at card-open takes the verdict in place, not through `approve_record.py`

`approve_record.py` serves the back-filled shape only: it looks for the `Back-filled from jobs.db; not reviewed yet.` line and refuses a record that has none. A record written at card-open has a pending Verdicts row instead, so patch it in place: `verdict` to `"approved"`, `asset` to the shipped vault path, `asset_location` to `"vault"`, `asset_present` to `true`, `superseded_by` left as the bare `null`, and the pending row replaced by the approval row. Assert every substitution matched exactly once — a `replace()` that hits nothing leaves the record reading `unreviewed` under an approved card, and nothing downstream contradicts it.

**The alt text describes the shipped pixels, and the card's wording for a prop does not override them.** When the card names a token "struck square with a single clipped corner" and the frame shows a round disc with one notch cut into its edge, the alt says what is in the file and the closing comment names the difference in one line. Copying the card's wording into the alt is how a draft ships a caption for a picture nobody rendered.

**An alt that is only the item slug fails the checker, so a draft written that way needs its embeds rewritten in the close.** `verify-slot.py` fails `alt text describes the picture, not a placeholder word` on the shape most older drafts use, `![<slot>](<path>)`, and the failure names the alt rather than the record — so it reads like a record defect and sends you back into the record that is already correct. Write one sentence per embed naming the subjects and their states; rewrite the post's other embeds in the same pass when they carry slugs too, because the check runs only on the slot under verification and one approved picture ships beside four placeholder captions otherwise.

## `post_status` comes from the draft, and a nulled `asset:` keeps its pointer in prose

**`post_status` is read from the post's own frontmatter at the close, never copied from a sibling record.** A sibling approved earlier on the same post can carry `post_status: null`, written by a run that never opened the draft, and copying the frontmatter forward leaves an approved record saying nothing about a post whose frontmatter plainly reads `status: draft`. Nothing later flags it: `verify-slot.py` does not assert the field.

**The `asset_location: "staging"` sweep covers every month folder, not only the month this close writes into.** The enum was invented by whichever close wrote those records, so the hits sit in the month their renders were made, and a sweep scoped to the current month answers clean while the lie stays in the library — this supersedes the month-folder wording in `library-records.md`. For each hit, read the owning post's state in `queue.json` before editing: `rendering`, or `card` with an open issue, belongs to the live round and that round's close owns its enum; repair only the closed ones, setting the bare `asset: null`, `asset_location: "max-only"` and `asset_present: false`.

**Nulling `asset:` destroys the only pointer to that render unless the staging path moves with it.** Put one sentence in that record's `## Why` in the same edit, naming the file — the rejected render stays on the Max at `<path>` and was never copied into the vault — and name the repaired files in the closing comment, because those posts' own issues will never show the change.

## A clean close reads zero failures, and the total is not fixed

`verify-slot.py` counts the earlier set, so a clean approved close totals in the low forties with one earlier record and a few more for each extra earlier record, all passing. Quote the number the run printed and its zero rather than a remembered total: seven failures is the unreviewed shape, zero with forty-odd checks is the approved one, and neither is a short run. When it prints a total you did not expect, read the checks rather than the total — a script that grew a check reads as a new total on a healthy close.

## The queue state follows the post, not the card

A card that closes every slot the post has releases the post. A card that closes some of them — a header deferred to a campaign issue, a round-2 slot with no renders yet — closes with `card-done <n> --rendering`, so the post stays in the queue as work pending; a plain `card-done` reports a four-slot post as finished on three pictures and nothing later opens its remaining slots. Follow it with one `note <n>` that names what shipped, what remains, and the issue carrying each remainder.

**A post left in `rendering` by an earlier round reads to `card-done` as already released, so a later round's card can be closed `done` while it is still open.** The command's third branch fires whenever no batch entry and no slot hold the post and its state is `rendering`: it writes `done`, prints `closed_without_slot: true` and exits clean, which is the right answer only when the round it is releasing has finished. Read `queue.json` for the post's `state`, its `batch` entry and the slot before every `card-done`, and when a later round's card is open, repair instead of releasing: `backlog.py ready <n> <round> <brief path>` returns the post to `ready`, then `backlog.py reopen-card <n> <issue> <round>` consumes that entry, sets the post to `card` and re-registers the batch entry that the real close will later release. Neither command writes to the board, so the repair is safe on a card that is still waiting for verdicts — and leaving it unrepaired marks the post finished behind a picture nobody has judged yet.

## A card's job id can be a transcription of the real one

A job id copied onto a card or a brief drops characters and changes case, and `imagegen status <that id>` answers `Job not found`, which reads like a pruned job rather than a typo. Before concluding the render is gone, resolve the id from the collect brief's job table by the fetched PNG stem, and use the renderer's spelling in the record filename, the `job_id:` field and the closing comment, with one line saying the card's form was corrected. Treating the card's spelling as authority writes a record that the filename and `job_id` assertions both reject.

## Write the held-back attempts' records in the same pass, and verify them the other way round

Every render of the slot that never reached the card gets a record in the close that lands the slot: `verdict: "rejected"`, `asset: null`, `asset_location: "max-only"`, `asset_present: false`, `superseded_by` naming the job that shipped, no `![[...]]` embed, and one row reading `held back at the self-check, never shown to Wojtek` plus the defect and the measurement that showed it. Its issue column names the campaign or round issue where the hold-back was decided, never the approving card. The approved record's table carries that render too, with the attempt's stem as the row prefix — the stem already ends in the fetched 8-hex token, so leave the job id out of it.

Because the attempt is verified with `--post`, its `## Why` needs the same provenance as an approved record: one blockquote taken from the post and a `From [[<post>]], section "<heading>":` line whose heading is the nearest heading above the quote by line position. Write that in the same pass; a missing provenance line is the one failure that does not belong to the documented six.

Write the attempts first, or in the same pass. The approved record's duplicate guard counts every file in the library that names the shipped job id, so an attempt written after the approved record was checked adds itself to that set and the re-verification fails `job id appears in exactly this record plus its earlier records` on a healthy close. That failure is the ordering, not a defect: an attempt that lands late is repaired by adding its record to the approved record's `--earlier` set and re-running the checker, whose total grows by one per earlier record and returns to zero failures. Re-verify the approved record after the last library write of the close, never only once in the middle of it, and pass every attempt record as an `--earlier` when you do.

Verify the attempt's own record with `--record`, `--job`, `--post` and `--prompt` and nothing else. No `--earlier`, because the slot's earlier records point at the shipped job and the chain check then fails `earlier points at the approved job`; and no `--asset-source`, because there is no vault copy. The run reports the five approval-shaped failures plus the embed check, which is the documented shape for a rejected render.

## Check the post's other slots before the closing comment promises anything

A render submitted before the card went up can land while the card is being closed. One `imagegen status <job>` per unclosed slot, taken just before the comment is written, decides what the comment may say: still running, or finished with a file in staging and a byte size. Name the job id, the staging file and the issue that opens that slot's card, normally the campaign issue that holds the collect, and close the post `card-done <n> --rendering` either way: that slot's card belongs to the campaign, so this issue still goes `done` on its own items.

## `ship-approved-batch.py` writes a Why with no section label, so its records fail the provenance check

The batch shipper is the fastest way to land two approved slots (preserve, copy, patch the earlier record, rewrite the alt, write the record, prove pixels), but its record template writes `From [[<post>]]` and no `, section "<heading>":`. `verify-slot.py` then fails `Why carries a section "..."` provenance line on a healthy close, and the record has to be rewritten anyway. Either pass a builder that emits the provenance line, or post-process each record's `## Why` into prose, blank line, `From [[<post>]], section "<heading>":`, blank line, exactly one blockquote — and take the heading by line position above the embed, not from the slot's earlier record. The script also re-encodes through PIL instead of copying the bytes, which trades the hash proof for a pixel proof; copy verbatim when the staging file is already what the post will serve, and keep the hash.

**The blockquote must be one line of the post, matched by line position.** `verify-slot.py` looks for the quote's first 60 characters inside a single line of the draft, so a quote that joins a heading to a code line, or that spans two sentences sitting on separate lines, fails `quote appears in the post` and then `quote found by line position` with it — even though the passage is plainly in the file. Quote the one line the picture sits under (`uv run camoufox-instagram-login`, the `Logged in: True` result line), and take the section label from the nearest `#` heading above that line, counting only headings outside fenced blocks: a shell comment inside a ```bash block is not a heading, and a quote above the first heading takes `section ""`.

**The earlier record's embed now moves with its asset inside the script.** Its patcher rewrites `asset:` and `superseded_by` and, in the same pass, the record's own `![[...]]` embed, so a batch close no longer needs those three hand edits — but it still needs the grep that proves them before the comment claims it: `grep -c superseded- <earlier record>` returns three on a correct close (the asset line, the embed line, and the closing marker's prose naming the preserved file).

## Close the issue `done` on the card's scope, not the post's

The issue's scope is the items the card carried. When the post still holds slots the card never had, the comment names them and the issue they ride, and the issue goes `done` on that scope — an issue left `in_review` to keep an unrelated slot alive strands the close and has no wake path of its own.

**A 409 on the checkout is not proof the issue is unwritable, so attempt the close's writes anyway.** A verdict wake can arrive with `checkoutRunId: null` and an `executionRunId` naming a run that has already ended, which makes `POST /issues/{id}/checkout` answer `409 Issue run ownership conflict`; the comment POST and the `done` PATCH still land on that shape. Attempt the comment first and read its `201` with an `id` as the proof, then the PATCH's echoed `status: done`; a close abandoned at the checkout 409 leaves an answered card `in_review` behind a write that would have worked. Go back to the checkout dance only when a write is actually refused.

## A re-render's record belongs to the render's month, not the post's

A hand-off brief is written before the renders exist, so it names the record under the post's own date (`<post month>/<post date>-<item id>--<job>.md`). A slot re-rendered in a later month cannot live there: `verify-slot.py` asserts the filename starts with the job's own `created_at` date, and the library files a record in the month of that same date. Ship the record to `<render month>/<render date>-<item id>--<job>.md`, where the date is the renderer's, beside the other renders of that month rather than beside the post's older pictures; the post's own older records stay put and point forward through `superseded_by`. When an earlier run already filed a held-back attempt under the post's month, move that file into the render month and rename it with its job's date — one move, no second copy — so one slot's history sits in one folder.

## The `> <alt>` line older records open with is not a quote you can carry forward

Records written while the draft still embedded the slot name could open `## Why` with `> <slot>` and pass, because that literal was in the post. The close rewrites every approved embed's alt to a description of the shipping picture, so the old literal exists nowhere in the draft afterwards and a record copied from that shape fails `quote appears in the post` on a phrase that was real one run earlier. Write the section as prose, then the `From [[<post>]], section "<heading>":` line, then exactly one blockquote taken from the post by line position — and pick the quote before the label, because an image embedded immediately above a heading has its natural passage under that heading, which makes the label the heading below the embed and not the attempt heading above it.
