# Woken on an issue whose verdict card is already live

Open this when a wake (`issue_assigned`, `issue_monitor_due`) lands on an issue whose verdict card is **already pending**. The common cause is mechanical: the run that built the card created the issue, the server then assigned it to you, and this run wakes into a finished card. Read the card, do not rebuild it, and finish the residual work the card run left behind.

**Never create a second card for one round.** Two cards give Wojtek two verdicts to give for one image, and the one-card-at-a-time rule exists to stop exactly that.

Treat the wake's inline message as evidence, not as completed action. It is usually written by your own sibling run and describes what it did, not whether the records exist on disk.

## Card already `answered`: verdict branch, not the card-build branch

**The first read on every card-issue wake is `GET /api/issues/<id>/interactions`, before any upload or card build.** When the `request_item_verdicts` comes back `status: answered` with a non-null `resolvedAt`, the verdicts already exist: handle them per the parent's "Per card" verdict step (ship approved renders, write records, run verify-slot, `card-done`, close the post) and do **not** build or upload a card. A card-issue wake can arrive on a card that an earlier part of the same run already created and answered, and the wake's `completedActions: []` / `completedWork: null` prove nothing — they are not evidence that no card exists.

**A `409 Interaction idempotency key already exists for a different request` from the card POST is the signal the card is already there, not a reason to post under a new key.** Read `/interactions`, not the build script. Read each verdict from `result.items[].verdict` (fall back to `responses.items[]`); a no-reason approval carries no `reason` key at all, and `resolvedByUserId` set is what makes it his verdict rather than an agent settling its own card.

**If you uploaded before checking, the duplicate attachment rows are the accepted cost — do not re-upload to "fix" it.** The answered card points at its own `attachmentId`s, which are the same bytes you would have shipped; match rows by `sha256` and leave the extra rows. Name the card's own attachment ids in a comment only if the thread needs to show which file the card judged.

## The checklist

1. **Confirm the card is a working review path.** `GET /api/issues/<id>/interactions`: `kind: request_item_verdicts`, `status: pending`, `effectiveResolverPolicy: human_only`, `continuationPolicy: wake_assignee`, item ids equal to the brief's ids, one attachment id per item. `wake_assignee` is the part that matters: without it the verdict never wakes you and `in_review` becomes a parked issue. **Count the payload's items against what the thread claims.** The opening comment belongs to the run that built the card and can carry a count from another card's template, so a comment promising two images over a one-item payload, or the reverse, is a leftover sentence and not a missing item: correct it in one line under the same card, and never open a second card for it. He reads the thread before the payload, and a stated count he cannot match costs him a search for an image that was never rendered.
2. **Hash the attachments, not their container.** Download `/api/attachments/<id>/content` for each and `shasum -a 256` it against the staging file named in the brief. **Build that URL from `$PAPERCLIP_API_URL` as it is:** the profile value already ends in `/api`, so appending a second `/api` answers `404 API route not found` with 31 bytes in the output file, and that reads like a missing attachment rather than a wrong path. Matching bytes are the proof the card shows the file you read. A content-type or `file(1)` mismatch is not a defect on this engine: nanobanana stages JPEG bytes under a `.png` name (`references/nanobanana-engine.md`).
3. **Read the frames yourself.** The card run's check notes are one run's read, and so is the brief's. Settle the beat, the text surfaces and the limb count on the PNG (or on a crop) before you sign off in a comment. **When every vision route is down, say so rather than sign off on the beat:** the aux proxy can answer `502` (dead cookie pool) while the provider answers `429` usage-limit or `400` model-unavailable for each vision id, and `vread.py` then names the reader that failed. The local mechanical checks (`check-palette-strip.py`, `check-green-share.py`, `check-blank-margin.py`) still run, and the comment credits the card run for the visual claims and states plainly that this run took no read of its own.
4. **Write the missing records.** A card run often uploads and opens the card without writing library records. Write them **unreviewed** so the verdict has somewhere to land: `verdict: "unreviewed"`, `asset: null`, `asset_location: "max-only"`, `asset_present: false`, `superseded_by: null`, `source: "studio"`, and one `## Verdicts` row that says it is on the card awaiting the verdict. **That placeholder row's verdict cell must be the frontmatter's own word, `unreviewed`** (`| 1 | <date> | unreviewed | on the card awaiting the verdict | [GUL-x](…) |`), because the checker asserts `last row's verdict matches the frontmatter`; a row reading `pending` or `on the card` fails a check on a healthy record. Header plus separator with no data row also passes, and is the shape `library-records.md` describes for a candidate — either is fine, the cell is not optional when the row exists. Field details are in `library-records.md`; `superseded_by` on the earlier records of the slot stays `null` until a replacement is actually approved. **Find each item's prompt by the job's own served `prompt_value`, not by a filename built from the post number.** Prompt files drift between post numbers during renumbering: a post's replacement prompts can sit on disk under an earlier post's prefix (`095-service-auth-fix-r2.txt`) while the attempt that shipped for one slot carries the post's own (`100-cpu-saturation-r2c.txt`). Diff each candidate against `imagegen status <job>`'s `prompt_value` (they differ only by the file's trailing newline) and write the match into the block, or the record carries another picture's prompt and nothing in it contradicts that.
5. **Read `verify-slot.py` correctly on an unreviewed record.** It fails **seven** checks by design until a verdict lands, in two groups. Four are the approval-shaped assertions: `verdict is approved`, `asset_location is vault`, `asset_present is true`, `asset names a file`. Three are the close-time chain assertions, which cannot pass before the verdict either: `job id appears in exactly this record plus its earlier records` (the earlier record carries this job id only once its `superseded_by` is written at approval), `earlier points at the approved job`, and `post embeds the asset exactly once`. Every other check must pass. Quote it as `29 of 36, seven failed, all approval-time`, and do not satisfy the three chain checks early by pointing an unreviewed record at itself. Pass **absolute** paths for `--record` and `--vault`: a vault-relative `--record` reports `FAIL record exists` for a file that is right there.
6. **End with the card as the wake path.** Leave the card pending and the issue `in_review`. No monitor is needed while a `wake_assignee` card is pending.
7. **Post one comment** and read it back: what was verified (hashes, what you saw), what was written (record paths), what happens on approval (asset paths, what old files are kept, whether alt texts need rewriting), and plainly that nothing was rendered or re-rendered in this run. **Finish steps 4 and 5 first:** on a card issue the missing records are usually the reason this wake exists, so a comment posted before they are written forces a second POST ("records are written now") that a settled pass would have merged into one. That comment is the audit trail for a run that changed no picture. **Settle every number and every claim before the POST, because a comment is one write and its corrections are visible rows.** A comment deleted and re-posted leaves a soft-deleted row in the thread he opens, so two consecutive repairs on one card mean the body was drafted before the measurements were settled, not after. When a posted claim turns out to be *wrong* rather than merely imprecise — a number from one unstable read, a figure the pixels contradict — delete and re-post it **once** with the settled wording, which is the repair `review-card-api.md` asks for; when it is only imprecise, leave it and correct it in one follow-up line. The same applies to the one-line skill-change notice: decide whether this run edited a skill *before* writing the comment, so the notice rides the same body instead of forcing a third post. **This comment is owed only when the run left something durable behind** — records written, a queue note, a corrected claim — and a wake that changed nothing posts nothing at all: `review-card-api.md` bans re-check chatter next to a live card, and "I verified the card again" is exactly that. When the only durable record of the pass is the queue note, the note is enough.
8. **Leave the queue alone.** A card run does not advance the slot and does not write the runner's queue document; the post stays in `card` state with its issue id, and the runner's own wake rebuilds the table.

## A slightly imprecise note is a comment, not a withdraw

Withdraw and re-post a card only when one of its check notes is **wrong about what decides the verdict**: a defect named that is not in the frame, or a defect passed that is plainly there. A supporting clause that is merely imprecise (an arm called level when it sits a few degrees low at the handle end, a count that is off by one on a prop the beat does not depend on) is disclosed in the run's comment with the reading that settles it, and the card stays. The comment reaches him at the verdict wake anyway, and a second card costs him more than the imprecision does.

**A caveat that sells the frame short is the safe direction and is not a withdraw either.** A card that says a detail is only implied or only partly there, while a crop shows it plainly, makes him judge nothing worse than the picture is: name the stronger reading in the comment and let the card stand. Withdraw only when the note would make him judge a different picture than the one attached.
