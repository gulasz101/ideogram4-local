# Verdict and round mechanics

Small mechanics that recur on every verdict wake and round hand-off. Split out because `references/archive/backlog-review.md` is at its size ceiling; the review procedure itself lives there. **`references/archive/review-loop.md` and `SKILL.md` have since crossed the same 100,000-character ceiling, so a patch to either is refused and rolls its whole batch back — new round and queue mechanics belong in this file, new verification rules in `references/verifying-image-details.md`, and the series' register in `references/series-look.md`.** `references/library-records.md` sits at 99,872 of the same ceiling, so anything longer than a sentence added there is refused too: put a new record-shape or close rule in this file and leave that one to the record format itself. `references/prompt-hygiene.md` and `references/paperclip-api.md` are close behind — their full text reads about 97,000 to 100,000 characters with escaping — so a multi-paragraph addition to either is a gamble: send a short patch, and when it is refused put the rule in a topical file with room rather than cutting the lesson to fit.

## The queue helper

- **`backlog.py status` prints a JSON summary and then a human-readable table**, so piping it into a JSON parser fails with `Extra data`. For structured checks — the slot, `batch`, `ready`, a post's state and its issue list — read `queue.json` directly; keep `status` for the view you read yourself.
- **On every runner wake, before deciding anything, list the `q["batch"]` entries whose `issue` is null.** An entry with no issue is a round that was claimed and never carded, so a finished, checked render sits in staging with nothing on the board in front of it — and nothing else reports it: `status` counts the post as `card`, `next` answers `wait`, and the round is absent from `ready`. The claim and the issue POST are two separate writes, so a run that dies between them, or one that answers `opened` and stops there, leaves this shape behind for as long as nobody looks. **`batch-open-ready`'s `opened` array is a queue claim, not a Paperclip issue:** read `q["batch"]` back, POST the issue from the entry's `brief` and `title` (parent the runner, your own agent id, `status: todo`, the brief as `description` byte for byte), then `batch-opened <n> <ID>`. The repair is one create and touches no slot.
- The render branch of a batch card is: `card-done <n> --rendering` at the verdict wake (drops the batch entry, sets the post to `rendering`), then at the monitor wake `ready <n> <k> <brief>` → `batch-open-ready 1` → POST the card issue → `batch-opened <n> <ID>`. A batch card never Advances, and the live slot is not yours to touch at any point in it.
- **`batch-open-ready` answers `{"ok": true, "opened": []}` — success with nothing opened — when the post still holds its previous round's batch entry.** It builds `taken` from `q["batch"]` plus the live slot and skips any post in either, so a round queued with `ready` while the earlier card was never released sits in `q["ready"]` for ever while the call reports ok. When the card you are on is that earlier card, the order is `ready <n> <k> <brief>` → `card-done <n> --rendering` (drops the old entry, sets the post to `rendering`) → `batch-open-ready 1` → POST the issue → `batch-opened <n> <ID>`; `batch-open-ready` itself flips the post back to `card`. Read `q["ready"]` and `q["batch"]` after the call — a round still in `ready` while the post is still in `batch` is the symptom, and the empty `opened` list is not evidence that there was nothing to open. **Once the new round's card exists, `card-done` on that post belongs to the card that answers the last slot of that round**: calling it again from the card that just handed off releases a post whose new card is already open and orphans the card.
- **An all-approved card is not a finished post, so decide the `card-done` shape from the post's embeds, not from the verdicts.** "Not before every item on the card has a verdict" is necessary, not sufficient: when one slot's renders were all held back at the self-check and never carded, every carded item can come back approved while that slot still shows the draft image in the post. That close is `card-done <n> --rendering` — the post goes to `rendering`, the batch entry (or the live slot) is released, and the held-back slot rides the next round via `ready <n> <k+1>` at the fetch wake. Plain `card-done <n>` writes `done` and leaves a post whose published image is one he never approved. Count the slots that still need an accepted asset, not the items the card returned.

**A batch card whose every slot comes back holding an accepted asset is the plain `card-done <n>`, even though the post was queued as a batch entry.** `--rendering` is the shape for a slot that still owes a render, not a property of batch cards — read `queue.json` for the post's state and its slots before choosing: with nothing outstanding, the plain call drops the batch entry and writes `done` in one step. The error in the other direction costs more, because `--rendering` on a finished post parks it behind a round it does not need and opens a second card for work already shipped.
- **The six-slot render cap makes a batch one post, not four.** Three slots × two engines fills it, so plan a batch as one post plus its re-render arcs, and say so when reporting instead of implying four posts are moving. A post whose slots fail twice costs two or three monitor wakes before its card exists: the collection is the long tail, not the submission. Write the pass number into the queue note (`r2`, `r2b`, `r2c`) so the next wake can see how many attempts a slot has had without reading the images again.

## A post whose card closed and was never released

**A card can be `answered` with every item approved while the post still reads `card` in `queue.json`, because the card's own run set the issue `done` and died before `card-done <n>`.** Nothing else in the flow reports it: `status` counts the post as open, `next` answers `wait`, and when it is the last open post the campaign can never reach `finished`. The tell is a single non-`done` post whose card issue already reads `done`: `GET /issues/<card>/interactions`, take the `answered` entry, and read `result.items[]` for the verdicts. An approval there authorises the whole close — copies, embeds, records, chain — and `card-done <n>` comes after it, never before: the plain call writes `done` over a draft that still embeds the files the render replaced.

- **Resolve a `GUL-` identifier from `queue.json` to its issue id by paging the company list and matching `identifier`** — `GET /companies/<id>/issues?limit=200&offset=<n>`. The bare `/issues` list and a `parentId=` filter both answer `400`, so paging is the only route to a status for an identifier the queue holds.
- **A close that has been dead for days is still the ordinary close.** The gap changes nothing about the order or the target paths: the run that died may already have written the vault copy or the record, so converge — compare bytes and hashes, write only what is missing, and do not refuse because part of the close exists.

## A freshly created card is claimed within seconds

The successor run takes a new card issue almost immediately, so an upload attempted from the run that created it usually answers `409 Issue run ownership conflict` — often on the very first response, not after a few tries. Treat that upload as opportunistic and never as the plan:

- write the handoff brief as if the upload will fail, carrying the absolute staging path, the byte size and the sha256 of every PNG, plus a line saying the files are **not** attached;
- attach the PNGs to the card you are closing — that upload always works — and link them with one comment carrying `attachmentIds`, then verify `issueCommentId` is non-null on each;
- post a short comment on the new card naming the same paths and hashes, because its description is frozen from the moment the create lands and a comment is the only place the paths can still be added.
- **The upload helper's `--output json` emits one pretty-printed object per call, so several calls appended to one file are a stream of objects, not an array.** A `json.load` over that file raises, and a parse that swallows the error prints nothing — which reads as "the uploads failed" when every file landed fine. Parse it with `json.JSONDecoder().raw_decode` in a loop from the first `{`, or write one response per line, and build the card spec from the parsed structure rather than from ids retyped off the transcript. Check each `sha256`, `byteSize` and `createdByAgentId` against the staging file and your own agent id in the same pass, so a landed upload can never be mistaken for a failed one.
- **put the verdict-card content in the brief too: one item id per PNG, its label, and its per-item description** (why it exists, what the check found, and the caveats named rather than decided), plus the `build-verdict-card.py` mechanics and the instruction not to re-render or re-audit. The successor run builds the interaction from the brief alone — it cannot see your checks — and a brief that only lists files gets a card whose items say nothing. Keep every description under the 500-character cap.
- **Start the brief with a numbered "what this run must do" block** — upload, build the interaction, PATCH to `in_review`, do not re-render — because the successor run reads the description as its own instructions and finishes without asking when the order is explicit. `templates/round-card-brief.md` is that shape filled in, ready to copy with the slot table and the per-item descriptions swapped.

## Binding the card to the issue: no `reviewInteractionId`

`PATCH /issues/<id> {"status":"in_review","reviewInteractionId":"<iid>"}` answers 422 `invalid_review_interaction` when `<iid>` is the `request_item_verdicts` card — the field only accepts a pending non-tool **confirmation**. Do not read that as a missing review path: the pending verdict card already satisfies the disposition guard, so PATCH `{"status":"in_review"}` alone lands (200, no confirmation needed). Verify with a read-back that `status` is `in_review`, `assigneeAgentId` is you and `assigneeUserId` is null.

**The 422 lands after the card is live, so the repair is a second PATCH, never a second card.** The order that leaves exactly one card and one waiting path: upload every passing PNG in the posting run and compare each upload's `sha256` and `byteSize` against the staging file → POST one comment carrying their `attachmentIds` → build the payload with `build-verdict-card.py` → POST the card → `PATCH {"status":"in_review"}` with no `reviewInteractionId` and no monitor → read back the issue, the attachment list and the interaction list. A PATCH hand-rolled from the plan or confirmation shape brings the field back, and re-POSTing the interaction to "fix" it answers the idempotency-key refusal instead of a second card.

## A card that already exists, and a slot already ruled on

**On a backlog-review card the issue already is the card, so the posting half never creates one.** `open-card-issue.py` is for a new round card, where the create and the uploads are one call; on a card the queue opened, the issue id exists and the order is: `upload-attachments.py <issue-id> <png>… --company <company id> --run <run id>` → one comment carrying `--attach <id>` for each PNG so their `issueCommentId` goes non-null and they render in the thread → `build-verdict-card.py <spec> --out <payload>` → `post-interaction.py <issue-id> <payload> <run id>` → `PATCH {"status":"in_review"}`. **Pass `--company` and `--run` explicitly:** `PAPERCLIP_COMPANY_ID` is not in the tool environment of an unattended run, so the call answers `--company or $PAPERCLIP_COMPANY_ID required` and uploads nothing, which reads like a permissions problem rather than a missing flag.

**A slot the owner has already approved on an earlier card of the same post is not a row on this card.** A post can be queued for review after one of its images was carded and shipped on its own issue; the brief's table still lists that slot because the brief is generated from the draft. Carry only the slots that are still open, and say the closed one on the card's face — its item id, the issue and job id the verdict was given on, and the record path — with one sentence that it is not a row because the verdict already exists. Asking again is a second verdict on one picture: it spends his click, and a rejection there would unpick an approval already shipped into the draft. State it rather than leaving the gap silent, because a card without its brief's item count otherwise reads as a card that lost a picture.

**A staged repair is checked against the thread before it goes in, because a sibling run may already be judging that slot's earlier render.** A held slot waits on a render outage for hours, and in that time another run can collect the post, card the frame you held back, and close out — so your repair prompt is no longer a fix but a competing picture for a slot the owner may have just approved. Read the post's open cards and their items first (`GET /companies/<id>/issues?status=in_review`, then each issue's interactions); when the slot is already carded, keep your prompt as a spare, say so in one line where it will be found, and spend nothing. Submitting it blind costs a render, and submitting it after an approval would replace a picture he accepted.

## Verifying the card the successor run built

A hand-off is not finished when the create returns: the successor run does the uploads and the interaction, and it can do them wrong or not at all. On the next wake, verify rather than assume, in one pass over three routes — the issue itself (`status` should read `in_review`), `GET /issues/<id>/attachments` (count, and every `byteSize` against the brief's numbers, plus a non-null `issueCommentId`), and `GET /issues/<id>/interactions` (one pending `request_item_verdicts` whose item ids are exactly the ones the brief listed). A card whose sizes or item ids disagree with the brief is showing a different set of pictures than the one you checked.

**Never repair a card you have not proven broken, and prove it at the attachments endpoint rather than the issue detail.** The issue payload does not carry its cards or its pictures — `interactions` reads an empty array and `attachments` reads `null` on `GET /issues/<id>`, even while a pending `request_item_verdicts` and every uploaded PNG sit on that issue, for every issue including one you built the card on.** Reading either field, or a status of `in_review` with no visible card, therefore looks exactly like a card that was never posted or never got its files — and the two mistakes are not the same size. A re-posted card is refused by the idempotency key, while a card wrongly judged empty gets a second upload of the same bytes, a replaced interaction, four attachment rows for two files, and a sentence on the owner's card that is simply false; the correction then has to sit on his card too, which costs more than the delayed read ever would. Always take the card list from `GET /issues/<id>/interactions`, the files from `GET /issues/<id>/attachments`, and check each payload `attachmentId` against that list before concluding anything about a card's pictures. The verdict is that entry's `status` (`pending` / `answered`) plus `resolvedAt`; never the issue's own `interactions` field and never `payload.items[].verdict`, which reads null on an answered card. One endpoint per question — the detail object answers neither.

**A second wake on the same card minutes later is not a new round, and `issue_assigned` on an `in_review` issue is that wake.** When the posting run ends and the card is already pending, the next heartbeat can arrive on the same issue with nothing new to answer: do not re-upload, rebuild or re-post, and do not read the assignment as leave to open another card. Spend that wake on the two things a second run can still add — the files against the hashes and byte sizes the description claims, and one crop pass over the props the card's prose counts **and over the caveats it states**. A caveat is a claim like a number, and this pass exists to find the wrong one before he reads the card against the picture.

**A full-frame claim of body contact is the count to re-cut first, and a tight crop usually beats it.** Two independent full-frame reads of a flux board said a hanging rope "loops snugly around his neck"; a crop of the head and shoulders at the frame's own resolution showed the rope behind the hair at the brick wall with visible separation, exactly as the card's caveat said. Read the same failure the other way too: a cord counted "six" in a full-frame read was one cord plus the edge of a review crop, and a crop of the board's underside settled it at five. When the crop agrees with the prose, no write is needed - the caveat already carries the finding; when it disagrees, line 39's short comment is the repair.

**The same wake after the verdicts are already applied is a duplicate, and the correct output is no write at all.** It arrives as `issue_commented` with `sourceRunId` equal to the run that created the card and the answered card in `interactionId`, so nothing about it is new: `result.complete` is true, the thread's last comment is your own closeout, and the render you are waiting for has its own monitor. Read the thread once to prove that (`GET comments?order=asc`, plus `GET interactions`), then end the run and say what you verified in the run report only. Posting a "no new direction, no writes" comment on the issue is the failure mode here — it answers your own trigger, buries the closeout the owner needs to read, and reads to a later run as a state change that needs analysis.

**The record filename drops the job id's leading dash, so the file carries two dashes and the frontmatter keeps one.** A job id of `-wrqiBF9yQo` names the record `...--wrqiBF9yQo.md` while `job_id:` reads `"-wrqiBF9yQo"` verbatim; writing the three dashes a literal join produces makes `verify-slot.py` strip `--` plus a dashless id, so it fails `heading is the stem` and prints a stem with a trailing `-`. The repair is `mv` on the filename (the heading is already right), never a rewrite of the record.

**Advance can hand the slot to a post whose replacement renders are already in the lane, and a card there would show the images the round exists to replace.** `next` reads `queue.json` only, so a post whose six round-1 jobs went straight into the render lane, with its round brief written and no `ready` entry, still looks like the next unopened post. Before creating anything, check that post's own notes and the renderer's `jobs.db` for jobs in the lane: when a round is in flight, run `backlog.py release` (the slot names no issue, so release returns the post to `todo`) and append a note naming the job ids and the ETA, so the collect owns the card. Opening the card instead puts the very pictures the campaign condemned in front of Wojtek, under a card he may answer before the replacements land.

**A wrong count in a live card's prose cannot be corrected in place, because the payload froze at the POST — a short comment naming the measured number and the crop that settled it is the repair.** Withdrawing a live card to fix a number costs the owner his click on every picture and hands back the same set. The comment costs nothing, the verdicts still count, and it should say which item, what the crop showed, and that the file on the card is unchanged.

**A caveat that is too harsh is the same defect in the other direction.** A caveat saying a part lacks a feature its twin has sends him hunting for something that is not there, and it spends the card's credibility on the lines that are right. Correct it in the same short comment, naming the neighbouring piece the read actually described, and leave the payload and the file alone.

## Retiring a pending card whose images fail the bar

A pending verdict card that shows a rejected-before-it-was-shown picture wastes the owner's time, and the card can be retired from a *different* run: `GET /issues/<id>/interactions`, `POST …/interactions/<iid>/withdraw` with a reason, then `PATCH /issues/<id>` to `cancelled` with a comment saying what replaces it and naming the new job ids. Withdraw and cancel are separate writes — a withdrawn interaction on an `in_review` issue leaves it waiting for nothing.

**When the card is yours and a corrected one follows in the same run, withdraw but do not cancel.** Retiring an issue to `cancelled` is for a card some *other* run is replacing. For a defect you found on your own frozen card, the order that leaves exactly one live waiting path is: `scripts/withdraw-interaction.py <issue> <interaction> <run-id> "<reason>"` → post the short comment saying what came off and what replaces it → build with `build-verdict-card.py` using `idempotency_key: verdicts:<issueId>:round-<k>-corrected` → `post-interaction.py` → `PATCH` the description to the items now on the card → leave the status `in_review`. The withdraw answers `200` with `status: cancelled` and the reason under `result.outcome: withdrawn`; read `status`, because a top-level `outcome` is absent on a correct cancel.

- **Reuse the withdrawn card's attachments when the files did not change.** `GET /attachments/<id>/content` for each `attachmentId` in the old payload and hash it against the staging PNG; a matching sha256 lets the new payload name the same ids, so nothing is re-uploaded and no second copy of the same bytes can drift from the checked file.
- **Name the withdrawn card, the rejected-nothing fact, and the held-back render on the new card's face.** A card that returns with a shorter item count and no sentence about the item that came off reads as a card that lost a picture.
- **`post-interaction.py` sends the file verbatim, so that file must be a whole interaction spec, not its `payload`.** A file holding only `version`/`prompt`/`items`/`detailsMarkdown` answers `400 Validation error … invalid_union … discriminator: "kind"` and creates no card — which reads as a card build that failed for an unrelated reason. Build a replacement by copying the `card-<n>-payload.json` that produced the original and substituting `payload.items[].attachmentId`, never by lifting the `payload` object out of the live interaction.
- **A replacement card needs its own `idempotencyKey`.** Reusing the one the frozen card was posted with answers the idempotency refusal, or hands back the very interaction you meant to replace; suffix the round key (`verdicts:<issue id>:round-<k>b`).
- **When the owner may be looking at the card, post the replacement before withdrawing the one it supersedes**, so the issue is never left with zero pending items; withdraw-then-replace is the order for a card coming off the board entirely.

**A card withdrawn before he ruled spends no round.** The three-round ceiling counts his decisions, so a card that reached no verdict leaves the request where it was: re-issue under the same round number, use the `-corrected` idempotency key, and say on the new card's face which withdrawn card it replaces and that nothing was rejected. A run that counts the withdrawal as a round escalates to a `request_confirmation` after two real rejections. The render that sat on the withdrawn card is recorded with that same distinction: its row reads `held back at the self-check before any verdict: <defect>; the card was withdrawn`, because the picture did reach the thread and no verdict was given — `never shown to Wojtek` is the row for a render a card never carried.

**The owner can also answer a pending card in the thread, and that settles it as `superseded_by_comment` with `result.items: []` — no verdict and no round spent.** Read the comment as his direction and apply it; do not post the same card again with the same pictures, and do not read the empty `items` as "he said nothing". When the comment rejects what is on the card, take the ordinary reject path in that run: a blanket comment about "the images" or "them" applies to every item, so mark every item's record rejected — not only the slots it happens to name — with his words as the reason and a row for the round; revise the prompts, save each as `~/image-studio/backlog/prompts/<item id>-r2.json`, submit `<slot>-r2` jobs, arm a 2-hour hop and `card-done <n> --rendering`. When it asks a question or leaves the pictures alone, answer in one comment and re-post a corrected card with the same items under the `-corrected` idempotency key. Say in the closing comment that the card was superseded by his comment and no round was spent, so the three-round ceiling is not advanced.

**A refusal here means the credential, not the boundary.** `interaction_run_attribution_required` on the withdraw and `403` on the PATCH, or a `403 cross_issue_influence_run_context_required` on your own issue, is the signature of a key belonging to another agent: the run-id header names your run while the key names theirs, so no `heartbeatRuns` row matches both. Re-read `references/paperclip-api.md` and prove the principal, then retry — both writes succeed as yourself, cross-issue, up to the per-run influence cap.

## A long render wait is a hop chain, not one monitor

The renderer queue is shared with every other run, so a card's wait is the queue's length, not the render time — a batch submitted behind seventy pending jobs is a night's work, and the FLUX pair can be hours from the ideograms.

- **Set 2-hour hops while the queue is deep, and shorten to the remaining ETA once the jobs reach the front.** A `nextCheckAt` many hours out is silently dropped; short ones persist, and a hop of about 45 minutes collects the FLUX pair the moment it lands instead of waiting out the ideograms. **This overrides the card procedure's "last job's ETA plus five" whenever `queue_ahead` is in the tens: that shape assumes an empty queue, and on a deep one the reported ETA is 11-13 hours out, so a single hop at it is the dropped-monitor case rather than a schedule.**
- **Read the pace from consecutive hops, not from `eta_minutes`.** The model assumes 21 minutes per ideogram and 3 per FLUX; an observed congested worker cleared 3.5–7 jobs an hour, so the reported ETA can be optimistic by 2×. Quote a range, and say plainly when the earlier estimate was wrong. **While a job is `running`, `eta_minutes` does not count down** — it keeps returning the engine's own duration (21 for an ideogram) until the job finishes, so it says nothing about that job's landing time: take the start from `started_at` or the first `running` sighting and add the duration, or just re-poll. **And a foreground `sleep` longer than about seven minutes is killed before it returns**, so a wait inside one run is repeats of `sleep 330-380` with a status check between them; anything longer is a monitor hop, not a sleep.
- **The worker's `started_at` and `finished_at` can be the Max's local time, so a job that is already `done` can show a `finished_at` an hour or more ahead of `date -u`.** Do not read that as a future timestamp or as the job not being ready: `status: done` plus an existing `output_path` is the authority, and the safe move is to fetch and check the file. Use `created_at` (UTC) and your own `date -u` for hop arithmetic, never those two fields.
- **Re-read every job of the card at each wake** (one `imagegen status <job>` per job, parsed for status / `queue_ahead` / `eta_minutes`) and fetch the `done` ones before re-arming: the fast engine's frames are worth checking while the slow ones still run, and a render that fails can be resubmitted behind the queue instead of costing a whole wake. **A failed job still reports an `output_path`, but the file is never written, so `imagegen fetch` on it errors — re-submit with the same prompt and name, and treat the new job id and its hash-suffixed output filename as a fresh attempt. When every job of a batch fails within the same few minutes with the same engine error, it is one worker failure, not as many bad prompts: resubmit them all unchanged in one pass and name every failed id in the comment and the queue note, so the records stay honest without a held-back row for an attempt that never reached the model.**
- **A hop can land well after its `nextCheckAt`** — hours late under load — so run `date -u` first thing on every wake and recompute the next hop from the real clock and the ETA you just read. Planning the next hop from the timestamp you stored in the last wake drifts the whole chain.
- **Keep the numbers in `backlog.py note` and in the monitor's `notes`, and comment on the card only when the state changes.** A hop that finds nothing new is bookkeeping, not news; six heartbeat comments on one card bury the one that matters.
- **`executionPolicy.monitor.notes` is capped at 500 characters.** A longer note answers `400 Validation error` with `too_big ... maximum 500` and the monitor is **not** set, so the run ends believing it armed a wake and `monitorNextCheckAt` reads null on the read-back. Keep the note to the job id, the checks the wake runs and the single next write; the fetch recipe, the asset paths and the queue steps belong in the `backlog.py note` and in the brief, which have room.
- **Check for a sibling once per long wait** — `GET /issues/<id>/activity`, and read the `runId` on the newest events: all your own runs means the card is yours alone, which is the precondition for trusting that no duplicate render is coming.
- **A monitor may run alongside a pending card, but only to collect renders — never as a second review path.** The card is what brings the verdicts back; the monitor exists when replacement renders are queued that would otherwise have no wake path at all (a spare that must be fetched and self-checked before it can answer a rejection, or a held-back slot's second attempt). Keep it bounded (`maxAttempts`, `timeoutAt`), set it on the card's own issue so the wake lands where the work is, and write in `notes` what the wake does — fetch and check, do not open a second card, leave the pending card alone. A wake that finds the card still `pending` collects the frames into staging, reports them and re-arms; it must not create a second card for the same round, and it must not read the silence as a reason to withdraw and repost the card.

**The runner's own monitor is part of its disposition: a runner wake that leaves `monitorNextCheckAt` null has not finished, it has parked.** Paperclip reads a wake that ends with no armed wake, no pending card and no terminal state as a wait without a target, and raises a disposition repair against the issue — an extra run spent fixing what the first one should have written. So the re-arm is the last write of a runner run, and the read-back must show a non-null `monitorNextCheckAt` alongside `in_progress`, your own `assigneeAgentId` and a null `assigneeUserId`. **A boundary worth knowing: when the bounded re-arm body is refused — a spent `maxAttempts` budget answers with a bounds error — send the minimal body (issue id and `nextCheckAt`, no bounds) and confirm it took.** The minimal body still arms after the attempt budget is exhausted, and a refused re-arm that was never read back is indistinguishable from a landed one until the next heartbeat never comes.

## The number of your own cards he is holding is the campaign's real limit

The render lane is rationed by the six-slot cap, but the review queue is rationed by his sitting and by nothing else, and it fills faster than renders land. So the limit on work in flight is not "one card per post" — it is **one unanswered card of yours at a time where possible, and never more than two**. While two of your own cards sit with every item pending, a new post gets its prompts written, linted and staged in `backlog/prompts/` and a queue note naming them; it does not get a card. A third card costs him a sitting without moving any post closer to done, and every extra card is one more chance for a blanket yes on pictures you wanted him to judge.

- **A staged prompt with no card is not wasted work — it is the whole of what a render outage can still buy.** On a hop whose probe fails, spend it on the next post in reading order: audit its live records at prompt level, write and lint the prompts for every slot, and record in `backlog.py note <n>` the draft path, each slot name, the prompt file that serves it and its word count, with one line saying do not re-audit and do not open a card before the collect. That note is what stops the next run, or your own next hop, from re-deriving three prompts that already exist on disk.
- **Submit a staged backlog as one batch, because a clean window is minutes wide.** Five staged renders across two posts go in together the moment a probe returns pixels; submitting them after the fetch waits out the window, and a half-submitted post then reads as work in flight while its siblings have no job id.
- **When the engine is the thing that keeps failing, the cap on unanswered cards yields to the window — and the yield is stated, not silent.** The "never more than two" above is a rule about his attention under a healthy renderer. When the path has been down for hours at a stretch and a probe finally answers, holding a checked batch back costs the work twice: the next window may be a day away, and frames left in staging go stale behind the following outage. So submit in the window, card what passes in that same run, and keep the count honest in one sentence of the comment — which limit this run is breaking, why, and that no further post is staged until one of those cards is answered. A limit broken knowingly and declared is a decision he can reverse; the same limit quietly abandoned is the drift the rule exists to prevent.

## A held-back round 1 is a render round with no card

When every draft image fails the show bar on a round-1 backlog card, there is no verdict and nothing to review: rewrite the prompts, submit the pair per slot (three slots × two engines is the six-render cap), `backlog.py note <n>` the failures and the job ids, and `card-done <n> --rendering`. That release is the default, not a narrow exception — the queue's single slot token is what every other post's card is waiting for, and a slot held through a night-deep render stops the whole backlog. Advance then opens the next post's card.

**The all-fail case is the only round-1 shape that becomes a render round with no card; a mixed card reviews the embeds.** A backlog-review card's items are the files the draft already carries, so the normal round 1 puts every slot on the card and names each defect plainly in its check note — a pasted overlay, invented lettering, a count that changes the beat. His rejection is what starts the re-render, and holding a draft slot back while carding its siblings asks him to rule on a post whose picture he cannot see. The show-bar hold governs the renders you produce for a later round and the repair campaign, not the embeds a review card exists to judge; the brief's `Do not render anything for round 1` is that same rule stated from the queue's side. A draft slot that fails still goes on the card unless every slot fails (the all-fail shape above) — or you already hold its replacement, in which case the replacement is the item.

**The renders' card is still the post's round 1, and it is a new issue opened from `ready`.** At the collect wake: fetch and check, write the brief, `ready <n> 1 <brief>`, `batch-open-ready 1`, POST the card issue, `batch-opened <n> <ID>`. Do not put that card on the render-round issue: a card there leaves the post in `rendering` with no slot and no batch entry naming it, which is indistinguishable from a released post and is what the runner's scan reports as a stall. Its legend is the render legend (`Approve: this render replaces the old image in the draft`), never the round-1 keep-it wording, because nothing on it is already in the draft.

**A collected round that still owes one slot keeps the render-round issue open as that slot's collector.** The collect wake can find every shipped render passing while one slot's ideogram is held back with its replacement hours out. Do the shipped half through the queue as above, and keep the render-round issue `in_progress` with a two-hour hop: the new card's run is not a monitor and a closed issue cannot hold one, so that issue is the only thing that can wake anyone to fetch the replacement. Put the replacement's job id and its real ETA in the monitor `notes` so an early hop re-arms without re-deciding anything, and say in the shipped card's brief and in the render-round comment that `card-done <n>` belongs to the card that answers the last slot — otherwise the run on the shipped card releases a post still waiting on a render, and the deferred slot's card opens with nothing tracking it.

**A release is never followed by a second card for a round that already has one.** The duplicate to avoid is a card created for items whose card already exists; a new issue for a round that has no card is the intended path, which is why the queue is the record of which case you are in — read `q["batch"]` and `q["ready"]` before opening anything.

- **The show bar tests defects, not exact prop counts.** A frame that draws two canisters where the prompt asked for three is a deviation to name in the check note, not a hold; hold it only when the missing item changes what the picture says.

- **The two items of a slot are `<slot>` and `<slot>-flux`, and a slot that ships one engine keeps that engine's name in the item id.** "Two items per slot" needs the ids written down, because the item id is the join key for the record, the vault filename and the post's embed: an ideogram carries the brief's bare slot id, and the flux companion carries `<slot>-flux`. When the ideogram is the one held back, the card's single row for that slot is `<slot>-flux` — not the bare id — or the picture that ships becomes a record and an asset whose names claim the main engine, and the next round cannot tell which engine produced the file it is comparing against. Name the engine and the job id in the item's description as well, since the id alone only carries the suffix.
- **A companion that fails the bar does not go on the card, and it does not hold the card either.** Hold it, resubmit as `<slot>-r1-flux-b`, and post the card with an odd item count — the slot carries its Ideogram and the remaining pairs carry theirs. Waiting for the replacement to make every slot a pair parks the round behind a queue the replacement is at the back of, which can be most of a day. Name the held-back attempt's job id and the replacement's job id in the note so the slot's history keeps both, and say in the closing comment that the slot shipped one engine this round.
- **A slot held with no card on it needs a note on the runner the first time the wait is measured in hours** — the job ids, the engines, the ETA, the queue depth, and one line saying do not re-render and do not release. The daily watchdog judges a slot over 24 hours old by holder state, and "recorded, not `in_review`, no pending card" reads to it as a dead run it should repair by re-rendering the slot.

## A card whose brief is a render plan

A round-2 card can arrive carrying a *plan*, not a checked round: its brief names the slots and the prompt files, but those files are not on disk and no job id exists yet. Read that as the card's own run starting at skill step 2, not as a missing render and not as a stall.

- **Write the prompts, lint, check the boxes, submit, arm the monitor, end the run.** One ideogram JSON plus one FLUX text per slot from the compositions in the brief; `lint` each to risk 0 with no flagged terms; `check-bboxes.py` on each JSON; submit as a `<slot>-r<k>` pair. Nothing goes on a card at that wake — a card for renders that do not exist is the defect the campaign forbids, and a "coming soon" item is the same defect one wake later.
- **The collect wake posts the round's verdict card on that same issue**, because the issue already *is* the round's card and its brief is the plan. This is the one shape where the round-2 card is not a new issue opened from `ready`: `ready` stays untouched and the monitor rides the card issue.
- **Two slots × two engines is four jobs, so the six-render cap is not the constraint — the queue is.** Read `queue_ahead` and `eta_minutes` per job immediately after submitting. A sibling-deep queue puts the last job hours out and spreads the pairs apart, so set the first hop at the last job's ETA plus five and put the real range in the issue comment instead of implying the pairs land together.
- **Record the submission with `backlog.py note` before ending the run** — each job id with its engine and slot, the prompt file names, the lint and bbox results, the ETAs. A run that dies before the collect wake otherwise leaves the ids unrecoverable, and a re-submitted pair costs a render plus a second record for one attempt.
- **A round slot that names no issue while its card already exists is the same window:** the creating run died between the issue POST and the `opened` call, so the repair is `backlog.py opened <n> <ID>` (it is guarded and refuses unless the slot still holds that post). Do not `release` — that hands a post with a live card back to the queue, and the next Advance opens a second card for it.
- **Make the writes from the script, not the command line.** `scripts/paperclip-write.py comment|patch|monitor|read` takes a body file and the run id, sends the header itself, and exits non-zero when the server refuses or when the read-back shows the field did not take — so a run can tell a landed write from a silent one.

## A partial verdict is applied as it lands

An item-verdict card stays `state: pending` after the owner resolves only some of its items, and the wake for it can arrive as an ordinary `issue_commented` whose `sourceRunId` is your own run, with the card still listed in `unresolvedInteractionIds`. Do not read the wake reason, the interaction `state` or that list as "no verdict yet": `GET /issues/<id>/interactions` and read `result.items[]`. Each resolved entry carries its `verdict`, its `reason` (empty means write `Approved on review.`), and `resolvedByUserId` set with `resolvedByAgentId` null — that row is the verdict, and the absence of one from `result.items` is what a real wait looks like.

Apply every resolved item in the same run and leave the issue `in_review` for the rest:

- **An approved render is copied and wired, not just recorded, and the target path depends on whether the draft already embeds that slot.** The case is set by whether the approved image is the one the draft already embeds or a replacement render — not by the card's round number. A round-1 card can carry a re-render (a slot held back at self-check and re-rendered before the card was posted) and its approval is still the full case: preserve the displaced file, copy the new bytes, rewrite the alt text, write the studio record, set superseded_by on every earlier record. Only an approval of the embedded original is the back-fill case (touch that record only). When the render replaces a picture the post already carries — a backlog re-review of an existing slot, which is what most round-1 approvals are — copy over the path the draft already embeds (`assets/<draft date>/<slug>.png`) after preserving the displaced file beside it as `<slug>.superseded-<old job id>.png`; the folder is the draft's date, not the render's, and the card's `detailsMarkdown` normally names both paths, so follow the card's promise over the generic route below. When the slot has no picture in the draft at all — a missing image, a new slot, or a later round whose brief repoints the embed — the copy goes to `tech_blog/assets/<render date>/<item id>.png`. Compare `shasum -a 256` of the copy against the staging file before going further.
- Repoint that slot's embed only, and rewrite its alt text to describe the picture now in the file — a stale alt text belongs to a different picture, while an unused slot's embed is not yours to touch until its own verdict lands.
- Write the new record for the approved job with the slot's history in `## Why` and a `## Prompt` block byte-identical to the prompt file. **Splice the file's own text into the block; never re-serialise the job's `prompt_value`.** `json.dumps(json.loads(prompt_value), indent=2)` can differ from the submitted file in escaping or key order and still land on the same byte count, so `verify-slot.py` fails `prompt block is the submitted file byte for byte` while printing two equal numbers — a failure that reads as a broken checker on a correct record. A trailing newline is the benign case the comparison already forgives; compare against the file on disk, never against your own dump.
- Mark the record the approved render supersedes, and let what that record documents decide the row. A render **you generated and withheld at the self-check** was never in a draft, so it gets `approve_record.py <old record> --rejected --reason "Held back at my self-check, never shown to Wojtek: <the defect>"`. A **draft picture that was in the post until this approval** is the other case: nobody judged it — he judged its replacement — so it keeps `verdict: unreviewed` and only `superseded_by` is set; writing `rejected` there puts a verdict in his name and erases the library's only statement that the image was never judged, and `verify-slot.py` treats such a record as an `--earlier` member whose verdict must not equal this approval. Either way set `superseded_by` to the approved job id and touch no other line of the old record.
- **A render that failed the self-check and never reached the vault gets its own record, not just a note.** Write it with `asset: null`, `asset_location: "max-only"`, `asset_present: false`, `verdict: "rejected"`, `superseded_by` set to the job that replaced it, and a Verdicts row whose reason says `Held back at my self-check, never shown to Wojtek: <the measured defect>`. **The enum has two values and neither is `staging`:** `asset_location` describes a vault copy (`vault`) or its absence (`max-only`), so a third value passes every reader that does not switch on the field and a run that writes it once carries it into every attempt of the round. The staging path and the byte size belong in `## Why`, where they are prose; before the close, `grep -l 'asset_location: "staging"' 3-resources/image-library/<YYYY-MM>/*.md` must print nothing. Leave the staging file in place and name its path in `## Why`. **The `## Prompt` block must carry the actual submitted prompt file's bytes, not a placeholder or a summary:** the record is the audit trail for which attempt produced which defect, and a later round that re-renders from "the held-back prompt" needs the exact file. Without that record the slot's history shows a gap between the render the owner judged and the one that shipped, and the next round cannot tell which attempt produced which defect.
- **An approved record carries a `## Verdicts` table with at least one data row, even when written by hand.** A record written directly (not promoted from a candidate, not via `approve_record.py`) ships with the header and separator only if you forget it, and `verify-slot.py` fails the check that asserts a data row. Candidate records are the only records whose table stays header-plus-separator; the moment a verdict lands, append the row (`| <round> | <date> | approved | <reason> | [GUL-<n>](/GUL/issues/GUL-<n>) |`). The reason cell for a silent approval reads `<stem>--<job>: Approved on review; no reason given.`

**A record shared by two posts has already lost its marker by the time the second card reviews it.** The same image can be embedded in two drafts (the header is the common case), and each post's card reviews it independently. The first card's `approve_record.py` run removes the `Back-filled from jobs.db; not reviewed yet.` marker and sets the frontmatter `verdict`. The second card's `approve_record.py` then fails with "has no marker line" because the marker is gone. The fix: update the frontmatter `verdict` to the new verdict and append a new row manually (same row shape as above), without touching the earlier row. The Verdicts table then carries one row per card, each with its own issue link, and the frontmatter reflects the latest review. Do not re-run `approve_record.py` on a markerless record, and do not delete or rewrite the earlier row — the table is append-only per card.
- Retain the taste memory when the card has fully resolved, not per item — one approval on a card that is still pending is a data point in flight, and recording it now splits one card into several.

**A bulk approve that resolves a paired card approves both engines of every slot, and that is an answer, not an ambiguity.** Each slot's ideogram and its `<slot>-flux` companion arrive approved in one submit, and the shipping rule decides the rest: the ideogram carries the draft, the companion keeps its own record as an approved comparison copy (`asset_location: "vault"`, `asset_present: true`, no embed, `superseded_by: null` — `references/library-records.md`). Do not open a question about which engine he meant, and never write the companion as `rejected`: a rejected row is a verdict he did not give, and an approval-shaped `verify-slot.py` run then reports three failures on a render he accepted. Say in the closing comment which engine shipped and that the swap would be one embed edit, because the approved file is already in the vault and the record already carries the job id. **That copy goes where the post's own images already live, and its existing siblings decide which folder that is.** When the draft's other approved slots keep their `<slot>-flux.png` beside the images under the draft's date, the new companion goes into that same folder, so the pair a reader compares sits together and the post keeps one naming convention; when the post has no such precedent, use the render's own date (`tech_blog/assets/<render date>/<item id>.png`). Decide it before the copy and say it once in the closing comment, because one post holding its companions in two day folders is what makes the next reader hunt for the name that is "wrong".

**A card that splits one slot — the ideogram rejected and its `<slot>-flux` approved — ships no new embed for that slot, because the approved item is the companion whose id says so.** Copy the approved twin to the vault as an approved comparison copy (its own record, `asset_location: "vault"`, `asset_present: true`, no embed, `superseded_by: null`) and leave `assets/<draft date>/<slot>.png` holding whatever it held before. Swapping the engine into the embed is an edit the owner asks for, and doing it unasked puts the next round's picture beside a file whose name claims the main engine. The rejected ideogram goes back to a re-render built from his reason, the batch card closes `card-done <n> --rendering`, and the post stays open until the slot holds an accepted render of its own.

**At the collect wake the answered card's issue closes `done`, because the round's next card is a new issue.** Do the queue hand-off first (`ready <n> <k> <brief>` → `batch-open-ready 1` → POST the card issue → `batch-opened <n> <ID>`), then PATCH the old issue `done` with the closeout: what shipped and where, what was held back, and the new card's identifier. An answered card left `in_progress` under a spent monitor is a second live path to nothing, and the runner's scan cannot tell it from work still in flight — while the new issue is claimed within seconds and owns the round from then on.

**A single-post monitor wake that creates the round-2 card must post the staging paths to that card in the same run.** `backlog.py next` creates the issue and its description is frozen from the brief, but the brief carries only the handoff text — the PNGs are not attached and the successor run cannot see them. Post one comment on the new issue naming every staging path, byte size and sha256, with a line saying the files are **not** attached, so the successor run can upload them; the successor run reads that comment, not the brief's prose, to find the files. Close the current issue only after that comment lands, because a closed issue with no path pointer leaves the round-2 run with nothing to upload.

## Candidate records belong beside the card, not beside the verdict

Write one candidate library record per render in the same run that posts the verdict card: `asset: null`, `asset_location: "max-only"`, `asset_present: false`, `superseded_by: null`, `verdict: "unreviewed"`, `source: "studio"`, no `![[…]]` embed, and the Verdicts table left as header plus separator. Take `created_at`, `finished_at`, the stem and the prompt from that job's own `imagegen status` line. The reason is mechanical, not tidy: `library_backfill.py` skips a job only on the exact `<stem>--<job_id>` filename, so a card whose renders have no record invites a second `unreviewed` record for a job that is already on a card.

**A later wake that finds the card pending and the records missing writes them, and that is what "the only thing left is the record" means.** The pending-card wake (`issue_assigned` on an `in_review` issue) must not re-render, re-upload or re-post the card; it checks the card's items against the attachments and then fills in whatever durable record the card run left out. Settle each record's `## Why` quote by line position in the post, ignoring `#` lines inside fenced code blocks — a YAML excerpt's `# apps/...` comment is not the nearest heading, and a fence-blind check flags a correct record as mismatched provenance.

## The close of a re-review, in order

The whole close is cheap and mechanical; do it in this order so a failure lands before the writes that depend on it.

**The close only starts after the verdict card is answered.** A monitor wake, an `issue_assigned` wake, or a continuation on a card that is still `pending` collects renders, checks them, and arms the next hop — it does not copy to the vault, promote candidate records to `approved`, edit the post's embeds, or run `card-done`. Those writes are the close of a *verdict*, and the verdict is the only thing that authorises them. If the card answers mid-run while you are still bookkeeping, re-read `GET /issues/<id>/interactions` first (line 140 above): a `pending` card means the run ends, an `answered` card means the close starts now. A close performed on a pending card is a verdict written in your own name — the one rule this skill exists to keep — and the records it produces are wrong even when the numbers happen to match.

1. **Copy, preserving what you displace.** `cp` the staging PNG over the path the draft embeds, after `cp` the file already there to `<slug>.superseded-<old job id>.png` — the displaced record keeps `asset:` pointing at the live path, so the preserved file is the only one left that still matches its prompt. Compare `shasum -a 256` against staging. The folder is the draft's date, not the render's.
2. **Then the post: that slot's embed only.** Rewrite its alt text from the picture now in the file, and **treat a placeholder caption as part of this close**: `verify-slot.py` fails `alt text describes the picture, not a placeholder word` when the draft's caption is the slot label itself (`header`), and that embed belongs to the approved render, so rewriting it is inside the close even when the brief named only another slot's stale caption.
3. **Promote the candidate record; do not rebuild it.** Three changes plus one addition: `verdict: "approved"`, `asset:` / `asset_location: "vault"` / `asset_present: true`, one Verdicts row appended by hand (`approve_record.py` refuses a studio record — it performs the back-fill's three edits and nothing else), and a `![[<asset>]]` line under the heading. **`verify-slot.py` does not assert that embed**, so prove it by grepping the record for its own `asset:` value and expecting two hits: frontmatter and embed. Its reason cell for a silent approval reads `<stem>--<job>: Approved on review; no reason given.`
4. **Chain every earlier record of the slot**, one line at a time: `superseded_by: "<approved job>"`, verdict untouched — a draft picture nobody judged keeps `unreviewed`, a held-back attempt keeps `rejected`.
5. **Verify with `verify-slot.py --record … --job … --earlier … --post <post path> --prompt <prompt file> --asset-source <staging PNG path>`.** **`--asset-source` takes the source file's path, not the word `vault`** — the literal string is opened as a filename and the run dies with `FileNotFoundError: 'vault'` after twelve green checks, on a slot that is otherwise clean. **`--earlier` takes one path per flag, so repeat the flag for every earlier record** (`--earlier a.md --earlier b.md`). One `--earlier` followed by several paths is answered `unrecognized arguments` for all but the first and no check runs at all. The total grows with that set — a slot with eight earlier records printed 83 checks, 0 failed, where a lone slot prints about 41 — so quote the number with its earlier count instead of reading a large total as a defect. A comparison copy runs with no `--earlier` and fails exactly the post-embed check.

**Two `verify-slot.py` failures on a healthy record are record defects and both are cheap.** `record carries a prompt block in a fence` reads a ```json fence or a bare ``` fence and nothing else, so a nanobanana record whose prompt sits in a ```text fence fails with the block plainly present — rewrite the opening fence to a bare ```. And `quote appears in the post` failing while `quote found by line position in the post` passes means the `## Why` quote lost characters, usually every inline code span, leaving text like "instead of one , it now has two": the line-position pass is the tell that the provenance is right and only the characters are missing, so quote a verbatim paragraph that carries no inline code or restore the spans. **An approved record can also carry an empty `## Prompt` block** when the run that wrote it dropped the fence contents; refill it from the file in `backlog/prompts/`, never from the job's re-serialised prompt, and re-run.
6. **Then the queue and the issue:** `backlog.py card-done <n>` (plain when every slot holds an accepted asset), one `backlog.py note <n>` carrying the job ids, hashes, preserved files and the captions rewritten, the closing comment, and `PATCH {"status":"done"}`. **The status write and the closing comment can be one request:** build `{"status": "done", "comment": "<the whole closing comment>"}` from the markdown file and send it with `scripts/paperclip-write.py patch --json-file <file>`, which carries the run-id header itself and exits non-zero unless the response echoes `status: done`. The short-comment warning is about a hand-sliced body — a PATCH `comment` built by taking a markdown file's first line posts a bare heading under the real comment — never about length.

## His reason in a Verdicts table

The table is one row per verdict, so quote his words verbatim but collapse the line breaks: a blank line between two clauses becomes ` / `. `approve_record.py --rejected --reason "..."` writes the string straight into the cell, so a reason passed with real newlines breaks the table that is supposed to store it.

**A reason about text readability splits into two cases, and the split is the whole decision.** "text not readable", "text not human language", "must be valid English", "must be valid plain English", "human readable", "human readable plain valid English", "garbled text", "unreadable lettering" applied to text that is *already on the image* — these mean the same thing under the standing series rule: no baked-in readable text. The re-render drops every text-bearing surface (tables, panels, banners, monitors, labels) and carries the information as shapes, icons, or absence. **A conditional phrase belongs in this case, not the next: "if you are using text, it must be plain english perfectly readable" is satisfied by using no text, so the re-render removes the text rather than adding labels; "this must be human readable" said about a frame full of random characters is the same complaint.** Rewriting the garbled text as proper English still violates the rule. But when the reason instead asks for *more* readable text to be present — "texts must be readable by human", "always make text in english unless i ask for different language", "nothing human readable there" on a render that has none — that is an explicit verdict and it overrides the standing series rule: the re-render includes clean readable English labels with valid content (real service names, real log lines, actual logos). The standing rule is the default; his verdict is the override. Read the reason for which case it is — does it complain about text that exists, or ask for text that is missing — before choosing removal or addition, and say in the closing comment which case you read it as. **Do not end the verdict-handling comment without naming the case (case-1 removal / case-2 addition / ambiguous → asked):** a comment that only describes the fix leaves the next reader to guess which rule was applied, and a case-1 fix misread as case-2 (or the reverse) ships a render with the wrong text policy. **When the reason does both at once (complains about garbled existing text AND dictates the words that should replace it), it is the ambiguous case: do not pick a side on your own. Open an `ask_user_questions` card (`resolverPolicy: human_only`, `continuationPolicy: wake_assignee`) offering removal (wordless — the recommended default) versus readable English labels (dictated exact words, spelling risk), and follow his pick; say in the closing comment which case you read it as and that you asked.**

**A case-1 re-render is a deletion, not a rewrite, and it takes the palette with it.** Removing the text-bearing surfaces (tables, panels, banners, monitors, labels) is only half the job: the original prompt's `color_palette` array is what renders as the swatch strip (engine pitfall 34), so drop `color_palette` from the JSON as well and carry the series look through `aesthetics`, `lighting` and `art_style` only. Lint the result to risk 0 and confirm no `text` elements remain before submitting. If the rejected image also carried pasted UI overlays or a palette strip, those are the same defect class, not new ones — do not add a ban naming them, since a negative clause leaves the noun in the file (pitfall 62); delete the request and fill the freed corner with a described physical object.

**A wordless case-1 prompt can still return the series' cap name, so crop the cap before writing "no lettering anywhere".** The cap is a label face and the series puts the character's own name on it; the model draws it even when the element description says "no text on the cap". A full-frame read reports no lettering while a 4x-6x crop of the cap shows the name, so a check note that says the frame is wordless is a claim you have not settled. Read the crop: a clean, complete name is the series' signature and belongs in the check note as such (do not read it as invented pseudo-text — the case-1 defect is random or garbled words, not the character's own name); letters that are partial, cramped or malformed are a lettering defect and a hold-back. Do not report the removal as complete until the cap has been read.

## A backlog card can carry the pre-audit originals, and that card is retired rather than commented on

`hold-back-or-ship.md` says never to touch another run's card, with one flagged embed and a clean card as its case. This is the other case and it is decided differently. A backlog-review card opened by the runner **before the campaign audited the post** lists the draft's current embeds, and on a pre-2026-10 back-fill post those embeds are the broken originals — the very pictures the audit exists to replace. The scripts will pass on them (the palette strip and grey-bar checks read the edge, not the idiom), so nothing mechanical raises a hand.

- **Read every item on an `in_review` post card against the prompt-level triggers before assuming it is somebody's work in progress.** Open its attachments, get each `byteSize`, and resolve each to the file in the vault. Two or more items whose library record carries `color_palette`, a literal mark or a text surface is a card showing the September pictures.
- **A card that is still being built is the other case and takes a comment, never a withdrawal.** `in_progress` with no attachments and no pending interaction means the card's own run has not chosen its items yet: comment on it with the embed paths, which check each file fails, and the two clean options (hold the card until the replacements exist, or post it saying plainly that the image is unreplaced), plus the staged prompt paths so nobody re-audits — and leave the card alone. Withdrawing a card mid-build kills a builder that is still working; `hold-back-or-ship.md` carries the comment shape.
- **When that is what you find, retire the card from your run**: `POST /issues/<id>/interactions/<iid>/withdraw` with a reason that names each failing file and what was seen in it, a comment on the issue saying which item is fine and which replace them, `PATCH /issues/<id>` to `cancelled`, then `backlog.py card-done <n> --rendering` so the post returns to the render lane instead of sitting `card` behind a dead entry.
- **Say that nothing was rejected.** A withdrawn card spends no round and asks him for nothing, and the thread must read that way — otherwise a card that vanished looks like a round he missed.
- **Retire a card only when its replacement is in hand, because a withdrawn interaction leaves him nothing to click.** With the card withdrawn and its issue cancelled, the owner's next move is *"there is no card i can approve all images here, or consider all images approved and just continue"*, and a run then records every item approved on that sentence while the draft still embeds the pictures the retirement was meant to remove. He is not approving them — a blanket yes is the only move the thread offers. So withdraw only with the re-render already submitted, or the prompts staged and the engine path proven; post the corrected card in the same working session; and when the wait is measured in hours, leave the card pending with the defect named on it instead of pulling it.
- **The replacement card carries all the slots at once.** The point of the retirement is that he never judges a broken picture to reach a clean one, so the corrected card waits for every render, and an item that was already approved (the header, usually) keeps its attachment.
- **A post reading `done` is a claim, not a fact: resolve its embeds before you trust it.** `card-done` writes `done` from the card's verdicts, and a blanket approval records every item approved whether or not a picture was replaced — so a finished post can still embed the very originals the round existed to swap, and nothing in the queue says so. After any close you did not perform yourself, or any close whose items were pre-audit files, `grep -n '!\['` the draft and compare each asset's byte size against the originals' known sizes. The queue state is the least reliable evidence in this flow; the draft and the vault are the evidence.
- **Reopening a `done` post has no dedicated verb, and `ready <n> <k> <brief>` is the honest repair.** `card-done <n> --rendering` refuses because the slot is not held by that post, and `reopen-card` needs a batch or `ready` entry to rebuild from — but `ready` demands only a brief file that exists. Write the round brief (the failing files with their byte sizes, the staged prompt paths and word counts, what is already approved and must not be re-rendered, the collect checks, and the close order), then `backlog.py ready <n> <k> <brief>`; the post moves to `ready` and the round is queued without any hand-edit of `queue.json`.

## When both variants of a slot are approved (bulk approve)

When a verdict card comes back with both the ideogram and flux variants of a slot approved, the approval does not mean both ship. The slot count (one image per slot in the post) still decides how many images ship, and the records-beat-memory rule applies: two variants approved on one card is one data point, not a preference.

- Ship the **primary** variant (ideogram, the one listed first on the card) to the canonical vault path from the brief, overwriting the old asset. Copy the **alternate** (flux) to a `-flux` suffixed path in the same folder so the approved alternate stays reachable, and write a library record for both (approved, round k).
- Repoint only the slot's embed at the canonical (primary) path and rewrite the alt text to describe the new picture. Do not embed the alternate.
- Set `superseded_by` on every earlier record of the slot to the **primary's** job id.
- State the choice plainly in the closing comment: both were approved, primary is embedded, alternate is in the vault under its suffixed name and recorded as approved, and offer to swap if Wojtek prefers the alternate. Do not silently pick without saying so.
- This is the handling when all variants pass; it is not a licence to ship both. Two variants approved on one card is one data point, not a rule (SKILL.md).

- **When both engines of a replacement pass self-check, ship the one consistent with the rest of the card's engine and record the other as the non-shipping attempt in the comment; do not put both on the card.** A held-back slot's two replacements (ideogram + flux) can both clear the show bar; the card stays on one engine so the owner judges one picture per slot, and the other engine's job id and its self-check result are named in the comment as the attempt that did not ship. Putting both on the card spends a second interruption on a comparison the owner did not ask for, and a spare that is never needed is one file in staging.

**A closeout comment that announces a skill or file change is posted only after the write has landed.** The skill files sit near a hard size ceiling, so the order is: make the write, confirm it (byte count or a re-read), then write the comment line that names it. A comment written first and a patch refused afterwards leaves a false claim on the board that the next run trusts and repeats, and correcting it costs a second comment on an issue the owner reads.

## Counting the campaign's totals when `next` says `finished`

The closing comment's numbers come from the record rows, and the whole library is the wrong denominator because it spans every campaign. Build the card-issue set from the queue (`{i for p in posts for i in p["issues"]}`), then count Verdicts rows whose issue cell names one of those ids, and split the approved rows by their record's `source`: an approval on a back-filled record is an original file kept in the draft, an approval on a `studio` or `backlog-review` record is a re-render that shipped. Read `keep-as-is` out of the reason cells, report `deferred` rows apart from it and say what they were — a spare companion deferred is not a blog image kept — and say plainly that a row reading `unreviewed` in the verdict column is a draft replaced before it reached a card, not a verdict.
