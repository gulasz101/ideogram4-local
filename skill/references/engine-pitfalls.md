# Engine pitfalls


**This file is shared, and two agents can write it in the same minute.** Re-read it immediately before patching, append at the end rather than renumbering, and if your `old_string` no longer matches, re-read and find the number your lesson actually landed on — a concurrent run may have taken it. Read the file back after writing, and report the number you used on the issue so a reader can find the lesson. Never renumber the existing entries to make room: the numbers are cited from `SKILL.md` and from issue comments.

1. **Always set `IDEOGRAM4_MODELS_DIR=~/sd.cpp-models`.** The old default `./models` made the worker re-download 10.6 GB of diffusion weights into the repo. The default is now `~/sd.cpp-models`, but always export it explicitly in scripts.

2. **The real safety-filter fix is a combination, not a single lever.** On 2026-07-06 we proved that neither the `DreamFast Heretic` encoder nor the `HauhauCS Aggressive` encoder alone cleared a dense beach canary. The working recipe is: (a) use the **HauhauCS Aggressive** encoder as `--llm`, and (b) write a **schema-compliant canonical JSON** prompt with no clothing/anatomy nouns and no `canvas`/`layout` fields. See `references/heretic-encoder-swap.md` for the exact prompt template and A/B results.

3. **Use the official Ideogram 4 schema, not a custom one.** After reviewing `ideogram-oss/ideogram4` (2026-07-10), the verifier only allows `high_level_description`, `style_description`, and `compositional_deconstruction` at the top level; `style_description` requires exactly one of `photo` or `art_style`; `compositional_deconstruction` contains exactly `background` and `elements`. Extra keys like `canvas`/`layout` are off-distribution and increase grey-box risk. See `references/ideogram4-oss-schema.md`.

4. **Capture stdout correctly.** The `submit` command prints the job ID to stdout and logs to stderr. Use `JOB_ID=$(python3 ideogram4_local.py submit ... 2>/tmp/log.txt)`.

5. **Do not cancel a running job.** Once `sd-cli` has loaded models, killing it wastes the progress. Either wait for completion or accept the waste.

6. **Load the LaunchAgent after the current generation finishes.** Loading launchd while a manual worker is mid-generation can create lock confusion. Let the manual worker finish, kill it, remove the stale lock, mark the finished job `done` in SQLite if needed, then load the plist.

7. **Cron `MEDIA:` lines do not reliably attach images, and `hermes send` falls back to the home channel.** For a dedicated channel target, use a direct Mattermost API script (`post_status.sh`) that sources `~/.hermes/profiles/andrzej/.env` for `MATTERMOST_TOKEN`/`MATTERMOST_URL`. The file upload endpoint requires `channel_id` as a form field (`-F channel_id=...`), not just the file. (Legacy: Matejko reviews in Paperclip, not Mattermost.)

8. **Keep notification state outside the repo.** Put `.notified_done_jobs` under `~/.ideogram4-local/`, not inside the git repo, so it survives repo resets. (Legacy with the Mattermost watchdog.)

9. **Job IDs can start with a leading dash, which breaks naive `grep`.** The done-job deduplication check must use `grep -qxF -- "$job_id"`. Without `--`, `grep` treats `-MuwvZtmc74` as an option and returns an error, making the watchdog think the job was never announced and repost it every tick. This filled the ideogram4-local channel with ~50 duplicate posts on 2026-07-05.

10. **Clean up test jobs before handing the queue to Florian.** Remove any accidental test submissions with `DELETE FROM jobs WHERE id='...';` so the first real job starts immediately.

11. **Verify the target channel is visible to the Mattermost bot account before relying on it.** `hermes send --list mattermost` shows the channels the gateway currently knows; if the new channel is absent, either have the bot user added to the channel or post a test message there so the gateway learns it. (Legacy with the Mattermost watchdog.)

12. **Safety bypass is built in, not bolted on.** Set `IDEOGRAM4_SAFETY_BYPASS=1` or add `"generation": {"safety_bypass": true}` to the JSON prompt. No agent CLI changes are needed. Use `two_pass` for persistent grey-outs; it costs roughly 2× generation time on the M1 Max. Use `single_pass` as a cheap desensitizer for borderline false positives.

13. **The filter watches your words, not your pixels.** The grey box is triggered by prompt vocabulary and JSON structure, not by the generated image. Use canonical JSON, avoid naming flagged garments/anatomy/situations, and describe the scene/location/mood instead. `python3 ideogram4_local.py lint` and `python3 ideogram4_local.py rewrite` help catch and fix risky prompts before generation.

14. **An uncensored text encoder swap is reversible but not a magic fix.** The `IDEOGRAM4_LLM_MODEL` env var (or per-prompt `generation.llm_model`) selects the Qwen3-VL GGUF used by `sd-cli --llm`. `heretic` uses `DreamFast/Qwen3-VL-8B-Heretic-1.3.0-Q4_K_M.gguf`; `instruct` uses the default unsloth model. In our 2026-07-06 test, Heretic alone still produced a grey box on a beach-scene canary, so treat it as one lever among several (prompt hygiene + encoder) rather than a single switch.

15. **Fashion and accessory vocabulary on animals is not safe just because the subject is an animal.** In the 2026-07-09 cat-poster reproduction, prompts describing "a cat wearing a red silk scarf, tiny black sunglasses, and a gold collar charm" grey-boxed deterministically, even with the aggressive encoder and `two_pass` bypass. Avoid accessorizing animals or describing them as fashion models.

16. **Know where each checkout lives.** The worker checkout is `~/git/ideogram4-local` on the M1 Max; the Air wrapper is `~/.local/share/ideogram4-local`. Do not point `imagegen` at the engineers' `~/Projects/ideogram4-local` clone, which switches branches.

17. **Text elements with technical/specific content cause full grey-boxing, not just garbled text.** In the 2026-07-12 comfyui/camoufox batch, four prompts with `"type": "text"` elements containing technical terms ("ComfyUI", "KSampler", "1216 x 832", "Logged in: True") all grey-boxed (file sizes 232–930 KB vs >1 MB for clean 1216×832 images). Meanwhile, prompts with simple text ("camoufox-kit", "#homelab #gitops", "phone verification") rendered cleanly at 1.7–2.2 MB. The trigger is the **semantic density and technical specificity of the text content**, not the presence of a text element per se. For tech blog images, **remove all `"type": "text"` elements** and describe the visual concept as an `obj` instead (e.g., "a glowing blue box node" instead of `"text": "CheckpointLoader"`). If you must keep a text element, use simple, non-technical language. Plan to overlay real text in an image editor afterward.


19. **A prompt that works on the hosted Hugging Face demo may still grey-box locally.** The local GGUF safety filter is prompt-structure driven. Dense structured JSON with multiple explicit `"text"` elements and fashion/accessory language on animals can reproducibly grey-box even with the aggressive encoder + `two_pass` bypass. See `references/ideogram4-cat-poster-reproduction.md` for the 2026-07-09 cat-poster case.

20. **Restarting the worker can leave a zombie `running` row in the queue.** If you kill a worker right after it has picked up a job but before it finishes, the job stays `running` in SQLite even though no `sd-cli` process exists. The watchdog then reports multiple running jobs. Fix: mark the stale row `failed` manually, or let the job finish before restarting.

21. **The official sampler schedule is high-CFG-first, not low-CFG-first, and `sd-cli` indexes it reversed.** The `V4_DEFAULT_20` preset uses 18 steps at CFG 7.0 followed by 2 polish steps at CFG 3.0 (`guidance_schedule=7.0x18+3.0x2` in `sd-cli` syntax). Our wrapper's `single_pass` uses the official schedule from 2026-07-10 onward. See `references/ideogram4-official-sampler-schedules.md`.

22. **`status` is a read-only variable in zsh.** Background bash scripts launched from the Hermes terminal may execute under zsh and fail with `read-only variable: status`. Use a different variable name such as `job_status` when polling job status, and invoke the script with `bash /path/to/script.sh` explicitly (or `exec bash /path/to/script.sh`) so it runs in bash rather than relying on the parent shell.

23. **The real safety-filter fix is prompt/schema hygiene, not sampler tricks.** In the 2026-07-10 verification, a canonical GitOps header rendered cleanly both with no bypass and with `single_pass`, while a robot/key-card prompt grey-boxed even with `two_pass` + aggressive encoder. If a prompt greys out, fix the vocabulary/structure before reaching for `two_pass`. See `references/ideogram4-oss-schema.md`.

24. **Pre-v3.4.0 prompts in `prompts/` produce unfinished/garbled images and must be migrated before regeneration.** The `prompts/` directory contains files from before the 2026-07-10 schema formalization. They use a non-canonical format that pushes the model out-of-distribution: an `image_prompt` wrapper object, `position` strings ("left side", "center") instead of `bbox` coordinates, invalid element types (`"character"`, `"effect"`), `scene_description` instead of `high_level_description`, and `text` elements that leak garbled safety-filter text into the image (see pitfall #17). When a user asks to regenerate an image that "looks unfinished," **check the prompt file format first** — if it has any of these markers, rewrite it in canonical schema format (three top-level keys, `type: "obj"`, `bbox: [y1,x1,y2,x2]`, no `text` elements) before resubmitting. Run `lint` on the rewritten prompt to confirm risk score 0. See `references/pre-v340-prompt-migration.md` for the full field mapping.

25. **Missing bboxes cause artifact soup even when the prompt doesn't grey-box.** In the 2026-07-12 comfyui batch, `comfyui-workflow.png` (1.5 MB, not grey-boxed) had severe visual artifacts because all 5 elements lacked `bbox` coordinates — the model had no spatial guidance and splattered elements randomly. Adding `bbox: [y1,x1,y2,x2]` (0–1000 scale) to every element in the v2 prompts produced clean, well-composed images. **Always include bbox on every element**, even for simple prompts. Without bboxes, the model guesses where things go and often overlaps or scatters them.

26. **Dense technical UI vocabulary in `desc` fields is a grey-box/artifact trigger separate from `text` elements.** In the 2026-07-12 batch, `desc` strings containing "CheckpointLoader", "CLIPTextEncode", "node-graph interface", "x.com/home", and "SDXL model icons" contributed to grey-boxing and garbled rendering — even though these were `type: "obj"`, not `type: "text"`. The model tries to render these technical terms as visible text in the image, producing artifacts. **Describe visual appearance, not technical names**: "a large glowing blue box node" instead of "a CheckpointLoader node box", "a connected-box interface with glowing lines" not "a ComfyUI node-graph interface", "a social media home feed" not "x.com/home". See `references/2026-07-12-tech-prompt-vocabulary-fix.md` for the full before/after.

27. **Empty JSON elements (no `desc`, no `bbox`) cause guaranteed grey-boxing.** On 2026-07-14, a cron agent submitted 4 prompts where every element was an empty shell like `{"type": "character"}` — no `desc` field, no `bbox`, no content at all. The model had zero information about what to render and grey-boxed every image (227–250KB). This is worse than a bad prompt — it's a non-prompt. Every element MUST have at minimum: `type: "obj"`, `bbox: [y1,x1,y2,x2]`, and `desc: "a concrete physical description"`. An element without a `desc` is a guaranteed grey-box. This happened because the cron job had no skills attached (`skills: []`), so the agent had no access to the ideogram4-local skill's rules. See the `homelab-blog-writing` skill's `references/2026-07-14-cron-safety-filter-incident.md` for the full incident.

28. **Cron jobs that generate image prompts MUST have `ideogram4-local` in their `skills` list.** On 2026-07-14, `skills: []` produced 8 grey-boxed images. After attaching `["homelab-blog-writing", "ideogram4-local"]` and embedding the 8 mandatory rules in the cron prompt, all 8 resubmitted images rendered cleanly (1.5–2.5MB). Belt and suspenders: attach the skill AND embed the rules in the prompt. For Matejko the equivalent is listing `image-studio` on the profile.

29. **Grey border bars (empty margins) are a distinct defect from safety-filter grey-boxing.** A 1216×832 image can render correctly in full color but carry uniform near-white bars (RGB ~243, std≈0) eating 15–20% of the top and bottom, leaving only ~65% of the frame for content. The discriminator is **file size**: a normal 1.5–2.5 MB render means this is not the safety filter but a spatial-guidance problem. It is caused by (a) elements clustered in the center vertical band with no bbox touching y=0 or y=1000, (b) a background description that does not explicitly demand full-frame fill, and (c) pre-v3.4.0 prompts using `position` strings instead of bbox coordinates. **Fix**: (a) give at least one element a `bbox` starting at y=0 and at least one ending at y=1000; (b) write in the background description "The scene fills the entire canvas with content from the very top edge to the very bottom edge, no empty space."; (c) spread the elements across the full vertical range rather than clustering them in the middle. On 2026-07-14 the observability forklift header had a 160 px grey bar on top and 126 px on the bottom (of 832 px) because its pre-v3.4.0 prompt had no bboxes at all; rewriting it with full-canvas bboxes (y-range 0–1000) eliminated the bars. Verify with `scripts/check-grey-bars.py`, which measures exact bar height in pixels; see `references/grey-border-bars.md` for the symptom/fix table.

30. **A `lint` density warning is an element-count problem, and the fix is merging decoration, never dropping the story's connector.** Past roughly six elements `lint` returns `Risk score: 2` with `Density risk: yes` and `Flagged terms: none`, while the same scene at six elements lints at 0 — the warning tracks element count, not vocabulary, so re-wording the prompt will never clear it, and the recommendation text blames `canvas`/`layout` even when the schema is already canonical. Do **not** fix it by folding a *relationship* into the `desc` of one end: a cable, chain, pipe, beam of light or line of sight that the picture exists to show needs its own element whose `bbox` spans both ends, or the model draws the prop and never connects it — a cable described only as running "from the machine's top, over the bench, up to the robot's back" rendered as bench-to-machine wiring with the robot standing free, and the image lost its point while still looking clean. Merge a decorative element instead (or move a wall fixture into the `background` description), re-lint to risk 0, and keep the connector as an element whose bbox covers the whole run between the two things it joins.

31. **A liquid level is not a controllable value: "drained to the bottom fifth" renders a third to two thirds full, and repeating the wording does not help.** On 2026-10-21 a wall gauge described as `level dropped to the bottom fifth, brass needle on the lowest tick` came back half to two thirds full; the re-render that spelled out `completely drained, only a thin amber film at the very bottom, red warning lamp` still came back about a third full and additionally multiplied into two gauges, one red. The model has no dial for a quantity, so it draws "a gauge" and fills it plausibly. When the point of an image is that a quota is *gone*, do not ask for a level: make the emptiness a shape. An overturned empty jar, a dry canister lying on its side, or a bare shelf with a few scattered coins all read as spent at a glance; the same beat written as a percentage reads as "still has some" and fails the intent check.

32. **A blank wall at the frame edge invites an invented emblem, and it is a defect.** The `zeroclaw-loop-b` render of 2026-10-21 came back with a flat red rounded-square badge with a green bar and a blue glyph superimposed on the right edge — solid unshaded colours, no perspective, overlapping the scene, i.e. a logo the prompt never asked for and the only readable mark on the canvas. The prompt had left that corner as plain concrete wall. Fill the right edge with a character or object (a bbox that actually reaches x=1000), and say `no logos, no badges, no emblems and no readable lettering anywhere` in the `high_level_description`; check the edges of every render before it goes on a card, because a badge is a hard defect even when the metaphor landed.

33. **The `color_palette` array can come back as a literal swatch bar along an edge.** The `zeroclaw-loop-b2` render of 2026-10-21 carried a strip of flat, saturated, uniformly sized colour blocks across the whole bottom edge, composited over the artwork with a thin pale rule above it: one block per palette entry, in order, ignoring the scene's light and perspective. It reads as an illustrator's palette widget, not as a floor. The prompt is not asking for it; the palette list is being rendered. Fix: keep the series palette (dropping it costs the look), fill the bottom edge with described content (`worn wooden floorboards filling the whole bottom edge of the frame`) so there is no bare band for the strip, and add `no colour swatch bars, no palette strips` to the `high_level_description`. Check the bottom and top edges of every render as a separate pass from the general description.

34. **The palette strip is cleared by removing `color_palette`, not by naming it in the prompt.** Same request, three renders: `zeroclaw-loop-b2` and `b3` both carried the swatch bar, and `b3` asked explicitly for `no colour swatch bars, no palette strips` and filled the bottom edge with described floorboards — the bar came back anyway. `zeroclaw-loop-a4`, written the same day with the same series style minus `color_palette`, came back clean with wood grain and coin shadows running to the bottom edge, and `lint` still returned risk 0 because the schema only requires one of `photo`/`art_style`. So the array is the trigger: when an image needs a clean edge, drop `color_palette` rather than writing a negative, and keep the series look through `aesthetics`, `lighting` and `art_style`.

34a. **The palette strip does not only come back at an edge — it can cross the middle of the frame, where the edge-checking script cannot see it.** On 2026-10-26 the `header-docs-mcp-transport` r4 render (job `WMV_yA9p1XA`) carried the swatch bar mid-frame: a 20-pixel band at rows 319-338 running the full width of the picture, four flat saturated blocks covering 1201 of 1216 pixels — green for 594, red for 97, red for 63, blue for 447 — plus a second bar at row 534, a one-pixel white line covering 1167 pixels with a blue band under it. The colours were the prompt's own `color_palette` entries, exactly as in #33 and #34. **The mechanical checks all passed: `check-grey-bars.py` found nothing and `check-palette-strip.py` reported "no palette strip on either edge", because both scripts look only at the top and bottom edges.** A render can therefore pass every shipped check and still carry the defect. **`scripts/check-flat-bands.py` is the whole-frame check this case needed, and it now ships:** it scans every row for a band of hard-edged, textureless colour blocks and reports the rows, the blocks, their widths and the hue groups, so the same render is caught by a number instead of a read. **It counts the blocks rather than the widest single one**, because a strip is several blocks side by side — the four blocks here were 594, 97, 63 and 447 pixels, and the widest was under half the frame, so a probe that measured only the longest run would have missed the strip it was written for. The crop is what catches it: a thin horizontal slice of the frame read as a digital progress bar over a hand-painted scene settles it, and the counts come from a row measurement, not from the read. **So the palette strip is a whole-frame check, not an edge check: when a render's `color_palette` is present, look for flat saturated blocks anywhere in the frame, and measure the rows to say how many blocks and how wide.** The fix is the one #34 already gives — drop `color_palette`, keep the look through `aesthetics`, `lighting` and `art_style` — and it does not need a negative clause naming the bar, because the array was the trigger. **And the general rule this belongs to: a shipped script answers the question it was written for, so a check that passes is not a clean bill of health for the frames it does not look at.** The render that had every one of Florian's described props in the picture, the 404 plaque legible and the corners clean, still went back for one flat band across the middle.

35. **A flat UI promo card can composite itself over a third of an illustration that never asked for one.** The render comes back with a flat rounded rectangle laid over the picture, carrying a tab, several lines of large white pseudo-text and two pill-shaped buttons. It is not a diegetic object: it has no perspective, ignores the scene's light, sits perfectly parallel to the picture plane and occludes the scene behind it with hard edges and a generic drop shadow. The gibberish text is the tell — text the prompt never asked for, and the model has no reason to spell it right. This is a hard defect on a blog header, because it reads as a clickbait thumbnail card pasted over the artwork. **Check a third of every render for a flat rectangular overlay with a drop shadow**, and when one appears, re-render with the offending region given real diegetic content (a wall, shelf or prop that reaches that edge) plus `no poster, no banner, no placard, no overlay card, no advertisement and no readable lettering anywhere` in the `high_level_description`.

36. **A `desc` that asks for numbers, lettering or a data-visualisation prop gets faked as pseudo-glyphs and meaningless grids, and Wojtek rejects the whole image for it.** Two shapes of the same mistake. (a) Asking for "a dial face full of blocky number cells" or "a chalkboard covered in columns of number marks" gets a grid of garbled numerals and a board of semi-random digits, because the model can only fake glyphs it was never told how to spell. (b) Asking for "rows of colored square chips arranged as a price chart" gets a pseudo-chart of aligned coloured tiles with no axes, no labels, no legend, an empty band underneath and an orphaned stud floating in it. Wojtek's read on both: any text in a picture must be explicit and spelled correctly, and a shape the model half-invented because it had no idea what to draw is an artifact. **The fix is not to reword the request for the same prop — it is to replace the prop with a physical object the prompt can describe and the model can draw**: a glass porthole with amber gears instead of a numbered dial, a shelf of closed plain ledgers instead of a chalkboard of figures, a plain wooden panel with three carved discs instead of a price chart. Then put `no charts, no graphs, no readable lettering anywhere` in the `high_level_description`, and fill the bottom edge with described content (a bench, a floor, coins) so the model has no empty band to fill with a shape it invents. A prop the prompt cannot describe concretely is a prop the model will hallucinate.


38. **A connector's `bbox` must span the whole run, and the target must be named in the same sentence as the source — otherwise the model parks the connector beside the target and the story dies.** Pitfall #30 says a connector needs its own element; it does not say the box has to cover the entire path. The `hidden-tokens` round-2 pipe had `bbox` [160, 500, 680, 800] and a desc saying the spout "hangs directly above the mouth of the machine's wide funnel" — and the model drew the pipe's spout ending at the **right shoulder of the funnel**, aimed at the outside of the bowl, with the coins sitting in a cluster where it met the side. Nothing entered the funnel, so "hidden tokens nobody wrote" did not read at all and the render had to be re-run. The fix that worked on the next attempt was spatial, not vocabulary: the pipe's box became [40, 300, 430, 720] so it runs over the **top** of the machine rather than beside it, the desc said the spout "hangs directly above the centre of the machine's wide funnel, pointing straight down into it", and the desc added "A clearly visible unbroken stream of extra gold coins falls straight down out of the spout into the open mouth of the funnel" — the source, the target, the direction and the visible action in one sentence. **When a picture exists to show one thing reaching another, check the connection on the render, not just the two ends: a pipe that ends beside the funnel and a pipe that ends above it look the same in a thumbnail and mean opposite things.**

38b. **A `vision_analyze` region crop is not a measurement, so a small detail must be settled on a crop written to disk before it goes on a card.** The region parameter silently lands on different content between two calls: one read of a box called it the alarm clock, the next read of the identical box called it a pegboard wall, and the two gave opposite answers about whether a cobweb draped the subject. A region crop is a prompt to the model about an area, not a measurement of it. **The tie-breaker is a PIL crop of the exact subject, written to disk and analysed as a file, upscaled 3-4x** — locate the subject by pixel signature rather than by eye, then crop exactly that. Pair it with a numeric check wherever the claim is countable: tick marks counted in an angular histogram around the detected dial centre, or a colour cross-count to tell a veil draped over a subject from a shape sitting behind it. `scripts/crop-probe.py` does the crop and the counting; `references/verifying-image-details.md` has the procedure. This matters because the card's text is frozen once posted, so a detail reported on the strength of one region read and later disproved is a defect Wojtek would judge from.

39. **A connector that reaches its target can still start from nowhere, and a source with a flag needs the flag to be the source.** The `hidden-tokens` round-2 pipe had its spout correctly above the funnel with coins falling in — the end was fixed — but its far end curled open in mid-air, so Wojtek rejected it: "The pipe dripping tokens is coming like... Out of nowhere, generally good but the pipe is not connected to anything. It should be like connected to something... Like some box in the background with kind of fading away Chinese flag or something since entire blog post was about shady proxy in china for anthropic API 😅". A connector therefore needs **both** ends attached to a thing: the model reads a pipe that starts in mid-air as a decorative curve, not as a supply line. The fix that worked in round 3: give the source its own element and make it physical — a battered wooden shipping crate in the background with a faded, tattered red flag with yellow stars, with the pipe bolted to the crate's front face through a visible round flange, running from there over the machine to the spout above the funnel. **When the source is a container or a building, describe the connection as a joint** ("bolted to the crate's front face through a round metal flange"), not as adjacency — a pipe merely passing near a crate is drawn as passing near it. And if the source carries a marking, say so in the same element: the flag is what makes the crate read as a place rather than as furniture, and it is what the picture is about.

40. **A request for figures "through a window" or "outside on a path" comes back as a foreign-style inset panel, and the mismatched art style is the tell.** The model cannot put extra figures behind glass in the same room, so it renders them in a separate rounded-rectangle cut-away: flat pastel chibi against a textured industrial scene, a pale rim and a drop shadow, its edges cutting straight through the server rack and the floor tiles, its interior ledge and sky unconnected to the room it sits in. The tell is not the shape but the style — a panel drawn in a different idiom from the frame, with a rim, a shadow, and geometry that does not continue the space, is a sticker pasted over the picture, so the "figures beyond the wall" beat is carried by a collage instead of by the scene. **Fix:** put the onlookers inside the window opening as their own element with a `bbox` and describe them *through* the glass ("faces pressed against the inside of the pane, their bodies cut off by the sill, the room's racks visible behind their heads"), or drop the window and place them in the room at the frame edge, then add `no inset panels, no cut-away views, no picture-in-picture frames, no framed miniatures` to the `high_level_description`. **Wojtek rejects the whole image for this, and his objection is conceptual rather than cosmetic** — he does not ask you to restyle the panel, he says the pasted part does not fit the picture's concept, so **the fix is to remove the request that caused the paste, not to redraw the panel**: drop the figures that needed a window altogether, and **fill the region they would have occupied with described diegetic content** (a bench, a pair of dumbbells, a rolled mat, their legs meeting the floorboards) so no bare area is left to paste into. Then add `no inset panels, no cut-away views, no picture-in-picture frames, no framed miniatures, no separate small picture inside the picture` to the `high_level_description`. Putting the figures inside the window opening as their own element, described through the glass, is the riskier option — the model still has to render a second space. **Judge every region by whether the whole picture reads as one scene: a region drawn in a different idiom from the frame is a collage, and no amount of detail inside it repairs that.**

41. **A connector described as one object can render as two unrelated gadgets, and a tube the model cannot end in a hand gets a flange instead.** The prompt's connector element named both ends ("a brass periscope tube mounted on the corridor wall, its upper eyepiece angled toward the gauge window and its lower lens at robot eye height") and the model still drew the tube as a wall pipe whose lower end was a bolted flange dead-ending on the wall and whose upper end was a lens pointing back out into the corridor, plus a *separate* brass lens on a chain in the robot's hand. The story — reading the gauges through a periscope instead of entering — did not read, because the two brass objects look like unrelated gadgets and the robot peers through neither. **Check the connection on the canvas, not in the prompt: one described object must appear as one object.** The fix is to make the hand-held end explicit and the path single: "the robot grips the brass eyepiece ring of the periscope and holds it up to its eye, the tube running unbroken from the eyepiece through the porthole glass and ending among the gauges", and to add `no disconnected pipes, no dead-end pipes, no unrelated brass gadgets` to the `high_level_description`.

42. **A lone prop placed on an empty floor reads as a product shot, and the model gives it a brand name.** On 2026-10-22 the `port80-fence-header` render came back with a single golden envelope on a bare pale floor, and the model printed an invented word under it — "Hojerlie" — in bold sans-serif. The prompt never asked for lettering anywhere; the word came from the *composition*, not the vocabulary: one isolated object, centred on empty ground, with nothing around it, is a product in an advert, and an advert has a name under the product. 49. **A mechanism drawn at the wrong scale or in the wrong material is a shape the model improvises, and the improvisation is what the reader sees.** On 2026-10-22 the `crown-jewel-vault` render was rejected with "The lock and the golden key are not generated correctly, it looks like there are some extra rectangular \"things\" created around it. 52. **A count the model is told about can still come out as flat emblems on one surface instead of as the separate things it counted — and the fix is the parts of the thing, not the count.** On 2026-10-23 the `netpol-three-gates` round-2 render was held back at the self-check, and the reason was the count: the prompt said "set into it three separate gate panels standing side by side with gaps of plain fence between them", and the model drew one continuous solid fence with three flat painted shapes on it — a blue shield, a green keyhole, a white envelope. 54. **The card that closes a round and the card that opens the next one are different issues, and the closing run cannot stage the new card.** On 2026-10-22 the round-1 card for post 010 was closed and a round-2 card was created for it in the same run. 56. **A mechanism described by some of its parts still gets the missing parts improvised, so name every visible part, not just the distinctive ones.** On 2026-10-26 the `csrf-scissors-cap` slot was re-rendered after Wojtek rejected round 1's scissors as "very weirdly" generated. 61. **A bbox written in the wrong axis order is a silent layout instruction, and `lint` cannot see it — so read back the box you wrote and check it against the word you used.** The schema's order is `[y1, x1, y2, x2]`, and a prompt written as `[x1, y1, x2, y2]` is not a formatting slip: it swaps every element's width and height, and the model obeys the boxes rather than the words. On 2026-10-26 the `header-docs-mcp-transport` slot lost two renders to this. The r4 prompt described "the left third of the wall" and "the right two thirds" and "a narrow pier between them", but its boxes said y 0-380 x 0-1000, y 420-1000 x 0-1000 and y 380-470 x 0-1000: three **full-width horizontal bands** with gaps between them, which is three comic-book panels, not a wall with two doors. Check the boxes before blaming the palette array.** **And a box can be in the correct axis order and still be too wide for the word in its own `desc` — that is a separate defect from a transpose, and it is the one that survives `lint` and a bbox audit that only checks for swapped axes.** `check-bboxes.py` reports it as `<desc says RIGHT but the box is 800px wide and 510px tall - a full-width band, not a right region>`: the four numbers are in the schema's order, the render will not come back as comic panels, and the element is still placed as a slab across most of the frame instead of the region its sentence names. The visible cost is a flattened composition — a three-quarter view collapses into stacked bands (bench, figure, wall layered one behind the other) because each wide box claims the same horizontal span. **So read the reported width against the spatial word rather than only against the axis order: a box covering 66-80% of the frame for a "left" or "right" element gets its coordinates tightened to the region the sentence describes**, and tightening the box is the fix whether the prompt is yours or the post author's — an author writes about the scene, not about the fields, so his JSON can carry this exactly as readily as a transposed box.
