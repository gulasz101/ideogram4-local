# Engine pitfalls

Every lesson the Ideogram 4 local stack has taught us, deduplicated and numbered. Read before writing a prompt; when a render fails, find the matching symptom here before changing anything else.

**This file is shared, and two agents can write it in the same minute.** Re-read immediately before patching, append at the end rather than renumbering, and if your `old_string` no longer matches, re-read and find the number your lesson actually landed on. Read the file back after writing, and report the number you used. Never renumber existing entries: the numbers are cited from `SKILL.md` and issue comments.

1. **Always set `IDEOGRAM4_MODELS_DIR=~/sd.cpp-models`.** The old default `./models` made the worker re-download 10.6 GB of diffusion weights into the repo. The default is now `~/sd.cpp-models`, but always export it explicitly in scripts.

2. **The real safety-filter fix is a combination, not a single lever.** Neither the `DreamFast Heretic` encoder nor the `HauhauCS Aggressive` encoder alone cleared a dense beach canary. Working recipe: (a) use the **HauhauCS Aggressive** encoder as `--llm`, and (b) write a **schema-compliant canonical JSON** prompt with no clothing/anatomy nouns and no `canvas`/`layout` fields. See `references/heretic-encoder-swap.md`.

3. **Use the official Ideogram 4 schema, not a custom one.** The verifier only allows `high_level_description`, `style_description`, and `compositional_deconstruction` at top level; `style_description` requires exactly one of `photo` or `art_style`; `compositional_deconstruction` contains exactly `background` and `elements`. Extra keys like `canvas`/`layout` are off-distribution and increase grey-box risk. See `references/ideogram4-oss-schema.md`.

4. **Capture stdout correctly.** The `submit` command prints the job ID to stdout and logs to stderr. Use `JOB_ID=$(python3 ideogram4_local.py submit ... 2>/tmp/log.txt)`.

5. **Do not cancel a running job.** Once `sd-cli` has loaded models, killing it wastes the progress. Either wait for completion or accept the waste.

6. **Load the LaunchAgent after the current generation finishes.** Loading launchd while a manual worker is mid-generation can create lock confusion. Let the manual worker finish, kill it, remove the stale lock, mark the finished job `done` in SQLite if needed, then load the plist.

7. **Cron `MEDIA:` lines do not reliably attach images, and `hermes send` falls back to the home channel.** For a dedicated channel target, use a direct Mattermost API script (`post_status.sh`) that sources `~/.hermes/profiles/andrzej/.env` for `MATTERMOST_TOKEN`/`MATTERMOST_URL`. The file upload endpoint requires `channel_id` as a form field (`-F channel_id=...`), not just the file. (Legacy: Matejko reviews in Paperclip, not Mattermost.)

8. **Keep notification state outside the repo.** Put `.notified_done_jobs` under `~/.ideogram4-local/`, not inside the git repo, so it survives repo resets. (Legacy with the Mattermost watchdog.)

9. **Job IDs can start with a leading dash, which breaks naive `grep`.** The done-job deduplication check must use `grep -qxF -- "$job_id"`. Without `--`, `grep` treats a leading-dash ID as an option and errors, making the watchdog think the job was never announced and repost it every tick.

10. **Clean up test jobs before handing the queue to Florian.** Remove accidental test submissions with `DELETE FROM jobs WHERE id='...';` so the first real job starts immediately.

11. **Verify the target channel is visible to the Mattermost bot account before relying on it.** `hermes send --list mattermost` shows the channels the gateway currently knows; if the new channel is absent, either have the bot user added to the channel or post a test message there so the gateway learns it. (Legacy with the Mattermost watchdog.)

12. **Safety bypass is built in, not bolted on.** Set `IDEOGRAM4_SAFETY_BYPASS=1` or add `"generation": {"safety_bypass": true}` to the JSON prompt. No agent CLI changes are needed. Use `two_pass` for persistent grey-outs; it costs roughly 2× generation time on the M1 Max. Use `single_pass` as a cheap desensitizer for borderline false positives.

13. **The filter watches your words, not your pixels.** The grey box is triggered by prompt vocabulary and JSON structure, not by the generated image. Use canonical JSON, avoid naming flagged garments/anatomy/situations, and describe the scene/location/mood instead. `python3 ideogram4_local.py lint` and `python3 ideogram4_local.py rewrite` help catch and fix risky prompts before generation.

14. **An uncensored text encoder swap is reversible but not a magic fix.** The `IDEOGRAM4_LLM_MODEL` env var (or per-prompt `generation.llm_model`) selects the Qwen3-VL GGUF used by `sd-cli --llm`. `heretic` uses `DreamFast/Qwen3-VL-8B-Heretic-1.3.0-Q4_K_M.gguf`; `instruct` uses the default unsloth model. Heretic alone still produced a grey box on a beach-scene canary, so treat it as one lever among several (prompt hygiene + encoder) rather than a single switch.

15. **Fashion and accessory vocabulary on animals is not safe just because the subject is an animal.** Prompts describing "a cat wearing a red silk scarf, tiny black sunglasses, and a gold collar charm" grey-boxed deterministically, even with the aggressive encoder and `two_pass` bypass. Avoid accessorizing animals or describing them as fashion models.

16. **Know where each checkout lives.** The worker checkout is `~/git/ideogram4-local` on the M1 Max; the Air wrapper is `~/.local/share/ideogram4-local`. Do not point `imagegen` at the engineers' `~/Projects/ideogram4-local` clone, which switches branches.

17. **Text elements with technical/specific content cause full grey-boxing, not just garbled text.** Prompts with `type: text` elements containing technical terms grey-boxed; simple text rendered cleanly. The trigger is the semantic density and technical specificity of the text content, not the presence of a text element per se. For tech blog images, remove all `type: text` elements and describe the visual concept as an `obj` instead. If you must keep a text element, use simple, non-technical language. Plan to overlay real text in an image editor afterward.

18. **When Wojtek explicitly approves a local model experiment, proceed.** A previous session's refusal does not bind a later session if he has re-approved in the current context. Document the approval and the reversible nature of the change in the tracking note.

19. **A prompt that works on the hosted Hugging Face demo may still grey-box locally.** The local GGUF safety filter is prompt-structure driven. Dense structured JSON with multiple explicit `text` elements and fashion/accessory language on animals can reproducibly grey-box even with the aggressive encoder + `two_pass` bypass. See `references/ideogram4-cat-poster-reproduction.md`.

20. **Restarting the worker can leave a zombie `running` row in the queue.** If you kill a worker right after it has picked up a job but before it finishes, the job stays `running` in SQLite even though no `sd-cli` process exists. Fix: mark the stale row `failed` manually, or let the job finish before restarting.

21. **The official sampler schedule is high-CFG-first, not low-CFG-first, and `sd-cli` indexes it reversed.** The `V4_DEFAULT_20` preset uses 18 steps at CFG 7.0 followed by 2 polish steps at CFG 3.0 (`guidance_schedule=7.0x18+3.0x2` in `sd-cli` syntax). Our wrapper's `single_pass` uses the official schedule. See `references/ideogram4-official-sampler-schedules.md`.

22. **`status` is a read-only variable in zsh.** Background bash scripts launched from the Hermes terminal may execute under zsh and fail with `read-only variable: status`. Use a different variable name such as `job_status` when polling job status, and invoke the script with `bash /path/to/script.sh` explicitly.

23. **The real safety-filter fix is prompt/schema hygiene, not sampler tricks.** A canonical GitOps header rendered cleanly both with no bypass and with `single_pass`, while a robot/key-card prompt grey-boxed even with `two_pass` + aggressive encoder. If a prompt greys out, fix the vocabulary/structure before reaching for `two_pass`. See `references/ideogram4-oss-schema.md`.

24. **Pre-v3.4.0 prompts in `prompts/` produce unfinished/garbled images and must be migrated before regeneration.** They use a non-canonical format: an `image_prompt` wrapper object, `position` strings instead of `bbox` coordinates, invalid element types, `scene_description` instead of `high_level_description`, and `text` elements that leak garbled safety-filter text. Check the prompt file format first; if it has these markers, rewrite it in canonical schema format before resubmitting. Run `lint` to confirm risk score 0. See `references/pre-v340-prompt-migration.md`.

25. **Missing bboxes cause artifact soup even when the prompt doesn't grey-box.** A render can be 1.5 MB and not grey-boxed yet have severe visual artifacts because all elements lacked `bbox` coordinates. Adding `bbox: [y1,x1,y2,x2]` (0–1000 scale) to every element produced clean, well-composed images. Always include bbox on every element.

26. **Dense technical UI vocabulary in `desc` fields is a grey-box/artifact trigger separate from `text` elements.** `desc` strings containing technical terms contributed to grey-boxing and garbled rendering even though these were `type: obj`. Describe visual appearance, not technical names. See `references/2026-07-12-tech-prompt-vocabulary-fix.md`.

27. **Empty JSON elements (no `desc`, no `bbox`) cause guaranteed grey-boxing.** A cron agent submitted prompts where every element was an empty shell; the model had zero information and grey-boxed every image. Every element MUST have at minimum: `type: obj`, `bbox: [y1,x1,y2,x2]`, and `desc: "a concrete physical description"`. An element without a `desc` is a guaranteed grey-box. This happened because the cron job had no skills attached (`skills: []`). See the `homelab-blog-writing` skill's `references/2026-07-14-cron-safety-filter-incident.md`.

28. **Cron jobs that generate image prompts MUST have `ideogram4-local` in their `skills` list.** `skills: []` produced grey-boxed images; attaching the skill and embedding the mandatory rules rendered all resubmitted images cleanly. Belt and suspenders: attach the skill AND embed the rules in the prompt. For Matejko the equivalent is listing `image-studio` on the profile.

29. **Grey border bars (empty margins) are a distinct defect from safety-filter grey-boxing.** A 1216×832 image can render correctly in full color but carry uniform near-white bars eating 15–20% of the top and bottom. The discriminator is file size: a normal 1.5–2.5 MB render means this is not the safety filter but a spatial-guidance problem. Fix: give at least one element a `bbox` starting at y=0 and at least one ending at y=1000; write in the background description that the scene fills the entire canvas; spread the elements across the full vertical range. Verify with `scripts/check-grey-bars.py`; see `references/grey-border-bars.md`.

30. **A `lint` density warning is an element-count problem, and the fix is merging decoration, never dropping the story's connector.** Past roughly six elements `lint` returns `Risk score: 2` with `Density risk: yes` and `Flagged terms: none`. The warning tracks element count, not vocabulary. Do not fix it by folding a relationship into the `desc` of one end: a cable, chain, pipe, beam of light or line of sight that the picture exists to show needs its own element whose `bbox` spans both ends, or the model draws the prop and never connects it. Merge a decorative element instead, re-lint to risk 0, and keep the connector as an element whose bbox covers the whole run.

31. **A liquid level is not a controllable value.** "Drained to the bottom fifth" renders a third to two thirds full, and repeating the wording does not help. The model has no dial for a quantity. When the point of an image is that a quota is gone, do not ask for a level: make the emptiness a shape (overturned empty jar, dry canister on its side, bare shelf with scattered coins).

32. **A blank wall at the frame edge invites an invented emblem, and it is a defect.** A render came back with a flat red rounded-square badge with a green bar and a blue glyph on the right edge — a logo the prompt never asked for. Fill the right edge with a character or object (a bbox that actually reaches x=1000), and say `no logos, no badges, no emblems and no readable lettering anywhere` in the `high_level_description`; check the edges of every render before it goes on a card.

33. **The `color_palette` array can come back as a literal swatch bar along an edge.** A strip of flat, saturated, uniformly sized colour blocks across the whole bottom edge, one block per palette entry in order. The prompt is not asking for it; the palette list is being rendered. Fix: keep the series palette, fill the bottom edge with described content so there is no bare band for the strip, and add `no colour swatch bars, no palette strips` to the `high_level_description`. Check the bottom and top edges as a separate pass.

34. **The palette strip is cleared by removing `color_palette`, not by naming it in the prompt.** Three renders: two with the array carried the swatch bar even when the prompt asked explicitly for no swatch bars and filled the bottom edge with floorboards; a third written the same day with the same series style minus `color_palette` came back clean. The array is the trigger: when an image needs a clean edge, drop `color_palette` rather than writing a negative, and keep the series look through `aesthetics`, `lighting` and `art_style`.

34a. **The palette strip does not only come back at an edge — it can cross the middle of the frame, where the edge-checking script cannot see it.** A render carried the swatch bar mid-frame: a 20-pixel band running the full width, four flat saturated blocks. The mechanical checks all passed because both look only at the top and bottom edges. `scripts/check-flat-bands.py` is the whole-frame check: it scans every row for a band of hard-edged, textureless colour blocks and reports the rows, the blocks, their widths and the hue groups. It counts the blocks rather than the widest single one. So the palette strip is a whole-frame check, not an edge check. The fix is the one #34 already gives — drop `color_palette`.

35. **A flat UI promo card can composite itself over a third of an illustration that never asked for one.** The render comes back with a flat rounded rectangle laid over the picture, carrying a tab, several lines of large white pseudo-text and two pill-shaped buttons. It is not a diegetic object. The gibberish text is the tell. Check a third of every render for a flat rectangular overlay with a drop shadow, and when one appears, re-render with the offending region given real diegetic content plus `no poster, no banner, no placard, no overlay card, no advertisement and no readable lettering anywhere` in the `high_level_description`.

36. **A `desc` that asks for numbers, lettering or a data-visualisation prop gets faked as pseudo-glyphs and meaningless grids.** Asking for "a dial face full of blocky number cells" gets garbled numerals; asking for "rows of colored square chips arranged as a price chart" gets a pseudo-chart with no axes, labels or legend. The fix is not to reword the request for the same prop — it is to replace the prop with a physical object the prompt can describe and the model can draw: a glass porthole with amber gears instead of a numbered dial, a shelf of closed plain ledgers instead of a chalkboard of figures, a plain wooden panel with three carved discs instead of a price chart. Then put `no charts, no graphs, no readable lettering anywhere` in the `high_level_description`, and fill the bottom edge with described content.

37. **A model artifact can look deliberate, so the self-check must ask what a reader gets from the prop, not whether it looks tidy.** A grid of aligned coloured tiles, a neat row of numbered panels, a framed board with a grid on it read as designed at a glance. What gives them away is asking what they mean: no axes, no legend and no readable label means the tiles carry no information. The prompt's own wording is the tell — if the old prompt could not describe the prop concretely, the render's version of it is an invention.

38. **A connector's `bbox` must span the whole run, and the target must be named in the same sentence as the source — otherwise the model parks the connector beside the target and the story dies.** A pipe described as hanging above a funnel but boxed beside it ended at the right shoulder of the funnel, aimed at the outside of the bowl, with nothing entering it. The fix that worked was spatial: the pipe's box large enough to run over the top of the machine, the desc saying the spout hangs directly above the centre of the funnel pointing straight down into it, plus a clearly visible unbroken stream of coins falling straight down out of the spout into the open mouth of the funnel. When a picture exists to show one thing reaching another, check the connection on the render, not just the two ends.

38b. **A `vision_analyze` region crop is not a measurement, so a small detail must be settled on a crop written to disk before it goes on a card.** The region parameter silently lands on different content between two calls. The tie-breaker is a PIL crop of the exact subject, written to disk and analysed as a file, upscaled 3–4×. Pair it with a numeric check wherever the claim is countable. `scripts/crop-probe.py` does the crop and the counting; `references/verifying-image-details.md` has the procedure. A card's text is frozen once posted, so a detail reported on the strength of one region read and later disproved is a defect.

39. **A connector that reaches its target can still start from nowhere, and a source with a flag needs the flag to be the source.** A pipe whose spout was correctly above the funnel with coins falling in still got rejected because its far end curled open in mid-air. A connector needs both ends attached to a thing. The fix: give the source its own element and make it physical — a battered wooden shipping crate in the background with a faded, tattered red flag with yellow stars, with the pipe bolted to the crate's front face through a visible round flange. When the source is a container or a building, describe the connection as a joint, not as adjacency.

40. **A request for figures "through a window" or "outside on a path" comes back as a foreign-style inset panel, and the mismatched art style is the tell.** The model cannot put extra figures behind glass in the same room, so it renders them in a separate rounded-rectangle cut-away in a different idiom. Fix: put the onlookers inside the window opening as their own element with a `bbox` and describe them through the glass, or drop the window and place them in the room at the frame edge, then add `no inset panels, no cut-away views, no picture-in-picture frames, no framed miniatures` to the `high_level_description`. Wojtek's objection is conceptual, not cosmetic: remove the request that caused the paste, not redraw the panel, and fill the region with described diegetic content so no bare area is left to paste into.

41. **A connector described as one object can render as two unrelated gadgets, and a tube the model cannot end in a hand gets a flange instead.** A brass periscope tube named at both ends still drew as a wall pipe with a bolted flange dead-ending on the wall plus a separate brass lens on a chain in the robot's hand. Check the connection on the canvas, not in the prompt: one described object must appear as one object. The fix is to make the hand-held end explicit and the path single, and to add `no disconnected pipes, no dead-end pipes, no unrelated brass gadgets` to the `high_level_description`.

42. **A lone prop placed on an empty floor reads as a product shot, and the model gives it a brand name.** A single golden envelope on a bare pale floor came back with an invented word printed under it — the word came from the composition, not the vocabulary. Fix by changing the composition, not by adding a negative: put the envelope in a wire mail tray heaped with other plain envelopes. Add `no brand names, no captions` to the `high_level_description`, and give the region a neighbour. A prop that stands alone in a bare region is an invitation to write on it.

43. **A prop described only by its outline renders as a bare shape, and a bare round shape is a hard defect.** A desc that names a prop by its shape alone tells the model the outline and nothing else, so it draws the outline and leaves the face empty. Round shapes are the worst case. The fix is to give the prop a face or change its shape — not to name the defect in a negative. Ask of every round prop: what is on its face?

44. **A prop that is supposed to rest on something can render floating in front of it, and the fix is a mount with a visible form.** "On the flat top of the tower" is a location the model can satisfy in the picture plane, so the prop comes back hovering with a sliver of background visible under it. The fix is to name a mount that has its own body — a stone slab, a shelf, a plate, a bracket, a plinth — and say the prop rests on it. Check every prop the prompt places on something for a gap under it.

45. **Two elements whose bounding boxes overlap are drawn overlapping, so elements that must not touch need boxes that do not.** Overlapping boxes are an instruction to overlap. When two elements in a scene must stay apart, give their boxes a gap between them, and when the story needs a connection between them, give the connection its own element with a box spanning both ends (#30, #38).

46. **A prop the model cannot draw concretely comes back as a near-miss object of the same family, and the near-miss still fails the beat.** A wall-mounted iron lever came back as a freestanding post with a T-grip. The fix is to describe the mechanism's parts and its state rather than its resemblance, and to verify on a disk crop (#38b) that the hand is on the thing and the thing is on its mount.

47. **A prompt that lists the scene's props gets an inventory with no story, and the fix is one action with one owner, not better descriptions of the props.** The model treats an element list as a set of things to place and places them all faithfully. The re-render must collapse the list: one action, in one frame, by one figure, with the thing being acted on as the target, and the connection given its own element whose `bbox` spans both ends (#30, #38). Ask what the verb is; a prompt with no verb produces a render with no story. A prop the prompt cannot say who is holding gets a holder invented for it (#48).

48. **One figure given two props gets split in two, and the model invents the second holder — so delete the prop, do not re-describe it.** When a prompt has a robot hold the gauge strings and, elsewhere, a sign board, the model splits the jobs and invents a headless, torsoless second figure to hold the sign. One figure, one prop, one job. When a prop needs a holder and the prompt gives it none, either name the holder and their grip in the same sentence as the prop, or delete the prop.

49. **A mechanism drawn at the wrong scale or in the wrong material is a shape the model improvises, and the improvisation is what the reader sees.** A mechanism is described by its parts and its size, never by an adjective. And a saturated accent belongs to exactly one prop: four gold props are not four gold accents, they are one gold wash, and the frame loses its detail.

50. **A recurring mascot is the enemy, and a cast of one needs a stated count or the model duplicates the protagonist.** State the count in the `high_level_description` ("one person only in the picture, no second person, no crowd") and give the figure a tight bbox. And give the scene an enemy drawn from the series' own cast: this post's header already established the red angry mail-bird as the Gmail mascot, so the bird became the antagonist. The enemy is not a new character to invent, it is the mascot the series already has.

But the count clause and a tight bbox are not sufficient on their own — the layout is the lever, and a row of identical boxes is what the model splits the figure across. Give the repeated objects distinct boxes and a legible depth order first, and state the count second. A duplicated figure is a layout symptom, and a count clause in the description does not cure it. And note the class when you report it: `wrong-count` is one of the classes the library rejects without a single approval naming it.

51. **A prop that invites writing must be replaced by a prop that does not, and the replacement is a physical object, not a wording change.** A "plain checklist board with three round tick marks" got three dash lines added beside the ticks standing in for words. A checklist, a clipboard, a ledger, a scoreboard and a notice board are all props that invite writing; a painted shape on a surface carries the same information without the invitation. The dash lines were extra, so the fix is to take the board away, not to forbid the dashes.

52. **A count the model is told about can still come out as flat emblems on one surface instead of as the separate things it counted — and the fix is the parts of the thing, not the count.** "Set into it three separate gate panels standing side by side with gaps of plain fence between them" drew one continuous solid fence with three flat painted shapes on it. A painted emblem carries the idea of a thing; the thing's own construction carries the thing. Give each one its own parts, so the count is legible as separate objects. A decorative border is a series trait, not a defect, and it is not the same as the bottom-edge swatch strip of #33. The self-check that catches this is a crop, not a glance.

53. **A connected action can still point the wrong way, because a verb is not a spatial instruction.** Hands closed on a push bar, the bar bolted to a dolly, the wheels on a ramp — one unbroken line — and the man standing at the low end facing downhill with the bar behind him, so the picture reads as hauling the load out of the building instead of into it. Direction is carried by spatial relations, not by the verb: say what stands between the figure and the target, which end of the handle his hand closes on, where his feet are planted, and which way the scene's own marker points. A directional mark in a scene is countable and the model will double it. The self-check is a spatial question, not a mood question, on a crop written to disk.

54. **The card that closes a round and the card that opens the next one are different issues, and the closing run cannot stage the new card.** The moment the new issue existed the harness claimed it for its own run, and every write against it from the closing run was refused with "Issue run ownership conflict". The closing run can only hand over; it cannot stage. The handover travels in the brief, not in the attachment table: the brief must name the absolute staging path of every PNG, its byte size and its sha256, and must say plainly that the files are not attached to the new card and that the new run must upload them. The queue has the same shape: the round-2 brief is queued before the issue is set to done.

55. **Ideogram 4 invents garbled text on any prop that looks like it should carry text, even when the prompt never asks for text — and the only reliable fix is to remove the prop, not to name the defect.** Readable UI panels with garbled words and wall plaques with "Session marker" alongside garbled variants, even though the prompt did not ask for specific text — the model invented it because the props looked like they should have text. Naming the defect in a negative does not clear it. The fix is to remove the prop entirely or fill it with described non-text content. Check every prop in the prompt: does it look like it should have writing on it? This is the broader version of #36 and #51.

56. **A mechanism described by some of its parts still gets the missing parts improvised, so name every visible part, not just the distinctive ones.** Scissors described as "sturdy golden safety scissors with curved blades and ergonomic handles" still drew finger loops merging with the man's fingers and a pivot screw tangled into the handle, because the prompt never said what the loops or the pivot look like. When a prompt describes a mechanism, list every visible part in the order a reader would see them, and state how they connect. The self-check for a mechanism is a crop of the mechanism, not a glance at the whole frame.

Follow-up: an approval can come with the mechanism still loose, so read the rejection as a complaint about the whole picture and fix the loudest wrongness first. A wrong count is louder than a wrong junction, and fixing the count can be enough. Both lessons are true: name every part so the count is right, and when the count was wrong, fixing it may carry the approval even if a finer junction stays loose.

57. **A "plain label panel" on a prop, a coloured glow around it, and a `color_palette` carrying that same colour are three invitations to paste a banner in the middle of the frame — and the model answers all three with one flat graphic.** A flat green banner with a white icon and invented lettering in the middle-right of the picture. The model does not invent a banner out of nothing, it builds one out of the three things a prompt gives it — a blank surface, a colour, and a place. The fix is to take all three away, not to forbid the result, then name the shapes to keep out in `high_level_description` and give the region described diegetic content.

58. **A reason that says "the prompt is fulfilled but it has no sense" is a request to re-read the section, and the section's own neighbouring line is the best statement of what the picture should carry.** A picture that illustrates the wrong neighbouring line is not a wording problem, it is the wrong picture, and no amount of re-describing its props fixes it. And when the fix itself is a guess, queue two attempts of it in the same round and let him compare the compositions.

59. **A re-render that fixes a banner can open a bare corner that the model fills with app-icon tiles, and the class is decided by the library's verdict counts, not by how small the shape is.** The r2 prompt dropped the element that described that corner to kill the banner, leaving the corner undescribed — a bare region is an invitation to paste something there. Put described diegetic content back into the region the re-render emptied. Count the library's verdict rows before deciding: a defect class with a 0-for-64 approval rate is not a note for the card; it is a render. And a brief's own check note is one run's read, not the verdict.

60. **A corner overlay that survives an explicit negative clause is a failure of the concept, not of the wording — so stop re-rendering and go ask what the picture should carry.** Three rounds with a multi-colour graphic pasted over a corner, the third naming the shape in the negative clause, and the model drew it anyway. The negative clause is not the lever: a shape the model wants to put in a corner gets put there, and the ban only tells it to pick a different shape. Give the corner a described prop that belongs to the room, and change what the picture is about. After the third identical failure, escalate the concept to the post's author instead of another re-render.

61. **A bbox written in the wrong axis order is a silent layout instruction, and `lint` cannot see it — so read back the box you wrote and check it against the word you used.** The schema's order is `[y1, x1, y2, x2]`, and a prompt written as `[x1, y1, x2, y2]` swaps every element's width and height, and the model obeys the boxes rather than the words. The tell is a render that is one scene in the words and several panels in the picture. The check is arithmetic, before the submit: for each element, print the box as "y a-b (h), x c-d (w)" and compare it with the words in the same element's `desc`. And a mid-frame swatch bar is a symptom of the same thing: the strip's position is exactly where a transposed box puts a band.

62. **Naming the banned shape in the negative clause can pull it into the frame — so a re-render for a text defect must change the props, not add a ban, and a reason that names the concept is an instruction to escalate.** A prompt that kept the same composition and ended with "No text, no UI panels, no pseudo-text anywhere" came back worse. The word "UI panels" in the negative clause is a concrete instruction, and a concrete instruction is what the model draws. A text defect is fixed by removing or replacing the text-inviting props, never by naming the banned shape in the negative clause. Count the shapes in the render that are the shape the ban named. And a reason naming the concept is an instruction to escalate, not to re-render.

63. **A picture built from props that all invite writing has no clean version — the concept asks for a surface the model cannot leave blank.** A jar "labeled by height marks", an engine block "with dials", a "brass plaque showing a checkmark" and a "measuring tape": four surfaces that read as instruments, and every one of them is a place the model puts invented characters. Before the render, list the props that want writing and cut the ones the section does not need.

64. **A robot's "face panel" and a clipboard are two surfaces that invite writing, so a prompt that gives a robot both will get a screen with gibberish on it — and the fix is to take the surfaces away, not to ban the outcome.** A flat blue UI panel pasted over the right third, carrying invented words. The round-2 prompt kept the robot and added a negative clause naming pseudo-text, and the render came back worse. The cause was in the props: a face panel plus a clipboard are exactly the two surfaces the model fills with invented characters. The fix: the robot got a plain round head with a painted-on smile, the clipboard became a round wooden token carrying one green checkmark, and the bare corner was filled with a pegboard of hanging hand tools. A round face with a painted smile is a face; a "face panel" is a screen.

65. **A head turned toward the target and eyes pointed at the prop are two separate outputs of the prompt, and satisfying one says nothing about the other — so ask the two questions separately, on a crop of the head.** The model places the head as geometry and the gaze as a separate, easier-to-skip detail. The second question has a geometric answer: an iris displaced toward the NOSE side of the eye opening means the eye is rotated toward the face's direction, and an iris displaced toward the LOWER lid means it is looking down. The prompt fix is to name the gaze in the same sentence as the turn. And a prop in his hands competes with the target for his attention. This is a note, not a re-render, unless the beat is specifically the gaze. Do not record a figure's gaze as a deviation until a crop has settled it.

66. **A defect script's exit code is not a verdict, because a painted scene trips it too — so measure the defect signature against a known-good image from the same series, not against the script's own threshold.** A script printed "PALETTE-STYLE BAND FOUND" for renders that were approved. The script is a detector, not a judge. What separates a real overlay from the background is the signature of the defect, measured as a number and compared with a known-good frame from the same series. A script that fires on approved pictures teaches you nothing unless you also run it on a known-good frame.

67. **An attachment can only be bound to a comment by the run that uploaded it, so a run that uploads a PNG and then dies leaves the PNG on the card but invisible in the thread, and the next run has to upload it again.** The upload and the linking have to happen in the same run, and the linking has to happen at all: `POST .../comments` with `attachmentIds` is the only call that sets `issueCommentId`. Read the attachments back and check `issueCommentId` is non-null before posting the verdict card. When a card run cannot upload to a new card because the harness claimed it first, it must say so in a comment on that card.

68. **A big prop described as "held in front of the chest" will cut the character's beard or chin, and re-wording the gap does not move it — the fix is to take the prop off the body.** Three renders moved the defect from "through the neck" to "through the beard" and no fourth wording will move it further. The reason is geometric, not lexical: a chibi's head is one third of his body, so a board wide enough to hold with two hands in front of the torso cannot clear a full beard that hangs to the chest. Put the prop at his side in one hand, drop the oversized prop for a small one, set it on a table, or put it on the wall. If three renders of one slot produce the same class of defect in a shrinking form, the slot is out of re-wordings.

69. **"The <prop> is all over the place" is a bbox defect, not a wording defect — check the element's box geometry before you touch its description.** A barrier element carried `bbox: [0, 100, 200, 380]`, which in the schema's `[y1, x1, y2, x2]` order is a 200-pixel-tall band across the top of the frame — the model painted stripe fragments wherever that band fell. When a rejection says a prop is scattered, duplicated or everywhere, read the element's bbox as a rectangle first. `scripts/check-bboxes.py` prints every box as a y-range and an x-range. The check is not "is the box the right aspect ratio" but "is the box big enough to hold the shape the words describe".

70. **The rejected prompt can be asking for the defect, so scan it for the rejection reason's own nouns before rewriting anything — a positive request is a stronger instruction than any ban.** An element asking for "two small red X marks drawn on the wood" got letter-shaped glyphs, because a red X is a letter-shaped mark. Take every noun, adjective and colour out of the owner's reason, grep the rejected prompt for it, and treat a hit as the prompt ordering the defect. The repair is to delete the request, not to reword it and not to ban it. An author's JSON gets the same per-defect sweep as your own, and any edit you make to it is named on the issue.

71. **An incompatibility drawn on the hiding side gives the model nothing to show, and it fills the frame with props instead — draw the fault on the side where the gap stays visible.** A part too big for its opening covers the opening, so the evidence is hidden; a model told to render a mismatch it cannot see has no way to satisfy the instruction except by surrounding it with invented objects. The same fault drawn the other way round needs nothing explained: a part seated in an opening a size too wide, so a band of dark empty space shows on both sides of the part. Decide which side of a mismatch carries the evidence, and prefer the side where the gap is visible; then name the gap as its own visible band with a stated width and check it on a crop.

72. **A pasted flat block is settled by its geometry, not by a read — a region that fills 100% of its own axis-aligned bounding box with near-zero interior variance is screen space, not painted space.** A connected component of one colour, a bounding-box fill ratio, and an interior standard deviation settled a green region: 101×119 px, filling 100.0% of its own bounding box, perfectly axis-aligned, with an interior colour spread of about 4 levels. No object in a perspective room is a mathematically perfect axis-aligned rectangle with zero texture. The control matters as much as the number: a real green indicator light in the same colour, measured as a separate component. And the measurement does not decide whether it is a defect, only whether it is pasted: a prompt that asks for "a symbol mounted flat on the wall" is asking for a screen-space graphic on purpose.

73. **A frame can be a photograph with flat vector stickers pasted on it, and every edge script passes it — so ask the medium question at full frame before judging any prop.** A base layer that is a photograph of an office with flat vector graphics laid over it. Every edge script was clean; the failure is the medium, not a margin and not a band. Ask: "is this a hand-drawn cel-shaded illustration, or a photograph with flat vector graphics pasted on top?" A photo base fails the series on its own. The companion failure in the same post is the same class one step milder: painted scenes each carrying one flat UI panel pasted over the figure, with misspelt lettering — so when a flat region is found, read its text twice on a disk crop and quote the misspellings.

74. **The pasted-overlay family arrives in three placements on one post, and only one of them sits at a frame edge — so a frame whose edge scripts are clean can still carry three overlays.** A full-height UI sidebar down the left edge, a flat saturated blue title bar cropped by the top edge of a device screen inside the scene, and a dark info panel over the lower right whose left border is a vertical strip of flat swatches — the prompt's `color_palette` array rendered as a bar on the panel's edge rather than the frame's. Locate the overlay by its fill colour and its blob bbox, not by whether it touches an edge, and quote the bbox in pixels and as a share of the frame. A device screen the prompt describes is not a licence for UI: describe the screen's whole surface. And a full-frame read supplies invented geometry alongside the true geometry; a crop settles it.

75. **A `color_palette` does not only render as an edge strip or a band — it can arrive as a cluster of flat blocks in one corner, and the palette entries are the evidence.** A Mondrian-like grid of red, orange, green and blue blocks with thick black outlines in the bottom-left corner against a textured painted floor. The prompt carried a six-entry `color_palette` whose blue, green, orange and red are exactly the four hues in the cluster, and its bottom-left corner had no described prop. When a corner of a render holds several distinct flat hues, sample them and compare them to the prompt's `color_palette`. The repair is to drop `color_palette`, give every corner a described physical object cropped by the frame edge, and say the frame fills all four edges with no empty border — do not add a ban naming the blocks.

76. **A described prop that stores cables is a magnet for the one cable that has to reach something, so keep the cable-collecting prop out of a frame whose story is a connection.** A connector element boxed across both ends with its target named in the same sentence, and the blue cable still ended in a wall rack instead of the laptop, because a "tall grey metal cable tray loaded with a few loose dark cables" was read by the model as the place cables belong. The audit for a connection is not only the connector's bbox — it is every other prop in the frame that could plausibly hold that connector. Replace it with a prop that stores nothing, or move it out of the connector's reach. And stating both ends in prose is not a fix on its own: verify on a crop where the cable should arrive.

77. **A jar, tin or bottle on a shelf is a container that invites a label, so a "plain shelf of jars and tins" comes back with one of them wearing a sticker of dash-lines — and the fix is to make the shelf a different kind of object, not to add a ban.** "Plain unlabelled jars and tins" is the phrasing that fails — a container is a shape the model knows is meant to be labelled. Re-render with plain closed wooden boxes and a coiled cable on that shelf instead. The check that catches it is a 4× crop of the shelf, not the full-frame read.

78. **A swatch strip can survive both the dropped `color_palette` array and an explicit "no colour bar" clause, so the prohibition has to be stated as filling the edge with painted content rather than as forbidding the strip.** A prompt already carrying `no colour bar or swatch strip along any edge` and `full bleed` with no `color_palette` array still drew a thin horizontal strip of colour across the top and bottom. The model treats a negative clause as a shape to avoid by drawing a slightly different shape. The fix is to make the edge content a positive description instead of a prohibition: say every corner and every edge is filled with painted scene content, and list the banned shapes explicitly. The self-check is a 2× crop of the top and bottom 40 px of the frame.

79. **A readable label the prompt asks for comes back as a flat pasted UI panel unless its surface is described as a physical material, and a brand colour has to be named or the model picks a generic one.** A prompt asked for `ACCESS GRANTED` and `CLOUDFLARE` as readable words, and the render drew them as flat rectangles with UI styling in a blue that is not Cloudflare's colour. The fix is to name the material the words are on: a wooden signboard with the words carved into the wood, a painted sign on a desk. And name the brand colour explicitly — "orange cloud". Add `no flat UI panels, no pasted rectangles, no circular icon in the corner` to `high_level_description`.

80. **A silently re-rendered slot that fails self-check again does not get a third silent re-render — it escalates to the broken-slot fix: rewrite + both engines side by side.** The standing rule gives a failing render exactly one silent re-render. When r2b still fails the show bar, the silent re-render budget is spent: do not silently re-render a third time. Rewrite the prompt and re-render with both engines (ideogram + flux2-klein) side by side. If both engines come back broken on the same defect, escalate the concept to the post's author instead of a fourth render.
