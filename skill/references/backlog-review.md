# Backlog review mode: existing images, one card per post

A "Backlog review <nnn>/<total>" issue is **not an image request**: it re-reviews images already embedded in unpublished drafts, one post per card, newest first. Round 1 renders nothing unless the brief lists a missing image.

**The parent runner issue's description is authoritative.** This file is the fast path plus the pitfalls that cost time. Read it when you are woken on a card or on the runner, and re-read the parent description before you act on anything it decides.

## The two issue types

- **Runner** — holds no card. It advances the queue, keeps the order in the `queue` document, and carries the daily watchdog.
- **Card** — one per post per round. Its description is the brief, verbatim, and the brief is authoritative for item ids.

## Queue state

Live state is `~/image-studio/backlog/queue.json`, and it changes **only** through `~/image-studio/backlog/backlog.py`, which takes a lock. Never edit `queue.json` by hand.

| command | use |
| --- | --- |
| `status` | table of every post not `todo`, plus the slot; this is what goes into the `queue` document |
| `next` | JSON `{"action":"create"\|"wait"\|"finished", n, round, brief, title}` |
| `opened <n> <ID>` | record the issue just created for the slot |
| `card-done <n> [--rendering]` | card complete; `--rendering` keeps the slot while renders run |
| `ready <n> <round> <brief>` | re-renders checked; queue the round |
| `note <n> <text>` | append a note to a post |
| `release` | free a stuck slot — repair only, say so in a comment |
| `batch-open <count>` | open up to `count` extra cards at once; returns one entry per card (brief, title, n) |
| `batch-open-ready <count>` | open up to `count` queued re-render rounds as batch cards, without touching the live slot |
| `batch-opened <n> <ID>` | record the issue created for a batch card |
| `fix-issue <n> <old> <new>` | correct a mis-recorded issue id for a post (repair only) |
| `reopen-card <n> <ID> <round>` | re-register a batch card that was released by mistake; a released entry is gone from the queue, so the round's brief path is needed to rebuild it |

There is no `--help`: the script prints its usage for any unknown argument, so `backlog.py --help` is a wasted call.

**`status` prints a JSON summary block and then plain-text rows, so its whole output is not JSON.** Piping it into a JSON parser fails with `Extra data: line N column 1` — that is the table starting, not a broken queue. Read the slot and the batch line out of `queue.json` with `json.load`, and grep the `^0<nn>` row when you want one post's state and its notes.

## Batch cards: more than one card in flight

**The one-card-at-a-time rule has an exception, and it is Wojtek's.** On 2026-10-21 he asked for five to ten review cards at once so there would be work to do overnight, and the helper grew a batch mode for it. The rule is not deleted — the live slot is untouched and the runner still advances one post at a time — but extra cards can be open alongside it.

- `backlog.py batch-open <count>` claims the next `count` `todo` posts, sets each to `card`, and returns one entry per card: `n`, `round`, `brief`, `title`. It never touches `q["slot"]`, and it skips posts already in the slot or in the batch.
- **`batch-open` is not repeatable.** A second call after a successful first returns `{"ok": true, "opened": []}` because there are no `todo` posts left to claim, and it does not re-print the entries it already claimed. If you lost the list (a crashed parse, a dropped terminal), read `q["batch"]` and filter for entries with `issue: null` — those are the ones still to create. Never call it twice expecting the same list, and never treat an empty `opened` as "nothing was claimed."
- **Fix the live slot's `issue` field before a large batch-open.** `batch-open` adds the slot's post number to `taken`, so a slot stuck at `issue: null` does not block the batch — but it does leave the board's live card unrecorded, and the daily watchdog reads that null as a stall. Run `backlog.py opened <n> <ID>` first (guarded: it refuses unless the slot still holds that post), then batch-open.
- Create the issue for each entry, then `backlog.py batch-opened <n> <GUL-id>` to record it. **`batch-open-ready` does not create the issue, however much its answer looks like it did:** it prints `{"ok": true, "opened": [{"n": …, "round": …, "brief": …, "title": …}]}` and the new batch entry carries `issue: null`, because `opened` there means the queue entry it claimed, not a Paperclip issue. Read `q["batch"]` after the call and POST the issue from the entry's `brief` and `title` — `parentId` the runner, `projectId` from the runner, `assigneeAgentId` yourself, `status: "todo"`, the brief as `description` byte for byte — then `batch-opened` with the returned identifier. An entry left at `issue: null` is a card the board cannot see and a monitor nobody armed.
- `backlog.py card-done <n>` releases a batch card as well as a slot card: it looks the post up in `q["batch"]` first, drops the entry and sets the post's state. A batch post that is not in the batch and does not hold the slot is still an error.
- **`card-done` is the post's release, not the card's completion, and a post with two open rounds has two releases.** `card-done <n>` closes the *post*: it drops the post's slot or batch entry and moves the post to `done`. A post that is on round 2 has already had round 1's card closed, so calling `card-done <n>` again while the round-2 card is still open releases the round-2 batch entry and marks the post `done` — the round-2 card is then an orphan: its issue is open and waiting for verdicts, but the queue no longer tracks it, and the post is counted as done before anyone has judged a single round-2 image. **Call `card-done` once per post, from the run that closed that post's last card.** A round that hands off to the next round does not release the post: it queues the round with `ready`, and the next round's card releases the post when that card closes. If you have already released a post whose card is still open, put it back with `reopen-card <n> <ID> <round>` — the post goes back to `card` and the batch entry comes back with it, and the round's brief path is needed because the released entry is gone from the queue. **`reopen-card` needs a `ready` round to rebuild from, and it now drops that ready entry as it builds the batch entry** — before that fix the stale entry stayed in `q[ready]`, and the next `next` would have popped it into a *second* card for the same round. If you repair a release on an older checkout, check `q[ready]` afterwards and expect the post to appear only under **Batch cards in flight**. **A post released while its card is still open has neither a batch entry nor a ready round, so `reopen-card` alone refuses it** ("post N has no batch entry and no ready round to rebuild from"). Re-queue the round first, then re-register the card: `backlog.py ready <n> <round> <handoffs/…-round-<k>.md>` puts the round back in `q[ready]` with its brief path, and `backlog.py reopen-card <n> <ID> <round>` then builds the batch entry from it and drops the ready entry again. Re-read `backlog.py status` afterwards and confirm the post reads `card` and not `done` — the release itself is what the earlier run got wrong, and the queue is the only place that shows it.
- **`card-done` also closes a post that is in `rendering` without holding the slot.** A card that queues re-renders calls `card-done <n> --rendering`, which sets the post to `rendering` and releases the slot so the next post can start. When the re-render comes back approved and the slot is long gone, `card-done <n>` on that post closes it: the `rendering` branch sets it to `done`. Without that branch the post is stuck in `rendering` forever and the runner's totals never reach it. **But a post that already reads `done` while your card is still open is released, not stuck, and `card-done` refuses it.** `card-done <n>` exits with `the slot is not held by post n` when the post is not in `q["batch"]`, does not hold the slot, and is not in `rendering` — which is exactly the shape after a round-1 close that called `card-done` while the round-2 card was already open. There is nothing to release: verify the end state instead of hunting for a call to make (every slot applied, records carry the verdict, embeds point at the shipped assets, the post's issue list carries both card ids) and say in the closing comment that the post was released early and the state is now genuinely correct. Do not reopen the post to re-close it.
- **`card-done` closes a post the queue still tracks, and a post the queue already released is not one of them.** Its branches are the batch entry, the live slot and `rendering`; a post in state `done` with no entry in either has nothing to drop, and the call errors. So a closeout reads the post's state in `queue.json` first and branches on it. **A post already `done` while its card is still open was released by the round-1 run, and the repair differs by whether the card's work is finished.** With the work still outstanding (a re-render in flight, a verdict not yet in), re-register the round so the queue tracks the open card again: `backlog.py ready <n> <round> <handoffs/…-round-<k>.md>` puts the round back in `q[ready]`, `backlog.py reopen-card <n> <ID> <round>` builds the card entry from it and drops the ready entry, and the post reads `card` again — then `card-done <n>` releases it normally. With the work already complete and applied (the approval in, the records written, the embed changed), the post's `done` is now true: do not call `card-done` and do not reopen, close the card issue and say in the closing comment that the earlier run had already released the post so no release was needed here. Re-read `backlog.py status` either way and confirm the post reads `done` before the card issue closes.
- The runner's `queue` document gets a **Batch cards in flight** line, built from `q["batch"]` by `scripts/build-queue-doc.py`. A batch card that is not in that line is a card the board cannot see.

**A card issue whose run died holds an approval nobody applied.** It sits `blocked` with no blocker and no pending card, invisible to the heartbeat inbox, so nothing wakes it again: the approval stays in the interaction result while the PNG never reaches the vault and the post still points at the rejected image. **A run that dies mid-card must not be trusted to have left a resumable state, and the runner's watchdog has to check the state of every card issue, not only the age of the slot.** The tell is a card issue that is `blocked` with `blockedBy` empty and `unblockDescriptor` null, or one whose interaction is `answered` while the issue is not `done`. The repair is the card's own closeout, done from the runner: copy the approved PNG, change that one embed, write the record with the slot's history, set `superseded_by` on every earlier record of the slot, comment, set `done`, and run `backlog.py card-done <n>`. The handoff brief already carries that bookkeeping verbatim, so the repair has no decisions in it.

**Two more shapes that hide finished work from the board, both found by one scan.** On 2026-10-22 a scan of every card issue found two more stalls that the queue did not report:

- **The verdict can land inside your own run, while you are still closing out.** A card goes up, Wojtek answers it minutes later, and the interaction you read back at the end of your own bookkeeping is already `answered` with a human's decision. Nothing will wake you for it: the wake belongs to the answer, and the answer is already here. **Re-read the interaction's status before you end a run that is waiting on a verdict** — a `pending` card means a wake is coming and the run ends, an `answered` card means the bookkeeping is yours to finish now. Applying the verdict in the same run that posted the card is the normal path, not a shortcut: copy the PNG, edit the embed, write the records, set the `superseded_by` chain, then close the card. Ending the run on the belief that a verdict wake is coming leaves a slot approved and unrecorded, which is the same stranded state the next bullet describes, reached by a shorter road.

- **A card that is `answered` while the issue is still `in_review`, with no run on it.** Wojtek answered GUL-79's card at 20:10 with three approvals; no run was created for that answer, the issue stayed `in_review` with an answered card, and the three library records still read `verdict: "unreviewed"`. The board showed a card that looked like it was still waiting, so nothing said the approvals were stranded. The repair is the same closeout as above.
- **A card whose run died after opening the verdict card but before flipping to `in_review`.** The interaction is `pending` (Wojtek has not answered yet) and the issue still reads `in_progress` or `todo`, so the scan flags it as `pending card on a {status} issue`. The verdict card itself is live and waiting on Wojtek — nothing about the card's work is missing, only the status transition. **The repair is the light touch:** PATCH the issue to `in_review` and read it back to confirm. Do not run the full closeout or the blocked-card repair: those are for a card whose monitor is dead or whose verdicts are stranded, and neither is true here. The card wakes normally when Wojtek answers.
- **A card that is `blocked`, which kills its monitor.** A monitor only fires on an issue that is `in_progress` or `in_review`. A card parked `blocked` with no blocker after its run died with `adapter_failed` has a render monitor that can never fire, and re-renders already finished on the worker sit uncollected. **Do not try to revive the card by writing its status.** The board's recovery re-parks an issue that has no live run and no pending interaction, so `in_progress`, `in_review` and `todo` each revert to `blocked` within seconds, and a monitor written in the same PATCH is cleared with the revert. A checkout holds the status steady for as long as it is held, but it also keeps the card's own run from ever claiming the issue, so it is not a way to hand the work back. **The repair is to finish the card's work from the runner's run** — fetch the renders, self-check them, write the handoff brief, queue the round, create the next card — and then close the dead card as `done` with the work already applied. A card's own run is not the only way to finish it.
- **A card that was never worked at all.** The sharpest version of the same shape is a card with no work in it: no attachments, no comments, no interactions, and an activity feed that carries only `issue.created` plus one `issue.execution_recovery_settled`. Nothing about it says "stalled" — it looks like a card that simply has not come up yet — so the queue does not flag it and no run is woken for it. The one signal is that it is the card the live slot names, or that it is older than the cards around it. Treat a card with an empty thread as unfinished, not as waiting, and check its `checkoutRunId` and `executionRunId`: a null on both with no `issue.checked_out` in the activity feed means no run ever took it.

**A card run reports a sibling's stall on the runner, it does not repair it.** The repair for a dead card is the runner's watchdog's job, and a run that is working a different card has no business taking the dead card's work: the dead card's own run owns its closeout, and taking it means two runs writing the same records and the same embeds. What a card run owes the board is the finding: name the stalled card, its status, the empty `blockedBy` and `unblockDescriptor`, the null monitor and the shape of its thread, and say that the repair is the runner's. A comment on the runner is the durable form of that, because the runner's `queue` document is rebuilt from live state and a stall in a sibling's thread is not in `queue.json` at all.

**The scan is the cheap part, and it is the watchdog's job.** For every card issue, compare three things: the interaction's `status` against the issue's `status`, the issue's `status` against the monitor's eligibility (`in_progress` or `in_review`, agent assignee, no user assignee), and the runs for a `queued` or `running` one. A card that fails any of those is a stall, and a stall can hold a signed approval, a finished render, or both. Do it on every runner wake, not only when the slot looks old — the slot age says nothing about a card two rounds downstream. `scripts/scan-cards.py` does that scan and prints the flagged cards; a flagged card is a candidate, not a verdict, so read its thread and its interaction result before touching it.

**Two shapes read as stalls and are not, so rule them out before repairing anything.** A card that is `in_progress` or `in_review` with a scheduled `monitorNextCheckAt` is waiting on a render, and a waiting card deliberately has **no run** on it: the monitor is the live mechanism, so an absent run there is the design rather than a stall. A `cancelled` card is retired — its work already moved to another card on the same post — so nothing can wake it and there is nothing to repair; read the post's other cards instead. `scripts/scan-cards.py` prints both as notes instead of flags, so a flag that names a scheduled monitor or a cancelled card is a false positive from an older checkout.

**The scan can time out, and a timeout is not a failure.** `scripts/scan-cards.py` walks every card issue on the board, and with 100+ cards and a slow API it can exceed the run timeout (exit 124). When it times out, skip it and note the last successful scan result in the watchdog comment ("Scan: skipped (timed out; last successful was N flagged of M)"). Do not retry in the same run — it will time out again. The scan is a candidate finder, not a gate; a missed scan does not block Advance or any other step. Re-run it on the next wake, and if it keeps timing out, raise the timeout or split the scan rather than treating the absence of a scan as a stall.

**A card can close `done` while its post never leaves `card`, and that is two failures in one.** A run that applies the verdict rows but never submits the re-render for a rejected item, and never calls `card-done <n>`, leaves every card issue on the post `done`, the post sitting in `card` with no open card, and his rejection with nothing behind it — the post can never reach `done`, so the runner's totals never finish while nothing on the board looks wrong. **Detect it by reading the post, not the card:** for each card whose interaction is `answered`, compare `result.items` against the library records (a rejected item whose record still has `superseded_by: null` and whose prompt folder holds no `<item id>-r<k+1>.json` never got a re-render) and against `queue.json` (a post in `card` that no slot and no batch entry names was never released). **Repair in this order:** write the prompt from his reason, lint it and run `check-bboxes.py`, submit it, save the prompt file, `card-done <n> --rendering` so the post stops reading `card`, then `note <n>` with his reason, the job id and what the prompt changed. Nothing was rendered by the closed card, so the vault, the records and the post stay untouched until the re-render is approved.

**A render submitted by such a repair has no card to hold its monitor, so the runner carries it.** PATCH the runner's `nextCheckAt` to the job's ETA plus five, with a `notes` that lists the whole wake (fetch the job, self-check it, write the handoff brief, `ready <n> <k> <brief>`, `batch-open-ready 1`, re-arm the daily watchdog), and set `recoveryPolicy: wake_owner` so a wake that dies comes back to the runner instead of vanishing. **One issue has one monitor slot, so the collect and the daily watchdog cannot both be armed:** the collect replaces the watchdog for one cycle, the wake re-arms it, and the comment says the watchdog time moved for this collect and when it returns. Never end that run with the post in `rendering` and nothing queued.

**A re-render's check note answers his reason clause by clause, and a re-render gets a fresh inventory.** The reason he gave is the acceptance criterion for that render, not the prompt: "the bar on the bottom does not fit" is cleared only by a floor that is not a strip of chips, and "no green rectangle left of centre" is cleared only by the absence of that shape. Quote his words and answer each clause with what the new picture shows, and name the props that are gone and the props that replaced them. And because a re-render fixes one defect while another can come loose, the new render gets a fresh inventory of every prop the prompt places — not a re-check of the old defect. The brief carries that check note, so the next round sees the verdict, the repair and the remaining props in one place. The brief on GUL-104's card had `<token>` placeholders in its staging paths and all three check notes reading "Pending the monitor wake" — it was written before any render was fetched, so it pointed at renders that did not exist yet. A brief written early points at a render that is not the one that ships. When you repair a card whose run died, check whether the brief names the real fetched paths and real check notes, and whether `backlog.py ready <n> <k> <brief>` was actually called; if not, the round's card was never queued and the post will sit in `rendering` for ever.

**A brief's check note is one run's read, and a re-render's direction can be inverted even when the prompt stated it.** On post 011 round 2 the brief said the node-parking re-render "points the same way" as the green ramp arrow; two crops written to disk showed the man facing downhill with the shaft behind him (a drag *out* of the bay, not a push in) and the ramp marking carrying two chevron heads. A card's own run checks every PNG again and owns the note it freezes, so measure the figure's posture and the arrow heads on a crop before uploading: the item stays back for one silent re-render instead of going on the card with a note that contradicts the file. **A fresh read is not automatically better than the note you inherited, so settle the disagreement on a crop and say on the card which reading won.** The brief and the render can disagree in both directions: a read that counts a master ring as a fourth key contradicts a brief that counted three, and there the brief was right. Neither side wins by age — the crop decides, and the card names the unit that makes the count checkable.

**A card you create carries an identifier the board assigns, and the queue must record the one the POST returned.** The identifier is not a predictable next number — a create can land on an identifier several slots away from the last one, so a guessed id can name an unrelated issue entirely. Read `identifier` from the POST response and record exactly that. When a wrong id has been recorded, `fix-issue <n> <old> <new>` replaces it in the post's issue list, its batch entry and the slot in one locked pass; never edit `queue.json` by hand.

**A finished re-render must not idle behind an open card.** A re-render round is queued with `backlog.py ready <n> <round> <brief>` and waits in `q[ready]` for the live slot. When the live slot is held by a card whose verdicts are still outstanding, that render sits done and unchecked for hours. `backlog.py batch-open-ready <count>` claims queued rounds as batch cards without touching the slot: it moves the post to `card`, appends an entry to `q[batch]` and removes the round from `q[ready]`, so `card-done` releases it the same way it releases any other batch card. Use it when Wojtek's batch mode is already in effect and a ready round is waiting — that is his exception, not your own widening of the rule. The document's **Rounds waiting for a card** line shows what is queued. `batch-open-ready` opens queued rounds in FIFO order (oldest first), not the one you just queued. If an older round sits ahead of yours in `q[ready]`, the first call opens that one and leaves yours waiting; run it again (or `batch-open-ready` with a count that covers every queued round) until your post's entry appears in `q[batch]` with `issue: null`, then record it with `batch-opened`. Do not assume a single call opened the round you intended — read `q[batch]` after the call and check the entry's `n`.

**The full sequence for a re-render round, in this order:** write the brief, then `backlog.py ready <n> <round> <brief>` to queue it; `backlog.py batch-open-ready 1` to claim it as a batch card rather than leaving it behind the live slot; POST the card issue with the brief as its description (`parentId` the runner, `projectId` from the runner, `assigneeAgentId` yourself, `status: "todo"`, an `idempotencyKey`); `backlog.py batch-opened <n> <GUL-id>` to record it; upload the render to the new card and link it with a comment; `backlog.py note <n> "<what this round carries>"` so the runner's table shows it; then close the card you were on. Verify the created issue's description is the brief byte for byte, and re-read `backlog.py status` to confirm the post now reads `card` with both issue ids on it.

**A hand-off is not done when the issue is created; it is done when the next card's own run has staged the render and opened its verdict card.** The new card is worked by its own run, and it may be minutes before that run uploads the PNGs and posts the card, so a closing run that stops at the create has left the round unverified. Watch for the two things that make the round live: the PNGs read back on the new card with a non-null `issueCommentId`, and a `pending` `request_item_verdicts` whose `items[].attachmentId` names one of those attachments. A card whose items point at no attachment shows Wojtek an empty row, and a card that never gets posted leaves the round with a brief and no way for him to rule. When the new run has taken the issue over, leave it alone and read only — polling its attachments and interactions until they appear is the verification, and the run's own closeout is the repair. If nothing appears and the run has finished, the round is stranded and the runner's scan is what names it.

**A batch card's own run is a normal card run.** The harness claims a freshly created card issue for its own run, so each card issue is worked by its own run, uploads its own PNGs and opens its own verdict card. Do not do a card's work from another run: the upload fails with `Issue run ownership conflict` because the issue is checked out by that other run. Check `GET /api/issues/<id>` for `checkoutRunId` and `executionRunId` — if they name a run that is not yours, the card is already being worked and you leave it alone.

**The round-2 card you open is a race with the harness's claim of it, and the claim can already be on the issue by your first read.** Read `checkoutRunId` and `executionRunId` on the create response or on the first GET rather than assuming either way. Sometimes the claim lands between the POST and that read — both fields name a run that is not yours, and an upload would answer `Issue run ownership conflict`, so skip it and let the brief be the only path. Sometimes both are still null, the window is open, and the upload lands: a `201` whose `sha256` and `byteSize` match the staging file is a landed attachment, so link it with a comment carrying its id, because an attachment with a null `issueCommentId` sits invisible in the thread. **Attach it to the card you are closing in both cases** — that card is yours, so that upload always works, and it is the fallback if the new card refuses it; link it in the closing comment by carrying its `attachmentId` in the same POST. And when the brief is the path, the brief must carry the absolute staging path, the byte size and the sha256, because the next run has to find and verify the file itself.

## Several of your own runs can be live at once

The harness starts a run per card, so one agent holds several live runs at once, and a run on the runner issue and a run on a card issue can both be mid-flight over the same vault files, the same queue and the same records. Two of them working the same slot is not a bug to work around — it is the normal shape of a batch.

**So the first thing a run does is find out what its siblings already did.** Before you render, re-render, copy a PNG, write a record or edit a post, read the live state:

- `GET /api/agents/me/inbox-lite` — every issue assigned to you, each with its `activeRun` and `execution.phase`. A phase of `reconnecting` is a **live** run, not a dead one.
- `GET /api/issues/<id>` — `checkoutRunId` and `executionRunId` name the run that holds the issue.
- `GET /api/issues/<id>/activity` — the per-issue event log, newest first, with a `runId` on every event. A different `runId` on the newest events means a sibling is working it right now.
- `GET /api/issues/<id>/runs` — whether the previous card's run is still alive.

**A refused file write is usually a sibling telling you it got there first — but read the refusal before you go looking.** When the refusal names the run and the issue that changed the file, a sibling changed it after your last read: re-read the file, re-read that issue, and look for the **residual gap** rather than repeating the finished work. When the refusal instead says the file exists but this task has not seen its full current content, no sibling is involved — your own earlier run on this same card wrote the file and this run has not read it: read the file (every page, when it paginates) and then write it. Do not skip the write, because the file on disk is your own earlier draft and the next step depends on it. A card that spans several runs re-touches the same prompt file, the same brief and the same records, so this second refusal is the common one. A sibling that already applied a verdict leaves the durable artifacts correct and your step redundant; what is left is usually a small correctness defect nobody patched: a record whose `created_at`/`finished_at` disagree with the renderer's `status` line, a `superseded_by` chain missing a record, a deliverable nobody created.

**The gap is the deliverable.** When a sibling has done the bulk of a card, the honest remaining work is to verify the whole closeout and fix what is inconsistent — do not re-render, do not re-copy the PNG, do not re-approve a record that already carries the verdict.

## The closeout checklist

An issue is only `done` when **every** line of this is true. It is a checklist of independent things that can each be wrong, so check each one rather than trusting the state you happen to remember:

1. Every slot has an approved image, and the approval is Wojtek's on the card (`result.items[].resolvedByUserId` set, `resolvedByAgentId` null).
2. The approved PNG is in the vault at `tech_blog/assets/<YYYY-MM-DD>/<slug>.png`, and its bytes match the staging file.
3. The post's embed points at that asset, no stale embed of an earlier round is left in the post, and the alt text on that embed describes the picture that is actually in the file — an approved re-render puts a new picture in the draft, so the alt text is rewritten together with the path.
4. A library record exists for the approved job, named `<YYYY-MM-DD>-<fetched PNG stem>--<job_id>.md`.
5. That record's `created_at` and `finished_at` match `imagegen status <job-id>`.
6. Every earlier record of the slot has `superseded_by` set to the approved job id, and the approved record's is `null`.
7. The queue state is right — `backlog.py card-done <n>` for the card, and the post is no longer counted as open.
8. The verdict card is `pending` or resolved with a human's decision, and its attachments read back with a non-null `issueCommentId`.
9. The Paperclip issue is `done`, and the closing comment carries every job id, asset path, record path and self-check note. **The PATCH field for the closing comment is `comment`, not `body`** — a body of `{"status":"done","body":"..."}` closes the issue and silently drops the note, so the audit trail never lands and nothing in the response says so. Post the closing comment as its own `POST /api/issues/{id}/comments` and read it back.
10. The runner's `queue` document is rebuilt from live state, not from memory. **A card run does not write it** — the runner's own description is authoritative and says a `Backlog review …` run must not check the runner out and must not PUT its document, so the card run posts the rows the document needs as a comment on the runner and says plainly that the document is behind live state. The runner's own wake and the daily watchdog rebuild it. **When the runner's checkout will not come, this item is satisfied by the comment fallback rather than by the PUT** — post the rows the document needs as a comment on the runner, say plainly that the document is one card behind live state, and let the runner's own wake rebuild it. The document is a derived view of `queue.json`; the card is still `done` without it.

**A closeout item you verified earlier in the run is still worth re-verifying at the end** — a sibling can land between the two checks, and the state you confirmed at the start is not the state you are closing on.

**The closing comment is the audit trail, and it has to say what did NOT happen.** On a review card it carries every item's verdict, the record paths and the files changed, and it states plainly that nothing was rendered — no job id and no vault copy belong to that card, so a reader checking the trail does not mistake an absent job id for a lost render. The job ids in the brief are the *original* renders the records were back-filled from, and saying so keeps them from being read as this card's work. It also names the questions the card left open — a stale alt text, a prose defect the runner's rule does not let a review card fix — because Wojtek answers what is named in the closing comment and reads the thread last.

**Checklist item 3 is not always clearable on a review card, and that is not a stall.** A backlog-review card approves the picture; the alt text around it belongs to the post, and the runner's rule allows a post edit only for an approved re-render's embed. So an approved *existing* image whose post alt text describes a different picture — a giant plug and a phoenix bird for a stopwatch drill — cannot be fixed by editing the draft on the card. Report it on the card, note it in the queue with `backlog.py note <n> "<what disagrees>"`, name it in the closing comment as an open question, and leave the post alone: the draft ships with a stale alt text until Wojtek says otherwise, and his go-ahead is what unblocks the edit. Do not open a follow-up issue for it on your own — how many cards are in flight is his call and the runner owns the queue. Item 3 is then satisfied in the only way it can be on that card: the picture is the one the draft points at, and the prose defect is reported rather than silently fixed.


## The runner's queue document is the list of everything

The runner holds no card, so the board shows one open review issue at a time. The full list of posts therefore has to live in one document on the runner: the `queue` document, addressed `GET/PUT /api/issues/{runnerId}/documents/queue` with `baseRevisionId` from the last `latestRevisionId` (omit it on the first write, get a `409` on a stale one).

**Rebuild it from live state, never from memory.** `scripts/build-queue-doc.py` reads `queue.json` plus every brief and prints the whole table: every post with its status field, image count, needs-render count and live state, plus the live slot and the posts that need a render. `backlog.py status` cannot build this table — it prints only the posts that are not `todo`, so it hides the todo backlog that is exactly what the reader is missing.

**The runner has to be checked out before the document can be written.** A document PUT is scoped to the run, so refreshing the queue document from a run that does not hold the runner answers `409` with `Issue run ownership conflict`, and the refresh silently does not land. Claim the runner first — `POST /api/issues/<runnerId>/checkout` with `{"agentId": ..., "expectedStatuses": [...]}` (both fields are required; `{}` answers `400`) — confirm the response carries `checkoutRunId` set to your run, then run `scripts/put-queue-doc.py`. A `409` from that script means the runner is not yours right now, **not** that the document changed underneath you; re-fetching the revision does not fix it.

**A `409` on the runner is usually transient, so retry it rather than abandoning the refresh — but bound the retry and know when to stop.** A sibling run working another card holds the runner's checkout and releases it when that run ends, often within the same run as yours. The `409` body names the `checkoutRunId` holding the runner, so you know which sibling to expect. While you wait, do not leave the refresh undone: post the content the document needs as a comment on the runner — the live-slot line, the batch line, the post's row and what changed — so the work is not lost if the checkout never comes free. Then retry the checkout, run the script, and release the runner the way the closeout below describes.

**Two things about that `409` that a null field on the issue does not tell you.** A `GET` on the runner can report `checkedOutByRunId: null` and `checkedOutByAgentId: null` and still refuse the checkout, because the lease is held separately and surfaces only in the `409` body as `checkoutRunId` and `executionRunId`. So **attempt the checkout to learn whether the runner is free; do not read the issue and conclude it is.** And a holder that produces **no** events on the runner's activity feed is not a card run that is about to end — it is a lease with no visible owner, and it may not release during your run at all. So bound the wait: try the checkout, and if it keeps answering `409` after a couple of attempts and the holder stays silent, stop and take the comment fallback, then say on the runner that the document is one card behind live state and which run holds it. Retrying without a bound is how a run burns its budget on a write it cannot make.

**The `queue` document is a derived view, so a card closes correctly even when its refresh is blocked.** The durable state is `queue.json` plus the library records plus the post; the document is a rendering of the first, rebuilt from live state by whoever holds the runner. So a card whose records are approved, whose comment carries the audit trail and whose post is untouched is **done** whether or not the document PUT landed — and a blocked refresh must not hold a finished card `in_progress` waiting for a lease it does not control. Close the card, advance the queue, and leave the refresh to the runner's own wake or the watchdog, with a comment on the runner carrying the rows it needs. Reading it the other way round — keeping a card open because a derived view is stale — stalls the queue behind a cosmetic problem.

**A checkout refused for a reason the issue read does not show is a lease, not a stall you can wait out.** The `queue` document is a rendering of `queue.json`, rebuilt by whoever holds the runner, so a card run that wants to refresh it has to claim the runner first. When the claim is refused, the refusal body names the holder — and **the holder can be another agent's issue rather than a sibling run of yours**: the body carried a `status` and an `assigneeAgentId` with both `checkoutRunId` and `executionRunId` null, which is a lease held by an agent that is not you and is not a run whose end you can wait for. Retry the claim a couple of times, and if it keeps refusing, take the comment fallback and say on the runner that the document is behind live state and who holds it. **A card still closes correctly without the document** — the durable state is `queue.json`, the library records and the post — so a refused refresh must never hold a finished card open.

**PUT the script's output; never regex-patch the stored body.** A patched body drifts from the script's column layout and from the counts the script derives from the briefs, so the next reader gets a table no tool reproduces. Run `scripts/put-queue-doc.py --issue-id <runnerId> --run-id <runId>`: it builds the body, fetches the current `latestRevisionId`, PUTs it and prints the new revision plus the live-slot line. Fall back to `scripts/build-queue-doc.py --out <file>` plus a hand-built PUT only when the script cannot run.

**A stored table whose columns drifted can only be re-synced by the whole body.** When the script gains a column (or the stored table has one it does not), rewriting cells in place leaves the old column count in place and the drift survives every later refresh. PUT the script's entire output each time; the column set comes with it. Refresh the document on every runner wake, right after reading `backlog.py status`, so the counts and the live-slot line in the runner's comment describe the same state the document shows. **A card's own run refreshes it too, because the card's run is what advances the queue.** The stored live-slot line names one post and its card; the moment that run calls Advance the slot has moved, and the document is describing a card that is no longer the live one. After Advance from a card issue, rebuild it: `scripts/put-queue-doc.py --issue-id <runnerId> --run-id <runId>`, then say on the runner which post moved to the slot and which card now holds it. The document is the board's map of the whole backlog, so a stale live-slot line sends the reader to the wrong card.

**The runner's description totals are prose; the briefs are the truth.** When the description's image count disagrees with what the briefs and the script measure, let the script's number stand, say so in a comment, and leave the description alone — the brief is the authoritative per-post source.

**A question about the backlog is a request for the queue document, not for a list in a comment.** When Wojtek asks where the remaining work is, the answer is the refreshed queue document plus a short comment that says: where the list lives, the counts, the rule that makes only one card open, which card is live and waiting for him, and which posts need a render. Do not paste 153 rows into a comment — the document is the artifact, the comment points at it.

**Never change the one-card-at-a-time rule to "go faster".** It is the runner's design and the helper enforces it; a queue with many cards open is many sets of unanswered verdicts. If Wojtek asks for more in flight, treat it as a question for him, and offer it — do not act on it unilaterally. **Exception, once granted:** Wojtek asked for more cards on 2026-10-21 and the helper grew a batch mode for it (see **Batch cards**). That is a decision he made, not a speed-up you decided on, and it does not license widening it on your own — ask again before opening more than he asked for.

## Advance

```bash
NEXT=$(~/image-studio/backlog/backlog.py next); echo "$NEXT"
```

- `create` — POST the card issue with `jq --rawfile desc "$BRIEF"` so the description is the brief byte for byte; `parentId` = the runner's id, `projectId` from the runner, `assigneeAgentId` yourself, `status: "todo"`. Then `backlog.py opened <n> <ID>` (**the identifier**, e.g. `GUL-72`, not the uuid). **Verify** by re-running `next`: it must now say `wait`. Then confirm the create by re-reading the issue and comparing its description to the brief — the brief is authoritative for item ids, and a truncated description silently changes what the next card reviews. **Compare with `jq -j`, not `jq -r`**: `-r` appends a newline, so `diff` reports a one-byte difference on a description that is in fact identical, and a run that reads that as a truncated create posts a second card for one post. `curl … | jq -j '.description' > /tmp/desc.md` writes the exact bytes, and `cmp` against the brief is the real test.
- `wait` — a card is open or re-renders are running. Do nothing.
- `finished` — do nothing; the runner's watchdog closes the runner.

- **`next` claims the slot; it is a write, not a read.** Calling it takes the next post, sets its state to `card` and installs the slot, so call it exactly once per card. Two runs calling it together cannot both get `create` — the loser gets `wait` — but the winner may be a run that never got as far as creating the issue, which leaves the slot held with `issue: null`. After Advance, read `backlog.py status` and check the slot names an issue: if it does not, either fill that slot (the post is already yours) or `backlog.py release` to hand the post back to the queue. Never create a second card issue for a post whose slot is already held.
   - **Never re-call `next` to recover the brief you already got.** The second call returns `{"action":"wait", …, "issue": …}` with no `brief` and no `title`, so the brief path and the title are gone from the output and a shell pipeline that reads `.brief` gets `null` and fails on the next command. **Capture the one response in a variable and read the fields out of that variable** — `NEXT=$(backlog.py next)` then parse `$NEXT` — and if the response was already consumed, read the brief back from `queue.json`'s `slot.brief` rather than calling `next` again.

**A slot with `issue: null` is often a card's own run in flight, not a stall.** The card's closing run ends with Advance: it claims the next slot and then POSTs the card issue for it. Between those two writes the slot names the next post with no issue, and a runner wake that reads the slot in that window sees an empty `issue`. So on a runner wake, when the slot names no issue, do not create a card and do not release the slot — check whether the previous card's run is still alive with `GET /api/issues/<cardId>/runs`; if it is, give it a moment and re-read `backlog.py status`, because that run is about to create the issue and record it. Only a slot that still names no issue after the card's run has finished is a real stall, and that is the case `backlog.py release` is for.

**A slot that names no issue while its card issue already exists is a different stall, and `release` is the wrong repair.** The creating run can die *between* the POST and the `opened` call: the card issue is on the board, the slot still reads `issue: null`, and the run that would have recorded it has failed. Its successor is queued against the card issue itself, so it works the card and never calls `opened` — **nobody will ever record the slot.** Left alone, the watchdog reads a slot that names a post and no issue, runs `release`, and hands the post back to the queue, so the next Advance opens a **second** card for a post that already has a live one, while the first card's run is still queued. The tell is a card issue whose title names the post the slot names, with the slot's `issue` still null: **the fix is `backlog.py opened <n> <ID>`, not `release`.** It is guarded (it refuses unless the slot still holds that post) and it writes only the missing record. Before running it, confirm the card really is that post's card — its title carries the post number, its `parentId` is the runner, and the post's own brief path matches the slot's brief — because recording the wrong id points the slot at a card for a different post. Then re-read `backlog.py status` and confirm the slot names the issue.

**A card run reports a sibling's stall on the runner, it does not repair it** — the rule above applies unchanged: the finding goes in a runner comment, and the dead card's own closeout stays untouched. The one thing that is yours is the queue's own bookkeeping: writing a missing slot record, or correcting a post's state in `queue.json`, is a queue repair and can be made the moment you find it, while the card's verdict, PNG, record and embed stay the sibling's work. Say in the runner comment which of the two you did.

**The card's own run advances the queue, so the runner often wakes late.** A card issue ends with Advance in its own run. By the time the runner's `issue_children_completed` wake arrives, the next post's card may already exist. On a runner wake, read `backlog.py status` first: when the slot already names an issue, the card is created and recorded — do not call `next` again, do not create another card, just report the new state.

**Verify a child's closing claim against the vault, not against the child's comment.** The card's comment says what it changed; the library record is the durable truth. Read the records the card names and check `verdict:` and the Verdicts row: `grep -h '^verdict:' 3-resources/image-library/2026-10/<record>.md` should read `"approved"`. A card that closed without touching its record is a card that did not do the work, and the runner's totals must not count it.

Approve a render by copying it into the vault, editing only that embed, and writing the record with the slot's history. Reject re-renders from the reason; at round 3 open a `request_confirmation` instead of rendering again. **An interaction outcome with `complete: true` means every item on the card has a verdict in that one submit — go straight to the 'When every item has a verdict' branch below; do not wait for a second wake, and do not leave the card in `in_review` with all verdicts already in.**
   - **A card can come back mixed, and the mixed verdict has one order.** Some items approved, some rejected, on the same card: apply every record edit first (`scripts/approve_record.py` for each — `--approved` or `--rejected --reason "..."`), then render the rejected slots, then schedule the monitor, then `card-done <n> --rendering`, then Advance — **except on a batch card, where the sequence stops at `card-done <n> --rendering`**: a batch card never holds the live slot, so that call sets the post to `rendering` and drops its batch entry, and `next` is not yours to call. The records are the durable truth and they are cheap; a render is 21 minutes. **Do not leave the approvals unapplied because a rejection is still being re-rendered** — an approved slot that still reads `unreviewed` is a card you will have to re-verify, and the approval does not expire while a sibling slot re-renders. **A rejection whose reason names a picture-level concept is a rebuild of the composition, not a patch to one prop.** "The weird window does not fit into concept of image generally" is not a request to restyle that window: the picture failed because part of it was a collage, so the re-render must make the whole frame one scene — drop whatever needed the second space, fill the vacated region with described diegetic content, and add the negative clause naming the shape you are banning. **When the reason is "text not readable" or "text not human language," ask which fix Wojtek wants: removal or readable text.** His verdict on GUL-1012 (tunnels-r2, apps-map-r2) said "texts must be readable by human" — meaning he wants readable English labels, not removal of all text. The standing series rule "no baked-in readable text" is a default, but an explicit verdict overrides it. When his reason says "texts must be readable by human," the fix is to include clean readable English labels with valid content (real service names, real log lines, actual logos), not to remove text-bearing surfaces. When his reason says "text not readable" without "must be readable," the old rule applies: remove all text, replace surfaces with physical objects or drop them. Rewriting garbled text as proper English only works when he asked for readable text; otherwise it still violates the series rule. **A re-render of a rejected slot is a new attempt on that slot, not a new round of the card** — it costs a render and goes on the next round's card, and the rejected record keeps `superseded_by: null` until a replacement is approved.
   - **A rejected slot's re-render goes on the next round's card, and this card stays open until the render is in.** The order for a card that came back with one rejection: apply every record edit, submit the re-render for the rejected slot, schedule the monitor at that job's ETA plus five, `card-done <n> --rendering`, and keep the issue `in_progress`. The brief is written on the **monitor wake**, not here, because the brief must name the render that is actually going on the next card and the render is not fetched yet — a brief written at the verdict wake can carry only a job id, and it has to carry a staging path. The monitor therefore belongs to *this* card: that wake is the one that fetches the render, checks it, writes the brief and closes the card. The parent issue's order is the same and is authoritative. **A rejection is a re-render now, not a round now**: the slot goes back to the next round's card, and the round-2 card is created from the ready queue at the monitor wake, so a card that came back with one rejection and one approval is finished the moment the re-render is submitted. **The approved slot's record is edited in the same pass as the rejection's, before the render is submitted** — an approval that sits unapplied while a sibling slot re-renders is an approval you will have to re-verify, and the record edit is seconds of work against a 21-minute render. **The re-render prompt is written for the reason, and a prompt file for the known next defect is written beside it.** When the reason names a defect class you have seen before — a `color_palette` array that renders as a swatch strip, a prop that invites pseudo-text — the remedy is known, so write the corrected prompt file now, one file write, and submit it only if the fetched render shows that defect. It is not a held-back attempt: it has no job id and nothing was rendered from it, so it goes in its own file with its own name and the brief names it as the file to submit on that outcome. **Check the clock when you compute the monitor time.** The worker's `imagegen status` reports its own local time on the M1 Max while Paperclip's `nextCheckAt` is UTC, so a job's `created_at` can read two hours ahead of the monitor you just scheduled; that is the timezone, not a bug, and the monitor is right when it lands after the job's real finish. Compute the monitor from your own UTC clock plus the ETA, and do not "correct" it to sit after the job's `created_at`.
   - **A re-render round is a new card issue, so this card's verdict card is finished.** The next round's card is created by Advance from the ready queue with the handoff brief as its description. Apply the verdicts, post the closing comment, `card-done <n> --rendering`, and let the brief carry the re-render to its own card. Do not open a second verdict card on this issue for the re-render. **The exception is a direct instruction from Wojtek to finish the work on the issue he is reading.** When he says the task must be finished on that card, or asks why there are no images on it, put the next round's verdict card on the card issue itself rather than creating a new one: he is watching that thread, and a new issue he has to go find is a round that looks stalled. Say in the brief and in the closing comment that the round's card sits on the earlier issue, so a later reader does not go looking for a separate card. Everything else is unchanged — one pending card for the round, the brief in the issue's history, `card-done` once.
   - **A re-render can be queued as two attempts when the composition itself is in question.** When the reason names a defect that the first fix might not clear, two renders in the same round cost one queue slot more but let Wojtek compare the two compositions on one card, which is the only way to find out which fix landed. Name the two prompts `<item id>-r<k>.json` and `<item id>-r<k>b.json` (or `attempt1`/`attempt2`), keep the job ids of both in the closing comment, and let the round-2 card carry both. When the brief names the render, it names the one that ships; the other is recorded as the attempt that did not.
   - **A silent re-render inside a round is an attempt, not a round.** Rounds are card rounds: one card per round per post, and the 3-round limit counts cards. The one silent re-render a failing variant gets (skill step 6) happens inside the same round and does not consume a round. So a slot can be on round 2 with two renders already spent, and what the 3-round limit stops is a third *card*, not a third render. Say which attempt you are on when you report a re-render, so Wojtek knows what the next card means.
   - **An approval with no reason is still an approval.** Write the row reason as "Approved on review." and record in the retained memory that no reason was given. Do not read a silent approval as a rule about the whole series: the same image approved without comment says nothing about the next one.
   - **A rejection is a record edit too, not just a render.** Mark the record `verdict: "rejected"` and add one row carrying his reason verbatim, then re-render from that reason. Leaving a rejected image's record at `unreviewed` makes the library disagree with the card.
   - **A slot whose re-render keeps carrying the same defect goes to the post's author, as a blocker on the card.** A defect that survives two silent re-renders is not a phrasing problem — it is the picture's concept — and the person who wrote the post is the one who knows what the picture should carry. So: create a **child issue of the card** assigned to the post's author, with a self-contained description (the post's path, the section, the rejection reason verbatim, what the current prompt describes, and exactly what is asked for: the idea, the props, the one action, the text, the alt text — the author cannot read your card, so the description carries everything), then set the card's `blockedByIssueIds` to that issue and the card to `blocked`. **The blocker is the waiting path**: the card wakes when the author's issue is done. An `in_progress` card with no monitor and no pending interaction is what the board's recovery re-parks, so a hand-off parked as a plain comment loses the work and has to be redone.
     - **A verdict that names the concept is the escalation order, and it does not wait for round 3.** The 3-round limit is a ceiling, not a schedule. A reason that says the image must be completely new, that the picture has no sense, or that it must be checked with the post's author has already settled the question — escalate on the round it arrives rather than spending a render on a concept the verdict overruled. `references/re-render-defect-persistence.md` has the hand-off shape and the rules for turning the author's answer into a prompt.
     - **An author can answer inside the same run, so re-read the hand-off issue before you end the run.** The author is an agent on the same board and a question with a self-contained description can be answered within minutes. **Read the hand-off issue back after creating it**: if it is already `done`, its answer is waiting and the card must not be left `blocked` on a resolved blocker, because the resolution wake has already fired and the card will never be woken by it. Take the answer, write the prompt from it, submit the render, and schedule the monitor in the same run — a card blocked on an issue that is already done is a card whose wake path has already gone by. The same applies to the blocker itself: a `blocked` card whose `blockedBy` issue is `done` shows `blockedBy` still set and `monitorNextCheckAt` null, and it is indistinguishable from a genuinely waiting card unless you read the blocker.
     - **Ask the author for a composition, not only an idea.** The answer that fixes a corner artifact is usually a camera and a crop — head-on, no perspective, both doorways cropped by the top edge, a described prop in every corner — and that is worth asking for explicitly, because "what should the picture show" alone gets you a concept the model still renders with a bare region.
     - **Route the post's prose defects through the same hand-off.** A review card may not edit a post, so a stale alt text can only be reported, never fixed — but the post's author owns the draft and can edit it, and the alt text belongs to the image question anyway, because it has to describe the picture the render ships. The author fixing it in the draft closes the defect outright, which a note on the queue never does.
     - The render that comes out of the answer goes on the next round's card like any other re-render, with the author's answer credited in the card's long note.
   - **A rejection replaces the prop, not just the wording of it.** When his reason names a defect (unreadable text, an invented artifact, a missing connector), the new prompt has to remove the thing that caused it: a prop the old prompt could not describe concretely gets replaced by a physical object the prompt can describe, and a connector that went missing becomes its own element with a `bbox` spanning both ends. Re-ask the same question of the old prompt: *what could the model not draw?* That is what he is looking at. **A reason that names a mechanism drawn wrong is a reason to describe the mechanism by its parts, not by an adjective.** "The lock and the golden key are not generated correctly… there are some extra rectangular things created around it" is not a request to reword the key: the model was handed a shape it had to improvise, so the new prompt says what the key *is* — a round ring, a short straight shaft, three square teeth on one side, no bigger than the hand — and the same question answers the rest of the frame, because a washed-out gold picture is a saturated accent on four props where the frame wanted it on one. `references/engine-pitfalls.md` #49 carries the case. **A reason that names the cast is a reason to state the cast.** "There should be only one character" means the count was never in the prompt, so the re-render states it in the `high_level_description` and gives the figure a tight bbox; and "add some sort of enemy" is answered from the series' own cast — the recurring mascot the post's other images already established — because an invented antagonist does not fit the set and the mascot does. `references/engine-pitfalls.md` #50 carries the case. **A reason that names fake text is a reason to remove the prop that invited it.** A checklist board comes back with dash lines standing in for words, and the fix is a physical object that carries the same information without inviting writing — a painted shape on a surface, not a board to write on — because the model adds the dashes on its own. `references/engine-pitfalls.md` #51 carries the case. **When his reason names a shape rather than a spelling, the shape itself is the defect.** "There is a white circle in the middle that does not logically make sense to be there... it gives the feeling like the model forgot to place something there" is not a request to reword the equals sign; it is a request to stop having a bare circle there. Give the round prop a face (the disc full of its engraving, the lens full of the magnified pattern) or change its outline (the round badge becomes a flat rectangular plaque with two visible bars hung from a visible chain). A negative in the `high_level_description` does not clear it — see pitfall #43. **Two round props side by side in one band is the shape of the trap**: the model fills the one it was told about and leaves the other blank, and the blank one reads as an oversight. When a scene needs two circles, describe what is on the face of each.
   - **A card can approve several images at once.** A card's result is per item; approve each one and record each one, and do not treat a batch of approvals as a preference for that composition in general.
   - **A card approving everything still means one data point.** When a whole card comes back approved with no reasons, retain one memory for the card: what the approved images have in common, plus the honest limit that one card is one post. Retaining one memory per image would multiply one observation into three and read as three independent data points later.
   - **A card that approves an image you had flagged does not make the flag disappear, and it does not make the flag a rule.** You may have put a defect on the card and he approved the image anyway — that is his eye overriding your filter, which is what the card is for. The retained memory says both halves: the image passed, and the specific thing you flagged was still there. Keep the flag as an observation about that image, not as a standing rule about the series, and do not spend a re-render on a slot he approved. **The contrast between the items on one card is the most informative part of it:** a card that rejects one image for a concept defect and approves another with a broken mechanism says the whole-scene read outranks the individual prop, and that is a fact about how he reads, worth one memory for the card.
   - **An approval can also cover an image that carries only part of its section, and that is a fact about which half he weighs.** When you flag that a picture shows the section's *observable* half but not the part the section is named for — a picture that draws the worker's instruments but not the denial that routed it there — and he approves it, then what he weighs in a section is the part that makes a scene, not the part the heading promises. Retain that as an observation about the image, and keep it distinct from a claim about every section: a section whose beat is a state change rather than a scene may still want its missing half drawn. Do not re-render an approved slot to add the half you wanted, and do not generalise it into a rule that a partial illustration is always enough.
5. **Every item resolved.** With queued re-renders: monitor at the last ETA + 5 min, `card-done <n> --rendering`, keep `in_progress`, end the run. Without: closing comment with every verdict, the files changed and the records, set `done`, `card-done <n>`. **Then Advance in both branches** — `card-done <n> --rendering` frees the slot, so the re-render branch needs Advance too or the queue stalls until the runner's watchdog. The two branches differ in what the card issue ends up as, not in whether the queue moves: without re-renders the card issue is `done` with its closing comment, and with re-renders it stays `in_progress` under the render monitor until the monitor wake closes it. **A batch card does not Advance, because it never held the live slot.** `card-done` on a batch card drops the entry from `q["batch"]` and sets the post's state; the live slot belongs to another card's run and is untouched. So check which one you are before calling `next`: read `q["slot"]` and `q["batch"]` in `queue.json`. If your post is in the batch, `next` is not yours to call — with the slot held it answers `wait`, and with the slot free it would claim the next post's card and create an issue that the runner's own wake also intends to create.
   - **The re-render branch's Advance opens the *next post's* card, not the re-render round's card.** The round-2 card is created later, from the `ready` queue, at the monitor wake. So after `card-done <n> --rendering` and Advance the live slot names a different post's fresh round-1 card, and the re-rendered post waits in `q[ready]` with its brief. Expect the queue document to show the re-rendered post in `rendering` while the live slot has moved on.
   - **A re-render round gets its own card issue, and this card issue closes.** The next round's card is a *new* issue, created by Advance from the ready queue with the handoff brief as its description; the card issue you are on is set to `done` with a closing comment and does not carry the next round's verdict card. Opening a second verdict card on the same issue while another post's card is still open breaks the one-card-at-a-time rule the queue exists to enforce, and it puts a later post's card on the board before the earlier post's slot is finished. The order on a re-render round is: write the handoff brief → `backlog.py ready <n> <k> <brief>` → set this card issue `done` → Advance. When the slot is still held by another post, Advance says `wait` and the ready brief waits its turn — that is correct, not a stall. **Unless Wojtek has told you to finish on this issue** — see the exception above; his instruction about where he wants to look outranks the queue's bookkeeping, and the round still carries one pending card.
   - **The handoff brief must name the render that is going on the card.** When a variant gets a silent re-render, the brief's staging path and job id belong to the *final* render, not the held-back attempt. Keep the held-back attempt's prompt file beside the final one (`<item>-r<k>-attempt1.json`) and name it in the brief, so the prompt history stays visible and the next round can find its predecessor. Write the brief only when every re-render of that card is fetched and checked: a brief written early points at a render that is not the one that ships. **The canonical filename is where the queue reads it** — `backlog.py ready <n> <k> <brief>` puts that file's text into the next card's description, so a canonical-named brief holding `<token>` placeholders hands the next run a card whose staging paths do not exist. Keep early notes under a name the queue never reads (`<nnn>-round-<k>.draft.md`) and write the canonical file once the render is fetched. **Split the brief by what each half can know, and give each half a file.** The verdict wake can already write the reasons, the taste rules, the prose defects, the prompt paths and the approval bookkeeping; the monitor wake is the only moment that knows the fetched staging path and the real check note. So the verdict wake writes its half to `<nnn>-round-<k>.draft.md`, and the monitor wake writes the canonical `<nnn>-round-<k>.md` with the paths filled in — a draft that is renamed, not a canonical file that is patched in place, because a canonical file holding placeholders is the exact shape that breaks the next card. **Do not cite the brief in a comment before it exists either**: at the verdict wake the render has not been fetched, so name the job id and the prompt file and let the monitor wake write the brief and name it. **The brief must also tell the next round to upload the staging PNG to its own card issue** — the round-2 card is a *new* issue and the attachments live on the card that closed, so they do not carry over, and an item pointing at no attachment shows Wojtek an empty row. **And the brief must not claim the files are attached to the card the brief is about to become.** The brief's text is frozen into the next card's description at creation time, and the upload to that card can be refused after the brief was written — so a line saying "both PNGs are attached to this issue" is a claim about a card that did not exist when it was written, and it is false the moment the create lands. Give the brief one claim about the files that cannot go stale: the absolute staging path, the byte size and the sha256. Then try the upload, and if it is refused, say so in a comment on the new card, because the description cannot be edited afterwards. **And it must say that the post's alt text is rewritten when the re-render is approved**: an approved re-render puts a new picture in the draft, so the alt text goes with it, and a back-filled alt text that described the render being replaced is not carried over. **The alt text to be written is not the old alt text with a noun swapped — it describes a different picture, so the brief names the props the old alt text mentions that the new render does not have.** A re-render that replaces a carried pod with a wheeled dolly leaves the old caption describing a carried pod, which is a second, quieter defect on top of the image one. The brief says which props are gone and what stands in their place, so the next run writes the caption from the file it is shipping rather than from the caption that is already there.
   - **The handoff brief must carry the approval bookkeeping, because the next round is a different run with none of this run's context.** The next card's run reads the brief and the queue, not this run's memory, so anything the approving round has to do that is not derivable from the vault goes in the brief, under a heading like *Bookkeeping when this one is approved*: the vault copy path for the approved PNG, the exact embed line to change and what its alt text must now say, the path of the new studio record to write, the slot's earlier records and the `superseded_by` job id to set in each of them, and which images of the post are already approved and must be left alone. Name the paths, not the intentions — a brief that says "update the embed" leaves the next run guessing, while a brief that quotes the embed line and the new path leaves it nothing to decide. **The bookkeeping covers every render of the slot, not only the one that shipped**: a render that was held back at the self-check and never reached Wojtek still gets a record with a `rejected` row that says so in its own words ("held back at the self-check, never shown to Wojtek"), and it joins the `superseded_by` chain with the same approved job id. A brief that lists only the shipped render leaves the slot's history short by one record, and the next run writes an incomplete chain without noticing.
   - **A brief written before the render exists is a draft, and the draft is the only half that can be written early.** The verdict wake knows the reasons, the taste rules, the prose defects, the prompt paths, the concept the author settled and the approval bookkeeping; the monitor wake is the only moment that knows the fetched staging path, the byte size, the sha256 and the real check note. So when a card's render is still in flight, write the early half to `<nnn>-round-<k>.card-draft.md` and leave the canonical `<nnn>-round-<k>.md` unwritten until the monitor wake. **The draft is not throwaway — it is where the bookkeeping lives, so the monitor wake copies its content forward instead of rewriting it from memory.** And a draft is where a contradiction hides: the item id in the draft's table and the item id in its bookkeeping paragraph have to be the same string, because the two are written at different moments by a run that may have changed its mind in between. Read the draft back whole before the monitor wake turns it into the canonical file, and check the rows against each other rather than only against the prompt file — the table and the prose are what the next run resolves the card from, and a mismatch there sends it to a card whose rows do not match its own table.
   - **A card's run must not leave the runner checked out, but `release` breaks the runner's watchdog.** The runner is checked out so the `queue` document PUT lands; when the run ends, that checkout has to go. `POST /api/issues/{runnerId}/release` does more than clear the checkout: it also drops `assigneeAgentId` and moves the issue to `todo`. The daily watchdog monitor only fires on an issue that is **assigned to an agent, has no user assignee, and sits in `in_progress` or `in_review`**, so a released runner has an unfireable monitor - the next watchdog wake never comes. After releasing, PATCH the runner back with `{"status": "in_progress", "assigneeAgentId": "<my agent id>"}` and read it back to confirm `assigneeAgentId` is set and `assigneeUserId` is null. **Read the runner back after the release, because a release does not always take the monitor with it, and a re-arm undoes the release.** The usual case is that a released runner reads `monitorNextCheckAt: null` and has to be re-armed, not just re-assigned: a monitor whose time has not yet come survives the release, and a PATCH that carries `executionPolicy` re-acquires the checkout, so a re-arm that was not needed leaves the runner checked out and the release undone. The order that works: release, re-assert `status` and `assigneeAgentId` with a plain PATCH, read the runner back, and re-arm only if `monitorNextCheckAt` actually came back null. Re-arm it with a second PATCH carrying only `nextCheckAt`, `scheduledBy` and `notes`: `{"executionPolicy":{"mode":"normal","monitor":{"nextCheckAt":"<ISO 8601 UTC>","scheduledBy":"assignee","notes":"daily backlog watchdog"}}}`. **Do not put `maxAttempts` or `timeoutAt` in that re-arm PATCH.** A monitor that has already fired carries a spent attempt budget, and a PATCH that sets the bounds again answers `Monitor bounds are already exhausted` and arms nothing — the issue comes back with `monitorNextCheckAt: null` and the failure looks like a scheduling problem rather than a bounds problem. The minimal body re-arms the same issue over the spent budget, and the read-back shows a non-null `monitorNextCheckAt`. Read the runner back after the re-arm and confirm all four: `status` is `in_progress`, `assigneeAgentId` is set with `assigneeUserId` null, `monitorNextCheckAt` is non-null, and `checkoutRunId` is null. The last one is the one a re-arm silently undoes, so it is the one a card run has to check. **Check that same read-back as a precondition whenever your run touches the runner, not only as the post-condition of your own release** — a runner you did not release can be sitting at `todo` with a live monitor on it, and every other field reads healthy while the watchdog can never fire, so the whole backlog stops silently and nothing on the board looks wrong. Treat `todo` plus a non-null `monitorNextCheckAt` as a dead watchdog wherever you find it, and re-assert `in_progress` with the assignee; when another run holds the runner's lease, report the status and the holder instead of fighting for it.
   - **Order matters: set `done` first, then `card-done`, then Advance.** `card-done` frees the slot, and Advance then claims the next post; setting `done` after Advance leaves the slot free while the card is still open, and a second run can pick the same post. **`card-done` reads `q["batch"]` before the slot, so call it before a sibling's `batch-open-ready` can open this post's next round — otherwise the round-1 close drops that batch entry and orphans the new card.**
   - **The three edits to a back-filled record are a fixed set, and each one is load-bearing.** `verdict:` becomes `"approved"`, one Verdicts row is appended under the header, and the `Back-filled from jobs.db; not reviewed yet.` line is deleted. The row replaces the blank line the back-fill left under the header — appending below that line instead leaves the marker in place and the record still reads as unreviewed. `scripts/approve_record.py <record.md> --approved --issue <GUL-x>` does all three and verifies the result; hand-editing the same three spots across 153 posts is where a half-applied edit creeps in, so prefer the script. **A reason that runs over two paragraphs is joined into one cell with ` / ` before it goes in** — a raw newline ends the table row, so the record then renders as broken markdown under a verdict that is otherwise correct. Verify anyway by grepping the record for the marker and reading the whole Verdicts table, not just the frontmatter.
   - **An approval with no reason still needs a row reason.** Write `Approved on review.` — the reason is not optional, but it is not yours to invent either.

## Pitfalls

- **On a backlog review card, a re-render that passes self-check and goes on the next round's card stays in staging.** Do not copy it to the vault or update the post embed before Wojtek approves it on the round-2 card — the vault copy, embed update, record write and `superseded_by` chain all happen at approval time, not at self-check time. The skill's rule is "keep drafts in staging and let only approved images into the vault." Pre-staging a re-render in the vault violates this rule and can cause the round-2 run to skip the vault copy at approval time.

- **A question comment reopens a closed card issue.** A user comment on a `done` card issue makes it `in_progress` again and wakes you; it is not a new card and the earlier verdicts still stand. Read the comment, answer it on that issue, then set the issue back to `done` — do not re-open the verdict card, re-append verdicts or rewrite the records, and do not re-run `card-done` for a post the queue already counted as done.
- **A freshly created card turns `in_progress` on its own** — the harness claims an assigned issue for its own run, so a fresh card is already being worked without your help. Do not PATCH it back to `todo` and do not treat it as a failed create; verify the create by re-reading the issue, not by its status. To see whether another run is live on it, read `GET /api/issues/<id>/activity` and look at the `runId` on the newest events: a card whose events all carry your own run id is untouched by anyone else, and one carrying a different run id is being worked right now. (The company- and agent-level `runs` routes are not served by the board API; the per-issue activity feed is the one that answers this.) On the runner, a live card run means the runner has nothing to do but refresh the queue document.
- **Item ids are the join key.** The brief's item id is the card's `id` and `label`, the render's `--name`, and the stem of the prompt file and the new asset. Change it and the next round cannot find its predecessor. **A second attempt inside a round keeps the brief's item id on the card and puts the attempt suffix on the render name only** (`--name <item id>-r2b`, prompt file `<item id>-r2b.json`, fetched PNG stem `<item id>-r2b-<token>`), so the card still carries one row per slot and the attempt is told apart by its job id and its note — never by a second item id, which would split the slot in two. **A new ROUND's card is the other case, and it carries the suffix in the item id itself** (`<slot>-r<k>`), because the round is a new card with a new brief. The two rules look alike and pull in opposite directions: the suffix rides the render name only when the attempt stays inside one round, and rides the item id when the card is a new round. **Three places have to agree, and a handoff brief that gets them wrong sends the next round to a card whose rows do not match its own table:** the card's item id and label, the render's `--name` and prompt file, and the vault asset's filename. A brief whose table says `context-autofit-header-r3` while its bookkeeping paragraph says the slot id stays `context-autofit-header` is a contradiction the next run will resolve the wrong way, so check the two against each other before the card goes up — The closing-line summary is shorthand for the slot and loses to the table's item id."
- **The record name and the `superseded_by` chain follow the render that actually shipped, not the one the brief names.** The brief's table lists the attempt it knew about; when a slot ships a later attempt, the new record's stem is the fetched PNG stem of the shipped render and the chain points at that render's job id. A brief that names only the earlier attempt's job id sends the next run to point the chain at a render that never reached Wojtek. **A round-2 card whose own brief names a render that this run then holds back is the sharpest version of this**: the brief's bookkeeping block names a job id to set as `superseded_by` and a record path to write, and both are now wrong, because the named render became a held-back attempt and the replacement is what ships. Write the correction into the handoff — the chain points at the replacement's job id, the held-back render gets its own record with a `rejected` row saying it was held back at the self-check, and the record path names the shipped render's stem. **The card's item id does not move**: the brief's item id stays the card's `id` and `label` and the attempt rides the render name, so the slot is still one row on the card.
- **Do not count on a comment closing the card.** `request_item_verdicts` defaults `supersedeOnUserComment` to `false`, so a comment arrives as its own wake and the card stays `pending`; set the flag explicitly **inside the `payload` object** when the close is what you want — a top-level copy is silently dropped by the server. Either way, put every instruction in the item reasons and repeat the legend on the card, so Wojtek knows the rules without scrolling the issue.
- **One card open at a time.** Never advance past a card that still has an unresolved item; the helper refuses it and the queue stops moving.
- **The runner's watchdog is not the card's monitor.** The watchdog updates the `queue` document and frees a dead slot; a render monitor wakes the card. Setting both on one issue means one of them never fires.
- **Advance is not reversible by release + card-done, and a reverted Advance orphans the re-render round.** `backlog.py release` frees the slot and `card-done <n>` moves the post, but neither re-queues the round that was already queued, and neither restores the slot Advance had claimed. The result is `slot: null` with `ready: []` while the post sits in `rendering` with re-renders in flight and no card path to the next round. **Do not revert an Advance once it has run.** If you doubt it, read `backlog.py status` and the issue activity instead; the monitor wake queues the round-2 card through `next`, which pops `q[ready]`. A real repair when state is already broken: call `backlog.py ready <n> <round> <brief>` with the fetched render's path before ending the run, so the monitor wake has something to pop. Never end a run with a post in `rendering` and an empty ready queue.
- **A render monitor must be scheduled with `nextCheckAt` in the PATCH body.** The correct shape is `{"executionPolicy":{"monitor":{"nextCheckAt":"<ISO 8601 UTC>","scheduledBy":"assignee","notes":"render ETA"}}}`. Do not use `timeoutAt`, `maxAttempts`, or a top-level `monitorNextCheckAt` field — those do not set the monitor. The monitor is a Paperclip issue monitor, not a renderer event; the ETA comes from your own UTC clock plus the render's ETA, not from the worker's local-time `created_at`. *Done when the PATCH response shows a non-null `monitorNextCheckAt`.*"
- **A document PUT needs the issue checked out.** Refreshing the runner's `queue` document from a run that does not hold the runner answers `409` `Issue run ownership conflict` and the refresh does not land. Checkout the runner first, then PUT — the shape is in `references/paperclip-api.md`.
- **The vault is not a git repo.** The library records and the post files are the durable change; there is no commit to make and no diff to show. Say which files changed in the closing comment instead of promising a commit.
- **Several cards open at once is not automatically a broken one-card rule.** Batch mode opens extra cards beside the live slot, so `backlog.py status` legitimately shows many posts in `card` state. Check `q["batch"]` in `~/image-studio/backlog/queue.json` and the runner's `Batch cards in flight` line before reporting a violation; the live slot is what Advance moves, and a batch card never touches it.
- **A sibling or PM run can block the issue while you are working it.** Re-read `status`, `dependencyReady` and `unresolvedBlockerIssueIds` before the final status PATCH and before posting any card. If the issue became `blocked` mid-run, do not PATCH it to `in_review` (it answers 409 `Issue follow-up blocked by unresolved blockers`), withdraw any verdict card you already created on it, and report the blocker instead of completing the card. Work that landed on the blocked issue (attachments, a card) is misplaced and must be re-done on the unblocked issue the blocker points to.
- **`vision_analyze` availability is intermittent, not a fixed property of a run.** It can succeed in one run and be text-only in the next on the same issue, so a previous run's "vision unavailable" note is stale — re-check every time. When it IS available, use it: it catches text defects (garbled labels, text banners) that mechanical checks (grey bars, palette strips, dimensions) do not detect, and a render that passes mechanical checks can still fail vision. When it is NOT available, run `check-grey-bars.py` and `check-palette-strip.py` regardless and put the gap in the check note (`"Vision self-check unavailable (text-only aux backend); mechanical checks pass."`). Do not stall the card waiting for vision, and do not invent a visual read you did not make. **Exception: when the card issue itself carries an instruction to block rather than post a half-built card**, follow that instruction and set the issue `blocked` with one sentence on why. The general fallback above is for image requests; a backlog-review card's own instruction governs.

**A `blocked` disposition with an `unblockDescriptor` is not a substitute for `in_progress` with a real monitor.** When a render is in flight and no monitor is set, the correct disposition is `in_progress` with a real `executionPolicy.monitor` (`nextCheckAt`, `scheduledBy`, `notes`), not `blocked` with an `unblockDescriptor`. The `unblockDescriptor` is for when there is a genuine external blocker (a missing permission, a tool outage, a human decision) that prevents any work. A pending render is not a blocker; it is work that will finish on its own and needs a scheduled wake to collect it. Parking the card as `blocked` kills the monitor eligibility (monitors only fire on `in_progress` or `in_review` issues), so the render sits finished and uncollected while the card looks idle. The recovery contract may suggest `blocked` as a valid disposition, but for a render-in-flight card the only valid disposition is `in_progress` with a real monitor whose `monitorNextCheckAt` reads back non-null.

**Setting a Paperclip issue to `blocked` needs a blocker, not just a status.** A bare `PATCH {status: "blocked"}` answers 422 `Entering blocked requires unresolved blockers, a pending interaction/approval, or unblockDescriptor`. Add `unblockDescriptor: {owner: {agentId: <your agent id>}, action: "<what unblocks it>"}` (or `blockedByIssueIds`) to the same PATCH. When the blocker is your own (a quota, a tool outage), the unblock descriptor is the right shape; a human-input wait uses `in_review` with a saved interaction instead. See `references/paperclip-api.md`.

**Do not locate vault files with a full-disk search.** The vault path on the Air host is fixed: `~/wojtek.second.brain.obsidian.vault/` (which is `/Users/paperclip/wojtek.second.brain.obsidian.vault/` for the matejko profile). `find / -name …` crawls the whole disk, hangs for an hour, and the PM will kill the process. Read the path from the issue's brief or from `~/image-studio/backlog/queue.json` instead.
