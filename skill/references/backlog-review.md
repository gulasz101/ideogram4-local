# Backlog review mode: existing images, one card per post

A "Backlog review <nnn>/<total>" issue is **not an image request**: it re-reviews images already embedded in unpublished drafts, one post per card, newest first. Round 1 renders nothing unless the brief lists a missing image.

**The parent runner issue's description is authoritative.** This file is the fast path plus the pitfalls that cost time. Read it when you are woken on a card or on the runner, and re-read the parent description before you act on anything it decides.

## The two issue types

- **Runner** — holds no card. It advances the queue, keeps the order in the `queue` document, and carries the daily watchdog.
- **Card** — one per post per round. Its description is the brief, verbatim, and the brief is authoritative for item ids.

## Queue state

Live state is `~/image-studio/backlog/queue.json`, and it changes **only** through `~/image-studio/backlog/backlog.py`, which takes a lock. Never edit `queue.json` by hand.

| command | use |
| --- | --- |
| `status` | table of every post not `todo`, plus the slot; this is what goes into the `queue` document |
| `next` | JSON `{"action":"create"\|"wait"\|"finished", n, round, brief, title}` |
| `opened <n> <ID>` | record the issue just created for the slot |
| `card-done <n> [--rendering]` | card complete; `--rendering` keeps the slot while renders run |
| `ready <n> <round> <brief>` | re-renders checked; queue the round |
| `note <n> <text>` | append a note to a post |
| `release` | free a stuck slot — repair only, say so in a comment |
| `batch-open <count>` | open up to `count` extra cards at once; returns one entry per card (brief, title, n) |
| `batch-opened <n> <ID>` | record the issue created for a batch card |

There is no `--help`: the script prints its usage for any unknown argument, so `backlog.py --help` is a wasted call.

## Batch cards: more than one card in flight

**The one-card-at-a-time rule has an exception, and it is Wojtek's.** On 2026-10-21 he asked for five to ten review cards at once so there would be work to do overnight, and the helper grew a batch mode for it. The rule is not deleted — the live slot is untouched and the runner still advances one post at a time — but extra cards can be open alongside it.

- `backlog.py batch-open <count>` claims the next `count` `todo` posts, sets each to `card`, and returns one entry per card: `n`, `round`, `brief`, `title`. It never touches `q["slot"]`, and it skips posts already in the slot or in the batch.
- Create the issue for each entry, then `backlog.py batch-opened <n> <GUL-id>` to record it.
- `backlog.py card-done <n>` releases a batch card as well as a slot card: it looks the post up in `q["batch"]` first, drops the entry and sets the post's state. A batch post that is not in the batch and does not hold the slot is still an error.
- **`card-done` also closes a post that is in `rendering` without holding the slot.** A card that queues re-renders calls `card-done <n> --rendering`, which sets the post to `rendering` and releases the slot so the next post can start. When the re-render comes back approved and the slot is long gone, `card-done <n>` on that post closes it: the `rendering` branch sets it to `done`. Without that branch the post is stuck in `rendering` forever and the runner's totals never reach it.
- The runner's `queue` document gets a **Batch cards in flight** line, built from `q["batch"]` by `scripts/build-queue-doc.py`. A batch card that is not in that line is a card the board cannot see.

**A batch card's own run is a normal card run.** The harness claims a freshly created card issue for its own run, so each card issue is worked by its own run, uploads its own PNGs and opens its own verdict card. Do not do a card's work from another run: the upload fails with `Issue run ownership conflict` because the issue is checked out by that other run. Check `GET /api/issues/<id>` for `checkoutRunId` and `executionRunId` — if they name a run that is not yours, the card is already being worked and you leave it alone.

## Several of your own runs can be live at once

The harness starts a run per card, so one agent holds several live runs at once, and a run on the runner issue and a run on a card issue can both be mid-flight over the same vault files, the same queue and the same records. Two of them working the same slot is not a bug to work around — it is the normal shape of a batch.

**So the first thing a run does is find out what its siblings already did.** Before you render, re-render, copy a PNG, write a record or edit a post, read the live state:

- `GET /api/agents/me/inbox-lite` — every issue assigned to you, each with its `activeRun` and `execution.phase`. A phase of `reconnecting` is a **live** run, not a dead one.
- `GET /api/issues/<id>` — `checkoutRunId` and `executionRunId` name the run that holds the issue.
- `GET /api/issues/<id>/activity` — the per-issue event log, newest first, with a `runId` on every event. A different `runId` on the newest events means a sibling is working it right now.
- `GET /api/issues/<id>/runs` — whether the previous card's run is still alive.

**A refused file write is a sibling telling you it got there first.** The write tools refuse to overwrite a file that a sibling changed after your last read, and the refusal names the run and the issue that changed it. That is not a wall to retry against — it is the cheapest possible answer to "who did this already?". Re-read the file, re-read that issue, and then look for the **residual gap** rather than repeating the finished work. A sibling that already applied a verdict leaves the durable artifacts correct and your step redundant; what is left is usually a small correctness defect nobody patched: a record whose `created_at`/`finished_at` disagree with the renderer's `status` line, a `superseded_by` chain missing a record, a deliverable nobody created.

**The gap is the deliverable.** When a sibling has done the bulk of a card, the honest remaining work is to verify the whole closeout and fix what is inconsistent — do not re-render, do not re-copy the PNG, do not re-approve a record that already carries the verdict.

## The closeout checklist

An issue is only `done` when **every** line of this is true. It is a checklist of independent things that can each be wrong, so check each one rather than trusting the state you happen to remember:

1. Every slot has an approved image, and the approval is Wojtek's on the card (`result.items[].resolvedByUserId` set, `resolvedByAgentId` null).
2. The approved PNG is in the vault at `tech_blog/assets/<YYYY-MM-DD>/<slug>.png`, and its bytes match the staging file.
3. The post's embed points at that asset, and no stale embed of an earlier round is left in the post.
4. A library record exists for the approved job, named `<YYYY-MM-DD>-<fetched PNG stem>--<job_id>.md`.
5. That record's `created_at` and `finished_at` match `imagegen status <job-id>`.
6. Every earlier record of the slot has `superseded_by` set to the approved job id, and the approved record's is `null`.
7. The queue state is right — `backlog.py card-done <n>` for the card, and the post is no longer counted as open.
8. The verdict card is `pending` or resolved with a human's decision, and its attachments read back with a non-null `issueCommentId`.
9. The Paperclip issue is `done`, and the closing comment carries every job id, asset path, record path and self-check note.
10. The runner's `queue` document is rebuilt from live state, not from memory.

**A closeout item you verified earlier in the run is still worth re-verifying at the end** — a sibling can land between the two checks, and the state you confirmed at the start is not the state you are closing on.


## The runner's queue document is the list of everything

The runner holds no card, so the board shows one open review issue at a time. The full list of posts therefore has to live in one document on the runner: the `queue` document, addressed `GET/PUT /api/issues/{runnerId}/documents/queue` with `baseRevisionId` from the last `latestRevisionId` (omit it on the first write, get a `409` on a stale one).

**Rebuild it from live state, never from memory.** `scripts/build-queue-doc.py` reads `queue.json` plus every brief and prints the whole table: every post with its status field, image count, needs-render count and live state, plus the live slot and the posts that need a render. `backlog.py status` cannot build this table — it prints only the posts that are not `todo`, so it hides the todo backlog that is exactly what the reader is missing.

**The runner has to be checked out before the document can be written.** A document PUT is scoped to the run, so refreshing the queue document from a run that does not hold the runner answers `409` with `Issue run ownership conflict`, and the refresh silently does not land. Claim the runner first — `POST /api/issues/<runnerId>/checkout` with `{"agentId": ..., "expectedStatuses": [...]}` (both fields are required; `{}` answers `400`) — confirm the response carries `checkoutRunId` set to your run, then run `scripts/put-queue-doc.py`. A `409` from that script means the runner is not yours right now, **not** that the document changed underneath you; re-fetching the revision does not fix it.

**PUT the script's output; never regex-patch the stored body.** A patched body drifts from the script's column layout and from the counts the script derives from the briefs, so the next reader gets a table no tool reproduces. Run `scripts/put-queue-doc.py --issue-id <runnerId> --run-id <runId>`: it builds the body, fetches the current `latestRevisionId`, PUTs it and prints the new revision plus the live-slot line. Fall back to `scripts/build-queue-doc.py --out <file>` plus a hand-built PUT only when the script cannot run.

**A stored table whose columns drifted can only be re-synced by the whole body.** When the script gains a column (or the stored table has one it does not), rewriting cells in place leaves the old column count in place and the drift survives every later refresh. PUT the script's entire output each time; the column set comes with it. Refresh the document on every runner wake, right after reading `backlog.py status`, so the counts and the live-slot line in the runner's comment describe the same state the document shows.

**The runner's description totals are prose; the briefs are the truth.** When the description's image count disagrees with what the briefs and the script measure, let the script's number stand, say so in a comment, and leave the description alone — the brief is the authoritative per-post source.

**A question about the backlog is a request for the queue document, not for a list in a comment.** When Wojtek asks where the remaining work is, the answer is the refreshed queue document plus a short comment that says: where the list lives, the counts, the rule that makes only one card open, which card is live and waiting for him, and which posts need a render. Do not paste 153 rows into a comment — the document is the artifact, the comment points at it.

**Never change the one-card-at-a-time rule to "go faster".** It is the runner's design and the helper enforces it; a queue with many cards open is many sets of unanswered verdicts. If Wojtek asks for more in flight, treat it as a question for him, and offer it — do not act on it unilaterally. **Exception, once granted:** Wojtek asked for more cards on 2026-10-21 and the helper grew a batch mode for it (see **Batch cards**). That is a decision he made, not a speed-up you decided on, and it does not license widening it on your own — ask again before opening more than he asked for.

## Advance

```bash
NEXT=$(~/image-studio/backlog/backlog.py next); echo "$NEXT"
```

- `create` — POST the card issue with `jq --rawfile desc "$BRIEF"` so the description is the brief byte for byte; `parentId` = the runner's id, `projectId` from the runner, `assigneeAgentId` yourself, `status: "todo"`. Then `backlog.py opened <n> <ID>` (**the identifier**, e.g. `GUL-72`, not the uuid). **Verify** by re-running `next`: it must now say `wait`. Then confirm the create by re-reading the issue and comparing its description to the brief — the brief is authoritative for item ids, and a truncated description silently changes what the next card reviews.
- `wait` — a card is open or re-renders are running. Do nothing.
- `finished` — do nothing; the runner's watchdog closes the runner.

**`next` claims the slot; it is a write, not a read.** Calling it takes the next post, sets its state to `card` and installs the slot, so call it exactly once per card. Two runs calling it together cannot both get `create` — the loser gets `wait` — but the winner may be a run that never got as far as creating the issue, which leaves the slot held with `issue: null`. After Advance, read `backlog.py status` and check the slot names an issue: if it does not, either fill that slot (the post is already yours) or `backlog.py release` to hand the post back to the queue. Never create a second card issue for a post whose slot is already held.

**A slot with `issue: null` is often a card's own run in flight, not a stall.** The card's closing run ends with Advance: it claims the next slot and then POSTs the card issue for it. Between those two writes the slot names the next post with no issue, and a runner wake that reads the slot in that window sees an empty `issue`. So on a runner wake, when the slot names no issue, do not create a card and do not release the slot — check whether the previous card's run is still alive with `GET /api/issues/<cardId>/runs`; if it is, give it a moment and re-read `backlog.py status`, because that run is about to create the issue and record it. Only a slot that still names no issue after the card's run has finished is a real stall, and that is the case `backlog.py release` is for.

**The card's own run advances the queue, so the runner often wakes late.** A card issue ends with Advance in its own run. By the time the runner's `issue_children_completed` wake arrives, the next post's card may already exist. On a runner wake, read `backlog.py status` first: when the slot already names an issue, the card is created and recorded — do not call `next` again, do not create another card, just report the new state.

**Verify a child's closing claim against the vault, not against the child's comment.** The card's comment says what it changed; the library record is the durable truth. Read the records the card names and check `verdict:` and the Verdicts row: `grep -h '^verdict:' 3-resources/image-library/2026-10/<record>.md` should read `"approved"`. A card that closed without touching its record is a card that did not do the work, and the runner's totals must not count it.

## Per card

1. **Read first.** The brief, the post, and each existing image's `## Prompt` and `## Why`; `hindsight_reflect` the taste for the post's topic. The records beat the memory.
   - **When `hindsight_reflect` and `hindsight_recall` both time out, the taste model is unavailable, not empty.** That happened on post 009 (GUL-80, 2026-10-21): both calls returned `TimeoutError` for the same query. Say plainly on the issue that the check was built from the library records and the post instead of from memory of his preferences, and do not present guessed taste rules as his. Retry the recall later; do not let it block the card.
   - **`hindsight_reflect` can answer about a different series entirely.** On the grey-market Claude post (GUL-72, 2026-10-21) it returned a "small grey boxy robot, brushed-steel panel, warm workshop" world — the language of a different series — while all three of that post's library records are Akira Toriyama chibi, and the post's own robot is a sketchy vendor. A reflect answer that names a style the post's records do not use is a different series, not this post's taste. Match the series from the records' `## Prompt` blocks and say on the issue that the model answered for another series.
   - **When the taste model is unreachable, the library's verdict history is the taste model.** `hindsight_reflect` and `hindsight_recall` can both time out; a failed call is not an empty model, and it is never a licence to invent preferences. Grep the verdict rows across the whole library for the reasons that recur (`grep -rh '^| [0-9]' 3-resources/image-library/ | sort`), hold the card to those, and say on the issue that the model was unavailable. When a deliverable must cite a memory id, the ranked path is also the wrong tool — `hindsight_retain` returns a receipt, not an id; use `scripts/hindsight-memory.py` and `references/taste-memory.md`.
2. **Missing image with no render** (the brief names it): render it, one render per item, `--name <item id>`, via skill steps 2–5. Then `card-done <n> --rendering`, Advance, end the run — its card comes later carrying both the existing images and the new render.
3. **Open the card.** `vision_analyze` every PNG (vault file for an existing image, staging PNG for a render); one check note per image — spelling, no grey box or bars, does it show what its section says. One `Why:` line per image from its section and prompt, and say plainly when it does not fit. **A back-filled record's `## Why` can describe a different picture than the one in the file:** on post 005 both `drill-header` and `drill-cleanup` carried a `## Why` (and a post alt text) naming a giant plug, a phoenix bird, a flashlight and a dog-shaped alarm clock — none of it in the PNGs, which show a stopwatch drill and a closing-time cleanup. Judge the PNG against the record's `## Prompt`, not against the `## Why`; when they disagree, the stale `## Why` and alt text are a post-prose defect, not an image defect. Say so plainly on the card and in a comment, and do not edit the post to fix it — the card's scope is the image, and the runner's rule allows post edits only for an approved re-render's embed. **A mismatched `## Why` is often off by one paragraph, and the alt text can name a prop that is not in the PNG at all.** On post 009 both inline records quoted the paragraph *after* the image instead of the section it sits in, and the draft's alt texts said "the robot points at the new crate" and "Wojtek points at the cable" for PNGs that show the robot holding a blank card and Wojtek holding a clipboard with no cable anywhere. Check the alt text against the picture prop by prop, not just the caption. **The quoted passage can be wrong while the picture is right**, which is the other half of the defect: on post 007 (GUL-78) both `one-sync-slot-turnstile` and `deletion-gate-locked` carry a `## Why` that quotes a section of the post other than the one the image sits under. The PNGs were right and the provenance was wrong, so the PNG is not the defect. Same rule: judge the PNG against `## Prompt`, report the mismatch, and do not edit the record's `## Why` or the post — a record edit is only ever the three verdict edits. **Record the defect in the queue so a later round on the same post sees it:** `backlog.py note <n> "<what disagrees, and that the PNGs were judged against the records' Prompt>"`. The note rides the runner's queue table, so it outlives this card. **An image can be embedded under a section it does not depict, and that is a placement defect, not an image defect.** The brief's "embedded under" column names a heading; when the PNG plainly illustrates the *next* section instead, the picture is not wrong and the slot is not broken — say plainly which section the image really serves and leave the embed where it is, because post edits are out of scope for a review card. Record it with `backlog.py note` so the runner's table carries it. **A prop that looks tidy can still be a model artifact: judge it by what a reader gets from it, not by whether it looks deliberate.** A grid of aligned coloured tiles with no axes, labels or legend is a pseudo-chart, not a chart; a flat rectangle with a drop shadow and no perspective is a pasted overlay, not a poster; a number panel of garbled digits is unreadable text. Ask of every prop: *did the prompt describe this concretely enough that the model knew what it was drawing?* When the answer is no, the render's version of it is an invention and the invention is the defect. Two tells that settle a case: a panel whose drawing style does not match the frame, with a rim and a drop shadow and geometry that does not continue the room, is a composite pasted over the scene rather than a window into it; and a connector that appears on the canvas as two separate gadgets has not connected, whatever the prompt asked for. Upload the PNGs, then one `request_item_verdicts` card: `human_only`, `wake_assignee`, `approve/reject/defer`, `requireReasonOn: ["reject"]`, bulk approve allowed, key `verdicts:<issue id>:round-<k>`, one item per image in brief order, `description` ≤500 chars, `detailsMarkdown` = legend + table of item id, section, record path, job id. Build the payload with `scripts/build-verdict-card.py` from a spec in the shape of `templates/verdict-card-spec.json` — it bakes in the safe defaults and refuses to write a payload with an over-long description. Set the issue `in_review`. See `references/paperclip-api.md` for the exact POST. **A taste model that lands after the card is live changes the card's read, not the card.** `hindsight_reflect` and the first recalls can time out and a later, narrower recall can still return the rules. When that happens the card's items are already frozen, so put the finding in an issue comment — name the image, the rule it touches, and what a re-render would change — and let the pending card carry the verdict. Do not withdraw and re-create the card: two cards for one round is exactly what the one-card-at-a-time rule exists to prevent. **A wrong check note is the exception that does justify withdrawing and re-posting.** The rule against two live cards is not a rule against correcting a card; it is a rule against Wojtek seeing two verdicts to give for one round. Withdraw the card (`POST /api/issues/<id>/interactions/<id>/withdraw` with a reason naming what was wrong), which settles it as `cancelled`, and post the corrected card under a new idempotency key (`verdicts:<issueId>:round-<k>-corrected`). The cancelled card is not a pending card, so one card stays open for the round. Verify with `GET /interactions` that exactly one is `pending`, and say in an issue comment what was wrong and what the correction is — the withdrawn card's wording stays in the thread, and a wrong note that vanishes without explanation reads as a quiet mistake rather than a correction.
   - **Two analyses of one PNG can contradict each other, and the crop is the tie-breaker.** A region-cropped read answers only about its region, so a full-frame pass reporting "no legible text" and a crop reporting a spelled label are both true of their own scope. When a claim decides the verdict, re-ask with a crop of the disputed region and a question scoped to it ("read every character on the clipboard verbatim") rather than picking the side that suits the conclusion. **But the `region` parameter is not a reliable cropper**: it can resolve to different content between two calls, so the same box reads as the subject in one pass and as bare wall in the next, and two reads of one box can give opposite answers. A claim that decides a verdict is settled on a crop **written to disk** — locate the subject by pixel signature, write an upscaled crop of exactly it, and count what is countable — not on a region read. `scripts/crop-probe.py` does the crop and the counting; `references/verifying-image-details.md` has the procedure. The card's text is frozen at the POST, so a note that later turns out to be wrong is a defect Wojtek would judge from.
   - **The 500-character description is a summary; the long-form check note belongs in `detailsMarkdown`, written before the POST.** The card is frozen once created, so put the full per-image note in `detailsMarkdown` (20000 chars), keyed by item id, and use the description for the why plus a one-line signal of what to look at.
4. **Verdict wake** — handle only `newlyResolvedItemIds`. Retain one memory per reject and per defer (the reason, the post, the image, the prompt traits), and one per card for its approvals: what the approved images have in common, plus the honest limit that one card is one data point. Approve an existing image by updating its record in place, exactly as `references/library-records.md` says — copy no PNG and edit no post, because the file is already where the draft points. Approve a render by copying it into the vault, editing only that embed, and writing the record with the slot's history. Reject re-renders from the reason; at round 3 open a `request_confirmation` instead of rendering again.
   - **A silent re-render inside a round is an attempt, not a round.** Rounds are card rounds: one card per round per post, and the 3-round limit counts cards. The one silent re-render a failing variant gets (skill step 6) happens inside the same round and does not consume a round. So a slot can be on round 2 with two renders already spent, and what the 3-round limit stops is a third *card*, not a third render. Say which attempt you are on when you report a re-render, so Wojtek knows what the next card means.
   - **An approval with no reason is still an approval.** Write the row reason as "Approved on review." and record in the retained memory that no reason was given. Do not read a silent approval as a rule about the whole series: the same image approved without comment says nothing about the next one.
   - **A rejection is a record edit too, not just a render.** Mark the record `verdict: "rejected"` and add one row carrying his reason verbatim, then re-render from that reason. Leaving a rejected image's record at `unreviewed` makes the library disagree with the card.
   - **A rejection replaces the prop, not just the wording of it.** When his reason names a defect (unreadable text, an invented artifact, a missing connector), the new prompt has to remove the thing that caused it: a prop the old prompt could not describe concretely gets replaced by a physical object the prompt can describe, and a connector that went missing becomes its own element with a `bbox` spanning both ends. Re-ask the same question of the old prompt: *what could the model not draw?* That is what he is looking at.
   - **A card can approve several images at once.** A card's result is per item; approve each one and record each one, and do not treat a batch of approvals as a preference for that composition in general.
   - **A card approving everything still means one data point.** When a whole card comes back approved with no reasons, retain one memory for the card: what the approved images have in common, plus the honest limit that one card is one post. Retaining one memory per image would multiply one observation into three and read as three independent data points later.
5. **Every item resolved.** With queued re-renders: monitor at the last ETA + 5 min, `card-done --rendering`, keep `in_progress`, end the run. Without: closing comment with every verdict, the files changed and the records, set `done`, `card-done <n>`. Then Advance.
   - **A re-render round gets its own card issue, and this card issue closes.** The next round's card is a *new* issue, created by Advance from the ready queue with the handoff brief as its description; the card issue you are on is set to `done` with a closing comment and does not carry the next round's verdict card. Opening a second verdict card on the same issue while another post's card is still open breaks the one-card-at-a-time rule the queue exists to enforce, and it puts a later post's card on the board before the earlier post's slot is finished. The order on a re-render round is: write the handoff brief → `backlog.py ready <n> <k> <brief>` → set this card issue `done` → Advance. When the slot is still held by another post, Advance says `wait` and the ready brief waits its turn — that is correct, not a stall.
   - **The handoff brief must name the render that is going on the card.** When a variant gets a silent re-render, the brief's staging path and job id belong to the *final* render, not the held-back attempt. Keep the held-back attempt's prompt file beside the final one (`<item>-r<k>-attempt1.json`) and name it in the brief, so the prompt history stays visible and the next round can find its predecessor. Write the brief only when every re-render of that card is fetched and checked: a brief written early points at a render that is not the one that ships.
   - **Order matters: set `done` first, then `card-done`, then Advance.** `card-done` frees the slot, and Advance then claims the next post. Setting `done` after Advance leaves a window where the slot is free but the card is still open, and a second run can pick the same post.
   - **The three edits to a back-filled record are a fixed set, and each one is load-bearing.** `verdict:` becomes `"approved"`, one Verdicts row is appended under the header, and the `Back-filled from jobs.db; not reviewed yet.` line is deleted. The row replaces the blank line the back-fill left under the header — appending below that line instead leaves the marker in place and the record still reads as unreviewed. `scripts/approve_record.py <record.md> --approved --issue <GUL-x>` does all three and verifies the result; hand-editing the same three spots across 153 posts is where a half-applied edit creeps in, so prefer the script. Verify anyway by grepping the record for the marker and reading the whole Verdicts table, not just the frontmatter.
   - **An approval with no reason still needs a row reason.** Write `Approved on review.` — the reason is not optional, but it is not yours to invent either.

## Pitfalls

- **A question comment reopens a closed card issue.** A user comment on a `done` card issue makes it `in_progress` again and wakes you; it is not a new card and the earlier verdicts still stand. Read the comment, answer it on that issue, then set the issue back to `done` — do not re-open the verdict card, re-append verdicts or rewrite the records, and do not re-run `card-done` for a post the queue already counted as done.
- **A freshly created card turns `in_progress` on its own** — the harness claims an assigned issue for its own run, so a fresh card is already being worked without your help. Do not PATCH it back to `todo` and do not treat it as a failed create; verify the create by re-reading the issue, not by its status. To see whether another run is live on it, read `GET /api/issues/<id>/activity` and look at the `runId` on the newest events: a card whose events all carry your own run id is untouched by anyone else, and one carrying a different run id is being worked right now. (The company- and agent-level `runs` routes are not served by the board API; the per-issue activity feed is the one that answers this.) On the runner, a live card run means the runner has nothing to do but refresh the queue document.
- **Item ids are the join key.** The brief's item id is the card's `id` and `label`, the render's `--name`, and the stem of the prompt file and the new asset. Change it and the next round cannot find its predecessor.
- **Do not count on a comment closing the card.** `request_item_verdicts` defaults `supersedeOnUserComment` to `false`, so a comment arrives as its own wake and the card stays `pending`; set that flag explicitly when the close is what you want. Either way, put every instruction in the item reasons and repeat the legend on the card, so Wojtek knows the rules without scrolling the issue.
- **One card open at a time.** Never advance past a card that still has an unresolved item; the helper refuses it and the queue stops moving.
- **The runner's watchdog is not the card's monitor.** The watchdog updates the `queue` document and frees a dead slot; a render monitor wakes the card. Setting both on one issue means one of them never fires.
- **A document PUT needs the issue checked out.** Refreshing the runner's `queue` document from a run that does not hold the runner answers `409` `Issue run ownership conflict` and the refresh does not land. Checkout the runner first, then PUT — the shape is in `references/paperclip-api.md`.
- **The vault is not a git repo.** The library records and the post files are the durable change; there is no commit to make and no diff to show. Say which files changed in the closing comment instead of promising a commit.
- **Several cards open at once is not automatically a broken one-card rule.** Batch mode opens extra cards beside the live slot, so `backlog.py status` legitimately shows many posts in `card` state. Check `q["batch"]` in `~/image-studio/backlog/queue.json` and the runner's `Batch cards in flight` line before reporting a violation; the live slot is what Advance moves, and a batch card never touches it.
