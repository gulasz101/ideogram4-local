# image-studio

Matejko's whole procedure for turning a Paperclip image request into an Ideogram 4 render, putting it in front of Wojtek, and learning from his verdicts. The generation stack runs on the M1 Max; `imagegen` submits and fetches from the Air.

## When to use

Use this skill on any of these branches:

- An issue asks for an image (a header, illustration, or diagram for a post).
- An issue monitor wakes you on a render (`monitorNextCheckAt` has arrived).
- An item-verdict wake arrives with a non-empty `newlyResolvedItemIds`.
- A wake arrives on an issue whose verdict card is **already pending** (`issue_assigned`, `issue_monitor_due`): verify the card and attachments, do not rebuild or re-render. Checklist in `references/paperclip-api.md`, order in `references/review-loop.md`.
- The owner says the backlog's images are broken and only the correct ones may be reviewed: audit the prompts first, repair and re-render the failing slots as ideogram + flux2-klein pairs, batch it. The gate, the batch cap against the shared queue and the two scripts (`scripts/sweep-assets.py`, `scripts/audit-table.py`) are in `references/prompt-repair-audit.md`.
- The issue is a backlog-review card or the runner behind it (`Backlog review <nnn>/<total>`) — review of images already embedded in unpublished drafts, no rendering in round 1. Follow `references/backlog-review.md`.
- Wojtek asks where the backlog review stands, or where the remaining posts are. The answer is the runner's `queue` document, rebuilt from live state with `scripts/build-queue-doc.py` — not a list in a comment. See `references/backlog-review.md`.
- Wojtek asks about an image's prompt, history, or why it looks the way it does.
- A taste note or observation in the bank misattributes a rule to Wojtek, or a verdict it recorded contradicts the card — correcting the memory is part of the image work, because the wrong rule drives the next prompt. `references/taste-memory.md` has the curation route.

## Choosing the engine

Three engines share the one queue and the one worker; the default is `ideogram4`.

- **`nanobanana` is the backlog engine** (Wojtek's call, GUL-893). Gemini's own web image tool
  through the `gemini-web2api` proxy on the Max: about **12 seconds** a picture, natural language,
  and it does not have Ideogram's prompt-vocabulary filter, so no canonical JSON and no grey-box
  dance. Use it **by default for the remaining unpublished posts**.
  ```bash
  imagegen submit --engine nanobanana --prompt "flat-vector blog header: …" --name <slug>
  ```
  - **Sizes are not yours to choose.** The web tool returns what it returns — 1376×768, sometimes
    1584×672. Design the layout to accept the real size; never promise 1216×832 from this engine.
  - **No seed, no `--prompt-json`, no `--seed`.** The CLI rejects them. A nano banana record carries
    `engine: "nanobanana"` and no seed.
  - **Pace it: at most one image a minute, 5-8 posts per wake.** The web backend rate-limits per exit
    IP; a burst gets the account throttled for about two hours and then *every* proxy call fails, on
    every engine. This is the one rule that can take the whole studio down.
  - **Text instead of an image is the failure you will meet.** A stale cookie or an exhausted quota
    makes the model answer in prose; the job then fails with the model's own words in `error`. Read
    them, skip that post, report it, and do not retry in a loop.
  - The check before a batch: `imagegen submit --engine nanobanana --prompt "a test rack" --name check`
    — if it says `unknown engine`, the deploy is behind and you stop, you do not fall back silently.
- **`ideogram4` is still the keeper engine.** JSON prompts, readable in-image text, about 21 minutes
  per 1216×832 render, and full size control. Use it where the image must ship at an exact canvas or
  carry legible text.
- **`flux2-klein` is for fast drafts and companion panels.** About 3 minutes for 1216×832: explore a
  composition, or render the companion he compares against (`references/style-and-companions.md`).
- **FLUX takes natural-language prompts, not JSON.** 368–425 words ships every clause; past 425 the
  negative clause drops first. There is no `lint` for a FLUX prompt and no JSON schema.
- **Everything after the render is the same.** The review loop, the verdict card and the library record
  do not change; the record and `status` name the engine, and a FLUX record carries its seed in the
  `generation` block.

## The request workflow

1. **Read.** Read the issue's post, section, excerpt, and the intent behind them (the "why"); read the post file in `~/wojtek.second.brain.obsidian.vault/tech_blog/`; run `hindsight_reflect("What is Wojtek's image taste for <post topic>?")`, which reads the mental model **Wojtek's image taste**. *Done when you can state the post's idea in one sentence and list the taste rules that apply.*
   - **Fit the series first.** When the post already has images, read their library records' `## Prompt` JSON before writing a variant, and reuse the series' `style_description` block, its character descriptions and its world (workshop, racks, the grey boxy robot) as written. Reusing the series' prompt is what makes a new image belong to the set; matching its look from the PNG alone does not.
   - **A reflect call that errors or times out is not an empty taste model.** Call `hindsight_recall` with the same query and use what it returns before concluding there is no history; report the failure only if both come back with nothing. A `500` wrapping a `429` whose body says all models are exhausted with a reset in seconds is the route rate-limited for a moment, not an empty bank: go straight to `hindsight_recall` on a short keyword and keep the card moving instead of waiting the round out. A timeout is a failed call, not an empty result: never read it as "no history yet" and never build a prompt on that inference — work from the library records and retry the recall later. Recall returns observations verbatim, so apply the records-beat-memory rule below to every claim it makes.
   - **A recall that returns nothing on the first keyword is not proof there is no history. The bank indexes on different phrasings, so a first keyword that comes back empty can be a phrasing miss, not an absence. Try a second distinctive keyword — another rule word, the post's subject, a recurring prop — before concluding the records are the only source. When the model lands after the card is live, apply it in an issue comment.** The long natural-language query is what times out; the same bank answers a single distinctive keyword (a rule word, the post slug, a recurring prop). So on a timeout do not repeat the same long query — narrow it to one keyword and try again before falling back to the records.
   - **The library's own verdict history is the taste model when hindsight is down.** When reflect *and* recall both fail, do not conclude there is no taste and do not invent rules: the `## Verdicts` tables under `3-resources/image-library/` hold his real reasons across every card ever reviewed, so read them (`grep -rh '^| [0-9]' 3-resources/image-library/ | sort`) and treat the reasons that recur across cards as the standing rules. Say on the issue that the model was unavailable and that the records stood in, then retry the recall on a later round.
   - **A deliverable that must cite a memory id needs the REST API, not the recall.** `hindsight_retain` answers `Memory queued for storage` — a receipt, not an id — and the ranked path can be down while the bank is up. The bank's own list route serves the same memories without the reranker and carries each memory's id: run `scripts/hindsight-memory.py list "<phrase from the reason>"` and then `... get <id>`. `references/taste-memory.md` has the routes and the rules.
   - **An empty taste model is not a licence to invent taste.** When `hindsight_reflect` finds no verdicts for the topic there is simply no history yet: say so on the issue and build the variants from the existing series and the section's intent instead of presenting guessed rules as Wojtek's preferences.
   - **The records beat the taste memory, and one verdict is not a rule.** `hindsight_reflect` synthesizes across verdicts and will assert a history the records contradict — it has described a round-1 rejection on a slot whose round-1 items were both approved. Before a claim shapes a prompt, check it against the library record's `## Verdicts` table and the card's `result`, and follow the records where the two disagree. A single approval or rejection is one data point about his eye, not a preference: two variants approved on one card does not mean he always approves both, and the request's slot count still decides how many images ship.

2. **Write 2–4 variants** as Ideogram 4 JSON, starting from `templates/` and following `references/engine-pitfalls.md`. Validate each with `python3 ~/.local/share/ideogram4-local/ideogram4_local.py lint <file>`. **Also run `python3 scripts/check-bboxes.py <file>` — `lint` cannot see a transposed bbox, and a box written `[x1, y1, x2, y2]` instead of the schema's `[y1, x1, y2, x2]` is a silent layout instruction the model obeys over the prose.** Default size 1216×832. *Done when every variant passes `lint` with risk score 0 and no schema issues, and has a one-sentence why.*
   - **Risk 0 has a mechanical cause, so edit the file until the number says 0.** The linter adds +2 when the prompt carries more than six elements (density), +2 for every flagged term, and +1 when the text is under twenty words. The way to 0 is therefore consolidation, not rewording: merge props that share a region or a beat into one element with one `desc` — the router into the man who holds it, the two cable runs into one, a second light source into the `lighting` key — and swap a flagged word for its plain synonym, because a term anywhere in the scanned fields counts (`brushed metal sheet` trips the garment flag on *sheet*; `brushed metal plate` does not). A seventh element costs the same as a banned word, so count elements before you add another prop.
   - **`check-bboxes.py` reads the words in a `desc`, so a wide box needs wide-box wording.** A prop that genuinely spans the frame — a bench across the room, a cable from one machine to another — is described by its extent ("spanning the whole width of the room", "running from the cabinet to the door"). Writing "from the left edge to the right edge" makes the checker flag the prompt's own box as a full-width band that contradicts the prose, and shrinking the box to satisfy the checker moves the prop out of the place the scene needs it. Reword the description, keep the box.
   - **The linter reads your prohibitions, so a negative clause cannot name the thing it bans.** `lint` scans for the term, not for the intent wrapped around it: `no other human figure` trips the `human_shape` flag, while the same prohibition phrased around the count — `one person only in the picture, no second person, no crowd` — does not. A picture can be safe and still be rejected over a word used to forbid something. Phrase a ban in terms of what the picture should contain, and re-lint after every reword. `references/prompt-hygiene.md` has the rule and the phrasing.
   - **A prompt that lists the scene's props gets an inventory with no story — write one action, one figure, one prop.** The model treats an element list as a set of things to place and places them all faithfully, so the render is a set of correctly drawn objects in a room with nothing happening: every item from the description is there and the picture says nothing the section needs. **Ask what the verb is before you write the elements — a prompt with no verb produces a render with no story, and a list of well-described props cannot be patched into one, only collapsed.** One action, in one frame, by one figure, with the thing acted on as the target of that action, and the connection given its own element whose `bbox` spans both ends (`references/engine-pitfalls.md` #30, #38, #47). The dressing props go: each one left in the list is another thing the model will place but not connect, and a prop nobody is said to be holding gets a holder invented for it — one figure, one prop, one job, and delete a prop the picture does not need rather than re-describing it (#48).

3. **Submit** each with `imagegen submit --prompt-json <file> --name <slug>` (stdout is only the job id). **On a resumed or re-woken run, read `GET /issues/<id>/interactions` and the comments before submitting** — a card already open for this round, or a `verdicts:<issueId>:round-<n>` already answered, means those renders exist: handle them (fetch, self-check, verdicts) rather than spending another 21 minutes per image on duplicates. **And do not trust a recovery or continuation summary's account of what is on disk — the queue keeps running while a run is dead.** A summary written when a run was killed records the queue as it looked at the kill: it can report a job as having no render anywhere when it has since finished, and report a file as mid-check when it is long since fetched. Query `imagegen status <job>` for every job the thread names and list the staging date folder before you conclude anything is missing or submit a replacement — re-submitting a render that already exists costs 21 minutes and leaves two records for one attempt. Comment the job ids and the prompt summaries on the issue. *Done when the comment lists one job id per variant.*

4. **Wait without polling.** Read `eta_minutes` from `imagegen status <last-job-id>`. Schedule an issue monitor at ETA + 5 minutes, keep the issue `in_progress`, and end the run. A render takes about 21 minutes and jobs queue one after another. The PATCH body must use `nextCheckAt` (not `timeoutAt` or `maxAttempts`): `{"executionPolicy":{"monitor":{"nextCheckAt":"<ISO 8601 UTC>","scheduledBy":"assignee","notes":"render ETA"}}}`. Read the ETA from `imagegen status` and compute the time from your own UTC clock plus the ETA plus 5 minutes. *Done when the PATCH response shows a non-null `monitorNextCheckAt`.* Use the shapes in `references/review-loop.md` and `references/paperclip-api.md`.

   - **Batch cards with pending re-renders:** If the card is a batch card (post in `q["batch"]`) and a re-render is pending, do not call `card-done <n>` yet. Instead, call `card-done <n> --rendering` to set the post to `rendering` state and remove the batch entry. The issue remains `in_progress` under the render monitor until the monitor wake fetches and checks the re-render. The next round's card will be created from the handoff brief at the monitor wake. **Do not call `card-done` on a batch card until the re-render is fetched and checked.**

   - **On a backlog-review card this monitor wake is the round's handoff, not a render to show.** Fetch the render, self-check it, then write the handoff brief that names it, run `backlog.py ready <n> <k> <brief>`, post the closing comment and set the card issue `done` — then Advance. The next round is a *new* card issue that carries that brief as its description, so the brief is the only thing the next run knows. `references/backlog-review.md` has the order and the closeout checklist.

5. **On a monitor wake**, run `imagegen status` for each job. If any job is still running, **fetch and self-check the ones already `done` first** — a variant that fails the step-6 check can then be re-submitted immediately, so it renders in the queue behind the job still running instead of costing a whole extra round — then reschedule the monitor and end the run. Otherwise run `imagegen fetch <job-id>`, which prints the local path of the fetched `<slug>-<8 hex>.png` under `~/image-studio/staging/<date>/`: keep that path in a variable and use it for every later check and upload. *Done when every PNG is local and over 1 MB.*
   - **Re-poll before you end the wake.** A job whose ETA is minutes away often finishes while you check the one already `done`, so run `imagegen status` again after that check: if it is now `done`, fetch and check it in the same run instead of paying a whole wake for it. Only a job still `running` at that second look belongs to the monitor you are about to re-arm.
- **A job that reports `failed` (engine error, not a prompt defect) gets re-submitted with the same prompt, not re-worded.** `sd-cli exited with code 1` or a `connection refused` is the worker's problem, not the prompt's: re-run `imagegen submit --prompt-json <same file> --name <same slug>` and note the failed job id in the comment so the record stays honest. Do not change the prompt, do not bump the round, and do not create a held-back record — the failed attempt never reached the model's output. Schedule the monitor from the new job's ETA plus five. *Done when the re-submitted job reads `pending` or `running` and the monitor is armed.*
   - **A wake that submits a render has to leave a wake path for that render.** The monitor you are serving was scheduled for the render that just finished, so a render submitted now has no monitor pointing at it: PATCH `nextCheckAt` at the new job's ETA plus five minutes, confirm the response reads back non-null, and keep the issue `in_progress`. A re-render left without a monitor sits finished on the Max with nobody scheduled to fetch it, and the card looks idle while a render it already paid for goes uncollected — the same shape as the dead-slot stalls in `references/backlog-review.md`. This is the silent re-render of skill step 6, not a new round: it costs a render, it does not cost a card.

6. **Self-check** each image with `vision_analyze`: text is spelled exactly as prompted, **and any text the model invented beyond the prompt's own labels counts as a defect too** — a label like 'Jellyfins' or 'SAF & CLEAN' that the prompt never asked for is invented text, not a harmless typo, and it freezes into the card's note where Wojtek judges it; **and pass it a resolved path — the vault is a symlink (`~/wojtek.second.brain.obsidian.vault` → `/Users/paperclip/vault`), and an image path spelled through the symlink answers `media file not found` for a file that is plainly on disk, so build every path a check or an upload uses from the resolved root (`readlink -f` it once) and the first call works;** there is no grey box and `scripts/check-grey-bars.py` passes; the image matches the intent. Run the grey-bar script with the check venv at `~/image-studio/.venv-imgcheck/bin/python` — the system `python3` has no Pillow or numpy and the script exits 2 with `ERROR: Pillow and numpy required`; `references/review-loop.md` step 6 carries the one-time setup, and the script path is `~/.hermes/profiles/matejko/skills/image-studio/scripts/check-grey-bars.py`. **A rendered colour-palette strip has its own script, and the grey-bar script cannot see it** — it only looks for grey margins. **And a pale cream, near-white or tinted grey-blue fill is not grey either, so the grey-bar script passes a frame the model left half empty:** one measured render carried 49.5% of its pixels in a single `#F8FAFA` fill with a 107 px right-edge strip that was 99.8% blank, and the grey-bar check reported "content fills the entire frame". Measure the fill with `scripts/check-blank-margin.py <png>` — it reports the dominant fill's share of the frame, every run of rows or columns that is mostly that fill, the blank strip at each of the four edges, and the content bbox. A fill that covers half the frame with the drawing squeezed into the rest is an empty margin; a fill that is the wall behind a full scene is scenery, so the crop decides. **When the grey-bar script reports a band at the top and another at the bottom of similar depth, suspect a border that closes on all four sides before calling it two margins** — the painted panel is then floating inside a pale frame, the blank vertical strips are the same defect, and neither edge script names them because both scan rows only. A band at one edge is an edge; matching bands at opposite edges are a frame, so run `check-blank-margin.py`, which prints the blank strip running in from each of the four edges and the dominant fill's share, instead of hand-rolling a near-white row-and-column sweep in the scratch directory. That script already answers the four-edge question, and a hand-rolled sweep reports numbers no later run can reproduce with one command. `scripts/check-palette-strip.py` settles the edge question with numbers: flat columns against a control band, distinct hue groups in one row, and each `color_palette` entry's share of the band versus the whole frame. Run it on any render showing a hard-edged band of colour at the top or bottom edge, and use its band-versus-frame count to spot the general case too — **a uniform saturated rectangle that bleeds off an edge and whose colour appears nowhere else in the scene is a generation artifact, not a prop.** A further tell: the strip's colours usually are not in the prompt's `color_palette` at all — they are invented by the model, so a flat band whose colour matches a palette entry **and whose colour is also painted on a prop the prompt describes** is a prop, not an artifact. A band carrying exactly the entries' own hexes, with that colour appearing nowhere else in the frame, is the `color_palette` array rendered, and it counts as a defect wherever it sits — mid-frame included, as two blocks side by side in one run of rows. **The edge scripts cannot see a band that crosses the middle of the frame, so the whole-frame check is `scripts/check-flat-bands.py`:** it scans every row for the same signature the edge probe looks for — hard-edged, textureless colour blocks carrying several distinct hues — and reports the rows, the blocks, their widths and the hue groups, so a mid-frame strip is a number rather than a read. **It counts the blocks rather than the widest one**, because a strip is several blocks side by side and the widest single block is often only half the row. **A strip can sit on both edges while the script announces only one**, so read its `[TOP EDGE]` and `[BOTTOM EDGE]` blocks rather than the headline: on two back-filled renders of one post the script printed `PALETTE STRIP on the bottom edge` where the top 126 rows carried the same seven blocks at 99% of the width, and `PALETTE STRIP on the top edge` on the other where four flat blocks sat along the bottom. Run it on every render whose prompt carries a `color_palette`, and treat a band it reports as a defect to settle on a crop — a band in a region the prompt describes as a flat painted surface may be intentional, so read the crop before it goes on a card. **A thin single-hue line across the frame is invisible to every one of those probes** — `check-flat-bands.py` wants several hues in the band and `row-band.py` wants saturation, while a near-white over near-black rule is neither — so measure it with `scripts/check-flat-lines.py`, which reports each run of rows that is flat and near-uniform across most of the width, plus the same scan over columns so one drawn rule is told apart from a page frame that closes on all four sides. Hand-roll the flatness arithmetic in scratch scripts only when the band you are looking at is none of an edge band, a thin line, and a whole-frame band the shipped scripts measure. **Both edge scripts scan rows, so neither can see a vertical panel:** a flat colour band running up the left or right edge passes both of them while being just as much a pasted graphic as a bottom banner. Sweep each block colour with `crop-probe.py --find <r,g,b> --tol 40 --min-px 3000` and read the blob bounding boxes — a tall narrow blob that touches `x=0` or `x=width` and runs down a side of the frame is a side-edge panel. `references/verifying-image-details.md` carries the numbers from a header that had one on each side plus a banner along the bottom. **Neither script also sees a cluster of flat fills sitting in a corner:** `check-palette-strip.py` can print `no palette strip on either edge` while one corner holds a clutch of unoutlined colour shapes and a solid rectangle bleeds off the opposite corner, so "no strip" is not clearance — map the corner with `frame-map.py --box` and read a crop of each cluster. **And none of those three passes is clearance for a pasted overlay sitting in the middle of a painted scene.** One header came back with a flat UI banner laid over the rug across the lower third — a blue rounded container, an amber text card inside it and a pale pill button, all carrying invented pseudo-text — and `check-grey-bars.py`, `check-blank-margin.py` and `check-palette-strip.py` each reported clean on that frame; the whole-frame read found it and a crop confirmed it. Take the banner's extent from a colour sweep (`crop-probe.py --find <r,g,b> --tol 40 --min-px 3000` on its fill colour), never from `check-flat-bands.py`: on a painted scene that script's band spans the scene as well as the banner, which is the wooden-scene false positive rather than a measurement of the overlay. **A band sitting on the top or bottom edge needs no sweep at all: `check-blank-margin.py` already prints its row range, the fill's share of the frame and the blank strip at that edge, so quote those three numbers** — a 104 px band at ≥98% fill whose colour covers 17.9% of the frame is the measurement of a pasted lower-third, and the crop then says whether the band is text on a plate (overlay) or scenery. **And one post's images often share one defect family**, because the batch's prompts came from one template: three images of a single post carried a bottom UI band, a full-width colour strip and a corner cluster, and each one needed its own probe. Every PNG on the card gets its own check, and the class is named on each item rather than once for the card.

If `vision_analyze` is unavailable, a mechanical script cannot stand in for a claim about what the picture holds: go to `scripts/vread.py` first (next paragraph) and use the grey-bar and palette-strip scripts alongside it, never instead of it. Do not invent a visual read you did not make. **A single `vision_analyze` error does not prove the tool is down — but which error it is decides whether retrying is worth anything, so read the code before burning retries.** A `400` or a transient `5xx` frequently clears on a second or third call, so retry that up to 3 times. That includes the gateway's `400 ... This API supports text input only` variant: it is a transient routing hiccup on a model that does support images (the same call can succeed on the next attempt), so retry it rather than concluding the model is text-only and routing to `vread.py`. **A `429` does not:** `ip_slot_full` is an hourly cap on the shared exit IP, so every retry inside the window fails identically and each one costs a wait. Do not sit on `sleep 45` and try again — go straight to `scripts/vread.py`, which reads the same pixels through the agent's own provider, and note which reader produced the claim. Retrying a capped route is the one failure mode where the second attempt is guaranteed useless, so the retry budget is for error classes that can clear.
   - **Mechanical-only notes are the last resort, not the second: the auxiliary vision proxy is one shared channel, and a second vision model exists on the agent's own provider.** `429 ip_slot_full ... rph limit reached` from `127.0.0.1:8083` is an hourly cap on the shared exit IP and it fails every caller, a plain text prompt included, so retrying that route only burns the run. **Run `scripts/vread.py IMAGE "question" [model] [--box x0,y0,x1,y1]` instead** — same pixels, a vision-capable model on `llm.voitech.dev`, default `qwen3.8-flash`, and `--box` crops and upscales first so a claim about one small prop is not answered from a downscaled frame. Two traps: `deepseek-v4-flash-vision-exp-go` is deprecated, so a `410` naming it is a stale model id and not a broken path (read `/v1/models` and pick another vision id); and that gateway sits behind Cloudflare and answers `403` code `1010` to a bare urllib request, which is why the script sends a browser User-Agent. **Say in the check note which reader produced it** — a read is a read only if the pixels were seen, and a note that hides its reader cannot be audited. On a review card this keeps the round's read honest instead of trading it for a mechanical-only note. **When no reader answers at all, the disposition is a monitor, not a card with a caveat.** If the round's acceptance criterion is itself a visual claim — his rejection said the text was unreadable, the prop was pasted, the direction was wrong — then "mechanical checks pass" does not answer it, and a card asserting "no lettering anywhere" without a read is the exact defect he would judge from. Fetch the render, keep the issue `in_progress`, PATCH a fresh `nextCheckAt` twenty to forty minutes out, and say in a comment what was checked and what was not: the render is already paid for and a wake costs minutes, while a false clean claim costs him a rejection and a whole round. Mechanical-only notes stay for the case where the criterion itself is mechanical (margins, a strip) or the render is a draft nobody has asked a question about.
   - **Look in `scripts/` before you hand-roll an analysis.** The skill ships the probe for a class of defect, and re-implementing its arithmetic in a scratch file costs a render cycle when the script would have settled the question in seconds. Before writing any analysis code, list `scripts/` and check whether one of them already measures the thing you are about to measure — `check-grey-bars.py` for grey margins at the top and bottom, `check-blank-margin.py` for a frame that is one flat fill or carries a blank band, `check-palette-strip.py` for a rendered palette strip at an edge, `check-flat-bands.py` for a flat band anywhere in the frame, `check-defect-signature.py` for the pasted-overlay signature (saturated blue pixels, near-white flat blobs of 400 px or more, flat-and-saturated band rows) measured against a baseline frame from the same series, `crop-probe.py` for a countable claim about one prop, `crop-probe.py --find` for where a colour sits across the whole frame, `check-prop-extent.py` for whether a prop is ONE object in one place or scattered and whether it overlaps the figure, `ascii-render.py` for reading a small prop's pixels as text when a zoomed read is unstable, `check-off-scene-colour.py` for colour a frame carries off its own hue axis, `measure-bodies.py` for whether a shape is ONE object broken in two or several objects, `hindsight-memory.py` for the bank. A scratch script is the right tool only for a question the shipped scripts do not answer; say in the comment which script you used and what it reported, so the number on the card has a provenance. **A fleet of throwaway scratch probes is a smell, not a solution** — six of them written in one session to settle one small claim means the question needs a shipped probe, because the next card will ask it again and the fleet will have drifted apart. Promote the one that works into `scripts/` and drop the rest. **Promote it in the same run, not in a later one: a probe left in scratch for the rest of the card is a probe the next card cannot use, and the question it answers comes back.**
   - **A structural claim is not settled by a read, and a read asked about a mechanism will supply that mechanism.** "Is this one plank cut in two, or two boards stacked?" is a claim about the arrangement of bodies, not about what they look like, and two reads of the *same* pixels at 7x and 8x answered opposite ways — the question biases the read, because a model completes the story it was handed. Settle it with `scripts/measure-bodies.py`: it counts the separate bodies a material mask holds, reports the **interior absences** inside the largest body (no absence = one unbroken piece, however many seams a read sees), and reports whether two bodies divided by a narrow gap are **aligned** (one object broken in two) or **offset** (one lying on another). A mask that includes skin splits at the face and the hands and then reports a break in the wood, so use the `wood` preset and read the crop of the supposed gap before believing it. When the inherited note says the cut is legible and the measurement says the body is continuous, the note goes up with the measurement and names the reading that won — the card's text is frozen, and a claim the pixels contradict is the defect Wojtek judges from. `references/verifying-image-details.md` has the procedure and the two box orders (a prompt `bbox` is `[y1,x1,y2,x2]`, a script `--box` is `x0,y0,x1,y1`; both scripts print the region they used, so a transposed box is visible in the output).
   - **Measure a small detail against the series before you call it a defect.** A detail on one prop is not a defect on its own; the question is whether it is how this series draws that prop, and the way to answer is to run the same measurement on an image Wojtek has already approved from the same series, with the same script. A candidate that carried one box label with dash-lines was the *cleaner* of two renders, because the approved header of that same post carried three — the detail was series texture, and judging the candidate alone would have put a false defect on a frozen card. Run the comparison and put both numbers on the card.
   - **A zoomed read of a small prop is not stable; print the pixels.** Upscaling a 20x12 px label adds moire, so the same region reads as "blank" on one crop and "dash-lines standing for words" on the next, and two reads of the identical file disagreed outright. `scripts/ascii-render.py --mode ink` prints only the drawn strokes, which settles the claim without a model in the loop — and the output is the evidence, so a later reader can re-run the same command and get the same characters. `references/verifying-image-details.md` has the procedure.
   - **Crop to the prop the verdict hinges on, and read a crop's claims as scoped to its region.** A region-cropped `vision_analyze` answers about that region but often states a global conclusion ("there is no legible text anywhere in the image"), so a full-frame pass can miss small lettering and a crop can contradict it. When a check turns on one prop — a label, a lever, a tube — re-ask with a crop of that prop and a question that names the region, and only then record a text or prop defect. **But the `region` parameter is not a reliable cropper — it can land on different content between two calls, so the same box reads as the subject in one pass and as bare wall in the next.** Settle a small claim on a crop written to disk instead: `scripts/crop-probe.py` writes one and prints pixel counts for countable claims, so "a veil drapes the clock" is answered by a number rather than an opinion. Analyse the written file, not the region parameter, and make sure a reported defect survives the crop — the card's text is frozen when it is posted and Wojtek cannot correct it. **A number in a check note comes from the count, not from the read.** A note that says "one glare" or "two bars" is a countable claim, and a vision read of a prop undercounts it: a read of a lens said "one curved white glare" where a blob sweep found two white marks, the larger a filled shape rather than a thin streak. Count the blobs over the whole prop (`--find <colour> --min-px <small>`) and compare each blob's pixel count with the area of its own bounding box: a thin streak fills a small fraction of its box, a filled blob a large one. When the count and the read disagree, the count wins and the note is rewritten — the image did not change, the note did. **A blob is a colour region, not an object**, so a count needs a named unit before it means anything: a key's bow and shaft are two blobs of one key, a lantern's flame is a blob of the accent colour that is a light rather than a prop, and a master ring reads as a fourth key. Write the unit into the note ("three keys, each a bow plus a shaft with teeth; the extra round shape is the master ring") so the claim is checkable, and when the claim is that an accent colour sits on one prop only, sweep the whole frame for that colour and read a crop of each blob before counting it. `references/verifying-image-details.md` has the procedure. **When the picture should show one thing and a copy of itself, compare the two instances properly:** a side-by-side montage shrinks each and invites a read of the difference between the panels, and it can report one instance as a single spiral and the other as a double while separate full-scale crops of the same two regions both report a double. Crop each instance separately at the same scale, read each on its own, and zoom the discriminating feature — for a spiral, the eye at the centre, where the whole-face read wavers. `references/verifying-image-details.md` has the procedure.
   - **Intent means the story beat reads, not that the objects are all present.** If the why says a cable joins the cheap machine to the proud robot, a clean render where the cable stops at the bench fails the check, and the repair is a prompt fix (the connector becomes its own element whose `bbox` spans the **whole run** from source to target, with the target named in the same sentence as the source, per `references/engine-pitfalls.md` #30 and #38), not a shrug.
   - **A figure's relation to its prop and its target is part of the beat.** When the prompt has a figure carry, place or walk something toward a target, check the body orientation and the grip: a figure facing the camera with the prop floating on the back satisfies the inventory but not the verb, and that is a story defect, not a quirk to note. **The direction of the action is part of it too: a connected action can point the wrong way.** Every part can be present and joined — hands on a bar, bar on a dolly, wheels on a ramp — and the picture still say the opposite of its section, because the figure stands on the far side of the object from the target and hauls it out of the building while the prompt said "pushing". **Ask the spatial question, not the mood question** — which side of the object does the figure stand on, which end of the handle does his hand close on, which way does the scene's own marker point — and settle it on a crop written to disk, because a read that says "he strains at a heavy load" has settled nothing. A directional marker is countable: one arrow asked for can come back as two heads in opposite directions, which reads as no direction at all, so count the heads before the note claims one. `references/engine-pitfalls.md` #53 carries the prompt-side fix: direction is carried by spatial relations, not by the verb.
   - **Hold back only what breaks the story; put the rest on the card as a note.** A re-render costs a render slot, so reserve it for defects that make the picture say something other than its section's beat: a connector that does not reach its target, a prop the model invented, unreadable text, a missing story element. A quirk that leaves the beat intact — an extra figure, a duplicated gauge, a shape drawn slightly wrong — is not a reason to spend another 21 minutes: put the image on the card and name the quirk in its description, so Wojtek sees it and decides. Two figures where the prompt asked for one is a defect you report, not one you silently re-render.
   - **An invented detail on a character is a note; an invented emblem pasted on a wall is a defect.** The model adds character details the prompt never asked for — a chest panel, an antenna, a badge on a uniform — and because they are drawn in the figure's own volume, with its light and its perspective, they read as part of the character rather than as something laid over the picture. That is the same tell that separates a collage from a scene (#40), so it decides the call: an integrated invention is a quirk to name on the card, while a flat shape that shares neither the frame's geometry nor its light is the hard defect that costs a render.
   - **But "breaks the story" is not the only test, and the one that decides this case is the defect's class, not its size.** A pasted overlay does not break the story — the scene still reads, every prop is in place — and it is still a hard defect, because the class itself is what he rejects. **Run `scripts/verdict-class-rate.py` before you decide**: it counts the approved and the rejected verdict rows in the library whose reason mentions each defect class and prints the approval rate, so the call is a measurement rather than a judgement. A class with no approvals and several rejections is a class he rejects, and that is a re-render; a class he has approved before is open to a note. The rows are the evidence (`--rows <class>` prints them), so the number on the card has a provenance. **A brief's check note is one run's read, and it can under-call a hard defect — so the class rate settles the disagreement, not your confidence.** A brief that calls a pasted collage a "minor quirk" because the shape is small in the frame is wrong on the rule above, and so is a brief that calls a real defect hard because the frame looks busy. Both are settled the same way: crop the region to disk to see what the picture holds, and run the class rate to see what that class is worth. **A class he has never approved is a prior, not a verdict.** Run `verdict-class-rate.py` and put the rate on the card; keep the silent re-render for the frame the defect dominates — `references/verifying-image-details.md` carries the two cases. `references/engine-pitfalls.md` #59 carries the case.
   - **A re-render's check note answers his reason clause by clause, quoting it.** The reason he gave is the acceptance criterion for that render, not the prompt: "the bar on the bottom does not fit" is cleared only by a floor that is not a strip of chips, and "no green rectangle left of centre" is cleared only by the absence of that shape. Quote his words and answer each clause with what the new picture shows, and name the props that are gone and the props that replaced them — the next round's alt text has to describe the picture that ships, and it can only do that if the check note says what the new picture holds. Re-render a failing variant silently; if the re-render also fails self-check, re-render again. Say in the closing comment what you held back and why.
   - **A re-render fixes one defect and can break another, so the new render gets a fresh inventory of every prop the prompt places, not a re-check of the old defect.** The prop that was wrong last time may be right now while a different prop has come loose — a variant held back for a defect it was never asked to fix is still held back, and it cost the same render as any other. Your check filters out defects; it never approves. *Done when each image has a pass/fail note, and every held-back render has a one-line reason.*
   - **The self-check is budgeted, and the card is the deliverable: one full-frame read plus at most two disk crops of the prop the clause names settles a ship-or-hold call.** The check has no natural end — every crop raises a finer question — so a run that keeps verifying can spend its whole budget and end with no card posted, which is the one outcome worth nothing to Wojtek. Decide on the evidence you already have. **A re-render that clears every clause of his reason ships with the residual named in the item description, even when the residual is the same class he rejected** — a defect that shrinks across attempts (the neck, then the chin, then the beard tips) is progress, not a failed fix, and the card is where he decides whether the remainder matters. Hold a render back only when it fails a clause outright or carries a new hard defect. State how many renders the slot has spent when you name the residual, and give him the next composition in one line, so a rejection costs him nothing to answer.

**A misspelt or garbled label is a defect, not a quirk** — readable English is a clause of the show bar, so that picture goes back for a prompt fix instead of onto a card with a note. A prop *count* that differs from the prompt is still a note when the beat reads: the model places every described prop and may add one.

**Split invented lettering by legibility, not by whether the prompt asked for it.** Pseudo-text — strings that differ between two reads, or that no reader can resolve — is the `unreadable-text` class and stays a hard defect. A word that reads the same way twice and is spelled right, painted where a marking belongs on that prop (a name across a gauge face, a scale number under a tick), is an invented detail: name it on the card as a quirk with the spelling quoted, next to the class rate for the unreadable ones, and let him decide. Calling every invented word unreadable flattens the one case he can actually judge from the card.

**Judge a flat shape by whether the prompt asked for it, not by its flatness.** A sticker, plate or badge the prompt named is a prop the model placed as asked: note it in the same breath if it floats and leave it out of the defect that decides the card. What breaks the frame is the flat shape nobody asked for — a pill, tag or banner carrying invented pseudo-text, crisp uniform edges and no relation to the room's perspective. Name the invented ones as the hard defect with their class rate; that is what holds the picture off a card and sends its slot to a repair.

## Provenance defects (review-card scope)

On a backlog-review card, some defects are **not image defects** and cannot be fixed by editing the render or the post. These are **provenance defects**:

* The `## Why` in an inline library record quotes the paragraph *after* the section the image sits under, or quotes a different section entirely, or quotes only the Just-the-Docs marker under the image (`{: .prompt-tip }`, `{: .prompt-info }`) — a marker is not prose and tells the reader nothing about why the picture is there. The PNG may be correct for its actual section, but the `## Why` is stale/provenance. **Do not edit the record's `## Why` or the post** — the review-card scope is the image, and the runner's rule allows post edits only for an approved re-render's embed. Record the mismatch with `backlog.py note <n> "<what disagrees, and that the PNGs were judged against the records' Prompt>"` so the runner's table carries it.

* The draft's alt text describes a prop that is not in the PNG (e.g. "the giant plug and phoenix bird" when the PNG shows a stopwatch drill). This is a post-prose defect, not an image defect. **Report it on the card**, note it in the queue with `backlog.py note`, and name it in the closing comment as an open question. Do not edit the post or the record's `## Why` on the card.

* The image clearly illustrates the *next* section rather than the one it is embedded under. The picture is not wrong and the slot is not broken — say plainly which section the image really serves and leave the embed where it is. Record it with `backlog.py note` so the runner's table carries it.

* **A pasted UI banner across the bottom of the image is a collage/overlay defect.** The model may generate a flat banner with text (e.g. "Wojtek", "offlinested gym tracker", "passkeys") that reads as a pasted overlay rather than part of the scene. This is a hard defect that costs a re-render, not a provenance defect. The fix is to remove the banner entirely from the prompt and re-render. **A typo in the banner text (e.g. "offlinosted" instead of "selfhosted") is also a defect that costs a re-render.**

* **On a round-1 review card the re-render is yours to spend, because he retired the show-it-anyway rule.** A picture that fails the show bar is not shown at all: rewrite the prompt, submit the Ideogram + FLUX pair, and let the card carry the renders that pass. Round 1 still renders nothing when the draft's images already pass.

* **A prop that looks coherent can still be a model artifact** — judge every prop by what it means to a reader and by whether the model knew what it was drawing, not by whether it looks tidy: a grid of aligned tiles with no axes or legend is a pseudo-chart, a flat rectangle with a drop shadow and no perspective is a pasted overlay, and dash lines standing in for words are pseudo-text. **A region of the frame drawn in a different idiom from the rest of it is a collage, and that is a whole-picture defect, not a detail.** Look for a panel whose art style does not match the frame, whose rim and drop shadow give it its own edge, and whose interior geometry does not continue the room it sits in — a picture pasted over a picture. Wojtek rejects the whole image for this and calls it a matter of the image's concept, so a self-check that only inspects each prop in isolation will miss it. Check the frame as one scene: every region either shares the frame's style and space, or it is a defect. **Locate the seam before you crop it, so the crop is aimed rather than guessed:** sample the frame's mean colour in horizontal bands down the height at a few fixed column positions, and a collage shows one hue axis above the seam and a different one below. A figure that carries a pale sticker outline crossing that seam settles it — a drawn figure takes the light and edges of the room it stands in, and a cut-out keeps its own rim over both spaces. Crop the seam at 1.5x and the figure at 2x and put both reads on the card, because "a collage" is the whole-picture defect he rejects as a matter of concept while "two colours in one room" is only a palette note.

When judging whether a defect is an image defect or a provenance defect, judge the PNG against the record's `## Prompt`, not against the `## Why`. When they disagree, the stale `## Why` and alt text are a post-prose defect, not an image defect. Say so plainly on the card and in a comment, and do not edit the post to fix it — the card's scope is the image, and the runner's rule allows post edits only for an approved re-render's embed.

Show the batch to Wojtek.** Upload the passing PNGs as issue attachments — **on a resumed run, list the issue's attachments first (`GET /api/issues/<id>/attachments`) and reuse the id already there for the same file** — but only when that attachment already has a non-null `issueCommentId`. **The binding is run-scoped: a comment can only carry an `attachmentId` that the *same run* uploaded.** A later run that posts a comment naming an earlier run's attachment answers `422 issue_attachment_run_origin_mismatch`, and the uploading run has finished, so that attachment can never be linked at all — it sits on the card with a null `issueCommentId` forever. When the only attachment is in that state, upload the file again in the current run and bind *that* id; the duplicate is not a problem, an invisible PNG is. A card whose item points at an unlinked attachment shows Wojtek an empty row.    - **Build the payload with `scripts/build-verdict-card.py` from a spec in the shape of `templates/verdict-card-spec.json`**, not by hand. The script bakes in the safe defaults, asserts the 500-character cap per item, **and that cap is hit by most cards on the first pass — so compose the descriptions inside your spec-building script and have it print each `len()` before you call the builder.** The count is of every character including em dashes and quoted pseudo-text, several items land 30-80 over, and the tail to trim is the caveat clause rather than the check note, because the check note carries the measurements the verdict rests on. The pending card is the review path on its own. **Post the attachment-linking comment after the PATCH**: the `comment` field of the PATCH carries no `attachmentIds`, so a comment is the only call that links the PNGs into the thread, and without it the images sit attached but invisible on the card. **That comment must carry `attachmentIds: [...]` in its POST body** — a body-only comment leaves `issueCommentId` null and the PNGs invisible; verify with `GET /api/issues/<id>/attachments` that every attachment now has a non-null `issueCommentId`, and re-post if any is still null. *Done when the card is `pending`, the issue is `in_review`, and the attachments read back with a non-null `issueCommentId`.
   - **A card that expires on a comment before any verdict was given is reissued, and the reissue turns the flag off.** The script bakes `supersedeOnUserComment: true`, which is right when a comment carries the decision — but a user comment that is not a decision ("you look blocked, unblock yourself") expires the only review path with every item unresolved, and the round then has a card that is `expired`, no verdict, and no wake. The card's `detailsMarkdown` names the expired card id, because the reader of the card alone cannot see the thread. Verify the reissue reads back with `pending` plus `supersedeOnUserComment: false`, and that the old card reads `expired`, so exactly one card is live.*
   - **One card carries the whole round, so a slot you held back goes back on that same card.** When your own check holds a render back before the card is posted, re-render it and ship the new attempt as that slot's item on the same card — the card's item id stays the brief's id, the attempt suffix rides the render name and the prompt file (`--name <item id>-r2b`), and the item's description says which attempt ships and why the earlier one was held back.    - **Read the card back and confirm a human decided it.** `result.items[].resolvedByUserId` must be set and `resolvedByAgentId` must be null. An agent-resolved verdict breaks the one rule this skill exists to keep, so a card that shows otherwise is a card to withdraw and re-open, not to act on.
   - **The verdict can land inside your own run, while you are still closing out.** A card goes up, Wojtek answers it minutes later, and the interaction you read back at the end of your own bookkeeping is already `answered`. Nothing will wake you for it: the wake belongs to the answer, and the answer is already here. **Re-read the interaction's status before you end a run that is waiting on a verdict** — a `pending` card means a wake is coming and the run ends, an `answered` card means the bookkeeping is yours to finish now. Applying the verdict in the same run that posted the card is the normal path, not a shortcut.
   - `hindsight_retain` the verdict, the reason, the post, and the prompt traits that mattered, with tags `taste` and `verdict`. The call answers `Memory queued for storage`: that is the receipt, the memory is not indexed yet, so a recall right after it may not find it — do not re-retain it. When `hindsight_recall` times out on the same query, fall back to the library records rather than blocking the card, and use `scripts/hindsight-memory.py` when a deliverable needs the memory's id. `references/taste-memory.md` has the routes and the rules.
   - **Separate his words from your conclusion in every retained note.** Quote what he said, and label any rule you generalised from it as yours — write "Matejko's hypothesis", never "Wojtek's rule". A generalisation is a hypothesis until he states it, and recall returns the text verbatim: a note that credits him with a rule he never uttered comes back as his standing preference and drives the next prompt, with the misattribution invisible in the note itself. This is the one mistake that survives every later check, because the note still reads as a fact about his taste.
   - **A prompt-side fix that appears to contradict his stated rule is the case where the misattribution does real damage.** When his rule is "text placed in a picture must be given explicitly" and the prompt that worked asked for *no* text at all and let the model write only the one inscription the scene needed, the two readings are not the same reading, and only one of them is his: the rule still stands, and the prompt that satisfies it is the narrow one — the characters you do want are given exactly, and the surfaces that had lettering and did not need it are taken away. Never record the prompt shape as his preference. Record it as what it is: an observation about the model, held as a hypothesis until he says otherwise, and never as a correction of his rule.
   - **A silent approval settles nothing about the rule that produced it.** When a card comes back approved with no reason, the approval clears that image and says nothing about the prompt shape that made it — he did not endorse the method, he endorsed the picture. A retained note about an approval must say the reason was not given, and must not let the prompt shape it describes read as the thing he approved. The same limit applies to a fix: a prompt that worked on one slot is one comparison inside one slot, and a hypothesis is what a generalisation from it is until he states it.
   - **Approve:** on a new render, copy the PNG into `~/wojtek.second.brain.obsidian.vault/tech_blog/assets/<YYYY-MM-DD>/<label>.png` and write the library record (`references/library-records.md`). **On a backlog-review card, which bookkeeping applies depends on the round.** A round-1 approval of an image already embedded is the back-fill case: the file is **already where the draft points**, so touch only that record — `verdict`, one Verdicts row, drop the back-fill line — and copy nothing, write no second record and edit no post. **A round-2 or later approval of a re-render is the opposite case: the draft still points at the old asset, so the vault copy, the embed edit and the record chain are all still yours to do** — copy the staging PNG to `tech_blog/assets/<date>/<card item id>.png`, repoint that one embed, rewrite its alt text to describe the picture now in the file, write the new record, and set `superseded_by` across every earlier record of the slot. The brief's bookkeeping block names the exact paths; follow it rather than the round-1 habit. `scripts/approve_record.py <record.md> --approved --issue <GUL-x>` (or `--rejected --reason "..."`) applies those edits in one verified pass; use it for every verdict, approval and rejection alike, rather than hand-editing the same three spots across many records. **Pass `--round <k>` for the round the verdict belongs to** — the script defaults to 1, and a round-2 row numbered 1 makes the slot's history read as two verdicts for the same round.
   - **Reject:** mark the record rejected with his reason verbatim, revise the prompt from the reason and start the next round at step 3. When the re-render carries the same defect, read `references/re-render-defect-persistence.md` first: it lists the prompt-side remedies (explicit bans, concrete replacements, removal) and the escalation rule after 3 rounds. **A defect that survives two silent re-renders is a concept problem, not a phrasing problem — so escalate it to the post's author rather than spending a third render.** Create a child issue of the card assigned to the post's author, ask for the picture's idea *and* its composition (camera, crop, what fills each corner), and set the card's `blockedByIssueIds` to that issue so the card wakes when the answer lands. **A verdict that names the concept is the escalation order and does not wait for round 3** — a reason that says the image must be completely new, that the picture has no sense, or that it must be checked with the post's author has already settled the question, and a render spent on it is 21 minutes on a concept the verdict overruled. **The mirror case is a reason that praises the picture and names one defect class** — "the image is amazing, but the text is bullshit" is a targeted fix, not a rebuild: keep the composition and the props he liked, change only the surface that caused the defect, and treat an offer to consult the post's author as conditional ("if you need more context"), not as the escalation order. A lettering complaint is answered by removing the lettered prop or giving the exact string, never by a new concept. **An author can answer inside the same run, so read the hand-off issue back before you end the run**: an already-`done` hand-off means the resolution wake has already fired and the card will never be woken by it, so take the answer and submit the render in the same run. `references/re-render-defect-persistence.md` has the hand-off shape. **A text defect is fixed by removing the text-inviting props, never by naming the banned shape in the negative clause** — a clause that says \"no UI panels\" is a concrete instruction, and a concrete instruction is what the model draws, so the ban can make the picture worse rather than better (#62, #63). **A reason that names a picture-level concept is a rebuild of the composition, not a patch to one prop** — "does not fit into concept of image" means the picture failed as a scene, so the re-render must make the whole frame one scene: drop whatever needed the second space, fill the vacated region with described diegetic content, and add the negative clause naming the shape you are banning. **A reason that says the image "does not tell any story" means the prompt was an inventory** — every prop was placed and nothing happened, so the re-render collapses the element list to one action by one figure on one prop rather than redescribing any of the props it already had (`references/engine-pitfalls.md` #47, #48). **A reason that names a defect the model half-invented means the prop was under-specified** — the shape came from the model filling a gap, so the fix is to give the prop something concrete to be or to remove it, and a negative naming the shape does not clear it (#43). Leave `superseded_by: null` on the rejected record until a replacement is actually approved — the field points at the job that replaced the image, so setting it to a render that was never accepted makes the slot history point at a dead end. When the replacement is approved, set `superseded_by` to that approved job id in **every** earlier record of the slot, the back-filled one included, in one pass — the pointer names the accepted image, not the next render in line, so a render that was briefly replaced by another *rejected* render still ends up pointing at the approved job. **And when he is explicitly waiting on a slot, the ship-with-caveat path above outranks this hand-off**: a card with the residual named is something he can judge in seconds, while a blocker on an author's answer parks the slot and puts nothing in front of him — escalate to the author only when the concept itself is in doubt, not when the composition merely needs one more idea.
   - **A defect class you already know is likely gets its corrected prompt written in the same pass.** A known trigger — a `color_palette` array that renders as a swatch strip, a prop that invites pseudo-text, a mechanism the model improvises — has a fixed remedy, so write the remedy's prompt file next to the one you submit: it costs one file write instead of a 21-minute render plus a whole round. **It is not a held-back attempt**, because it has no job id and nothing was rendered from it — name it as the file to submit on that outcome, in a file of its own, and keep the submitted prompt's name for the render that was actually queued.
   - **Defer:** leave the item.
   - Run at most 3 rounds per request. After round 3 with a slot still unapproved, ask Wojtek on the issue what to change instead of rendering again.
   - **A check note that turns out wrong is withdrawn and re-posted, not left on a frozen card.** The card's `items[].description` and `detailsMarkdown` cannot be edited after the POST, so a note you later disprove is a defect Wojtek would judge from. Withdraw the card (`POST /api/issues/<id>/interactions/<id>/withdraw` with a reason naming what changed), which settles it as `cancelled`, then post the corrected card under a new idempotency key (`verdicts:<issueId>:round-<k>-corrected`) — build it with `scripts/build-verdict-card.py` from `templates/verdict-card-spec-corrected.json`, whose `idempotency_key` field carries the key the default spec shape cannot express. The cancelled card is not a pending card, so exactly one card stays open for the round — verify with `GET /interactions` that one is `pending` and the other `cancelled`. **The corrected card says on its own face that it replaces the withdrawn one**, naming the old card's id and what changed in its `detailsMarkdown`, because the reader of the card alone cannot see the thread. Say plainly in an issue comment what was wrong and what the correction is, because the withdrawn card's wording is still in the thread. The one-card-at-a-time rule counts *pending* cards, not cards you have already retracted.
   - **On a comment wake, read the comment.** A user comment while the card is pending supersedes the rest of the card (`superseded_by_comment`); when that happens, open the next round's card with a new idempotency key, carrying the remaining items and revised by the comment.
   *Done when every newly resolved item is retained and handled.*

9. **Close** when every requested slot has an approved image. The closing comment is the audit trail, so it carries: the job id of every render per round, the vault asset path, every library record path, the self-check note for each image (held-back renders included, with the reason), any `skill_manage` patch you made, **the next round's card issue by identifier, and every question you left open for Wojtek** — a stale post alt text, a missing render, a slot still unapproved. A question named in the closing comment is one he can answer without re-reading the thread, and the thread is where he looks last. Then set the issue to `done`. **On a backlog-review card, say plainly that nothing was rendered this round** and that no job id or vault copy belongs to it, so a reader checking the audit trail does not mistake an absent job id for a lost render. *Done when the issue is `done` and the comment carries every job id, asset path, record path and self-check note.*

## The show bar (always on)

Only an image that passes all four clauses reaches a review card: **figures correct** (two hands, two arms, one head, one person unless the prompt says otherwise), **no colourful artifacts** (no pasted panel, badge, sticker, banner or swatch strip, nothing in another idiom from the frame, no photograph with vector graphics laid over it), **text only if readable English** (`Racoiving`, `HelmRelest`, `H16` are defects; no lettering at all is fine), **the beat reads**. A failure is not shown — the prompt gets rewritten and the slot re-rendered as an `ideogram4` + `flux2-klein` pair on one card. Full bar, prompt-repair recipe, batching and the library-wide sweep: `references/bulk-library-triage.md`.

## Rules

- **Let only Wojtek's verdict on the card approve an image.** He owns the taste; your self-check exists to remove defects, not to bless a render.

- **A check whose pass condition only vision can see does not downgrade to a mechanical one.** When the render answers a reason that named lettering — text, spelling, pseudo-text — the grey-bar and palette scripts cannot clear it, because they cannot see a word, and a note reading "mechanical checks pass" asserts the very thing that failed. Re-read the file when a read is available (a rate-limit window clears within the hour, which is what a scheduled monitor wake is for) and post the card then. Keep the mechanical-only gap note for checks about margins, framing and composition.

- **When a backlog-review round 1 card rejects all images and re-renders are submitted for round 2:** the monitor wake (not a subsequent card run) handles the round transition. `card-done <n> --rendering` advances the queue slot and sets the post to `rendering`, but the actual round close (closing comment stating plainly that nothing was rendered this round, no job id or vault copy belonging to the card) and round-2 card creation happen at the monitor wake. Do not call `card-done <n>` on the round-1 card intending to close the round — doing so releases the slot prematurely and stalls the queue. Keep the issue `in_progress` under the monitor, and let the monitor wake fetch the re-renders, write the handoff brief, create the round-2 card from the ready queue, and close the round-1 issue.

- **When an issue is stuck `in_progress` with a render in flight and no live monitor, the repair is a monitor — not `blocked`.** A monitor only fires on an issue that is assigned to an agent with no user assignee and sits in `in_progress` or `in_review`, so moving the issue to `blocked` disables the very wake the card is waiting for. PATCH `executionPolicy.monitor.nextCheckAt` at the job's ETA plus five minutes, confirm `monitorNextCheckAt` reads back non-null, and keep the issue `in_progress`. Reserve `blocked` for a genuine external blocker — a missing permission, another issue's answer, a human decision — because an issue parked `in_progress` with no monitor, no pending interaction and no blocker is exactly what the board re-opens as a disposition-repair action on the assignee, and that repair costs a whole run. `references/disposition-repair.md` has the causes and the dispositions the board accepts.

- **A monitor that reads null after the PATCH is a monitor that does not exist.** In this session, the issue was left `in_review` with a comment saying "Monitor wake scheduled" while `monitorNextCheckAt` was null. The card had no wake path, and the renders sat finished on the Max for hours. The PM had to intervene. Always verify `monitorNextCheckAt` is non-null in the PATCH response before ending the run, and never write "monitor scheduled" in a comment unless the read-back confirms it.

- **A sibling run of yours can be working the same backlog at the same time.** The harness starts a run per card, so one agent holds several live runs at once, and a run on the runner issue and a run on a card issue can both be mid-flight over the same vault files and the same queue. Read `GET /api/issues/<id>` for `checkoutRunId` and `executionRunId`, and `GET /api/agents/me/inbox-lite` for the `activeRun` on every sibling issue before you re-do work: a run whose `execution.phase` is `reconnecting` is still live, and a sibling that already applied a verdict leaves the durable artifacts done and your step redundant. **A refused file write is the signal, not an obstacle** — a refusal comes in two flavours and they need opposite responses. One that names a run and an issue means a sibling changed the file after your last read: re-read the file and that issue, then find the residual gap (a wrong field, a missing record, a deliverable nobody created) instead of repeating the finished work. One that says the file exists but this task has not seen its full current content means no sibling is involved — your own earlier run on the same card wrote the file and this run has not read it: read the file (every page, when it paginates), then write it. Do not read that one as a sibling and do not skip the write, because the file on disk is your own earlier draft and the next step depends on it.
- **A card issue the harness has claimed is already being worked — by its own run, but the claim is asynchronous.** A freshly created backlog-review card is checked out for a separate run, which uploads the PNGs and opens the verdict card; do not do that work from another run or a subagent, because the upload answers `Issue run ownership conflict`. But the claim lands *after* the create, not with it: right after the POST the issue still carries a null `checkoutRunId` and a null `executionRunId`, and in that window your own upload succeeds. **So try the upload and read the response rather than assuming it will be refused** — a `201` whose `sha256` and `byteSize` match the staging file is a landed attachment, and you link it with a comment carrying its id, because an attachment with a null `issueCommentId` sits invisible in the thread. Only a refusal means the card is claimed; then leave it alone and carry the file in the brief. Read `checkoutRunId` and `executionRunId` on the issue before touching it, and leave it alone when they name a run that is not yours. **The same window takes the verdict card, and taking it is usually the better call when the round is finished:** a card opened by the run that already holds the render, the check note and the record paths reaches Wojtek immediately instead of waiting for a harness claim that may be hours away, and it costs no extra step because the round was ready. The `idempotencyKey` is what makes this safe — a claimed run that later posts the same `verdicts:<issueId>:round-<k>` key cannot produce a second card, so the risk is a duplicate attempt, not a duplicate card. **If you do it, leave a comment on that issue saying the card already exists, is `pending`, and must not be reopened**, because the run that picks the issue up next sees a normal unstarted card and nothing else tells it otherwise.
- **A closing run hands over the round, it does not stage it, so the brief has to carry what the next run cannot get from you.** The card that closes a round and the card that opens the next one are different issues, and the new one belongs to its own run the moment it exists: on it, the attachment upload, the description PATCH and the comment DELETE all answer `Issue run ownership conflict`, while a plain comment still posts. So the hand-off travels in the brief — the absolute staging path, the byte size and the sha256 of every PNG, because the next run has to find the file and verify the bytes itself — and the brief must not claim the files are attached to the card the brief is about to become, since that claim is false the moment the create lands and the description is frozen from then on. Say plainly in a comment on the new card which files it must upload. **A brief is the next card's description, so write it as the next run's instruction, not as a note about yours.** `references/backlog-review.md` has the order and the closeout checklist.
- **Do not probe a route with a write you cannot take back.** On an issue another run holds, a comment is the one write that still succeeds, and it cannot be deleted afterwards — so a throwaway probe comment is permanent litter on a thread Wojtek reads. Probe with a read, and if a probe comment is already out there, say what it is in the next comment rather than leaving it unexplained.
- **A document PUT needs the issue checked out by your run, and the `409` that says so is not always transient.** Refreshing the runner's `queue` document from a run that does not hold the runner answers `409` and the write does not land. Checkout the issue first — `POST /api/issues/{id}/checkout` with `{"agentId": ..., "expectedStatuses": [...]}` — then PUT. The shape is in `references/paperclip-api.md`. A sibling run working another card often holds the runner's checkout and releases it when that run ends, so retry the checkout rather than abandoning the refresh; the `409` body names the `checkoutRunId` holding it. **But bound the retry: the issue read can show `checkoutRunId: null` and still refuse the checkout, and a holder that produces no events on the issue's activity feed may never release during your run.** After a couple of attempts, take the fallback — post the content the document needs as a comment on the runner — and say on the runner that the document is behind live state and which run holds it. **The document is a derived view of the queue's live state, so a card closes correctly without it: never hold a finished card open waiting for a refresh you do not control.**
- **Wojtek can ask for more than one card in flight, and that is his call to make.** The queue's one-card-at-a-time rule keeps the board readable by default; when he asks for a batch, open exactly the number he names and do not widen it on your own — he has asked for five to ten and, later, for 25 in a single run, so the size is his to set and a request of that shape is an instruction, not a question. Run `backlog.py batch-open <count>`, POST one issue per entry with `jq --rawfile`, record each with `batch-opened <n> <identifier>`, then **GET every issue and `cmp` its `jq -j '.description'` against its brief** — a truncated description silently changes what that card reviews, and a 25-card batch is not the place to sample. A card run does not hold the runner's checkout, so report the batch in a comment on the runner instead of PUTting its `queue` document. `references/backlog-review.md` has the batch commands.
- **Act in Paperclip as yourself with `PAPERCLIP_API_KEY` from `~/.hermes/profiles/matejko/.env`.** Load the whole file in the shell that makes the calls — `set -a; . <file>; set +a` — rather than extracting the single line with `grep … | cut -d= -f2-`: an extraction that yields an empty or truncated value makes `curl` return an error body, and the failure surfaces as a JSON decode error on the response, which reads like a broken API rather than a missing key. Proof of load costs nothing and prints no secret: `echo ${#PAPERCLIP_API_KEY}` must be a non-zero length. That keeps every card and comment attributed to Matejko; `~/.paperclip/auth.json` is the board's token and stays closed. **Put that shell prologue in a `.sh` file written with `write_file` and run it as its own `terminal` call, or make each mutating call its own plain one-liner.** A single `terminal` invocation that chains `set -a; . .env; set +a`, a `for` loop over several attachments and an inline `shasum`/`python3 -c` stalls on an approval prompt for a minute and returns `BLOCKED` with nothing executed — the command never runs, and retrying it the same way stalls again. Two shapes do run on an unattended surface: one file per call (a plain `curl … -F "file=@<one path>"` line, one per upload, each read back for its `sha256` and `byteSize`), and a whole batch inside a written script run as `bash <path>` or `python3 <path>`. Build the loop into the file, never into the invocation line: **Export `PAPERCLIP_RUN_ID` from the wake payload in the same command** — it is not in the shell environment, and every mutating call, attachment uploads included, answers `401 Agent run id required` without the `X-Paperclip-Run-Id` header, which reads like a credential problem rather than a missing header.
- **The vault lives at `~/wojtek.second.brain.obsidian.vault` (the agent's home).** Do not substitute `OBSIDIAN_VAULT_PATH` from the florian profile, which still points at the old M1 Max path `/Users/wojciechgula/...` and does not exist on this host; every path the briefs and records use is relative to that root.
- **Never search from `/` (e.g. `find / -name ...`):** it crawls the whole disk and hangs for an hour. Search within the vault or `~/image-studio` only; the file you want is always under one of those two roots.
- **Keep drafts in staging and let only approved images into the vault.** The published library then contains only work Wojtek has approved.
- **Report any `skill_manage` patch to this skill in the issue comment.** It keeps the procedure reviewable by the person who owns it.
- **On a repair or resumed wake, lead with the work and keep the repair out of the thread.** A run that woke to fix an earlier failure (a recovery wake, a disposition repair, a resumed card) says what it did and what is now true, with the cause in at most one short sentence. A run-by-run account of what a dead run did, or a mid-run "state confirmed, now I will…" narration, is not progress and it is permanent — comments cannot be deleted and Wojtek reads the thread last. Put the findings in the deliverable (the card's `detailsMarkdown`, the record, the closing comment) and leave the thread carrying the outcome and the open questions.
- **Use `imagegen` for every render.** It is the one supported path from the Air to the M1 Max worker, with a single queue and ETA the board can monitor.
- **Never restart Paperclip or the Hermes gateway to clear a blocker.** Diagnose it from the server log, state what you ruled out, and open a `request_confirmation` for the board owner instead (`references/paperclip-api.md` carries the recipe and the storage-relay fix). Withdraw it (`POST …/interactions/<id>/withdraw` with a reason) once it is moot.
- **Attachment-linking comments must carry `attachmentIds` in the POST body.** Build the body as a file and let python encode it — `write_file` the markdown, then `json.dump({"body": open(path).read(), "attachmentIds": [...]}, ...)`. A heredoc nested inside `$( … )` breaks on the first apostrophe in the prose (`unexpected EOF while looking for matching`) and the comment never posts, so the linking step fails for a reason that has nothing to do with the API. A comment without `attachmentIds` leaves `issueCommentId` null and the PNGs invisible in the thread. After posting, verify with `GET /api/issues/<id>/attachments` that every attachment has a non-null `issueCommentId`; re-post the comment if any attachment still has null `issueCommentId`. **The POST response's own `attachmentIds` field may read null even when the linking succeeded and the GET shows a non-null `issueCommentId` — trust the GET, not that field, and do not re-post on a null response field alone.**

- `scripts/check-palette-strip.py` — detects a rendered `color_palette` swatch bar along the top or bottom edge by flatness and hue spread, and compares each palette colour's share of the band against the whole frame; run it on any render with a hard-edged band of colour at an edge, because the grey-bar script only looks for grey margins and a palette strip is invisible to it.
- `scripts/check-flat-bands.py` — scans every row of a render for a band of hard-edged, textureless colour blocks and reports the rows, the blocks, their widths and the hue groups; run it on every render whose prompt carries a `color_palette`, because the grey-bar and palette-strip scripts look only at the top and bottom edges and a strip crossing the middle of the frame passes both of them. It counts the blocks rather than the widest one, since a strip is several blocks side by side. **It is a detector, not a judge: on a hand-painted cel-shaded scene it fires on pictures Wojtek approved, so its exit code is never a verdict on its own — read the crop (engine-pitfall #66).**
- `scripts/row-band.py` — measures every row of a frame for a horizontal swatch band (rows that are both flat and saturated) and prints the wide colour blocks of the longest such run; use it when a band can cross the middle of the frame where the edge-only palette-strip script cannot see it.
- `scripts/check-flat-lines.py` — scans rows **and** columns for runs that are both flat (low luminance std) and near-uniform across most of the width, and prints each line's span, thickness, fill colour, coverage and std range; use it for a thin single-hue rule across the frame, which neither the flat-band nor the row-band probe can see because one wants several hues and the other wants saturation. Its column scan is what tells a single drawn rule (`no flat columns`) from a page frame that closes on all four sides, and a `no flat columns` verdict is the reason not to report a two-panel split.
- `scripts/check-defect-signature.py` — measures the signature of a pasted-overlay defect (saturated blue pixels, near-white flat blobs of 400 px or more, flat-and-saturated band rows) on a candidate **and** on baseline frames you pass in; use it to decide a clean render from a defective one, because the signature is only meaningful against a picture from the same series Wojtek already approved. The check venv has no scipy, so the blob labelling is a union-find in the script (engine-pitfall #66). **Its blue count is a signature, not a location.** A series lit cool on purpose reads tens of thousands of blue pixels on a clean frame — a night window and two screen glows are enough — so the blue blobs point at the scenery while the pasted cluster sits in the opposite corner. Run the script for the number against the approved sibling, then find the cluster with `crop-probe.py --find` on the fill colour of its own buttons or cards and crop that bbox: the button-colour blobs are the region the note names.
- `references/verifying-image-details.md` — how to settle a small self-check claim before it goes on a card: locate the subject by pixel signature, crop it to disk, count what is countable, and withdraw-and-re-post a card whose note turns out wrong.
- `scripts/check-prop-extent.py` — given a prop's colour (and optionally the figure's), reports the prop's x/y span as a fraction of the frame, its orientation (taller-than-wide reads as a post, wider-than-tall as a bar or banner), how many bands its pixels occupy, and **how many rows carry both the prop and the figure** — the number that settles "the prop is all over the place" and "the prop runs across his neck", because a prop sharing rows with a body is drawn across that body. A zero count means raise `--tol` (painted props are textured), not that the prop is absent; a span near the full frame means the mask is too loose or the model scattered the prop. Run it before hand-rolling a colour mask in scratch.
- `scripts/crop-probe.py` — writes an upscaled crop of a pixel region to disk and prints pixel counts for countable claims (colour overlap, blob bounding boxes); use it to settle a small self-check claim before it goes on a card, because a `vision_analyze` region crop is not a measurement. `--box` is `x0,y0,x1,y1` and the script prints the region it actually cropped, so a transposed box is visible in the output. **`--out <path>` together with `--scale <n>` is what writes the file: a bare `--box` run prints the region header and its counts and leaves nothing on disk, so a check whose note says "the crop decides" must pass both flags or the region it was meant to read does not exist.**
- `scripts/measure-bodies.py` — counts the separate bodies a material mask holds, reports the interior absences inside the largest one (continuity) and whether two bodies separated by a narrow gap are aligned (one object broken in two) or offset (a stack); use it for every **structural** claim, because no vision read settles one. `--box` is `x0,y0,x1,y1`, and the `wood` preset excludes skin so a face or a hand does not read as a break in the wood.
- `scripts/check-bboxes.py` — prints every element's bbox as "y a-b (h), x c-d (w)" and flags the boxes whose geometry contradicts the spatial words in their own `desc`; run it on every prompt before the submit, because `lint` only requires four numbers and a transposed box is a layout instruction the model follows over the prose.
- `scripts/ascii-render.py` — prints a pixel region as text (`--mode shade` for the whole region, `--mode ink` for the drawn strokes alone); use it as the tie-breaker when a zoomed read of a small prop is unstable, because a label read at 12x and at 16x on the same file can disagree, and the printed characters are the evidence.
- `scripts/vread.py` — reads an image, or a `--box` crop of one, with a vision model on the agent's own provider; use it when `vision_analyze` answers `429 ip_slot_full` from the shared auxiliary proxy, so the round keeps a real read instead of a mechanical-only note. Name the reader in the check note.
- `scripts/frame-map.py` — prints a render's layout as a coarse colour map of text, one letter per cell (`G` green, `B` blue, `#` near-black, `+` dark grey, `.` near-white, `-` mid tone), with `--cell` and `--box`. Use it as the **locator before a crop** when a prop's coordinates are unknown — `--box` on the quadrant with a small `--cell`, because a screen or a pale panel shows as a run of `.` cells — and as the fallback when the vision tool is rate-limited and a check note still has to say what the frame holds and where a flat block sits. **A negative read from a crop aimed by guesswork is not clearance**: a box that missed the prop answers "there is no text there", which reads exactly like a clean result, so locate the prop first and only then let the absence into a note. It is a layout view, not a defect judge — a flat fill is normal in cel-shaded art, so settle a prop with `crop-probe.py` and a band with `check-flat-bands.py`.
- `scripts/check-off-scene-colour.py` — measures, per image, the vivid pixels whose hue falls outside the scene's own axis, with the largest contiguous off-scene region and the busiest 32x32 cell; use it to answer a "colorful artifacts" rejection clause numerically, always by comparing the candidate against the rejected original and an approved sibling image of the same series. **It is also the probe for a flat colour panel down a side edge**, which the three edge/band scripts cannot see because they scan rows: a single contiguous off-scene blob whose bbox touches x=0 or x=width and runs most of the frame's height is that panel, and `frame-map.py` shows the same shape as a column of hue letters (G/Y/R/B) down one edge. Quote the blob's bbox, its pixel count and its share of the frame on the card.
- `scripts/build-verdict-card.py` — builds a `request_item_verdicts` payload from a spec file with the safe defaults baked in (`human_only`, `wake_assignee`, `allowBulkApprove`, `supersedeOnUserComment` inside `payload`, where the server actually reads it) and asserts the 500-character cap per item; use it on every card so a hand-written payload cannot lose `resolverPolicy` or fail the whole POST on one long description. See `templates/verdict-card-spec.json`, and `templates/verdict-card-spec-corrected.json` for a card that replaces a withdrawn one (it carries the `idempotency_key` field the default shape cannot express).
