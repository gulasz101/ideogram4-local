# image-studio

Matejko's whole procedure for turning a Paperclip image request into an Ideogram 4 render, putting it in front of Wojtek, and learning from his verdicts. The generation stack runs on the M1 Max; `imagegen` submits and fetches from the Air.

## When to use

Use this skill on any of these branches:

- An issue asks for an image (a header, illustration, or diagram for a post).
- An issue monitor wakes you on a render (`monitorNextCheckAt` has arrived).
- An item-verdict wake arrives with a non-empty `newlyResolvedItemIds`.
- The issue is a backlog-review card or the runner behind it (`Backlog review <nnn>/<total>`) — review of images already embedded in unpublished drafts, no rendering in round 1. Follow `references/backlog-review.md`.
- Wojtek asks where the backlog review stands, or where the remaining posts are. The answer is the runner's `queue` document, rebuilt from live state with `scripts/build-queue-doc.py` — not a list in a comment. See `references/backlog-review.md`.
- Wojtek asks about an image's prompt, history, or why it looks the way it does.

## Choosing the engine

Two engines share the one queue and the one worker; the default is `ideogram4`.

- **`ideogram4` is the main engine.** JSON prompts, readable in-image text, about 21 minutes per 1216×832 render. Use it for anything that will ship.
- **`flux2-klein` is for fast drafts.** It renders 1216×832 in about 3 minutes (4 steps, including the model load), so use it to explore compositions before committing to 21-minute Ideogram renders, or when the request asks for speed.
- **FLUX takes natural-language prompts, not JSON.** Keep them under about 300 words; the text encoder truncates at 512 tokens. There is no `lint` for a FLUX prompt and no JSON schema.
- **Everything after the render is the same.** The review loop, the verdict card and the library record do not change; the record and `status` name the engine, and a FLUX record carries its seed in the `generation` block.

## The request workflow

1. **Read.** Read the issue's post, section, excerpt, and the intent behind them (the "why"); read the post file in `~/wojtek.second.brain.obsidian.vault/tech_blog/`; run `hindsight_reflect("What is Wojtek's image taste for <post topic>?")`, which reads the mental model **Wojtek's image taste**. *Done when you can state the post's idea in one sentence and list the taste rules that apply.*
   - **Fit the series first.** When the post already has images, read their library records' `## Prompt` JSON before writing a variant, and reuse the series' `style_description` block, its character descriptions and its world (workshop, racks, the grey boxy robot) as written. Reusing the series' prompt is what makes a new image belong to the set; matching its look from the PNG alone does not.
   - **A reflect call that errors or times out is not an empty taste model.** Call `hindsight_recall` with the same query and use what it returns before concluding there is no history; report the failure only if both come back with nothing. A timeout is a failed call, not an empty result: never read it as "no history yet" and never build a prompt on that inference — work from the library records and retry the recall later. Recall returns observations verbatim, so apply the records-beat-memory rule below to every claim it makes.
   - **A recall that times out often answers on a shorter query.** The long natural-language query is what times out; the same bank answers a single distinctive keyword (a rule word, the post slug, a recurring prop). So on a timeout do not repeat the same long query — narrow it to one keyword and try again before falling back to the records. When the model lands after the card is already live, apply it in an issue comment: the card's items are frozen, so name the image, the rule and the change it implies, and let Wojtek judge on the card he can see.
   - **When both reflect and recall time out, the records carry the round.** This happens (the Hindsight bank can be unresponsive while `hindsight_retain` still answers `Memory queued for storage`). Then the taste model for that topic is simply unavailable, and the library records are the only source: read the `## Verdicts` table of every record from the same series and take his stated reasons from there. Say plainly on the issue that both calls failed and that the records were the source — do not present inferred rules as his preferences, and do not let a timeout stall the card.
   - **The library's own verdict history is the taste model when hindsight is down.** When reflect *and* recall both fail, do not conclude there is no taste and do not invent rules: the `## Verdicts` tables under `3-resources/image-library/` hold his real reasons across every card ever reviewed, so read them (`grep -rh '^| [0-9]' 3-resources/image-library/ | sort`) and treat the reasons that recur across cards as the standing rules. Say on the issue that the model was unavailable and that the records stood in, then retry the recall on a later round.
   - **A deliverable that must cite a memory id needs the REST API, not the recall.** `hindsight_retain` answers `Memory queued for storage` — a receipt, not an id — and the ranked path can be down while the bank is up. The bank's own list route serves the same memories without the reranker and carries each memory's id: run `scripts/hindsight-memory.py list "<phrase from the reason>"` and then `... get <id>`. `references/taste-memory.md` has the routes and the rules.
   - **An empty taste model is not a licence to invent taste.** When `hindsight_reflect` finds no verdicts for the topic there is simply no history yet: say so on the issue and build the variants from the existing series and the section's intent instead of presenting guessed rules as Wojtek's preferences.
   - **The records beat the taste memory, and one verdict is not a rule.** `hindsight_reflect` synthesizes across verdicts and will assert a history the records contradict — it has described a round-1 rejection on a slot whose round-1 items were both approved. Before a claim shapes a prompt, check it against the library record's `## Verdicts` table and the card's `result`, and follow the records where the two disagree. A single approval or rejection is one data point about his eye, not a preference: two variants approved on one card does not mean he always approves both, and the request's slot count still decides how many images ship.

2. **Write 2–4 variants** as Ideogram 4 JSON, starting from `templates/` and following `references/engine-pitfalls.md`. Validate each with `python3 ~/.local/share/ideogram4-local/ideogram4_local.py lint <file>`. Default size 1216×832. *Done when every variant passes `lint` with risk score 0 and no schema issues, and has a one-sentence why.*

3. **Submit** each with `imagegen submit --prompt-json <file> --name <slug>` (stdout is only the job id). **On a resumed or re-woken run, read `GET /issues/<id>/interactions` and the comments before submitting** — a card already open for this round, or a `verdicts:<issueId>:round-<n>` already answered, means those renders exist: handle them (fetch, self-check, verdicts) rather than spending another 21 minutes per image on duplicates. Comment the job ids and the prompt summaries on the issue. *Done when the comment lists one job id per variant.*

4. **Wait without polling.** Read `eta_minutes` from `imagegen status <last-job-id>`. Schedule an issue monitor at ETA + 5 minutes, keep the issue `in_progress`, and end the run. A render takes about 21 minutes and jobs queue one after another. Use the shapes in `references/review-loop.md` and `references/paperclip-api.md`. *Done when the PATCH response shows a non-null `monitorNextCheckAt`.*

5. **On a monitor wake**, run `imagegen status` for each job. If any job is still running, **fetch and self-check the ones already `done` first** — a variant that fails the step-6 check can then be re-submitted immediately, so it renders in the queue behind the job still running instead of costing a whole extra round — then reschedule the monitor and end the run. Otherwise run `imagegen fetch <job-id>`, which prints the local path of the fetched `<slug>-<8 hex>.png` under `~/image-studio/staging/<date>/`: keep that path in a variable and use it for every later check and upload. *Done when every PNG is local and over 1 MB.*

6. **Self-check** each image with `vision_analyze`: text is spelled exactly as prompted; there is no grey box and `scripts/check-grey-bars.py` passes; the image matches the intent. Run the grey-bar script with the check venv at `~/image-studio/.venv-imgcheck/bin/python` — the system `python3` has no Pillow or numpy and the script exits 2 with `ERROR: Pillow and numpy required`; `references/review-loop.md` step 6 carries the one-time setup, and the script path is `~/.hermes/profiles/matejko/skills/image-studio/scripts/check-grey-bars.py`. **Crop to the prop the verdict hinges on, and read a crop's claims as scoped to its region.** A region-cropped `vision_analyze` answers about that region but often states a global conclusion ("there is no legible text anywhere in the image"), so a full-frame pass can miss small lettering and a crop can contradict it. When a check turns on one prop — a label, a lever, a tube — re-ask with a crop of that prop and a question that names the region, and only then record a text or prop defect. **But the `region` parameter is not a reliable cropper — it can land on different content between two calls, so the same box reads as the subject in one pass and as bare wall in the next.** Settle a small claim on a crop written to disk instead: `scripts/crop-probe.py` writes one and prints pixel counts for countable claims, so "a veil drapes the clock" is answered by a number rather than an opinion. Analyse the written file, not the region parameter, and make sure a reported defect survives the crop — the card's text is frozen when it is posted and Wojtek cannot correct it. `references/verifying-image-details.md` has the procedure. **Intent means the story beat reads, not that the objects are all present** — if the why says a cable joins the cheap machine to the proud robot, a clean render where the cable stops at the bench fails the check, and the repair is a prompt fix (the connector becomes its own element whose `bbox` spans the **whole run** from source to target, with the target named in the same sentence as the source, per `references/engine-pitfalls.md` #30 and #38), not a shrug. **A prop that looks coherent can still be a model artifact** — judge every prop by what it means to a reader and by whether the model knew what it was drawing, not by whether it looks tidy: a grid of aligned tiles with no axes or legend is a pseudo-chart, a flat rectangle with a drop shadow and no perspective is a pasted overlay, and dash lines standing in for words are pseudo-text. When the prompt could not describe a prop concretely, the render's version of it is an invention, and the invention is the defect. `references/engine-pitfalls.md` #35–#37 carry the cases and the fixes. **A figure's relation to its prop and its target is part of the beat.** When the prompt has a figure carry, place or walk something toward a target, check the body orientation and the grip: a figure facing the camera with the prop floating on the back satisfies the inventory but not the verb, and that is a story defect, not a quirk to note. **Hold back only what breaks the story; put the rest on the card as a note.** A re-render costs a render slot, so reserve it for defects that make the picture say something other than its section's beat: a connector that does not reach its target, a prop the model invented, unreadable text, a missing story element. A quirk that leaves the beat intact — an extra figure, a duplicated gauge, a shape drawn slightly wrong — is not a reason to spend another 21 minutes: put the image on the card and name the quirk in its description, so Wojtek sees it and decides. Two figures where the prompt asked for one is a defect you report, not one you silently re-render. Re-render a failing variant once, silently, and say in the closing comment what you held back and why. Your check filters out defects; it never approves. *Done when each image has a pass/fail note, and every held-back render has a one-line reason.*

7. **Show the batch to Wojtek.** Upload the passing PNGs as issue attachments — **on a resumed run, list the issue's attachments first (`GET /api/issues/<id>/attachments`) and reuse the id already there for the same file**, so a second attempt does not leave orphan copies on the card. Create one `request_item_verdicts` card with one item per image: `attachmentId`; `label` = the slug; `description` = the prompt summary, the why and the self-check note in **500 characters or fewer**; `resolverPolicy: "human_only"` so only Wojtek can resolve an image verdict. Use verdicts approve/reject/defer, `requireReasonOn: ["reject"]`, `continuationPolicy: "wake_assignee"`, and idempotency key `verdicts:<issueId>:round-<n>`. Set the issue to `in_review`. **Post the attachment-linking comment after the PATCH**: the `comment` field of the PATCH carries no `attachmentIds`, so a comment is the only call that links the PNGs into the thread, and without it the images sit attached but invisible on the card. *Done when the card is `pending`, the issue is `in_review`, and the attachments read back with a non-null `issueCommentId`.*

8. **On a verdict wake** (`newlyResolvedItemIds`), handle each newly resolved item:
   - **Read the card back and confirm a human decided it.** `result.items[].resolvedByUserId` must be set and `resolvedByAgentId` must be null. An agent-resolved verdict breaks the one rule this skill exists to keep, so a card that shows otherwise is a card to withdraw and re-open, not to act on.
   - `hindsight_retain` the verdict, the reason, the post, and the prompt traits that mattered, with tags `taste` and `verdict`. The call answers `Memory queued for storage`: that is the receipt, the memory is not indexed yet, so a recall right after it may not find it — do not re-retain it. When `hindsight_recall` times out on the same query, fall back to the library records rather than blocking the card, and use `scripts/hindsight-memory.py` when a deliverable needs the memory's id. `references/taste-memory.md` has the routes and the rules.
   - **Approve:** on a new render, copy the PNG into `~/wojtek.second.brain.obsidian.vault/tech_blog/assets/<YYYY-MM-DD>/<label>.png` and write the library record (`references/library-records.md`). On a backlog-review card the file is **already where the draft points**: touch only that record — `verdict`, one Verdicts row, drop the back-fill line — and copy nothing, write no second record and edit no post. `scripts/approve_record.py <record.md> --approved --issue <GUL-x>` (or `--rejected --reason "..."`) applies those edits in one verified pass; use it for every verdict, approval and rejection alike, rather than hand-editing the same three spots across many records.
   - **Reject:** mark the record rejected with his reason verbatim, revise the prompt from the reason and start the next round at step 3. Leave `superseded_by: null` on the rejected record until a replacement is actually approved — the field points at the job that replaced the image, so setting it to a render that was never accepted makes the slot history point at a dead end. When the replacement is approved, set `superseded_by` to that approved job id in **every** earlier record of the slot, the back-filled one included, in one pass — the pointer names the accepted image, not the next render in line, so a render that was briefly replaced by another *rejected* render still ends up pointing at the approved job.
   - **Defer:** leave the item.
   - Run at most 3 rounds per request. After round 3 with a slot still unapproved, ask Wojtek on the issue what to change instead of rendering again.
   - **A check note that turns out wrong is withdrawn and re-posted, not left on a frozen card.** The card's `items[].description` and `detailsMarkdown` cannot be edited after the POST, so a note you later disprove is a defect Wojtek would judge from. Withdraw the card (`POST /api/issues/<id>/interactions/<id>/withdraw` with a reason naming what changed), which settles it as `cancelled`, then post the corrected card under a new idempotency key (`verdicts:<issueId>:round-<k>-corrected`). The cancelled card is not a pending card, so exactly one card stays open for the round — verify with `GET /interactions` that one is `pending` and the other `cancelled`. Say plainly in an issue comment what was wrong and what the correction is, because the withdrawn card's wording is still in the thread. The one-card-at-a-time rule counts *pending* cards, not cards you have already retracted.
   - **On a comment wake, read the comment.** A user comment while the card is pending supersedes the rest of the card (`superseded_by_comment`); when that happens, open the next round's card with a new idempotency key, carrying the remaining items and revised by the comment.
   *Done when every newly resolved item is retained and handled.*

9. **Close** when every requested slot has an approved image. The closing comment is the audit trail, so it carries: the job id of every render per round, the vault asset path, every library record path, the self-check note for each image (held-back renders included, with the reason), and any `skill_manage` patch you made. Then set the issue to `done`. **On a backlog-review card, say plainly that nothing was rendered this round** and that no job id or vault copy belongs to it, so a reader checking the audit trail does not mistake an absent job id for a lost render. *Done when the issue is `done` and the comment carries every job id, asset path, record path and self-check note.*

## Rules

- **Let only Wojtek's verdict on the card approve an image.** He owns the taste; your self-check exists to remove defects, not to bless a render.
- **A card issue that the harness has claimed is already being worked — by its own run.** A freshly created backlog-review card is checked out for a separate run, which uploads the PNGs and opens the verdict card. Do not do that work from another run or a subagent: the upload answers `Issue run ownership conflict`. Read `checkoutRunId` and `executionRunId` on the issue before touching it, and leave it alone when they name a run that is not yours.
- **A sibling run of yours can be working the same backlog at the same time.** The harness starts a run per card, so one agent holds several live runs at once, and a run on the runner issue and a run on a card issue can both be mid-flight over the same vault files and the same queue. Read `GET /api/issues/<id>` for `checkoutRunId` and `executionRunId`, and `GET /api/agents/me/inbox-lite` for the `activeRun` on every sibling issue before you re-do work: a run whose `execution.phase` is `reconnecting` is still live, and a sibling that already applied a verdict leaves the durable artifacts done and your step redundant. **A refused file write is the signal, not an obstacle** — a write refused for being modified by a sibling after your last read names that run and its issue; re-read the file and the issue, then find the residual gap (a wrong field, a missing record, a deliverable nobody created) instead of repeating the finished work.
- **A document PUT needs the issue checked out by your run.** Refreshing the runner's `queue` document from a run that does not hold the runner answers `409` and the write does not land. Checkout the issue first — `POST /api/issues/{id}/checkout` with `{"agentId": ..., "expectedStatuses": [...]}` — then PUT. The shape is in `references/paperclip-api.md`.
- **Wojtek can ask for more than one card in flight, and that is his call to make.** The queue's one-card-at-a-time rule keeps the board readable by default; when he asks for a batch, open the batch he asked for and do not widen it on your own. `references/backlog-review.md` has the batch commands.
- **Act in Paperclip as yourself with `PAPERCLIP_API_KEY` from `~/.hermes/profiles/matejko/.env`.** That keeps every card and comment attributed to Matejko; `~/.paperclip/auth.json` is the board's token and stays closed.
- **Keep drafts in staging and let only approved images into the vault.** The published library then contains only work Wojtek has approved.
- **Report any `skill_manage` patch to this skill in the issue comment.** It keeps the procedure reviewable by the person who owns it.
- **Use `imagegen` for every render.** It is the one supported path from the Air to the M1 Max worker, with a single queue and ETA the board can monitor.
- **Never restart Paperclip or the Hermes gateway to clear a blocker.** Diagnose it from the server log, state what you ruled out, and open a `request_confirmation` for the board owner instead (`references/paperclip-api.md` carries the recipe and the storage-relay fix). Withdraw it (`POST …/interactions/<id>/withdraw` with a reason) once it is moot.
